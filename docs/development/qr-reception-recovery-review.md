## 既存設計と追加課題

BD-03では、受付イベント、送信キュー登録、端末連番の更新を同じIndexedDBトランザクションで確定する。端末保存が完了した後だけ成功を表示する。共有先への再送には同じイベントIDを使い、応答だけが失われても同じ受付を二重計上しない。

現在の画面設計は、カメラ読取り中または端末保存中にブラウザーが更新された後の表示と、読取りを再開する条件を明記していない。ブラウザーの更新警告だけでは誤更新や強制終了を防げないため、起動後の保存状態確認を必要とする。UIモックはメモリー上だけで動き、この対策の実証には使用できない。

## 追加する動作案

1. QRを認識した時点で読取りを止める。対象公演、端末の利用条件、QRの有効性を確認し、同じ画面で続けて別の受付を開始しない。
2. 初回受付イベントを作る場合は、イベントIDを発行し、イベント本体、送信キュー、端末連番をBD-03の端末内トランザクションで確定する。結果を再表示するための未確認イベント参照も同じ保存処理に含める案とする。
3. 端末保存の確定後にだけ、受付結果を表示する。端末に保存済みで共有待ちの場合と、共有先で受領確認済みの場合を区別する。共有待ちを保存失敗と表示しない。
4. 更新・再起動後はカメラの読取りを止めたまま、対象公演、端末状態、未確認の受付結果、送信キューを端末内の正本から確認する。保存済み結果があれば再表示し、担当者が「次へ」を選ぶまで読取りを再開しない。
5. 保存の成否が確認できない間は成功・失敗を推測せず、「受付状態を確認しています」と示す。端末内データを確認できなければカメラ受付を再開せず、管理者確認または紙受付へ案内する。
6. 送信中の更新や応答喪失では保存済みイベントIDを使って再送する。画面の再表示だけで新しい受付イベントを作らない。同一QRの再読取りは既存の受付済み判定へ進める。

端末内イベントが存在しないと確認できた場合に限り、その操作を未記録と扱い、必要ならQRを読み直す。端末の保存領域自体が消去・破損した場合や端末を回収できない場合は、自動復旧を保証しない。既存の紙記録と管理者照合へつなぐ。

## 試験条件案

| 中断する時点 | 確認する結果 |
|---|---|
| QR認識前のカメラ表示中 | 更新後に公演・端末状態を確認してから読取り可能になる。別公演を自動で開かない |
| QR認識後、端末保存の確定前 | 成功を表示しない。再起動後にイベントの有無を確認し、未確認のまま再読取りしない |
| 端末保存後、結果表示前 | 保存済みの同じイベントと結果を復元し、追加読取りを止める |
| 結果表示中、「次へ」の前 | 更新後も保存状態と結果を示し、担当者の確認前に次を読まない |
| 共有先へ送信中 | 端末イベントと送信キューを保持し、同じイベントIDで再試行する |
| 共有先保存後、端末への応答前 | サーバー由来の確認後に同一イベントを1件として扱い、受付数を増やさない |
| 端末保存領域を読めない場合 | 成功も未記録も断定せず、カメラを止めて管理者確認または紙受付を案内する |

対象実機でブラウザー更新、タブ終了、PWA終了、OSによる強制終了を試す。保存イベント数、送信キュー、共有先イベント数、受付結果、集計を架空データで照合する。合格条件は、保存済み受付の欠落、同一操作の二重計上、保存前の成功表示、状態未確認での読取り再開がないこととする。

## 確認事項

**依頼者に確認してください**

- 中断後に保存済みの結果を再表示し、「次へ」を押すまで読取りを再開しない流れを確認してください。お客様の前で保存状態を誤認しないためです。推奨は端末保存と共有先受領を区別して示すことです。

**開発者が確認してください**

- 端末内トランザクションと同一イベントIDの再送を、詳細設計と実装後試験で検証してください。ブラウザー更新警告を唯一の保護策にしないでください。
- 未確認結果の参照を端末内で保持する方法、複数タブからの同時読取り、保存領域の使用不能時の停止方法を詳細設計で確定してください。
