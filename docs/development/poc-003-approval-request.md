## 結論

POC-001・POC-002で確認したPWAとIndexedDBを基礎に、QRカメラ解析、A6縦電子チケット、500人分ZIP、指定実機の動作を検証できる見込みである。

実機カメラにはHTTPSが必要なため、保持中のFirebase検証プロジェクトに既に存在する既定Hostingサイトの**一時プレビューチャネル**へ、架空データだけを含む静的アプリを配信する。公開中のliveチャネルは変更せず、確認後にプレビューチャネルを削除する。FirestoreとAuthenticationは使用しない。

POC-003は実機を物理的に操作する必要があり、開発者側の自動試験だけでは完了できない。依頼者または実機確認担当者には、後述する3機種でのカメラ許可、紙・別端末画面からの読取り、オフライン確認、結果記録をお願いする。操作は画面の短い手順に沿って行い、コマンド入力やFirebase Console操作は求めない。

## 承認を依頼する範囲

明示承認後、次の作業だけを`POC-003`として行う。

1. Issue #6用ブランチの`poc/POC-003/`へ、本番利用を前提としない最小PWAを作成する。
2. QR解析、QR生成、PDF生成、ZIP生成に必要な固定バージョンのnpmパッケージを追加する。
3. 架空チケット500件について、A6縦1ページPDFの個別生成と500ファイル入りZIPを自動確認する。
4. 座席変更時のQR維持、紛失再発行時の旧QR拒否・履歴、短い確認コード検索、役割別ZIP出力可否を架空データで確認する。
5. カメラ入力を端末内で解析し、次へ進むまで別QRを受け付けない制御と、通信切断中のIndexedDB保存を確認する。
6. ローカル自動試験へ合格した後だけ、Firebase Hostingの一時プレビューチャネル`poc-003-{実施日YYYYMMDD}`へ最大3回配信する。各回の有効期限は1日とする。
7. iPhone 17、iPhone 13 miniのSafari、Galaxy Z Fold8のChromeで、紙と別端末画面の架空QRを読み取る。Fold8は外側・内側画面と開閉後を確認する。
8. 匿名化した結果、端末・OS・ブラウザー版、制約、削除確認を文書化する。
9. 終了時にプレビューチャネル、ローカルの架空データ・ダウンロード・生証跡を限定削除する。Firebaseプロジェクトと既定HostingサイトはPOC-005終了確認まで保持する。

`POC-004`、`POC-005`、Firebase方式の採用、本番実装、実在データ、個別認証・権限制御、暗号化、Firestore接続、Authentication接続、liveチャネル配信、カスタムドメイン、Analytics、課金機能は承認対象外とする。

## 対象機能と合格基準

| 対象 | 評価方法 | 合格基準 |
|---|---|---|
| カメラ許可 | 各実機で初回許可、拒否時案内、再許可後の起動を確認 | 手順を記録でき、許可後に背面カメラ映像を取得できる |
| 通常QR読取り | 各実機で紙5回、別端末画面5回以上を読む | 全試行で正しい架空チケットを識別し、判定は10秒以内。2秒以内は目標として記録 |
| 連続読取り防止 | 判定表示中に別QRを提示し、「次へ」後に再提示 | 「次へ」前は次のQRを受け付けず、「次へ」後は受け付ける |
| 完全オフライン | 開催前準備後に機内モード等で通信を切り、架空QRを読む | 判定と受付記録を継続し、IndexedDBへ保持できる |
| Fold8画面 | 外側・内側で表示と読取りを行い、開閉する | レイアウトが操作不能にならず、入力・受付状態を失わない |
| A6縦PDF | 1人分と代表ケースをA6縦100%で表示・印刷確認 | 公演、日時、架空氏名、架空会場・住所、階・区画・列・席、QR、確認コードが1ページに収まる |
| 紙・画面提示 | 印刷物と対象実機に表示したPDFを別の対象実機で読む | どちらも通常受付できる。読めない組合せは条件と要件影響を記録する |
| 確認コード | QRを使わず短い確認コードを入力する | QRと同じ架空チケットを一意に照合できる |
| 座席変更 | PDF再生成前後のQR値と表示席を比較する | QRを維持し、PDFは変更後の現在席を示す |
| 紛失再発行 | 理由付き再発行後に旧・新QRを読む | 旧QRを拒否し、新QRを受け付け、旧値・理由・時刻の履歴を残す |
| 500人分ZIP | 架空500件から個別PDFを生成する | ZIP内に重複のないPDF500件があり、各PDFがA6縦1ページである |
| 出力権限 | 架空の主担当、代理、受付担当、一時管理者で操作する | 主担当・代理だけがZIP生成できる。認証強度はPOC-004で別検証 |
| 非恒久保存 | 生成前後の外部資源とブラウザー保存を確認する | PDFをFirestore、Hosting、Storageへ保存せず、自動送信しない。利用者が明示保存したダウンロードだけを終了時に削除できる |

実機のいずれかが利用できない、最新安定版へ更新できない、プリンターまたは別画面を用意できない場合は、代替機で合格扱いにせず、その組合せを未判定として報告する。

## 実施シナリオ

### P003-01 自動生成・業務規則

- 架空の公演・会場・来場者500件をブラウザー内で生成する。
- QRには個人情報を含めず、架空チケットを識別する不透明な検証用トークンだけを入れる。
- 1件のA6縦PDFと500件のZIPを生成し、ページ寸法、ページ数、ZIP件数、ファイル名重複、必要項目を自動確認する。
- 座席変更、紛失再発行、確認コード、役割別出力を単体・E2E試験で確認する。

### P003-02 カメラと連続読取り

- 各実機でプレビューURLを開き、端末名、OS、ブラウザー版を確認票へ記録する。
- カメラ許可画面と拒否時の復旧案内を確認し、背面カメラで架空QRを読む。
- 判定中に別QRを提示し、「次へ」前後で読取り制御が変わることを確認する。
- カメラ映像とフレームは端末内で処理し、録画、ファイル保存、外部送信をしない。

### P003-03 紙・画面・Fold8

- A6縦PDFを100%倍率で1部印刷し、3機種から読む。
- 対象実機へ表示したPDFを別の対象実機から読む。自分自身の画面を自分のカメラで読む試験は行わない。
- Fold8は外側・内側の両方で表示・操作し、開いた状態と閉じた状態の切替後も受付状態が残るか確認する。

### P003-04 完全オフライン

- オンラインでPWAと架空参照データの事前取得完了を確認する。
- 通信を切って再度QRを読み、判定結果と受付記録をIndexedDBへ保存できることを確認する。
- POC-003ではFirestore同期を行わない。復旧後統合はPOC-001、性能・通信量はPOC-002の結果を参照する。

## 依頼者または実機確認担当者にお願いする作業

開発者が確認用URLと画面手順を用意した後、次だけをお願いする。

1. 対象3機種を充電し、標準ブラウザーを開ける状態にする。
2. 表示された確認用URLを開き、画面に従ってカメラを許可する。
3. 用意した架空チケットを紙と別端末画面から読む。
4. Fold8を開閉し、外側・内側画面の確認項目へ回答する。
5. 画面指示が出た箇所だけ通信を切り、確認後に戻す。
6. 結果画面のチェック欄を完了し、必要なら架空データだけが写ったスクリーンショットを共有する。
7. 完了後、案内に従ってサイトデータ、カメラ許可、ダウンロードした架空PDF・ZIPを削除する。

OS更新、端末初期化、Googleアカウント設定、Firebase Console、開発コマンドの操作は依頼しない。最新安定版でない場合も勝手にOS更新せず、検証を止めて相談する。

## 削除方法と確認

1. 実機確認票、匿名化集計、必要な再現情報を確定する。
2. 各実機でPOC-003画面のローカル削除を実行し、IndexedDB、Cache Storage、Service Workerを削除する。
3. 各実機のサイト設定からプレビューURLのカメラ許可とサイトデータを削除する。
4. Downloads内の`FAKE-P003-`で始まるPDF・ZIPだけを確認して削除する。端末内の他ファイルは削除しない。
5. FirebaseプロジェクトID、HostingサイトID、実施時に記録した`poc-003-{実施日YYYYMMDD}`チャネルIDを照合し、そのプレビューチャネルだけを削除する。
6. Hostingチャネル一覧で対象URLが無効になったことを確認する。関連ReleaseとVersionはFirebase仕様により24時間以内の削除予定となるため、直後の完全消去とは区別して記録する。
7. `poc/POC-003/artifacts/raw/`の絶対パスを確認し、生PDF、ZIP、スクリーンショット、ログを削除する。
8. Firebaseプロジェクト本体と既定HostingサイトはPOC-005終了確認まで保持する。liveチャネルは変更しない。

削除操作が一部失敗した場合は対象を広げず、残存状態と理由を報告する。既定Hostingサイトは削除せず、他のチャネル、Firebaseプロジェクト、端末の他データを削除しない。

## 費用0円の根拠と停止上限

2026-09-03時点のFirebase公式情報では、Sparkプランは支払情報なしで開始でき、Firebase Hostingはプロジェクト単位で保存10GB、データ転送10GB/月まで無料である。上限到達時はSparkでは追加課金されず提供停止となる。今回使うnpmパッケージは公開OSSで、ライセンス料のある外部APIやSaaSを使わない。

| 指標 | POC-003停止上限 | 無料枠・想定との比較 |
|---|---:|---|
| Hosting配信資産 | 20MiB、最大3バージョン | 10GBの1%未満 |
| Hostingデータ転送 | 1GiB/月 | 10GB/月の10%以下 |
| プレビューチャネル | 1件、有効期限1日 | 終了時に手動削除も実施 |
| 自動生成PDF | 500件×最大3回 | ブラウザー内生成でHostingへ保存しない |
| ZIP | 1回最大250MiB | 端末ローカルだけ。上限超過時は停止して記録 |
| 外部データベース操作 | 0件 | Firestore・Storage・Authenticationを使用しない |
| 実機 | 指定3台 | 既存端末だけ。購入・レンタル・有料クラウド端末を使わない |

配信前にSpark・請求未設定、Hosting使用量を確認する。既使用量と停止上限の合計が無料枠の80%へ達する見込み、カード・請求先接続要求、Blaze変更要求、有料端末要求のいずれかがあれば停止し、費用を発生させず未判定または不適合として報告する。
