## 結論

PoCの合格は、限定した条件で技術的に実現できることを示すものであり、本番環境の安全性、完全な業務機能、使いやすさを保証しない。セキュリティは設計時だけの作業にせず、要件で守る対象を定め、設計で方式を決め、実装で対策し、試験と運用で継続確認する。UI/UXは完成後の装飾にせず、実装前の操作見本と実装中の実機レビューで調整する。

## 来場状態の扱い

- 公演中の基本状態は「未受付」と「来場済み」とする。
- QRの初回受付または管理者の手動受付で「来場済み」にする。
- 「来場済み」から「未受付」へ戻す操作は単純な上書きにせず、管理者の確認と理由を必須にする。
- 初回受付と訂正前の状態は削除せず、担当者、端末、時刻、理由を追記する。
- 一般受付担当者は状態を直接確定・取消しせず、必要な場合は例外を仮登録して管理者へ渡す。
- オフライン変更は入力端末に保存し、復旧後に共有する。同じ対象への複数変更は競合として管理者へ示す。
- 締め処理時に「未受付」のまま残る対象を「未来場」として一覧・集計・出力する。
- 座席表と来場者一覧の状態、受付済み数、未受付数は同じ履歴から計算し、一致させる。

## チケット準備状態の表示と操作

- 交付方法は未選択、電子チケット、紙チケットを区別し、未選択も許容する。
- 購入確定、入金確認、発行済み、交付済みを独立したチェックとして表示する。未入金の発行・交付を許し、各項目を済み・未済みで並べ替える。
- 一覧ではチェックボックス等により、各席がどこまで進んだかを視覚的に確認できるようにする。
- チェック時と解除時の両方で、対象と変更後の状態を確認する。
- 一斉操作では、対象席と件数を確認してから実行する。
- 各状態の到達日時を表示する。この状態操作だけを目的とする担当者項目は表示・記録しない。
- 後続状態だけが残る等の矛盾を作らない。[BD-06](../basic-design/screen-flow-wireframe-design.md#bd-06-09-お客様チケット管理)では、次の状態だけを選択可能とし、解除は現在の最新状態だけに限定する。

QR再発行、座席変更、来場状態訂正、削除等は従来どおり監査対象とする。チケット準備状態で担当者を記録しない方針を、他の監査対象へ広げない。

## 専用カメラモード

- QR読取りは通常画面内のスクロール領域へ埋め込まず、スマートフォンの表示領域を使う専用モードとする。
- 専用モード中はカメラ表示、読取り対象の枠、オフライン・未送信状態、終了操作を常に確認できるようにする。
- 読取り後は判定結果をカメラ表示の前面へ重ね、背後のカメラから追加のQRを受け付けない。
- 「次へ」が選ばれた時だけ判定結果を閉じ、同じ専用モードで次の読取りを再開する。
- ブラウザーの戻る操作、カメラ権限拒否、カメラ停止、画面回転、バックグラウンド復帰時の安全な状態を画面設計と実機レビューで確認する。

## 公開リポジトリと評価環境の分離

- 公開リポジトリは第三者評価者が主要機能を確認できるようにするが、依頼者用環境は依頼者だけが所有・管理する。
- 評価者はローカル環境または評価者自身が所有する評価専用環境と架空データだけを使用し、依頼者用環境を使用しない。
- 公開リポジトリ、履歴、手順書、設定例、ビルド成果物へ、依頼者用の環境識別子、接続設定、認証情報、実データを含めず、既存環境へ接続する既定値を設けない。
- 設定が不足または不正な場合は、既存環境へ接続せず安全に停止して評価用設定手順を示す。
- 評価手順には、架空データ限定、依頼者環境の使用禁止、評価利用への個別サポート・動作保証なし、第三者の本番運用は対象外であることを記載する。
- 画面、初期設定、手順書、エラーメッセージは、将来公開ライセンスを採用した場合にも、ITに詳しくない個人コンサート主催者が開発者の口頭支援なしで進められる分かりやすさを目標とする。
- 現在の公開リポジトリで第三者への利用許諾を行うことと、将来の公開ライセンス採用を妨げない構成にすることは区別する。

## セキュリティを扱う工程

| 工程 | 実施内容 | 主な成果物 |
|---|---|---|
| 要件 | 守る情報、許可する役割、保存・削除、監査、費用、環境所有を定める | 要件定義書、受入条件書 |
| 設計 | データの流れと攻撃・誤操作の想定を整理し、認証、セッション、権限、暗号化、鍵、秘密情報、バックアップ、監視を決める | セキュリティ設計、権限表、データフロー、ADR、テスト方針 |
| 実装 | 入力検証、出力の安全化、サーバー側拒否、秘密情報分離、監査記録、依存関係固定をコードへ反映する | アプリケーションコード、自動テスト、設定例 |
| 試験 | 役割外操作、直接API操作、セッション失効、不正入力、オフライン復旧、依存関係、公開物、復旧手順を確認する | セキュリティ試験仕様・結果、残存リスク一覧 |
| リリース・運用 | 本番所有者、開発者権限削除、異常確認、連絡、権限停止、データ出力・復旧、更新方法を確認する | 引継ぎチェックリスト、運用・障害対応手順 |

## 設計時に必ず決める事項

- 個別アカウントの発行、無効化、パスワード再設定、連続ログイン失敗への対応。
- セッション有効期間、開催前準備後のオフライン利用可能期間、ログアウトと権限停止後の削除。
- 主担当、代理管理者、臨時管理者、一般受付担当者の画面・API・データ単位の権限表。
- 端末、通信、サーバーそれぞれの暗号化範囲と、公演・端末専用の非抽出CryptoKeyの生成、IndexedDB保存、利用条件、停止時保持、停止解除後再利用、全件受領後の条件付き削除。スタッフへ追加パスフレーズ・PINを要求しない。
- データ項目ごとの保存先、保存期間、出力可否、削除方法、削除完了確認。
- 秘密情報をGit、公開文書、クライアント配信物へ含めない設定方法。
- 不正入力、スクリプト注入、不正な別サイト経由操作、別公演データ参照への対策。
- 監査ログへ残す操作、異常の確認方法、端末紛失・認証情報漏えい・障害時の連絡と権限停止。
- 費用0円で利用できるデータ出力・復旧方法と、実際に戻せることを確認する練習手順。
- 依存パッケージの更新、脆弱性確認、例外を残す場合の承認と期限。

## セキュリティ試験の最低範囲

- 役割外の画面操作と直接API操作がともに拒否される。
- 別公演の識別子、無効QR、改変QR、期限切れ・停止済みアカウントを拒否する。
- 長すぎる値、不正形式ファイル、画面へ影響する文字列を安全に処理する。
- オフライン中の権限変更の限界を表示し、復旧後に停止が反映される。
- ログアウト、締め処理、権限停止後に対象の認証情報と復号可能な個人情報が残らない。
- Git履歴、ビルド成果物、公開サイト、ログ、エラー表示へ秘密情報が含まれない。
- 依存関係の自動監査と静的解析を行い、High・Criticalの未対応を残さない。
- データ出力、復旧、端末紛失、認証情報漏えい、外部サービス障害を手順書に沿って確認する。

外部の有償セキュリティ診断は費用0円の前提には含めない。無料範囲の自動検査、設計・コードの手動レビュー、権限・入力・復旧試験を必須とし、有償診断が必要と判断した場合は契約せず、理由と選択肢を依頼者へ提示する。

## UI/UX設計方針

当日の受付では、装飾よりも速度、視認性、誤操作防止、通信障害時の安心を優先する。受付担当者だけでなく、管理者である依頼者にもIT知識を前提としない。準備・管理画面では、年1回の利用でも順番に進められることを優先する。

### 利用者向けメッセージ

- スマートフォンでの読みやすさを重視し、原則として「短い見出し」「現在の状態」「次に必要な操作」の順で簡潔に表示する。
- 短くしても、受付へ反映済みか、確認が必要か、次に何をするかを省略しない。
- 詳細な時刻、端末情報、技術情報は初期表示へ詰め込まず、必要な場合だけ展開して確認できるようにする。
- 「競合」「隔離」「認可」「CryptoKey」等の内部・技術用語を利用者向け画面へそのまま表示しない。設計文書、技術ログ、開発者向け調査情報では、正確性のためこれらの用語を使用してよい。
- 競合時は「競合が起きました」ではなく、「同じQRコードが別の端末でも読み取られています。受付状況を確認してください」のように、起きた事実と必要な操作を示す。
- 隔離記録の利用者向け見出しは「停止中の受付記録」等とする。説明は「ロック端末が停止期間中にスキャンした受付記録です。受付には未反映です。内容を確認してください」のように、正式な受付へ未反映であることと確認が必要なことを示す。
- 高影響操作は技術用語で説明せず、「実行すると何が起きるか」「元に戻せるか」を確認画面へ明記する。削除、締め、役割変更、端末廃止等では対象と影響も省略しない。

この表現方針は2026-09-17の開発者判断であり、依頼者の回答または画面文言の最終承認ではない。[BD-06](../basic-design/screen-flow-wireframe-design.md#主要メッセージ一覧)で操作見本へ具体化した。BD-09では受付担当者・管理者の両方について、スマートフォン表示、専門用語の不使用、重要事項の欠落を確認する。詳細展開と高影響操作の影響・取消可否も確認する。

Firebaseの上限接近・到達またはオンライン共有停止時は、一般受付画面に課金判断を出さず、端末保存済みであること、未送信件数、受付継続可否、管理者への連絡を表示する。各端末の未送信一覧は、席番号と表示用チケット番号を主列として読取時刻、操作種別、端末、同期状態を簡潔に並べ、紙へ転記しやすくする。QR生データと氏名は表示・印刷しない。

管理画面は、Firebaseプロジェクトを作成した管理者1名だけに、紙運用または同じプロジェクトへの手動課金の選択肢と手順を示す。アプリケーションから課金を実行せず、新しいFirebaseプロジェクトへの切替を案内しない。開催前準備では、当日運営表の予備印刷を促し、印刷確認が未完了であることを見落としにくく表示する。

実装前に少なくとも次の操作見本を作成し、依頼者とレビューする。

1. QR読取りと初回受付結果。
2. 受付済み、受付不可、特別対応、同じQRコードが別端末でも読み取られた場合の結果と次の操作。
3. 座席表、会場画像、来場状態、選択中の席。
4. 手動受付、来場済みへの変更、未受付へ戻す訂正と確認。
5. 名簿取込、公演・座席準備、交付方法、チケット準備状態の個別・一斉操作。
6. 締め処理、未送信確認、端末別削除状況。
7. Firebase上限時の一般受付案内、端末別未送信一覧、管理者用の紙運用・手動課金分岐、開催前の予備印刷確認。
8. 会場席管理画面での座席表示名変更、来場状態変更、購入者名の参照。

各画面では、処理中、成功、失敗、オフライン、未送信、同じ対象に複数端末から操作があった状態、選択中の対象、次に行う操作を文字と記号で示す。主要ボタンは片手でも押し間違えにくい大きさと間隔にし、重大操作には確認画面を設ける。失敗しても入力を失わず、安全な再試行または管理者確認へ進める。

操作見本の確認後に画面単位で実装し、PC、iPhone 17、iPhone 13 mini、Galaxy Z Fold8でレビューする。指摘、対応、保留理由を記録し、要件や受入条件に影響する場合は実装だけを変更せず文書も更新する。
