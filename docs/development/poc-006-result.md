## 実施条件

[POC-006](../../poc/POC-006/README.md)を、既存のFirebase Authentication・FirestoreエミュレーターとNode.js 24で実施した。架空アカウントと架空バイト列だけを使用し、実Firebase、Cloudflare、本番環境へ接続していない。試験用Rulesは本番Rulesではなく、設計候補の境界を再現したものである。

## C-01 端末単位認可

同じ利用者UIDに関連付けた端末A・Bへ、別々のFirebase匿名認証UIDを与えた。管理者が端末UIDと利用者UIDを公演ごとに関連付け、利用者の個別認証から有効なセッション証跡を書いた。業務要求は端末側の匿名Authで送信し、Rulesが端末UID、停止状態、利用者役割、セッション証跡を照合した。高影響の端末停止では最近の利用者認証に基づく短時間の証跡を追加した。

| 試験 | 結果 |
|---|---|
| A・Bが同じ利用者に属し、両方で業務データへアクセス | 成功 |
| セッション証跡なし、未承認端末のアクセス | 拒否 |
| AがBの端末UIDを本文に指定した作成 | 停止前も拒否 |
| Bの高影響証跡なしでAを停止 | 拒否 |
| Bの高影響証跡ありでAを停止 | 成功 |
| 停止後のAによる読取り・書込み・自己復帰 | 拒否 |
| A停止後のBによる読取り・書込み | 成功 |
| 利用者ログアウトの証跡失効、利用者役割停止 | 対象端末を拒否 |
| 同じFirebaseプロジェクトの利用者用・端末用の名前付きSDKインスタンス | 別UIDとして動作し、端末用だけが業務データを読めた |

現在の「同じ利用者UIDと自己申告の端末ID」方式は、停止端末AがBのIDを名乗る要求を拒否できない。上記の別認証主体方式は、その指摘に対するローカルの成立根拠となる。[Firebase匿名認証](https://firebase.google.com/docs/auth/web/anonymous-auth)と[Firebase Authenticationの制限](https://firebase.google.com/docs/auth/limits)ではSparkで利用可能であり、追加の有料実行基盤は要しない。

残る限界は、端末Authの更新トークンが複製された場合に物理端末を区別できないこと、オフライン中の停止反映が遅れること、実機・本番相当環境での本人ログインと端末資格のライフサイクルが未検証であること。完全オフライン中の停止遅延は既存の`CONF-040`の範囲にある。端末資格の複製や漏えい時は該当資格を停止し、再登録に管理者承認を要する。外部サーバーと端末署名を使う候補も別にローカルで模擬したが、Cloudflare Workersの実行時間と運用は検証していない。

## C-03 会場画像の共有保存

Firestoreの固定5画像枠、各2バンク、各7分割をRulesで制限した。分割`0`～`5`は750,000バイト以下、分割`6`は500,000バイト以下とした。確定バンクのみ閲覧担当が読め、作業バンクは管理者だけが書ける。版切替後は旧バンクの閲覧を拒否し、旧分割の削除を確認した。

| 試験 | 結果 |
|---|---|
| 6枚目、8分割目、分割上限超、版不一致、閲覧担当の書込み、作業版の閲覧 | いずれも拒否 |
| 5画像各5,000,000バイトの保存・再構成 | 35文書、合計25,000,000バイト、SHA-256一致 |
| 別認証の6取得元への最大画像配布 | 210文書読取り、画像本体150,000,000バイト、全取得元でSHA-256一致 |
| 新版公開後の旧版読取り・旧分割削除 | 読取り拒否、旧分割7件の削除成功 |

固定2バンクにより、画像本体の保存上限は確定版と作業版を合わせて50,000,000バイトとなる。Firestoreの[1文書1MiB上限](https://firebase.google.com/docs/firestore/quotas)と[Sparkの無料枠](https://firebase.google.com/pricing)には試験値が収まる。ただし他の業務データ、索引、Rulesの追加読取り、複数公演、再取得を含む全体消費量は別に監視する。[Cloud Storage for FirebaseはBlazeが必要](https://firebase.google.com/docs/storage/web/start)であり初期候補から除く。

残る限界は、実画面でのPNG・JPEG形式・破損検査、通信断と再試行、作業版の途中失敗時回収、公開前の全分割整合検査、C-01の正式な役割・端末認可との結合、実機のオフライン表示である。これらは詳細設計と実装後のAC-025で確認する。PoCの成功をAC-025・AC-030の合格に読み替えない。

## 判定

C-01は、別のFirebase認証主体と利用者セッション証跡による端末別停止を第一候補とする。C-03は、Firestoreの固定枠・2バンク分割保存を第一候補とする。いずれも本番方式の採用にはADRと統合した基本設計の変更承認が必要である。

**依頼者に確認してください**

- 基本設計の統合再レビュー後に、端末用認証主体の追加と画像分割保存を採用するか確認してください。理由は、既存の認証・保存設計を変更するためです。推奨案は無料・カード登録なしを維持する上記2候補です。

**開発者が確認してください**

- C-01のセッション証跡と端末資格の管理を正式Rulesへ展開し、全業務経路の直接API試験を行ってください。
- C-03の実ファイル検査、途中失敗、版切替、削除、オフライン表示を詳細設計と受入試験へ割り当ててください。
