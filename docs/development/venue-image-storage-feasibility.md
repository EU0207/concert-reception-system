## 結論

`CONF-052`の200KB上限を`CONF-053`で1MB/枚、最大5枚、合計5MBへ変更した。Firestoreの固定5枠、各2バンク、1画像1文書を維持する。POC-006では1,000,000バイト×5枚を6つの別認証取得元が取得し、30文書読取り、画像本体30,000,000バイト相当で一致した。[Firestoreの1文書上限は1MiB](https://firebase.google.com/docs/firestore/quotas)で、画像本体との差は48,576バイトである。実装時は文書名と少量のメタデータを含む文書全体のサイズを検査する。[Sparkの無料枠](https://firebase.google.com/pricing)には保存量1GiB、月間転送10GiB、1日5万読取り・2万書込みがある。通信プロトコル、メタデータ、索引、Rules参照、再取得、複数公演は別途加算する。

`CONF-051`では「スマートフォンで拡大して見える程度」を画質条件とした。1MBで実画像が読めるかは未確認であり、対象実機のAC-025に残す。容量内で読めない画像は調整するか座席一覧を代替表示する。[ADR-006](decisions/ADR-006-firestore-image-storage.md)に採用理由と残存リスクを記録した。

[Cloud Storage for FirebaseはBlazeが必要](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)であり、現在のカード登録なし条件には合わない。画像をFirebase Hostingの公開資産へ置く案は、役割別の非公開配布と管理画面からの登録を満たさない。

## 候補比較と旧5MB案の検証記録

2026-09-25の[POC-006](poc-006-result.md)では、固定5枠・2バンク・各7分割のRulesで上限外の要求を拒否した。架空の5画像各5,000,000バイトを6つの別認証取得元へ配布し、全取得元でSHA-256一致を確認した。合計35書込み、210読取り、画像本体150,000,000バイト相当だった。公開後の旧バンク読取り拒否と旧分割削除も確認した。以下の「検証待ち」は初版時点の記録であり、エミュレーターで確認済みの項目は本段落とPOC-006を優先する。

旧案でも実PNG・JPEGの判定、途中アップロードの回収、実機オフライン表示、C-01の正式認可との結合は未検証だった。実装後のAC-025合格は別判定とする。

| 候補 | 利点 | 制約・運用影響 | 判断 |
|---|---|---|---|
| Firestoreへ1画像1文書で保存 | 既存の認証・公演境界と同じ基盤を使え、分割・再構築が不要 | 1MiBの文書上限との差が48,576バイト。実画像の可読性とC-01の正式認可は未実証 | 採用。POC-006で1MB境界、Rules、6取得元への配布を限定確認 |
| Firestoreへ分割保存 | 5MB上限を維持できる | 文書分割、再構築、途中失敗の処理が必要 | 旧上限案としてPOC-006で確認。CONF-052後は不採用 |
| Cloud Storage for Firebase | 画像の保存・取得に適したサービス | Blazeへの変更とカード登録が必要 | 現行条件では採用しない |
| 公開Hosting資産 | 配布は単純 | 認証済みスタッフへの限定配布と管理画面からの登録に合わない | 不採用 |
| 端末間手動配布 | サーバー保存が不要 | 全スタッフへの更新・削除、端末準備、引継ぎが複雑になる | 通常方式として採用しない |

## 旧5MB案の設計境界と検証記録

- 管理者は公演準備中にPNG・JPEGを登録する。ブラウザーで種類、ファイルサイズ、画像としての復号可否を確認し、Rulesでサイズ、申告形式、権限を検証する。当日は更新を拒否する。
- 公演ID、画像ID、版、階・区画、形式、元サイズ、分割数、全体のハッシュをメタデータに持つ。画像本体は画像ID・固定2バンク・連番ごとの文書へ保存する。分割文書のバイナリ項目は索引対象から外す。
- 端末は全分割文書を取得し、個数、順序、総サイズ、ハッシュを確認してから画像を表示・オフライン保存する。欠損や不一致があれば旧版を維持し、座席一覧を代替表示する。
- 管理者の確定操作まで新しい版を配布対象にしない。途中アップロード、端末の再試行、旧版の削除を区別し、旧版を先に消さない。削除時は対象公演と版を確定し、残件を確認する。
- すべての分割文書の読取りに、同じ公演の有効な役割と承認端末の条件を適用する。C-01の端末所持検証が成立するまで、安全な配布方式と判定しない。

分割サイズ、文書IDの範囲、総量上限をSecurity Rulesで強制できるかを限定技術検証で確かめた。クライアント画面だけの5枚・25MB制限は合格にしなかった。

### 容量と文書IDの検証用案

| 項目 | 上限案 | 理由 |
|---|---:|---|
| 画像枠 | `0`～`4`の固定5枠 | 任意のIDを無限に作成できないようにする |
| バンク・分割番号 | 各枠に固定2バンク、各`0`～`6`の7文書 | 版番号を増やして無制限に保存できないようにする |
| 分割`0`～`5` | 各750,000バイト以下 | 文書のメタデータを含めても1MiBから余裕を取る |
| 分割`6` | 500,000バイト以下 | 画像1枚の合計を5,000,000バイト以下に抑える |
| 公演の確定版と作業版 | 最大70文書、画像本体50,000,000バイト | 確定版だけなら35文書、25,000,000バイト |
| 6端末へ各1回配布 | 最大210文書読取り、画像本体約150MB | 再取得とRulesの追加読取りは別途計測する |

[RulesのBytes型](https://firebase.google.com/docs/reference/rules/rules.Bytes)には`size()`があり、分割文書ごとのバイト数を検査できる。固定の画像枠・バンク・分割番号と上限外要求の拒否は[POC-006](poc-006-result.md)でエミュレーター確認した。大きなバイナリ項目は[自動索引の除外](https://firebase.google.com/docs/firestore/query-data/index-overview)を検討する。画像だけで40公演分を満額保持すると25MB×40で約1GBとなり、索引や他の業務データを含む無料枠を超え得るため、公演後の画像版の保管・削除時点も設計判断に残す。

版番号ごとに可変の保存場所を作る方式は全体容量を制限できないため、固定2バンクとした。確定版と作業版を同時に持つ間は画像本体だけで最大50MBとなる。メタデータを偽る直接API要求と古い版の閲覧拒否はPOC-006で確認した。途中失敗後の孤立分割の回収、公開前の全分割整合確認は実装後の検証条件とする。

2026-09-25にNode.jsの一時実行で、架空の5,000,000バイト画像5枚を7分割へ切り、各画像を再結合したSHA-256が元データと一致することを確認した。続くPOC-006ではエミュレーターに35文書を書き、6つの別認証取得元が各35文書を取得してSHA-256一致を確認した。合計25,000,000バイト、210文書読取り、画像本体150,000,000バイト相当である。実サービスの無料枠消費量、オフライン配布、実画像の成功は未確認である。

## 採用した1MB案の検証と判定

1. 架空バイト列で1,000,000バイトの登録、1,000,001バイトと6枚目の拒否をPOC-006で確認した。5枚を6つの独立した認証取得元へ配布し、SHA-256一致を確認した。
2. 確定版だけの読取り、版切替、旧版の読取り拒否と削除を確認した。画像本体は確定・作業の2バンクで最大10MBである。
3. 実画像の復号・拡大時可読性、途中失敗、正式な端末認可、完全オフライン表示は実装後に確認する。Rulesは申告形式を検査できるが画像実体の復号はできない。
4. 実サービスの保存量、転送量、追加のRules読取り、複数公演の累積を監視する。1MBの画像だけではプロジェクト全体の無料運用を保証できない。

`CONF-053`の最新上限とPOC-006の限定検証を根拠に[ADR-006](decisions/ADR-006-firestore-image-storage.md)で単一文書方式を維持した。POCの成功は実装後のAC-025合格判定を代替しない。
