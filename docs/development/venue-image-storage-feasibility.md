## 結論

画像本体の保存方式として、Firestoreの複数文書にバイナリを分割する案を第一候補とする。Firestoreの[1文書上限は1MiB](https://firebase.google.com/docs/firestore/quotas)であり、5MB画像を1文書に保存できない。一方、[Sparkの無料枠](https://firebase.google.com/pricing)には保存量1GiB、1日あたりの読取り5万件・書込み2万件、月間転送10GiBがある。下記の固定35分割なら、画像25MBを6端末へ1回ずつ配布する概算は210文書読取り、約150MBの転送である。通信プロトコル、メタデータ、Rules参照、再取得、複数公演は別途加算する。

[Cloud Storage for FirebaseはBlazeが必要](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)であり、現在のカード登録なし条件には合わない。画像をFirebase Hostingの公開資産へ置く案は、役割別の非公開配布と管理画面からの登録を満たさない。

## 候補比較

| 候補 | 利点 | 制約・運用影響 | 判断 |
|---|---|---|---|
| Firestoreへ分割保存 | 既存の認証・公演境界と同じ基盤を使える。Sparkの範囲で検証できる | 文書分割、再構築、途中失敗の処理が必要。C-01の端末認可が未解決 | 第一候補。限定技術検証後に採用判断 |
| Cloud Storage for Firebase | 画像の保存・取得に適したサービス | Blazeへの変更とカード登録が必要 | 現行条件では採用しない |
| 公開Hosting資産 | 配布は単純 | 認証済みスタッフへの限定配布と管理画面からの登録に合わない | 不採用 |
| 端末間手動配布 | サーバー保存が不要 | 全スタッフへの更新・削除、端末準備、引継ぎが複雑になる | 通常方式として採用しない |

## 第一候補の設計境界

- 管理者は公演準備中にPNG・JPEGを登録する。ブラウザーで種類、ファイルサイズ、画像としての復号可否を確認し、サーバー側でも許可形式と上限を検証する。当日は更新を拒否する。
- 公演ID、画像ID、版、階・区画、形式、元サイズ、分割数、全体のハッシュをメタデータに持つ。画像本体は画像ID・版・連番ごとの固定数の文書へ保存する。分割文書のバイナリ項目は索引対象から外す。
- 端末は全分割文書を取得し、個数、順序、総サイズ、ハッシュを確認してから画像を表示・オフライン保存する。欠損や不一致があれば旧版を維持し、座席一覧を代替表示する。
- 管理者の確定操作まで新しい版を配布対象にしない。途中アップロード、端末の再試行、旧版の削除を区別し、旧版を先に消さない。削除時は対象公演と版を確定し、残件を確認する。
- すべての分割文書の読取りに、同じ公演の有効な役割と承認端末の条件を適用する。C-01の端末所持検証が成立するまで、安全な配布方式と判定しない。

分割サイズ、文書IDの範囲、総量上限をSecurity Rulesで強制できるかは限定技術検証で確かめる。クライアント画面だけの5枚・25MB制限は合格にしない。

### 容量と文書IDの検証用案

| 項目 | 上限案 | 理由 |
|---|---:|---|
| 画像枠 | `0`～`4`の固定5枠 | 任意のIDを無限に作成できないようにする |
| 分割番号 | 各枠`0`～`6`の固定7文書 | 35文書より増やせないようにする |
| 分割`0`～`5` | 各750,000バイト以下 | 文書のメタデータを含めても1MiBから余裕を取る |
| 分割`6` | 500,000バイト以下 | 画像1枚の合計を5,000,000バイト以下に抑える |
| 公演の確定版 | 最大35文書、画像本体25,000,000バイト | 作業中の新旧版は別途保存量を消費する |
| 6端末へ各1回配布 | 最大210文書読取り、画像本体約150MB | 再取得とRulesの追加読取りは別途計測する |

[RulesのBytes型](https://firebase.google.com/docs/reference/rules/rules.Bytes)には`size()`があり、分割文書ごとのバイト数を検査できる。固定の画像枠・分割番号と合わせた拒否試験をエミュレーターで行うまでは、上記を実証済みの上限とは扱わない。大きなバイナリ項目は[自動索引の除外](https://firebase.google.com/docs/firestore/query-data/index-overview)を検討する。画像だけで40公演分を満額保持すると25MB×40で約1GBとなり、索引や他の業務データを含む無料枠を超え得るため、公演後の画像版の保管・削除時点も設計判断に残す。

版ごとの固定枠だけでは、版番号を増やして全体容量を超える要求を拒否できない。メタデータで作業中の版を1つに限定し、確定版との合計と旧版破棄を管理する方式を検証する。確定版と作業中の版を同時に持つ間は画像本体だけで最大50MBとなる。メタデータを偽る直接API要求、古い版への追記、途中失敗後の孤立分割も拒否または回収できることを採用条件とする。

2026-09-25にNode.jsの一時実行で、架空の5,000,000バイト画像5枚を上記の7分割へ切り、各画像を再結合したSHA-256が元データと一致することを確認した。結果は35分割、合計25,000,000バイト、末尾分割各500,000バイト、6端末への1回配布で210文書読取りである。これは容量計算と再結合の確認であり、Firestore書込み・Rules・オフライン配布・無料枠の実測成功ではない。

## 限定技術検証と判定

1. 架空画像で5MB以下の登録、5MB超・6枚目・合計25MB超・PDF・破損画像の拒否を確認する。
2. 最大5枚を独立した複数端末へ配布し、完全オフライン表示、階・区画連動、取得失敗時の座席一覧を確認する。
3. 途中アップロード、分割文書の欠損・改変、再送、版切替、旧版削除を確認する。未確定版を一般スタッフへ配布しない。
4. 直接APIの役割外・別公演・停止端末の読取り・書込みを拒否する。停止端末についてはC-01の方式決定後に再確認する。
5. 文書数、保存量、読取り・書込み回数、転送量を測定し、年1～2回・複数公演での余裕を見積もる。

画像保存候補は実装後のAC-025合格判定を代替しない。検証結果をBD-01、BD-02、BD-05、BD-07、BD-09とADRへ反映してから方式を確定する。
