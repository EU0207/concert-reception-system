## 結論

`POC-001`は、承認済みの範囲と合格基準に対して**合格**と判定する。

- 6つの独立したブラウザ環境で、通信を切ったまま架空QR 500件をIndexedDBへ保存できた。
- 復旧後、初回受付501件、再読取り1件、重要連絡1件、利用者別確認5件の合計508イベントを、欠落なく全6環境へ統合できた。
- 同じ架空QRの初回受付2件を消去せず、競合1件として導出できた。
- 1環境を再びオフラインにして停止した後も、残る5環境で連絡を追加し共有できた。停止環境だけに残した1件は他環境へ現れず、回収不能時の損失限界も再現できた。
- ローカルエミュレーターと実Firebaseの両方で同じE2Eテストに合格した。

この合格は、Firebase方式の**限定した技術的成立性**を示す。技術採用、本番利用、性能・通信量、実機、QRカメラ読取り、個別認証、権限制御、暗号化の合格を意味しない。

## 検証結果

| 確認項目 | ローカルエミュレーター | 実Firebase | 判定 |

| 6環境・架空QR 500件の完全オフライン保存 | 成功 | 成功 | 合格 |
| 508イベントの復旧後統合 | 全環境で508件をサーバー確認付き取得 | 全環境で508件をサーバー確認付き取得 | 合格 |
| 同一QRの複数初回受付 | 初回受付2件を競合1件として表示 | 同左 | 合格 |

| 重要連絡と5利用者の確認 | 追記・共有を確認 | 同左 | 合格 |

所要時間はテスト全体の実行時間であり、実運用のQR判定時間、同期時間、500人の受付処理時間、通信量を測る`POC-002`の結果ではない。

## 検証中に判明し対処した事項

| 事項 | 対処 | 本番候補への引継ぎ |
|---|---|---|
| 開発サーバーではオフライン再読込み用資産が十分に事前保存されなかった | 本番ビルドのプレビューをE2E対象にした | オフライン試験は配布相当ビルドで行う |
| Authエミュレーター接続前に認証永続化が始まる場合があった | 初期化順を固定した | SDK初期化順をテストする |
| 端末内だけの同期状態をFirestoreへ送るとRulesで拒否された | 業務イベントだけに正規化して送信した | 端末状態と共有データを分離する |
| キャッシュ読取りをサーバー確認と誤認できた | 送信確認と再取得にサーバー指定APIを使用した | 未送信削除条件をサーバー確認に限定する |
| 全件スナップショットの反復適用で処理量が増えた | `docChanges()`による差分適用へ変更した | POC-002で通信量と処理量を測る |
| 逐次送信では実サービス検証に時間がかかった | 同時送信数を8件に制限した | 端末・回線別の適正値をPOC-002で測る |
| Firestoreがオブジェクトのキー順を変え、同一イベントを不一致と判定した | キー順によらない正規化比較を追加した | 保存前後の意味的同一性をテストする |
| API有効化直後は認証などが一時的に失敗した | 反映待ち後に再試行した | 初期設定手順に待機と再試行を記載する |

## 保存データと費用

- 端末にはPWA静的資産、架空イベント、送信状態、匿名認証状態だけを保存した。
- Firestoreには専用実行パス以下の架空イベントだけを保存した。
- 外部プロジェクトはSparkで、請求先アカウントを接続していない。Console上でも無料プラン、月額0円を確認した。
- Google Analyticsは作成時に無効化した。POC-001では利用目的がなく、データ最小化と管理負担軽減の点から適切である。
- 実測件数は承認時の停止上限より十分小さい。無料枠は将来変わり得るため、本番採用時と開催前に再確認する。

## 残るリスクと未判定事項

- Chromiumの自動試験であり、iPhone Safari、Android Chrome、実機ストレージ制限は未確認である。
- 匿名認証は環境分離用であり、本番の個別認証、役割、失効、退職者対応を確認していない。
- 回収不能端末だけの未送信記録は復元できない。紙の当日運営表との照合が必要である。
- オフライン中の端末間では重複受付を即時に防止できず、復旧後の競合対応が必要である。
- 実運用性能、共有10秒上限、当日通信量20MB以下は`POC-002`で別途確認する必要がある。
- 端末内個人情報の暗号化と締め処理後削除は`POC-004`の対象である。
- Firebaseの採用、POC-002以降、本番プロジェクト作成は未承認である。
