# C-01 端末単位認可の成立性調査

## この文書について

| 項目 | 内容 |
|---|---|
| 目的 | 同じ利用者の端末を個別に停止するためのサーバー側認可方式を比較し、基本設計で未解決の境界を明らかにする |
| 主な読者 | 開発者、設計担当者、依頼者 |
| 対象 | 第三者品質レビュー C-01、REQ-F-031、REQ-NF-017、AC-030 |
| 関連Issue | [#71](https://github.com/EU0207/concert-reception-system/issues/71) |

## 結論

現在の「同じFirebase UIDで複数端末にログインし、静的PWAからFirestoreへ直接アクセスする」構成では、クライアントが指定する端末IDだけを根拠に、停止端末Aと有効端末BをSecurity Rulesが区別する設計は成立しない。端末AはBのIDを指定できるためである。端末IDをパスや文書に置くだけでは、要求元による所持証明にならない。

Firebaseの[Firestore Rules Request](https://firebase.google.com/docs/reference/rules/rules.firestore.Request)には認証済み利用者等の要求情報があるが、アプリが端末内で発行したIDを認証済みの端末属性として受け取る項目はない。[カスタムクレーム](https://firebase.google.com/docs/auth/admin/custom-claims)は利用者アカウントに設定され、更新後のトークンはその利用者の端末へ伝播する。同じUIDの端末を区別する用途には使えない。これは現行構成との照合結果であり、Firebase全体で端末単位認可が不可能という意味ではない。

## 候補比較

| 候補 | 成立条件 | 利点 | 欠点・影響 | 判断 |
|---|---|---|---|---|
| A：信頼できるサーバーで端末の所持を検証し、業務APIを通す | 読取り・書込みの双方で本人トークンと端末固有の署名等を検証し、停止状態を確認する | 同じ利用者IDと端末別停止を両立できる | サーバーの運用、費用、障害時の扱いが増える。静的PWAからFirestoreへの直接アクセス範囲を変更する | 要件を維持する場合の第一候補。費用条件と構成変更の承認が必要 |
| B：端末ごとに異なるFirebase認証主体を使用する | 各端末資格と業務利用者を安全に関連付け、本人のログイン・ログアウトをサーバー側でも検証する | Rulesが端末資格ごとに停止を判定できる可能性がある | 現行の「UIDが業務利用者」の設計とGoogleログインの扱いを大きく変更する。単純な匿名端末資格では本人確認を保証できない | 本人と端末の結合方式が未証明のため採用しない |
| C：端末IDを要求へ入れ、Rulesで端末文書を参照する | 端末IDが改変できない必要がある | 現行設計に近い | 同じUIDの停止端末が有効端末IDを指定できる | 不採用 |
| D：利用者アカウント全体を停止する | 端末個別停止の要件を変更する | 現行の静的構成で単純 | 有効端末も停止し、当日の継続に影響する | 依頼者が要件を変更した場合だけ再検討 |

## 限定技術検証

方式採用前に、架空アカウントと独立した端末A・Bで次を試す。端末IDを画面で変更する試験だけでは足りず、直接API要求でも確認する。

1. 同じ業務利用者として端末A・Bを承認し、両方で読取りと書込みを行える。
2. 端末Aだけを停止し、Aの資格でAのIDを指定した読取り・書込みを拒否する。
3. Aの資格でBのIDへ書き換えた読取り・書込みも拒否し、B自身は継続できる。
4. 別公演、期限切れ、停止解除、回線復旧後の隔離送信を確認する。
5. 追加サービス、資格情報、費用、利用量、障害時の紙切替を記録する。

技術検証には本番環境や実在の来場者データを使用しない。方式が決まるまで、BD-04とBD-05にある端末IDのRules判定を「成立確認済み」と扱わず、詳細設計・本番実装の前提にしない。

## 次の判断

現行要件を維持する場合は候補Aの具体構成と費用をADRで比較し、依頼者の費用条件と整合するか確認する。無料・カード登録なしの条件を維持したまま同等の保証が可能な別案が見つかれば、同じ限定技術検証で比較する。成立する方式がない場合は、端末個別停止または費用条件の変更案を影響とともに依頼者へ提示する。

**依頼者に確認してください**

- サーバー方式に費用やカード登録が必要と判明した場合、現在の無料・カード登録なしの条件と、端末個別停止のどちらを優先するか確認してください。両条件を同時に満たす方式が未確認のためです。推奨は、まず要件を維持する方式の費用と運用負担を提示してから判断することです。
