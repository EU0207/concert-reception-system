## 結論

POC-001で合格した「PWA＋IndexedDB＋Firebase Authentication／Cloud Firestore」を対象に、追加パッケージと追加FirebaseサービスなしでPOC-002を実施できる見込みである。

POC-002では、デコード済みの架空QR文字列を受け取った後の業務判定、端末保存、500件の処理時間、復旧・オンライン共有時間、当日相当の通信量を測る。カメラ起動、画像からのQR解析、紙・スマートフォン画面からの読取り、実機固有の性能はPOC-003の対象であり、本書には含めない。

## 承認を依頼する範囲

明示承認後、次の作業だけを`POC-002`として行う。

1. Issue #6用ブランチの`poc/POC-002/`へ、POC-001の最小PWAとテストを複製し、性能・通信量計測に必要な変更だけを加える。
2. ローカルエミュレーターで計測器、集計、停止条件、削除手順を検証する。
3. 6つの独立したChromiumプロセスと架空QR 500件で、業務判定時間、全体処理時間、復旧後統合時間、オンライン共有時間を測る。
4. 開催前のアプリ資産取得を済ませた6つの分離プロファイルを使用し、外部ソケットの送受信量を環境別に測る。
5. POC-001から保持しているFirebase Spark検証専用プロジェクトへ、1回の正式計測だけ接続する。計測不備時の再実行は停止上限内で最大2回までとする。
6. 結果、中央値、95パーセンタイル、最大値、失敗件数、環境別通信量、制約、再現手順を記録する。
7. 結果採取後、POC-002のFirestoreデータ、匿名利用者、ブラウザプロファイル、NetLogを削除し、検証専用プロジェクト本体はPOC-005終了確認まで保持する。

`POC-003`～`POC-005`、技術採用、本番実装、実在データ、実機、QR画像解析、メール＋パスワード認証、役割制御、暗号化、Hosting、Analytics、課金機能は承認対象外とする。

## 測定対象と合格基準

### 指標の定義

| 指標 | 開始 | 終了 | 集計 |
|---|---|---|---|
| 通常判定時間 | デコード済み架空QR文字列を判定処理へ渡す直前 | 判定結果を端末のIndexedDBへ保存し、同じ処理から成功応答が戻った時 | 500件の中央値、95パーセンタイル、最大値、失敗件数 |
| 500件全体所要時間 | 6環境へ最初の架空QRを投入する直前 | 500件目の端末保存が完了した時 | 全体時間、環境別件数 |
| 復旧後統合時間 | 6環境の通信を復旧する直前 | 全送信がサーバー確認済みとなり、全環境が期待イベント集合を確認した時 | 1回の全体時間、欠落・重複 |
| オンライン共有時間 | 送信元環境でオンライン変更処理を開始する直前 | 各受信環境が対象eventIdを画面状態へ反映した時 | 30変更×他5環境の150標本について中央値、95パーセンタイル、最大値、失敗件数 |
| 当日相当通信量 | 事前取得済みプロファイルで計測用ブラウザを起動した時 | 全シナリオ終了後にブラウザを正常終了した時 | 環境ごとの外部ソケット送信、受信、合計バイト。最大値も記録 |
| 差分同期 | 初期500件の統合後 | オンライン変更30件の共有完了時 | 受信した文書変更数を記録し、各変更で初期500件を反復取得していないことを確認 |

時間はOS時刻変更の影響を受けにくい単調増加時計を使う。ブラウザ内処理は`performance.now()`、環境間の開始・終了はPlaywrightを実行するNode.jsプロセスの`performance.now()`で測る。サーバー時刻は記録の順序確認に使い、経過時間の差分計算には使わない。

### 合格基準

| 項目 | 合格に必須 | 目標達成として別記録 |
|---|---|---|
| 通常判定 | 失敗0件、全500件が10秒以内 | 95パーセンタイルが2秒以内 |
| 500件処理 | 6環境合計500件を30分以内に端末保存 | 参考として環境別ばらつきを記録 |
| 復旧後統合 | 統合可能な全記録に欠落・重複・未表示競合がない | 時間を次の設計判断へ引き継ぐ |
| オンライン共有 | 150標本すべて10秒以内、欠落0件 | 95パーセンタイルが5秒以内 |
| 通信量 | 事前取得を除き各環境20MB以下 | 送信・受信の内訳と最大環境を記録 |
| 差分同期 | オンライン変更ごとに初期500件の全取得を繰り返さない | 変更1件当たりの文書変更数を記録 |

10秒上限、30分上限、20MB上限、欠落・重複のいずれかを満たさない場合は不合格とする。2秒または5秒の目標を満たさないが必須上限を満たす場合は、合格と目標未達を併記し、改善要否を別途判断する。測定器が通信量を取得できない場合は通信量を推測で合格にせず、その項目を未判定として方法を再提案する。

## 実施シナリオ

### P002-01 計測器のローカル確認

- エミュレーターと20件の架空ウォームアップデータで、時刻、標本数、パーセンタイル、通信集計、停止判定を確認する。
- ウォームアップ結果は正式な合格値へ含めず、次のシナリオ前に削除する。

### P002-02 完全オフライン500件と復旧

- 6環境を事前準備後にオフラインとし、`FAKE-P002-QR-0001`～`0500`を均等に割り振る。
- 各文字列の形式・公演・未受付を判定し、追記イベントをIndexedDBへ保存する。
- 500件の判定時間と全体所要時間を集計する。
- 通信復旧後、500件を送信し、全環境のサーバー確認付き取得、欠落0、重複0を確認する。

### P002-03 オンライン共有30変更

- 6環境が順番に5件ずつ、合計30件の架空変更を作成する。
- 各変更について送信元以外の5環境への反映を待ち、合計150件の共有時間を集計する。
- 1件が10秒を超えた時点で上限違反を記録し、費用停止条件に抵触しない範囲で残りの標本を取得する。

### P002-04 通信量と差分確認

- 6環境を別々のChromium永続プロファイルとして事前準備し、Service Workerと静的資産を取得後に一度終了する。
- 計測時は各プロファイルを別プロセスで再起動し、Chromium NetLogを既定の「秘密情報を除外」モードで保存する。
- NetLogの外部ソケットに対する`SOCKET_BYTES_SENT`と`SOCKET_BYTES_RECEIVED`の`byte_count`を環境別に合計する。ループバック通信は除外し、Firebase認証・Firestore接続・TLS通信を含む外部通信は含める。
- NetLogとは別に、アプリ側の送信イベント数とFirestoreの受信変更数を記録し、全件反復取得の有無を確認する。
- 生のNetLogは機密性のある診断情報として扱い、Gitへ含めず、集計確認後に削除する。

NetLogは低レベルのパケットキャプチャそのものではない。ブラウザ外のOS通信とIP層の付加情報は含まれないため、結果には「ブラウザ外部ソケット観測値」と明記する。20MBへ近い場合は合格とせず、実機・携帯回線または別の測定方法を再提案する。

## 削除方法と確認

1. 全環境の未送信0件、結果集計、証跡作成を確認する。
2. 削除前にFirebaseプロジェクトID、POC-002の`runId`、匿名UID一覧、ローカル絶対パスを読み取り照合する。
3. FirestoreのPOC-002専用`pocRuns/{runId}`と`events`配下だけを削除する。APIで親文書不存在、イベント0件を確認する。
4. POC-002中に記録したUIDだけを対象とし、メール・電話・外部プロバイダーを持つ利用者が混在していないことを確認して削除する。Auth一覧で残存0件を確認する。
5. 6プロファイルを閉じ、POC-002用IndexedDB、Cache Storage、Service Workerを削除する。
6. `poc/POC-002/artifacts/raw/`内のプロファイル、NetLog、UID一覧、trace、ログを、絶対パス確認後に削除する。
7. 匿名化した集計、再現手順、合否、削除確認だけをGit管理に残す。
8. Firebaseプロジェクト本体、Web App、Firestoreデータベース、RulesはPOC-005終了確認まで保持する。

削除操作が一部失敗した場合は対象を広げず、残存件数と失敗理由を報告する。プロジェクト全体削除、データベース削除、他の`runId`、記録していないUIDの一括削除は行わない。

## 費用0円の根拠と停止上限

2026-09-03時点のFirebase公式情報では、Sparkプランは開始時の支払情報が不要である。Cloud Firestore Standardの無料枠は、プロジェクト内の最初の1データベースについて保存1GiB、1日50,000 document reads、20,000 writes、20,000 deletes、月10GiBのoutbound transferである。無料枠はアプリ単位ではなくプロジェクト単位である。

POC-002では既存の最初のデータベースだけを使い、請求先を接続しない。TTL、PITR、backup、restore、cloneを使用しない。

| 指標 | POC-002停止上限 | 無料枠との比較 |
|---|---:|---|
| 保存 | 10MiB | 1GiBの1%未満 |
| document writes | 2,000/日 | 20,000/日の10% |
| document reads | 15,000/日 | 50,000/日の30% |
| document deletes | 2,000/日 | 20,000/日の10% |
| Firestore outbound | 200MiB/月 | 10GiB/月の約2% |
| 匿名利用者 | 最大20件 | 6環境と再実行用。電話認証なし |
| ローカルNetLog | 最大50MiB×6環境 | ローカル一時保存のみ。Git管理外 |

正式計測は1回、計測不備による再実行は最大2回とし、合計3回を超えない。実行前にConsoleで当日のプロジェクト使用量を確認し、既使用量とPOC-002停止上限の合計が無料枠の80%へ達する見込みなら、その日の外部試験を開始しない。いずれかの停止上限到達、請求先要求、Spark以外への変更要求、無料枠縮小を確認した場合は停止し、不適合または未判定として報告する。

## 主なリスクと停止条件

| リスク | 対応・停止条件 |
|---|---|
| 自動試験が人のQR提示速度を表さない | 業務操作全体ではなく、デコード後のシステム処理性能として記録する |
| Chromium結果をSafari・Androidへ一般化できない | 実機固有結果としない。POC-003へ引き継ぐ |
| NetLogが携帯回線の全通信を完全再現しない | 外部ソケット観測値と明記し、20MBへ近い場合は未判定にする |
| NetLogに診断情報が含まれる | 既定の秘密除外モード、Git管理外、集計後削除を徹底する |
| 計測処理自体が性能へ影響する | ローカルで計測あり・なしを比較し、差を記録する |
| 初期購読と増分購読を混同する | 初期取得件数と`docChanges()`の増分件数を分ける |
| POC-001後のFirebase使用量が同日に残る | 開始前にConsole使用量を確認し、プロジェクト単位の停止条件で判断する |
| 良い結果が出るまで反復する | 正式1回、計測不備時だけ最大2回とし、全実行結果を記録する |
| 依存関係の重大脆弱性 | High/Critical検出時は外部接続前に停止する |
| POC-002データが後続PoCへ残る | 専用runId・UID一覧で限定削除し、残存0件を確認する |

## 承認後の実施順序

1. 本書の承認日時とIssue #6コメントURLを記録する。
2. `.gitignore`へPOC-002用ルールを追加し、除外・追跡対象を確認する。
3. `poc/POC-002/`を作成し、POC-001の承認済み範囲を複製する。
4. 固定依存関係の完全性、ライセンス、High/Critical脆弱性を確認する。
5. ローカル計測と削除確認に合格した後だけ、実Firebaseへ接続する。
