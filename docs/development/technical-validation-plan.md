## 結論

- 暫定要件、対象外、制約は、承認済み議事録の決定事項と意味上の矛盾がない。
- 追加要望 `RQ-001`～`RQ-006` は詳細確認を終え、`REQ-F-032`～`REQ-F-037`、`REQ-NF-012`、`AC-022`～`AC-027` として正式要件化した。
- 受入条件は各要件を確認可能な形で用意されている。ただし、対応環境、同期方式等の未決定事項に依存する詳細手順はIssue #6の結果反映後に確定する。
- Issue #6では、先に公開情報と候補資料を調査し、調査だけでは判定できない項目に限ってPoCを行う。
- 本計画の承認は要件、受入条件または技術方式の最終承認を意味しない。

## Issue #6の実施順序

1. `RES-001`～`RES-004` の調査を行い、前提、出典、確認日、候補間の差、PoCが必要な残課題を記録する。
2. 調査結果と技術候補について、利点、欠点、費用、セキュリティ、運用影響、推奨案を依頼者へ提示する。
3. 依頼者がPoC対象候補と対象端末を確認し、PoCを別途承認する。外部サービス、依存関係、費用が発生する候補はこの時点で個別承認を得る。
4. `RES-005` で自動座席配置の具体例を机上確認し、PoCコードを作らず受入テスト設計へ引き継ぐ。
5. 明示的に承認された場合だけ `POC-001` を先に行い、完全オフライン受付と統合を実現できる候補があるか確認する。
6. `POC-001` を満たす候補だけを対象に `POC-002`～`POC-005` を行う。
7. 結果を質問ID、要件ID、受入条件IDと対応付け、各要件について維持、変更候補、保留のいずれかを記録する。

- `POC-002`の測定方法、再利用範囲、外部資源、保存・削除、停止上限は[POC-002開始承認依頼書](poc-002-approval-request.md)で具体化し、2026-09-03にPOC-002だけ開始承認を得た。
- `POC-002`は2026-09-03にローカルエミュレーターと専用実Firebaseの両方で合格した。結果と制約は[POC-002実施結果報告書](poc-002-result.md)に記載する。
- `POC-003`の追加依存関係、Hosting一時配信、実機協力、保存・削除、費用は[POC-003開始承認依頼書](poc-003-approval-request.md)で具体化し、2026-09-03にPOC-003だけ開始承認を得た。実機操作は[POC-003実機確認手順書](poc-003-device-test-guide.md)に従う。
- 架空データだけを使用し、実在する来場者情報を使用しない。
- APIキー、認証情報、個人情報をリポジトリへ保存しない。
- 外部サービスへの接続、依存関係の追加、契約、課金は、必要性と影響を説明して個別承認を得るまで行わない。
