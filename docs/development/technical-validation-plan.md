## 結論

- 暫定要件、対象外、制約は、承認済み議事録の決定事項と意味上の矛盾がない。
- 追加要望 `RQ-001`～`RQ-006` は、採用済み要件および受入条件から分離されている。
- 受入条件は各要件を確認可能な形で用意されている。ただし、対応環境、同期方式等の未決定事項に依存する詳細手順はIssue #6の結果反映後に確定する。
- トレーサビリティ表の受入条件欄にあったID種別の転記誤りを修正する。要件や受入条件の内容は変更しない。
- Issue #6では、先に公開情報と候補資料を調査し、調査だけでは判定できない項目に限ってPoCを行う。
- 本計画の承認は要件、受入条件または技術方式の最終承認を意味しない。

## Issue #6の実施順序

1. `RES-001`～`RES-004` の調査を行い、前提、出典、確認日、候補間の差、PoCが必要な残課題を記録する。
2. 調査結果と技術候補について、利点、欠点、費用、セキュリティ、運用影響、推奨案を依頼者へ提示する。
3. 依頼者がPoC対象候補と対象端末を確認し、PoCを別途承認する。外部サービス、依存関係、費用が発生する候補はこの時点で個別承認を得る。
4. 承認された場合だけ `POC-001` を先に行い、完全オフライン受付と統合を実現できる候補があるか確認する。
5. `POC-001` を満たす候補だけを対象に `POC-002`～`POC-004` を行う。
6. 結果を質問ID、要件ID、受入条件IDと対応付け、各暫定要件について維持、変更候補、保留のいずれかを記録する。

## PoC実施ルール

- Issue #6は、依頼者が本計画とPoC実施を明示的に承認するまで開始しない。
- 架空データだけを使用し、実在する来場者情報を使用しない。
- APIキー、認証情報、個人情報をリポジトリへ保存しない。
- 外部サービスへの接続、依存関係の追加、契約、課金は、必要性と影響を説明して個別承認を得るまで行わない。
- PoCコードはIssue #6用の独立ブランチ内で本番コードと分離し、本番利用または流用を前提としない。
- PoC成果物の保存場所、再現手順、削除対象をIssue #6の着手時に記録する。不要になった成果物は、削除対象と影響を確認してから削除する。
- 合格、不合格、未判定のすべてを記録し、不合格を理由に無断で要件または技術方式を変更しない。

## 追加要望の確定方法

`RQ-001`～`RQ-006` は無視せず、採用済み要件とも混在させない。各要望について次のいずれかを依頼者が選び、理由と影響を記録する。

- `採用`：詳細を確認し、新しい要件IDと受入条件IDを発行する。
- `将来候補`：現時点の受入対象には含めず、技術候補比較の「将来への影響」欄だけで考慮する。
- `不採用`：対象外として理由を記録する。

採否判断の前に、開発担当者は各要望の選択肢、利点、欠点、推奨案、費用・日程・個人情報・既存要件への影響を提示する。技術検証へ影響し得る要望はPoC対象の承認前に方向性を決め、それ以外も要件定義書の最終承認前に決める。

| 要望ID | 技術検証へ加味する場合の確認時期 | 確定までの扱い |
|---|---|---|
| RQ-001 | 出力方式の設計前。PoC対象とする場合はPoC承認前 | 現行の印刷データ出力だけを合格基準とする |
| RQ-002 | `RES-003` の結果確認時、遅くとも `POC-004` 承認前 | 電話番号等を受付用データへ含めない |
| RQ-003 | `RES-002` の結果確認時、遅くとも `POC-001` 承認前 | 再読取り時刻だけを必須履歴とする |
| RQ-004 | `RES-001`、`RES-002` の結果確認時、遅くとも `POC-003` 承認前 | 座席番号の一覧管理と手動変更だけを対象とする |
| RQ-005 | 要件最終承認前。別の技術検証が必要なら新しい検証IDを発行する | 1名・1席・1QRと手動の座席変更だけを対象とする |
| RQ-006 | `RES-002` の結果確認時、遅くとも `POC-001` 承認前 | 来場者ごとの例外対応一覧だけを対象とする |
