## 結論

- 暫定要件、対象外、制約は、承認済み議事録の決定事項と意味上の矛盾がない。
- 追加要望 `RQ-001`～`RQ-006` は詳細確認を終え、`REQ-F-032`～`REQ-F-037`、`REQ-NF-012`、`AC-022`～`AC-027` として正式要件化した。
- 受入条件は各要件を確認可能な形で用意されている。ただし、対応環境、同期方式等の未決定事項に依存する詳細手順はIssue #6の結果反映後に確定する。
- Issue #6では、先に公開情報と候補資料を調査し、調査だけでは判定できない項目に限ってPoCを行う。
- 本計画の承認は要件、受入条件または技術方式の最終承認を意味しない。

## Issue #6の実施順序

1. `RES-001`～`RES-004` の調査を行い、前提、出典、確認日、候補間の差、PoCが必要な残課題を記録する。
2. 調査結果と技術候補について、利点、欠点、費用、セキュリティ、運用影響、推奨案を依頼者へ提示する。
3. 依頼者がPoC対象候補と対象端末を確認し、PoCを別途承認する。外部サービス、依存関係、費用が発生する候補はこの時点で個別承認を得る。
4. `RES-005` で自動座席配置の具体例を机上確認し、PoCコードを作らず受入テスト設計へ引き継ぐ。
5. 明示的に承認された場合だけ `POC-001` を先に行い、完全オフライン受付と統合を実現できる候補があるか確認する。
6. `POC-001` を満たす候補だけを対象に `POC-002`～`POC-005` を行う。
7. 結果を質問ID、要件ID、受入条件IDと対応付け、各要件について維持、変更候補、保留のいずれかを記録する。

## PoC実施ルール

- Issue #6のPoC段階は、依頼者が更新後の対象、合格基準、外部サービス、依存関係、削除方法を確認して明示的に承認するまで開始しない。
- `POC-001`の具体的な承認対象は[POC-001開始承認依頼書](poc-001-approval-request.md)に記載し、同書への明示承認をIssue #6へ記録する。
- `POC-001`は2026-09-02にローカルエミュレーターと専用実Firebaseの両方で合格した。結果と制約は[POC-001実施結果報告書](poc-001-result.md)に記載する。
- 架空データだけを使用し、実在する来場者情報を使用しない。
- APIキー、認証情報、個人情報をリポジトリへ保存しない。
- 外部サービスへの接続、依存関係の追加、契約、課金は、必要性と影響を説明して個別承認を得るまで行わない。
- PoCコードはIssue #6用の独立ブランチ内で本番コードと分離し、本番利用または流用を前提としない。
- PoC成果物の保存場所、再現手順、削除対象をIssue #6の着手時に記録する。不要になった成果物は、削除対象と影響を確認してから削除する。
- 検証専用Firebaseプロジェクトは`POC-005`の終了確認まで保持する。各PoCの終了時に架空データと不要な認証利用者を削除し、全PoC終了後にプロジェクト本体を1回だけ削除する。既存プロジェクトの保持は後続PoCの開始承認を意味しない。
- 合格、不合格、未判定のすべてを記録し、不合格を理由に無断で要件または技術方式を変更しない。

## Issue #6の終了条件

- 各検証IDについて条件、対象バージョン、結果、証跡、限界、再現方法が記録されている。
- 各結果が質問ID、TBD ID、要件ID、受入条件IDと対応付いている。
- 暫定要件ごとに維持、変更候補、保留を記録し、変更候補は依頼者の承認待ちとして区別されている。
- 技術候補の利点、欠点、費用、セキュリティ、運用影響が比較されている。
- 重要な技術判断はADR案として記録され、採用決定とは区別されている。
- 要件定義書と受入条件書の最終承認へ進めるか、追加確認が必要かを判断できる。
