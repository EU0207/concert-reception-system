## 結論

クライアントからFirebaseへ直接接続する構成を維持し、Firebase Authentication、Firestore Security Rules、環境分離、端末単位の許可を組み合わせて、明示的に許可した要求だけを受け付ける。画面上の非表示やクライアント側検査だけを認可根拠にせず、Firestoreでは公演、UID、役割、端末、期限、操作、状態遷移、フィールドを要求ごとに検証する。

公開トップ、ログイン、パスワード再設定、招待URLの初期表示ではFirestoreへ接続しない。認証とメール確認の完了後、最初のFirestore接続前にApp Checkを初期化する。Cloud Firestoreは監視結果と対象実機の確認後にApp Checkを強制適用し、未認証要求はRulesの確認用読取りより前に拒否する。

端末内の本番業務データは、公演・端末単位で生成したランダムなAES-GCM 256ビットの非抽出CryptoKeyで暗号化する。CryptoKeyは端末のIndexedDBへ永続保存し、スタッフへFirebase Authentication以外のパスフレーズやPINを要求しない。認証パスワード、共有パスフレーズ、PBKDF2、鍵暗号化鍵（KEK）を暗号鍵の生成・保護・復号に使用しない。

同じ端末へ複数公演を準備する場合も、公演ごとにCryptoKeyと暗号化データを分離する。公演シリーズを認可または暗号化の境界に使用しない。1公演の停止、締め、削除で別公演の鍵と暗号化データを変更しない。

完全オフラインの紛失端末は、端末停止を検知するまで保存済みCryptoKeyを利用される可能性を残存リスクとして受容する。代わりに、オンライン接続または回線復旧時は通常操作を保留し、最初にサーバー上の端末状態を確認する。停止済みなら通常画面を直ちにロックし、画面表示を伴わない未同期記録の隔離送信だけを許可する。端末停止では鍵と暗号化データを削除せず、停止解除後に同じ鍵・既存データを再利用する。鍵の削除は全件受領後の締め処理または端末廃止・データ削除と一体で行う。

パスワード、トークン、秘密鍵、実在する個人情報はリポジトリ、ログ、監査、解析、画面へ残さない。招待・追加端末リンクは推測困難な1回限りの値をURLフラグメントで渡し、サーバーにはダイジェストだけを保存する。依存関係と公開物は実装開始前、各PR、公開前のゲートで検査する。自動検査の実装、Firebase設定変更、有料診断は本書では行わない。

| 保護対象 | 主な脅威 | 境界と基本対策 |
|---|---|---|
| 来場者、受付、例外、任意項目、座席、連絡 | 別公演・役割外閲覧、端末紛失、XSS、過剰配布 | 公演単位の分離、最小配布、Rules、端末暗号化、期限・停止、出力制限 |
| 受付イベント、未同期、競合、隔離記録 | 改変、重複、削除、停止後の通常反映 | 変更不能イベント、冪等ID、整合性認証、受領確認、隔離、監査 |
| 利用者、役割、端末、招待 | なりすまし、権限昇格、トークン再利用 | Firebase Authentication、メール確認、明示割当、1回限りトークン、Rulesによる状態遷移検証 |

## BD-05-02 Firestoreの認可とデータ境界

第三者品質レビューC-01の端末IDなりすましに対し、[POC-006](../technical-validation/poc-006-result.md)では端末別匿名Auth UIDと本人Authのセッション証跡を照合する候補を限定検証した。以下の端末承認確認は要求条件を表す。クライアント指定の端末IDだけで成立するとみなさず、業務要求の`request.auth.uid`を端末資格として、本人対応、役割、セッション、停止状態を照合する。[ADR-005](../decisions/ADR-005-device-principal-authorization.md)は変更承認待ちである。

Security Rulesは既定拒否とし、公開読取りを許可するコレクションを作らない。許可する読取り・作成・更新・削除は、データ区分ごとに列挙する。

拒否までの順序は次のとおりとする。App Checkの強制適用はRulesより前のサービス境界として扱い、App Checkだけで認証・認可済みとはみなさない。

| 順序 | 条件 | 読取り方針 |
|---|---|---|
| 1 | 有効なApp Checkトークン | 強制適用後は、不足・無効な要求をFirestore文書へ到達させない |
| 2 | `request.auth != null` | 未認証なら役割・端末文書を`get()`・`exists()`せず拒否する |
| 3 | 公演ID、端末ID、文書パス、入力形式 | 形式・長さ・列挙値の明らかな不正を追加読取り前に拒否する |
| 4 | メール確認、役割、端末承認 | 認証済み要求だけ、必要最小限の文書を参照して判定する |
| 5 | 操作、状態遷移、フィールド | 対象文書と要求内容に応じた条件を判定する |

`get()`・`exists()`によるRulesの確認用読取りもFirestore利用量へ算入され得るため、認証と形式の確認より前に呼び出さない。同じ確認文書の重複参照を避け、単一要求に必要なアクセス呼出しを最小化する。SDKを介さない直接API要求にも同じ順序を適用する。

すべての認証済み本番要求で、少なくとも次を検証する。

- Firebase AuthenticationのUIDとメール確認状態
- 環境ID、公演ID、対象文書パスの一致
- 選択中公演、役割割当、端末割当が同じ公演IDを参照し、公演シリーズの一致だけでは許可しないこと
- 公演単位の有効な役割と操作権限
- 承認済み端末ID、停止・廃止状態、準備状態、許可期限
- サーバー時刻を基準にした役割・招待・オフライン許可の期限
- 作成可能なフィールドの許可リスト、必須項目、型、長さ、列挙値
- 更新可能なフィールドと許可された状態遷移、変更不能ID・発生情報の不変性
- 削除が許される対象、再認証を要する高影響操作の事前記録、未同期・履歴の不存在

Firestoreは文書単位で読み取られ、同一文書の一部フィールドだけをRulesで隠せない。そのため一般受付へ不要な任意項目、管理情報、招待、監査、隔離記録は別文書・別コレクションへ分離する。クエリはRulesが許可できる絞込みを必須とし、一覧取得後のクライアント側除外で代替しない。管理用SDKなどRulesを迂回するサーバー処理を将来追加する場合は、別の認可境界、秘密管理、監査を設計してADRと承認を得る。

通常業務の期限後も、端末へ既に保存済みの未同期イベントを失わないため、BD-04の同期・管理者確認専用経路への作成と受領確認だけを例外的に許可する。この経路は既存記録の更新・削除、通常データの読取り、新しい業務操作を許可しない。端末上の発生時刻は信頼済み時刻とみなさず、オフライン許可のスナップショット、UID、端末ID、公演ID、端末連番、イベントID、サーバー到着時刻を記録する。停止端末は隔離領域、期限切れ端末は期限後到着が判別できる専用状態へ受け入れ、必要な管理者確認を経るまで通常操作から新規作成した記録と区別する。

一般受付担当者を当日に臨時管理者へ任命しても、管理画面の全データは配布しない。追加準備では、対象公演の来場状況、会場席、例外処理、スタッフ連絡を含む当日業務用データだけを差分取得する。当日業務範囲の監査は別の読取り経路に分離する。次の情報は取得対象に含めない。

- 電話番号、メールアドレス、住所。
- 管理者用任意項目と認証・役割管理監査。
- 他公演の情報と管理者専用出力データ。

Security Rulesは臨時管理者用の各読取り・書込みで、公演ID、UID、端末IDを確認する。さらに、有効期限内の臨時管理者役割版と、当該端末の準備済み役割版が一致することを検証する。役割変更だけで管理データ全体を取得できる経路は設けない。

実装時はFirebase Local Emulator Suiteで、正常要求だけでなく未認証、別UID、別公演、未承認・停止端末、期限切れ、専用送信経路の範囲外、余分なフィールド、型・長さ違反、不正遷移、直接API要求を自動試験する。Console上の一時変更を正本にせず、レビュー済みRulesを環境別手順で配備する。

## BD-05-03 招待・追加端末リンク

招待および追加端末関連付けは、暗号学的乱数で128ビット以上の推測困難なトークンをブラウザーで生成する。URLへは氏名、メールアドレス、公演名、UID、端末IDを含めず、トークンをクエリではなくURLフラグメントへ置く。受信画面は読み取り後直ちに`history.replaceState`でフラグメントを除去し、第三者スクリプト、解析、外部画像、リファラー送信を使わない。

招待URLを開いただけではFirestoreへ接続しない。トークンは認証完了までブラウザー内だけに保持し、公開画面から業務データを取得しない。Firebase Authenticationによる本人認証とメール確認の後にApp Checkを初期化し、最初のFirestore要求で招待先メール、期限、使用状態を確認する。

Firestoreにはトークン平文を保存せず、SHA-256ダイジェストを照合用識別子として、用途、対象公演、招待先メールの正規化値、予定役割、有効期限、発行者、未使用・使用済み・失効状態だけを保存する。受諾時は認証済みUID、確認済みメール、対象、期限を検証し、未使用から使用済みへの変更と役割または端末の関連付けを同一トランザクションで確定する。再読込み、別メール、別用途、期限切れ、取消し済み、使用済みを拒否する。リンクを知るだけでは本番データを取得できない。

この方式はCloud Functionsを前提にしない。実装設計でSecurity Rulesとクライアントトランザクションだけでは一回性・権限付与の原子性を安全に満たせないと判明した場合は、管理者による確認方式を優先し、Functionsを無断採用せず費用条件と代替案をADRへ戻す。

## BD-05-04 端末内暗号化と鍵管理

| 項目 | 方針 |
|---|---|
| 対象 | IndexedDBへ保存する本番公演の来場者、受付・未同期イベント、例外、任意項目、連絡、座席・会場情報、隔離対象を含む業務データ。公開済みPWA静的資産は対象外 |
| データ暗号鍵 | 端末準備時に、公演・端末ごとにWeb Crypto APIでランダムなAES-GCM 256ビット鍵を`extractable=false`として生成する。環境ID、公演ID、端末ID、鍵版の組合せに対応付け、別公演・別端末と共有しない。同じ端末では複数公演の鍵を同時に保持できる |
| 鍵の保存 | 非抽出CryptoKeyをStructured Cloneにより端末のIndexedDBへ永続保存する。鍵素材のエクスポート、文字列化、Firestore・Cache Storage・ログ・監査・画面・ファイルへの複製、他端末への転送を禁止する |
| 不採用方式 | スタッフ向け暗号用パスフレーズ、追加PIN、共有パスフレーズ、認証パスワードからの鍵導出、PBKDF2、鍵暗号化鍵（KEK）、鍵包みを本番方式に使用しない |
| 暗号化 | レコードまたは安全なまとまりごとに重複しない96ビットIVを生成し、AES-GCMで暗号化する。環境ID、公演ID、端末ID、スキーマ版、レコードIDを追加認証データへ結び付ける |
| 保存形式 | アルゴリズム版、鍵版、IV、暗号文、追加認証データの識別情報、データ版を保持し、平文を同じ保存領域へ複製しない |
| 再起動・完全オフライン | ブラウザーまたはPWAを開き直した時は、Firebase SDKの認証状態と、端末準備時に保存した役割、端末承認、公演、オフライン許可期限、データ整合性を確認する。オンラインならサーバー確認完了後、完全オフラインなら有効な準備済みスナップショットと期限の範囲だけで保存済みCryptoKeyを使用する |
| オンライン復旧 | App Checkトークンの取得と、認証済み要求によるサーバー状態確認の両方が成功した時点で成立する。片方でも完了しない間はオンライン処理へ移らず、後述のオフライン継続条件を満たす端末だけが端末内受付を続ける。`CONF-040`で依頼者承認済みである |
| 停止中 | 停止済みなら通常画面をロックし、CryptoKeyと暗号化データを保持する。未同期イベントは画面へ復号内容を表示せず、対象レコードを内部処理で必要最小限だけ復号して隔離領域へ送信し、受領後は平文参照を破棄する。失敗時は暗号文と鍵を保持して再送専用状態にする |
| 停止解除 | 管理者による同じ端末IDの停止解除後、本人の再ログインとオンライン確認を行う。公演、役割、端末、期限、アプリ版、データ版、鍵・暗号文の整合性に問題がなければ、同じCryptoKeyと既存データを使い、差分同期から復帰する |
| 鍵の削除 | 端末停止、公演終了、オフライン許可期限、通常のサインアウトだけでは削除しない。未同期・隔離対象の全件受領を確認し、締め処理または端末廃止・データ削除の条件が成立した時だけ、対象公演のデータ、関連メタデータ、CryptoKeyを同じ削除処理の対象にする。別公演の鍵と暗号文は削除しない |

臨時管理者用の追加データは、対象端末に既にある公演・端末専用CryptoKeyで暗号化する。役割変更を理由に鍵を作り直さず、全公演データを再取得しない。追加データにはデータ区分と役割版を結び付け、準備済み役割版が一致しない場合は復号結果を画面へ渡さない。

任期終了または役割解除後は、臨時管理者用データを利用不能にする。未送信記録がある間は、その送信に必要な暗号文とCryptoKeyを保持する。全件受領後に臨時管理者専用データを削除する。削除に失敗した場合は平文表示を禁止したまま削除待ちとし、一般受付用データと区別して再試行する。

Firebase Authenticationのパスワードは本人認証だけに使用し、暗号鍵の生成、暗号化、復号、鍵復旧へ使用しない。スタッフへ暗号化用の追加文字列、PIN、共有パスフレーズを入力させない。CryptoKeyを失った場合にパスワードから再生成する回復経路は設けず、未同期データがある場合はデータ損失の可能性を管理者へ示して復旧手順へ移す。

端末停止は暗号文とCryptoKeyを削除せず、新規受付、通常画面での復号・閲覧、通常同期、データ取得、オフライン再準備を禁止する。隔離送信の内部復号は通常利用ではなく、既存未同期記録を失わないための作成専用処理とする。全件受領前に端末内公演データやCryptoKeyの削除を完了扱いにしない。

IndexedDBでは暗号化レコード、鍵参照、送信状態、削除状態を公演IDで名前空間分離する。復号時は選択中の公演IDとAADの公演IDを照合し、不一致なら復号結果を表示しない。削除処理は対象公演IDを固定し、別公演の保存領域を列挙・削除対象に含めない。

非抽出属性は鍵素材のエクスポートを防ぐが、同一オリジンで実行される正規または悪意あるスクリプトによる暗号操作まで防がない。暗号化はXSS、ログイン済み利用者の誤操作、OS・ブラウザー侵害を単独で防げないため、BD-05-05のCSP、出力エスケープ、依存関係制限を同時に必須とする。完全オフラインの紛失端末は停止検知まで正規PWAから鍵を利用される可能性があり、`CONF-036`で受容された残存リスクとしてBD-08の紛失対応とBD-09の試験へ引き継ぐ。App Checkまたはサーバー状態確認の障害中も検知が遅れる残存リスクは、`CONF-040`で依頼者が受容した。

## BD-05-05 ブラウザー、PWA、通信の保護

- Firebase HostingのHTTPSを使用し、HTTPからの利用を許可しない。
- 外部入力をHTMLとして連結せず、テキストとして出力する。`innerHTML`相当を原則禁止し、HTML入力要件を追加する場合だけ検証済みサニタイザーを採用する。
- CSPは`default-src 'self'`を基準に、スクリプトを自己配信かレビュー済みハッシュ・nonceへ限定し、`unsafe-inline`と`unsafe-eval`を使わない。`object-src 'none'`、`base-uri 'none'`、`frame-ancestors 'none'`、`form-action 'self'`を設定し、接続先、画像、ワーカー、マニフェストを必要最小限の送信先へ限定する。
- `Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`、不要機能を拒否する`Permissions-Policy`を設定する。カメラは自己オリジンの必要画面だけで利用する。
- HTML、環境設定、招待受信画面、認証応答はブラウザーの通常HTTPキャッシュに対して`no-store`を基本とする。完全オフライン起動に必要な汎用PWAシェルだけは、環境値、認証状態、トークン、業務データを埋め込まず、版と整合性を確認してService Workerが明示的に保存する。ハッシュ付き静的資産は長期キャッシュできるが、Service Workerは認証応答、Firestore通信、トークンURL、業務データ、秘密情報をCache Storageへ保存しない。
- 第三者解析タグ、広告、外部CDNスクリプトを本番へ入れない。必要な依存資産は版と権利を確認して自己配信する。

### 公開画面とFirestore接続開始

公開トップ、ログイン、パスワード再設定は、静的資産とFirebase Authenticationに必要な処理だけで表示する。表示時はFirestore SDKを初期化せず、読取り・書込み・リスナー開始も行わない。未認証状態では、公演一覧、利用者情報、端末情報を取得しない。

Firestore接続開始の条件は次のとおりとする。

1. Firebase Authenticationのログインを完了する。
2. メール・パスワード利用者はメール確認済みであることを確認する。
3. App Checkを初期化し、有効なトークンを取得する。
4. 最初のFirestore要求で、役割と端末承認を確認する。

### App Check方式

App Checkは、正規Webアプリ以外からの単純な要求を減らす追加防御である。Firebase AuthenticationとSecurity Rulesの代替にはしない。大規模DDoS向けの専用対策基盤としても扱わない。

| 項目 | 方針 |
|---|---|
| 対象 | WebアプリからCloud Firestoreへ送る要求 |
| 第一候補 | reCAPTCHA Enterpriseプロバイダーのスコア方式。通常利用者へ画像選択等の課題を表示しない |
| 初期化順序 | 認証とメール確認の完了後、最初のFirestore接続より前 |
| 導入 | 最初は管理された検証環境の監視モードとし、正規端末のVerified・Invalid等の判定結果を確認する |
| 強制適用 | 対象PCと対象3実機で誤拒否がないことを確認後、Cloud Firestoreを対象に有効化する。本番URLの一般利用開始前に完了する |
| 強制適用後 | 有効なApp CheckトークンがないFirestore要求を拒否する |
| トークン | 要求ごとの使い捨てにせず、有効期間内で再利用する。Firestore向けに限定使用トークンや再利用防止を採用しない |
| TTL初期案 | 公式既定値の1時間。必要以上に短くせず、SDKの自動更新による評価回数を考慮する |

App Check SDKは、有効なトークンをメモリまたはIndexedDBから再利用する。強制更新を通常操作ごとに行わない。公式仕様ではおおむねTTLの半分で自動更新されるため、管理者の操作回数とreCAPTCHA評価回数を一致させない。

### 評価枠と異常時

2026-09-20時点の公式条件では、請求先を設定しないreCAPTCHAの無償枠は組織全体で暦月10,000評価である。上限超過後の新しい評価は`RESOURCE_EXHAUSTED`等で失敗する。提供条件は変動するため、実装時とリリース前に再確認する。

- 課金設定、自動課金、有料プランへの自動移行を行わない。
- App Checkトークンの発行・更新数と、月間評価数を監視する。
- 上限接近、評価失敗、Invalid増加をBD-08の異常確認対象とする。
- App CheckまたはFirestoreを利用できない時も、準備済み端末は受付記録を暗号化して端末内へ保持する。

無料条件で要件を満たせない場合は、強制適用を無断で解除しない。新しい業務要求を安全に停止し、BD-08の復旧・紙切替へ進む。方式変更または有料化が必要なら、ADRと承認へ戻す。

### オフライン継続とオンライン復旧

次の方針は、`CONF-040`で依頼者承認済みである。`CONF-036`で承認された完全オフライン時の残存リスクを、App Checkまたはサーバー状態確認の一時的な障害中にも適用する。

| 判定 | 端末の扱い |
|---|---|
| オフライン継続条件 | 対象公演の準備が完了し、端末内で確認できるオフライン許可が有効であること |
| 一時的な失敗 | 通信不能、App Checkサービス利用不能、または一時的なトークン更新失敗だけを理由に新規受付を停止しない。オンライン処理へ移らず、受付記録を暗号化して端末内へ保存する |
| オンライン復旧成立 | 有効なApp Checkトークンを取得し、サーバーで端末状態、公演状態、役割、許可期限を確認できた時点とする。両方が成功するまで通常同期、データ取得、再準備を開始しない |
| 受付ロック | 明示的な不正判定、端末停止、役割失効、または許可期限切れを確認した場合は新規受付を直ちに禁止する。端末内で許可期限切れを判定できる場合も、サーバーへ接続できなくてもロックする |
| 判定不能の継続 | サーバー状態が未確認の間は、最後に確認した有効状態を新たなオンライン確認結果として扱わない。オフライン継続条件の範囲だけで受付し、未送信件数を保持する |

App Check取得だけが成功してもオンライン復旧とはみなさない。サーバー状態確認だけをApp Checkなしで迂回する経路も設けない。確認途中の要求を通常同期へ混在させず、両方の成功後に未送信記録の送信を開始する。

### 設計上の保証目標

| 対象 | 保証目標 |
|---|---|
| 公開URL・公開画面 | 開いただけではFirestoreの読取り・書込みを発生させない |
| App Checkなしの直接要求 | 強制適用後はFirestore文書の読取り・書込みを許可しない |
| 未認証要求 | 役割・端末文書をRulesで参照せず拒否する |
| 正規利用 | ログイン、メール確認、有効な役割、端末承認が揃った場合だけ業務データを読み書きする |

Firestoreへの業務要求はFirebase SDKがAuthorizationヘッダーで送る認証情報とSecurity Rulesで判定し、外部サイトから自動送信されるCookieだけで状態変更を許可しない。CORSや画面のオリジン判定だけを認可にせず、直接API要求も同じRulesで拒否する。将来Cookie認証の独自サーバーAPIを追加する場合は、許可Origin、CSRFトークン、SameSite属性を含む別の設計とADRを必須とする。

FirestoreはTLS通信と保存時暗号化を提供する。本設計ではFirestore上の全項目をクライアント側暗号化しない。全項目暗号化はRulesによる値検証と検索を妨げ、鍵管理を過度に複雑化するためである。任意項目など特に制限する情報は文書分離、役割制限、保存期限を優先し、追加のクライアント暗号化が必要な項目はBD-07の出力・検索要件と併せて個別に判断する。

## BD-05-06 入力、ファイル、出力の保護

入力は画面、ファイル、URL、QR、Firestoreの各境界で許可リスト、型、文字数、件数、範囲、列挙値を検査する。クライアント検査は早い案内のため、Rulesまたは取込確定処理の検査は改変要求を拒否するために行い、片方で代替しない。制御文字、不可視文字、過大入力、余分な列・項目、想定外の文字コード、別公演IDを拒否し、意味が変わる自動補正をしない。

Excel、CSV、PDF、画像、QRの具体的な形式、マジックバイト、展開後サイズ、数式・外部リンク、CSV式注入、PDF/ZIP一時生成物、画像再符号化はBD-07で定める。取込前のプレビューと件数・エラー表示、本番確定時の再認証、出力対象・項目・件数の確認、生成後の一時ファイル削除を引継ぐ。画面、通知、ファイル名、URL、エラーへ不要な氏名、メールアドレス、トークン、内部構造を出さない。

## BD-05-07 認証情報、秘密情報、個人情報

- パスワードの設定・照合・再設定はFirebase Authenticationへ委任し、アプリ独自に保存、暗号化、復号、一覧表示しない。
- 公演限定スタッフはFirebase AuthenticationのパスワードポリシーをRequireモードで最小6文字、最大20文字、数字必須として設定する。登録・再設定画面ではさらにASCII半角英字1文字以上を検証し、「半角英字と数字を含む6～20文字」と表示する。氏名、メールアドレスのローカル部、公演名、共有語、`123456`等の推測容易値との一致・単純な組合せを拒否し、比較対象や拒否値をログへ出さない。
- 認証用パスワードを暗号鍵の生成・暗号化・復号に使用せず、他利用者・他公演と共有・再利用しない。管理者はスタッフのパスワードを設定、閲覧、記録、再通知せず、忘れた場合は本人宛てのFirebase再設定メールと同じ入力検査を使用する。
- パスワード、生のID・更新トークン、秘密鍵、サービスアカウント、`.env`、認証済みブラウザー状態、依頼者用Firebase設定、実データファイルをGit管理しない。
- ログイン失敗時もパスワード、入力内容、メールアドレス全文をログへ残さない。アカウント存在有無を第三者へ判別させない一般化した案内を用いる。
- 連続失敗はFirebase Authentication側の保護を有効にしたうえで、画面でも同じ案内のまま段階的な再試行待ちを設ける。クライアントの待ち時間だけを防御とせず、制限が繰り返された場合は運用ログの個人情報を増やさず異常件数を確認する。
- 実在する氏名、メールアドレス、電話番号、住所、受付情報を機密度の自己判断にかかわらずGit/GitHubへ送らない。例、試験、画面見本は明確な架空データと`example.com`だけを使う。
- `.env.example`を作成する場合はキー名と架空のプレースホルダーだけを記載し、動作する資格情報や依頼者固有値を含めない。
- ブラウザー保存パスワードをアプリから削除できない前提とし、停止端末や未承認の新端末は認証成功後もRulesで拒否する。
- 認証情報そのものの漏えいが疑われる場合に限り、影響する利用者のトークン失効、利用者停止、パスワード再設定を検討する。端末紛失だけでは利用者全体や同じUIDの他端末を停止しない。

初期主担当はFirebaseプロジェクト初期設定時にGoogleアカウント本人とGoogle側の2段階認証有効化を人が確認し、Googleログインで得たFirebase UIDを対象公演へ明示的に割り当てる。最初にアクセスした利用者、メールアドレス一致だけの利用者、招待URL所持者を主担当へ自動昇格しない。Firebase IDトークンだけではGoogle側の2段階認証が毎回実行されたことを保証できないため、追加端末はGoogleプロバイダーで再認証し、既存承認端末が発行したBD-05-03の1回限りリンクによる所持確認を組み合わせる。既存のメール・パスワード利用者とGoogle資格情報をリンクする場合は、認証済みの本人が両方を再認証して同じFirebase UIDへ明示的にリンクし、メール一致だけでアカウントを自動統合しない。Firebase MFAはIdentity Platformの料金と費用0円条件を確認するまで採用しない。

`CONF-047`により代理管理者も各自のGoogleアカウントでログインする。代理管理者UIDと公演役割は主担当とは別に明示割当し、Firebaseプロジェクト所有権やメール一致から権限を自動付与しない。本人再認証、端末承認、アカウント復旧、既存メール・パスワード資格情報とのリンク失敗を、ADR-003の設計整合とBD-09の試験対象とする。ADR-003は公式条件と設計・試験割当の確認後にAcceptedとした。Firebaseの実設定と対象実機での検証は後続工程で行う。

## BD-05-08 ログ、監査、プライバシー

運用ログは時刻、環境、処理区分、結果、匿名化した相関ID、エラーコードを基本とし、業務データ本文を記録しない。監査記録は要件で必要なUID、端末ID、公演ID、操作、理由、結果、サーバー到着時刻、対象を特定できる内部IDを記録するが、パスワード、トークン、暗号鍵、招待URL、メールアドレス全文、来場者情報全文を記録しない。画面用表示名が必要な場合も正本はUIDとし、保持期間と閲覧権限を設ける。

臨時管理者の任命、追加準備、利用開始、期限切れ、役割解除は監査対象とする。操作者UID、対象者UID、公演ID、端末ID、有効期限、変更前後の役割、サーバー時刻、結果を記録する。追加準備の監査には取得本文を含めず、データ区分、件数、データ版、役割版、整合性結果だけを残す。臨時管理者には当日業務範囲の監査だけを表示し、この任命・解除監査と認証・役割管理監査は表示しない。

例外の詳細は公開コンソールへ出さず、利用者には復旧行動を伴う短い案内と問い合わせ用相関IDを示す。開発者向け詳細にも秘密情報や入力本文を含めない。外部解析サービスは初期版で使用しない。利用目的を超えた収集をせず、一般受付へ管理・個人情報を過剰配布しない。削除希望、保存期限、締め後削除はBD-02とBD-08のライフサイクルを適用する。

## BD-05-09 リポジトリ、PR、公開物のゲート

実装工程では、ローカルコミット前とPRで次を自動検査し、公開前に人が結果を確認する。ツール選定とCI導入は設計承認後の実装Issueで行う。

1. 秘密情報パターンと高エントロピー値の検査
2. `.env`、秘密鍵、サービスアカウント、認証済みブラウザー状態、実データ、未承認の生成物など禁止ファイルの検査
3. サンプル・試験データが架空で、メールドメインが`example.com`であることの検査
4. ビルド成果物、ソースマップ、ログ、スクリーンショット、エクスポートへの環境値・個人情報混入検査
5. 依存関係の既知脆弱性、ライセンス、固定版、ロックファイル差分の検査
6. Firestore Rules、入力境界、ログマスキング、権限変更を対象にした試験

PRチェックリストでは、実データ・秘密情報なし、権限・Rulesへの影響、ログとエラー表示、追加依存関係、外部送信先、保存期間、削除・復旧、架空データ、必要文書・試験を確認する。GitHubの秘密情報保護機能は利用可能な範囲で追加防御に使うが、プランや公開範囲に依存するため唯一の防止策にしない。

公開評価物は既定で依頼者環境へ接続せず、ローカルまたは評価専用環境と架空データを使う。公開リポジトリに利用許諾を付与せず、第三者向け本番利用・保証・個別サポートを示さない。README、設定例、Issue、PR、履歴、Release、添付物も検査対象に含める。

## BD-05-10 依存関係と第三者資産

依存関係または第三者資産を採用する前に、名称、版、用途、直接・推移依存、配布元、更新状況、ライセンス、再配布条件、既知脆弱性、ブラウザー送信先、費用条件を記録する。必要性が同等なら、標準API、依存が少なく保守中の一般的な製品、自己配信可能な資産を優先する。

ロックファイルを正本として予期しない版更新を防ぐ。重大・高リスクの既知脆弱性、出所不明、保守終了、権利不明、不要な外部送信、費用条件不適合があるものは採用を止める。例外が必要な場合は、影響、期限、代替、補完対策、確認者を記録し、無期限に許容しない。自動更新の採否と更新頻度は実装工程で定める。

これにより`TBD-011`は、実装開始前に候補一覧と権利・安全性の見込みを開発者が確認し、各依存追加PRで再確認し、公開前に成果物全体を再確認する三段階のゲートとして具体化する。`TBD-012`に関係する新規外部サービス、有料機能、支払方法登録はADRと明示承認なしに追加しない。

## BD-05-11 インシデント対応

| 事象 | 初動 | 復旧・記録 |
|---|---|---|
| 端末紛失 | 対象端末IDだけを停止し、他端末・アカウントは維持 | 復旧時は隔離送信、確認後に停止解除または別操作で廃止。BD-04、BD-08に従う |
| 認証情報漏えい | 影響利用者を特定し、必要なトークン失効・パスワード再設定・利用者停止 | 影響端末・公演・監査を確認。端末紛失と区別する |
| Git/GitHubへの秘密情報送信 | 先に資格情報を失効・再発行し、公開範囲を確認 | ファイル削除だけで済ませず、履歴、PR、Release、キャッシュ、cloneへの対応を記録する |

| XSS・依存関係問題 | 該当機能・配信を停止し、秘密・データへの影響を評価 | 修正版、鍵・トークン対応、公開物再検査、原因と予防策を記録する |

証拠保全を理由にパスワードや秘密鍵をコピーしない。削除・履歴改変など元に戻しにくい対応は対象と影響を確認し、資格情報の失効を先行する。具体的な連絡網、担当、復旧確認、訓練はBD-08で定める。

### 残存リスク

- 完全オフライン端末へ停止を即時反映できず、次回起動・接続まで物理削除もできない。
- 臨時管理者の期限前解除も完全オフライン端末へ即時反映できない。復旧まで保存済み役割版の権限が残る可能性がある。
- 完全オフラインの紛失端末では、停止検知まで保存済みCryptoKeyを正規PWAから利用され、不正受付や保存データ閲覧が行われる可能性を`CONF-036`により受容する。
- App Checkまたはサーバー状態確認の障害中は、端末停止や役割失効の検知が遅れる。最後に確認した許可が有効な端末では、その間に新規受付が保存される可能性があり、`CONF-040`で依頼者が残存リスクを受容した。
- 復号中のXSS、ブラウザー・OS侵害、画面撮影、利用者自身の持出しを端末暗号化だけでは防げない。
- 非抽出CryptoKeyは同一オリジンのスクリプトから暗号処理に利用できるため、XSSや端末・ブラウザー侵害時の不正復号を防ぐ境界にはならない。
- ブラウザーのストレージ消去、CryptoKey欠損、端末廃止時の物理的完全性をアプリだけでは証明できず、鍵欠損時に未同期暗号文を復旧できない。
- App Checkは不正クライアントを完全には排除せず、提供条件と無料枠も変更され得る。
- 実ブラウザーまたは高度なBotが正規Webアプリを実行した場合、reCAPTCHA評価回数の消費を完全には防げない。
- Firebase Authenticationへの不正ログイン試行と、Firebase Hostingの静的配信量は、このFirestore保護だけでは防げない。
- App Checkは大規模DDoSを完全には防止せず、専用のDDoS対策基盤は初期設計へ導入しない。
- クライアントだけで招待・端末関連付けの一回性を安全に実現できない場合、管理者確認またはサーバー処理の再設計が必要になる。

### 確認事項

**依頼者に確認してください**

- なし。信頼済み端末のオフライン継続と、サービス障害中に停止等の検知が遅れる残存リスクは、`CONF-040`で依頼者承認済みである。

**開発者が確認してください**

- 本設計が承認済み要件、BD-01～BD-04、ADR-001・ADR-002と矛盾せず、費用0円の前提で実装可能な境界になっていること。
- 実装開始前に第三者資産・依存関係の候補一覧、ライセンス、脆弱性、外部送信、費用条件を確認し、`TBD-011`のゲートを完了すること。
- App Check、MFA、Functions等の採用候補は、実装時点の公式条件と対象実機を再確認し、有料契約や方式変更を無断で行わないこと。
- App Check強制適用前に、正規端末の監視結果と誤拒否時の復旧手順が揃っていること。
