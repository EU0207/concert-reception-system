## 結論

以下は`CONF-049`を受領する前に依頼者へ提示した確認事項である。回答と残る判断は[依頼者回答記録](basic-design-remediation-client-response.md)で管理する。元の質問は回答の経緯として保持する。

## 確認・承認先

**依頼者に確認してください**

- **C-02 詳細履歴の削除時期：** 誰もシステムを起動しない期間にも、公演終了後1か月で詳細履歴を削除する必要があるか。静的PWAは無操作中に削除を実行できず、Firestore TTLには請求有効化が必要なためです。推奨は、現行要件を維持する実行方式と費用を開発者が先に提示し、その後に方式を判断することです。次回オンライン管理時の削除を選ぶ場合は、REQ-F-025とAC-013の変更承認が必要です。
- **C-04 未受領記録の保全：** サーバーが全件を受領する前に、記録を失ってでも端末データとCryptoKeyを削除する業務上の必要があるか。唯一の受付記録が復元不能になるためです。推奨は現行のREQ-NF-015・AC-028どおり受領前削除を禁止することです。
- **M-06 バックアップの範囲：** どの時点まで復旧できればよいか。また、バックアップ各世代をいつまで保管するか。必要な取得時点、世代数、削除済み個人情報を含む旧世代の破棄時期を決めるためです。推奨は公演前確定後と締め後を必須取得時点として検討することです。
- **M-03 通信断時の座席・QR対応：** 管理端末が通信できない時の座席変更とQR再発行を、当該チケットの紙の例外記録で扱い、回線復旧後にシステムへ確定する運用でよいか。複数端末で現在席と有効QRを一意に保つためです。推奨はオンラインでだけ確定することです。
- **Q-01 購入済みの意味：** 未入金のまま事前にチケットを発行または交付する運用があるか。現行の「購入済み」が入金確認を表す場合、当日現金受領まで状態を正しく表せないためです。該当するなら支払状況とチケット準備状態を分けることを推奨します。決済機能の追加は提案していません。

**開発者が確認してください**

- C-01の端末単位認可方式とC-03の会場画像保存方式の限定技術検証を行い、費用と運用影響を依頼者へ提示してください。
- 依頼者回答を開発者の判断で代理しないでください。要件・受入条件を変更する場合は、変更対象の文書と承認対象コミットを示してください。
- 指摘11件の変更文書、試験条件、未解決事項、PRとProject状態を照合してから一式再レビューを実施してください。

## 回答の記録方法

指摘IDごとに「回答日、回答者、回答内容、変更する要件・受入条件、記録先」を残す。開発者が「依頼者の回答」と明示して伝えた内容だけを正式な回答として扱う。回答がない項目は未決定と記載し、推奨案で埋めない。

## 再レビューの判定

- C-01～C-03は方式の成立性、費用条件、限定技術検証を確認する。C-04は全件受領前の削除経路が残らないことを確認する。
- M-01～M-06はデータの正本、権限、画面、競合、復旧が同じ条件を示すことを確認する。
- Q-01と上記の依頼者回答を設計へ反映し、必要な要件・受入条件の変更承認を確認する。
- 技術検証の成功を、実装後の受入条件の合格として扱わない。基本設計再レビュー後もUIモック工程を省略しない。

## 承認に含まれないもの

本書の作成だけでは、要件変更、設計の再承認、外部サービスの契約、課金、本番アプリケーションの実装を承認しない。
