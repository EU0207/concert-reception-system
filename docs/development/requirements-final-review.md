## 最終レビュー結論

Issue #6の調査、POC-001～POC-005、RES-005、追加確認CONF-025～CONF-030の結果は、要件定義書、受入条件書、トレーサビリティ表、本番向け引継ぎ事項へ追跡可能な形で反映されている。

要件定義書は業務・機能・非機能要件、制約、対象外を定め、受入条件書は33件すべてについて確認方法と期待結果を定めている。PoCの合格は本番受入の完了と混同せず、限定した技術証跡として分離した。

要件承認前の業務確認事項はCONF-027～CONF-030まで反映済みである。依頼者が次の事項を一括して明示承認した場合、要件定義工程を完了できる。

1. 要件定義書と受入条件書の内容。
2. 本書に示す未決定事項の区分と後続工程への引継ぎ。
3. 本書に示す残るリスクを、設計・試験・運用で管理すること。
4. 承認に含まれない作業は、別の判断ゲートまで開始しないこと。

## 残るリスク

| リスク | 影響 | 現在の扱い | 次の確認ゲート |
|---|---|---|---|
| オフライン中は端末間の重複受付を即時防止できない | 二重受付や判断遅れ | 復旧後に競合を消さず管理者へ表示 | AC-011、AC-015、AC-029 |
| 回収不能端末だけの未送信記録は復元できない | 受付記録の一部欠落 | 残り端末で継続し、紙の当日運営表と照合 | AC-015、AC-021 |
| QR読取りの2秒目標は指定3実機で未達 | 受付速度低下 | 10秒上限は達成。印刷品質、焦点案内、QR生成を改善 | AC-004、AC-018、AC-022 |
| 500件の自動処理合格は500人を30分で受付できる保証ではない | 混雑 | 人、画面、カメラ、会場回線を含む運用確認を行う | AC-018 |
| 接続・起動されないWeb端末を遠隔で物理消去できない | 端末内データ残存 | 暗号化、鍵の非保存、権限停止、未確認表示、回収・手動削除 | AC-028、AC-030 |
| 任意項目の期限後削除は管理者操作を要する | 期限切れ暗号文の残存 | 閲覧を拒否し、管理画面で削除を継続案内 | AC-023 |
| 無料枠・料金・提供条件は変更され得る | 費用0円要件の不適合、方式変更 | 採用前と各開催前に公式条件を確認し、有料化せず不適合を報告 | AC-020 |
| PoCは本番セキュリティ全体を保証しない | 不正アクセス、情報漏えい、復旧不能 | セキュリティ設計、直接API試験、静的解析、秘密情報検査、復旧訓練を実施 | AC-030、AC-031 |
| POC-005後に追加した本番UI/UXは未実装・未試験 | 操作性不適合 | 実装前の操作見本と対象3実機の小単位レビュー | AC-025、AC-032 |
| 外部サービスと本番方式は未採用 | 設計・日程の不確実性 | 要件承認後に候補比較し、ADRと別承認で決定 | TBD-002～TBD-004、TBD-012 |
| 公開配布物の設定誤り | 第三者データの混在、依頼者環境への誤接続 | 既存環境への既定接続を禁止し、未設定時は安全に停止し、2環境間の分離を試験 | AC-033 |
| 公開ライセンスと免責が未決定 | 第三者が利用できる範囲や責任が不明確 | 実装・配布前にTBD-011を決定し、ライセンスと手順書へ記載 | TBD-011、AC-033 |

残るリスクは隠れた例外ではなく、承認済み要件を満たすために後続工程で管理する事項である。受入条件を満たせないことが判明した場合は、費用や仕様を無断で変更せず、不適合、選択肢、影響を依頼者へ提示する。

## 承認対象

今回の明示承認対象は、PR #24の承認時点の最新コミットに含まれる次の内容とする。

1. [要件定義書](../client/requirements.md)に記載した要件、制約、対象外、未決定事項の区分と決定ゲート。
2. [受入条件書](../client/acceptance-criteria.md)に記載した33件の確認方法と期待結果。
3. 本書の「2026-09-09に確認した方針」と「残るリスク」の受容・引継ぎ方針。
4. [トレーサビリティ表](traceability-matrix.md)と本番向け引継ぎ文書を、上記2文書の補足・追跡情報として使用すること。

## 承認に含まれないもの

- PR #24のmainへの統合。承認記録を反映して再確認した後に別操作として行う。
- Firebase、Cloudflareその他の技術・外部サービスの採用、契約、設定変更、本番資源作成。
- 基本設計、詳細設計、画面設計、セキュリティ設計の開始または承認。
- 本番アプリケーションコードの実装、依存関係の追加、CI/CD、デプロイ。
- 受入条件への合格判定。現在は33件すべて未実施であり、本番相当構成で将来判定する。

## 明示承認後の記録手順

1. Issue #23に承認日、承認対象コミット、承認範囲を記録する。
2. 要件定義書、受入条件書、本書の状態を`Approved`へ更新し、承認情報を記載する。
3. 文書だけの更新をPR #24へ追加し、差分とリンク・ID検査を再実施する。
4. 依頼者のmain統合指示または統合承認を確認してからPR #24を統合する。
5. 要件確定後の次工程は別Issueと別の承認ゲートで扱う。

明示承認前は上記の記録更新、main統合、設計、本番実装、外部サービス変更を開始しない。
