## 何が公開されるか

Gitの `commit` はローカルの履歴へ記録する操作であり、それだけでGitHubへ送信されるわけではない。Publicリポジトリへ `push` すると、作業ブランチの内容も公開対象になる。mainへ統合する前やDraft PRであっても、秘密情報の保管場所にはできない。

GitHub Flowは継続する。Issue単位でブランチを作り、変更確認・検査を済ませてpushし、PRレビュー後にmainへ統合する。

## 変更を始める前

- 架空データを使う。来場者の実名・連絡先と受付情報を、コードや試験素材へ持ち込まない。
- 認証情報と環境固有の設定はGit管理外へ置く。`.gitignore` は既に追跡中のファイルを取り除く機能ではなく、強制追加も防がない。
- コミットメールがGitHubの匿名用アドレスであることを確認する。2026-11-18のローカル設定は匿名形式だったが、別PC・別worktreeでも確認する。

## コミット前

1. `git status --short` と `git diff --cached --name-status` で、追加するファイルを確認する。必要なパスを指定してステージし、未追跡ファイルも確認する。
2. ローカルで差分を読み、秘密値・実データと個人目的の記載がないことを確認する。画像は実物を開き、画面やメタデータの混入も確認する。値を実行ログへ転記しない。
3. 対象変更に必要な型検査・試験を実行する。依存を変えた場合は固定版と既知脆弱性を確認し、第三者資産のライセンス表示も照合する。
4. `git diff --cached --check` を実行し、Issueに対応するコミットを作る。

## push前

ローカルに用意した公式Gitleaksで、送信するコミットの範囲を検査する。今回の監査は8.30.1を使用した。監査ツールをアプリの依存へ追加する必要はない。

[公式Release](https://github.com/gitleaks/gitleaks/releases)から実行ファイルを取得する場合は、同じ版のチェックサムと照合する。以下の `gitleaks` は、必要に応じて実行ファイルへのパスに読み替える。

```sh
git fetch origin
gitleaks git . --log-opts="origin/main..HEAD" --redact=100 --ignore-gitleaks-allow
```

- 検出や検査エラーがあれば、送信前に原因を確認する。未実行の状態を検査済みとはしない。
- チェックサムのような誤検出は、元データと生成処理を照合して根拠を残す。`artifacts/` 全体や汎用キー検査全体を除外して通さない。
- すべての送信コミットを確認する。最新の差分から消しただけでは、途中のコミットに秘密が残ることがある。

私的情報や実利用者の情報は、秘密情報検査だけでは判別できない。差分を読む確認と併用する。

## GitHubで確認する保護

Publicリポジトリでは[Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)が無料で動作する。公開前のローカル検査を続け、公開後にはSecurity設定と検出結果を再取得する。

[Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)の有効状態も確認する。ユーザー単位では既定で有効だが、このアカウントの実設定確認とリポジトリ側の確認は別に行う。無料で利用できる範囲を優先し、有料契約やカード登録へ進まない。

対応する秘密情報パターンへの追加防御であり、氏名・電話番号や、すべての独自パスワードを防ぐ保証にはならない。ブロックされた要求を理由未確認のまま回避しない。

## PR・CI・配信

- PRには確認結果と文書への影響を記載する。本文とコメントにも秘密情報・実データを貼り付けない。
- CIはpush後に動くため、公開前の検査の代わりにはならない。最小CIの導入は既存のIssue #259で扱い、今回の文書だけでフックや新しいCIを導入しない。
- GitHub Pagesは静的モックだけを配信する。コード公開を理由に、依頼者用Firebaseへ接続したりRulesを緩めたりしない。

## 誤って公開した場合

秘密値を検出したら、最初に対象サービスの資格を失効・更新し、影響を確認する。ファイルを消すだけでは、既存コミットや取得済みコピーからの参照を解消できない。

履歴書換え・強制pushと公開停止は、対象・影響を確認して実施する。事故の詳細や秘密値を公開Issueへ書かず、公開する変更記録は対処の目的と事実に限定する。
