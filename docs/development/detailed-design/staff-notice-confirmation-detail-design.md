## DD-90-01 範囲と表示

作るものは、同じ公演の全スタッフ向けテキスト連絡と、本人ごとの未読・重要確認の保存契約である。重大操作の共通UIも定めるが、締め・削除等の権限や成立条件は各業務へ委ねる。連絡を管理者向けのスタッフ既読管理や来場者への送信機能へ広げない。

投稿・訂正・取消しは主担当・代理管理者と有効な臨時管理者に許可し、一般受付は閲覧・自分の読了と重要確認だけを行う。投稿者本人であることを管理権限の代用にせず、訂正時も現在認可を確認する。タイトルは50文字以内、本文は500文字以内のテキストとし、空白だけは拒否する。訂正・取消しには空白だけでない理由を200文字以内で入力する技術案とする。来場者固有の情報を入力しない案内を置き、HTMLとして実行しない。

### 一覧・ベルと読了

未確認の重要連絡を先頭へ固定し、残りは重要・通常を問わず新しい順に表示する。固定対象内も同じ順序とする。新しい順は共有時の順序番号で決め、端末時計や受信順を使わない。同順位はnoticeIdで安定化する。訂正は新しい内容版として並びを更新する。

各行の左端に未読マークを置き、読み上げ名に「未読／既読」「重要・確認が必要／確認済み」を含める。本文を開いた後の「読了して閉じる」で、その内容版を読了にする。一覧・ベルを開いただけでは全件既読にしない。重要連絡には別の「内容を確認しました」を置き、本人が押した場合に読了と重要確認を同じ操作で保存する。通常連絡に重要確認を作らない。

ベルの件数は本人の未読の現行連絡数であり、重要未確認の件数と混ぜない。0件はバッジなし、1～9件は数値、10件以上は`9+`。読み上げには実数を使う。重要連絡を読了しても明示確認までは固定を続ける。確認済みの重要連絡は通常の時系列へ戻す。取消済み連絡は新着件数・重要固定から外し、取得済み一覧では取消しを明示して原文と理由へ進める。

BD-06の公演準備ホーム・担当公演ホームからもD-06へ進める。カメラ上のベルを開いている間は読取りを止める。閉じる時は#89・92の結果未確認状態を優先し、未確認の受付結果を閉じて読取りを再開しない。D-06へ遷移する場合はカメラとライトを停止する。

## DD-90-02 保存単位と現在認可

公演ルートは[正式RTDB契約](rtdb-storage-contract.md#名前空間形式版索引)と同じ。追加領域`notice`の形式版は1とし、席・券やcustomerの形式版を変更しない。以下は製品の追加契約案であり、既存PoCのRulesが保証した領域ではない。

| 領域 | 正本と検査 |
|---|---|
| `notice/events/{noticeId}/{eventId}` | 投稿・訂正・取消しと競合解決の不変イベント。元イベント・基準内容版、本文・理由、本人・端末と観測時刻・共有順序を保持。訂正で原文を上書きしない |
| `notice/heads/{noticeId}` | 現行の内容版ID・通常／重要・取消しと競合状態。イベントから導出する表示用投影で、直接の無条件編集を許可しない |
| `notice/head` | 領域revisionと共有順序の次番号。イベント受領・対象投影と操作結果を一体更新し、取得前後の同一版を照合する |
| `notice/userStates/{personUid}/{noticeId}/{contentVersion}` | 内容版ごとの本人の読了・重要確認。別版へ複写せず、同じ版のfalseへの巻戻しを許可しない。本人の有効端末間で共有する |
| `notice/userOperations/{personUid}/{operationId}` | 自分の投稿・訂正等と読了・確認の不変結果。対象版・本人と端末を固定し、応答不明時に照会する。権限を操作種別別に検査する |

投稿・訂正と取消しは#234が追加保存処理を担当し、#110の本人・端末・セッション結合を使う。読了・確認も本人UIDをパスの自己申告から信用せず、結合済み本人と一致する場合だけ許可する。通常の連絡取得では管理者にも他人の状態取得・変更を許可せず、`userStates`親からの一括読取りを禁止する。管理用の既読一覧・集計・既読確認依頼は追加しない。

連絡本文・原文と履歴は有効な公演所属のスタッフが必要範囲を取得できる。来場者管理の権限を連絡領域へ広げず、購入者名や任意項目を投影へ混ぜない。端末停止・役割失効と期限切れ、別公演の直接要求を拒否する。#98の未承認カスタマイズを先取りしない。

取得済み本文と本人状態は公演・本人を分けて暗号化IndexedDBへ保存する。本人切替時に前の本人の既読を使わず、既存の鍵・復号制限へ従う。連絡の現行一覧は32件以下のキー順ページとし、取得前後のnotice/headを照合する。並び替えは取得済みの同一版で行い、一覧未取得部分があれば「件数確認中」と表示し、0件や部分件数を全体確定値と表示しない。変更のない画面往復で全履歴を再取得しない。

## DD-90-03 訂正・取消しと同期

1. 投稿・編集案を確認し、eventId・operationIdと元内容版を固定する。本文・イベントと送信キューを端末内で一体保存できた後にだけ「未共有」を表示する。端末保存失敗なら投稿成功を表示しない。
2. 復旧時はApp Checkと現在の本人・端末認可、公演状態を先に確認する。許可された経路から同じIDで送信し、受領結果と投影を照合する。通信の再試行で別イベントを作らない。
3. 独立した連絡の投稿は両方を受領する。同じ内容版からの矛盾する訂正・取消しは両候補を保持し、到着順で片方を採用しない。BD-03の競合確認イベントで候補と理由を固定して解決する。

競合中は最後の非競合の本文を「訂正・取消しの照合待ち」と共に表示し、候補を現在の確定本文と混同しない。重要確認の新規確定は解決まで止める。解決では対象候補集合の版を照合し、確認後に候補が増えていれば再確認する。後着候補を消して成功としない。

本文・タイトル・優先度の変更は新しい内容版とする。以前の読了・重要確認は元版の記録として保持するが、新版の既読・確認済みに流用しない。重要へ変更した場合も新版への本人確認が必要。取消しは履歴であり、投稿・原文や既存の確認記録を物理削除しない。

本人の別端末の既読は同じ版に限り合流する。同じ版の読了・確認は一方向なので、古い未読状態の同期で取り消さない。旧版をオフラインで読了・確認していた場合、その版の事実を保持し、現在の新版の未読・未確認は残す。知らない内容版への確認と通常連絡への重要確認は拒否する。

| 状態 | 表示・処理 |
|---|---|
| オフラインで投稿・読了・確認 | 取得済み内容を使用し、本人の端末保存分と共有受領済みを区別。未共有投稿は他端末へ届いたと表示しない |
| 連絡の新着0件・未読0件 | 取得時点と未更新を表示。オフラインの0件を新着なしの保証にしない。緊急連絡は口頭・紙へ切り替える |
| 応答喪失・再起動 | 同じ操作IDと送信内容を復元して結果照会。読取り拒否を未送信と誤認せず、二重投稿・二重確認を防ぐ |
| 復旧時の失効・停止 | 未受領記録を消去せず通常共有を止める。既存の隔離・管理者照合の契約へ渡し、失効前の観測時刻だけで通常投稿を許可しない |
| 公演終了後 | 既存の確認・同期専用期間を維持し、新規投稿や内容編集を再開しない。期限後は公演後管理の権限へ従う |

未共有の投稿・訂正・取消しと未解決競合は、#111の全登録端末の締め照合へ含める。同じ締めIDで固定した送信境界を使い、受付キューだけが0件で連絡の未受領を隠して締めない。締め後に許可された本人の読了・確認同期は既存の確認専用経路とし、締め済み実績や投稿本文を変更する経路にしない。

連絡原文・本人状態と未受領記録を、経過時間や取消しだけで削除しない。保存期間は詳細履歴と同じで、利用者の明示削除まで保持する。連絡領域も#221の正式バックアップ目録と削除証跡の照合へ含め、削除した本文・確認記録を古い世代から復活させない。復元した旧本人IDの確認を新しい本人へ付け替えず、本人・端末の利用許可は復元先で再承認する。

本人状態のバックアップ取得だけは#221の限定された例外とする。主担当・15分以内の再認証、対象公演の保守状態と有効なバックアップ実行IDをサーバーで照合する。代理・臨時管理者や単なる「バックアップ用」という要求値では他人の状態を読めない。取得結果は暗号化バックアップへ渡し、通常の既読一覧へ転用しない。#221・110でこの例外と通常取得の拒否を同じRulesで確認する。

## DD-90-04 重大操作の一覧と共通UI

以下はCONF-056の回復不能という基準を、承認済み操作へ対応付けた一覧である。高影響の再認証と、回復不能操作の独立2回確認は別条件。2回確認の完了を認可情報として信用しない。

| 操作 | 2回確認・示す影響 | 業務側の検査・担当 |
|---|---|---|
| 通常締め・例外締め | 必須。公演・締め種別と、受付再開不可。例外では未確認範囲・理由と損失可能性も表示 | #111・110。全登録端末の受領・隔離、例外時の停止と紙照合。全件受領済みと偽らない |
| 詳細履歴・個人情報等の物理的な完全削除 | 必須。環境・公演、データ種別と件数、復活不可。確定実績等の保持部分と区別 | #239・110。保持条件・対象参照と削除証跡を照合し、他人の本文や別公演を削除しない |
| 端末廃止・対象公演の端末内データと鍵の削除 | 必須。廃止と物理削除の実行時点を区別し、対象端末と復号不可を表示 | #110。全件受領、未解決案・応答不明、代替管理端末を検査。遠隔端末を削除済みと表示しない |
| 発行済みQRの無効化・紛失再発行、発券済み不参加 | 必須。対象券と旧QRが復帰・取消しでは再有効にならないことを表示 | #107・112・110。全稼働端末の停止・更新と、席解放・資格の一体確定 |
| 確認用項目の削除 | 必須。項目・対象範囲、復元UIがないことを表示。過去値・履歴を物理削除する操作と区別 | #230・110。固定3項目の拒否、定義版・scopeとactive=false。既存DD-93の確認を独立2回へ具体化 |

完全削除のUIは#234、手動削除・証跡生成の業務側は#239が担当する。#221はバックアップ・復旧の照合担当であり、それだけで通常の削除機能を実装済みとしない。#239はTodoで、対象別の物理計画とRulesの承認が不足する範囲には着手しない。

復活可能な通常取消し・訂正、席移動・交換、通常のチェック解除には2回確認を一律適用しない。受付開始・停止、端末の一時停止、役割変更等も回復不能という理由だけで対象へ追加しない。各業務の通常確認・再認証と権限制約は維持する。

### 独立した2回の確認

1. 「重大操作」の文字・警告アイコンと警告色を併用し、対象と具体的な回復不能の影響を表示する。「中止／次へ」を置き、まだ業務要求を送らない。
2. 別の確認画面で同じ対象と最終操作名を再表示する。「中止／○○を実行」を置く。最初のクリック・Enter・連続タップを第2画面へ持ち越さず、フォーカスを中止側へ置く。色だけに頼らず読み上げ名を付ける。
3. 実行時に現在認可と対象版、未受領等の成立条件を再検査する。対象・版・締め種別と影響範囲が変われば両確認を無効にし、入力を保持して最初から確認する。失敗・中止で業務状態を進めない。

確認状態は対象公演・操作種別、対象IDと期待版に結び付く画面内状態であり、他操作・別端末へ流用しない。再起動で確認済みとはせず、送信前の案なら最初から確認する。送信後の応答不明は操作IDの照会を優先し、再び実行ボタンを押して別要求を作らない。
