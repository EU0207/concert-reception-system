## 簡易な操作履歴（CONF-283-C）

選択中の公演の「その他」から「操作履歴」を開く。後日の不正操作調査に必要な重要な確定操作を、日時の新しい順に一覧で確認する。

| 表示項目 | 内容 |
|---|---|
| 日時 | サーバーで確定した時刻。端末時刻だけで確定順を決めない |
| 操作内容 | 初回席確定、席構成の変更など、記録対象の操作名 |
| 対象 | 公演内の区画や席を識別できる簡潔な表示 |
| 実行者 | 確定操作の認証済み実行者。調査用に照合できること |
| 理由 | 入力された操作理由。理由不要の操作は「―」と表示する |

- 初回の席確定と理由が必要な再確定・当日の業務反映、既存設計で記録対象となる重要操作を扱う。下書き編集・保存と表示・選択のたびに記録を追加しない。
- 確定操作1件は操作IDに対応する1件として表示する。複数席の変更をセル操作ごとのログへ分解しない。応答不明の再送でも重複させない。
- 既存の安全性・復旧のために必要な記録は維持する。簡易一覧と技術的な診断ログを混在させず、氏名・連絡先・QRや秘密情報を自動で複写しない。

## 保存・閲覧の技術追補

この節はIn Review。確定保存と一覧の実装前に取得契約を承認する。

- 理由は確定要求の変更一式と操作IDへ結び付ける。共有先は現在認可と期待版を検査し、変更内容・日時・実行者と理由を同じ確定境界で保存する。履歴を後から書いて成功扱いにしない。
- 理由判定に使う確定済み状態、公演日と初回本番受付開始は保存側が取得する。クライアントの「下書き」申告で、確定要求の理由検査や割当保護を回避させない。
- 一覧は既存の確定操作・監査から必要項目を取得する。公演単位の閲覧権限を現在認可で確認し、一般受付へ管理履歴を配布しない。主担当・代理管理者の管理範囲を基準に、取得契約で閲覧対象を確定する。
- 履歴全体を一括取得せず、件数を制限した取得方法を設計する。読込み失敗を「履歴なし」と表示せず、旧履歴・別公演の混同を防ぐ。保持・削除とバックアップは既存契約に従う。

## 今回の実装と後続

PR #281では、製品開発版の個別編集から理由欄を除き、下書き計算で省略を許可する。段階を指定しない既存の計算呼出しは理由必須を維持する。理由付きの旧下書きの読込みと形式降格拒否を維持し、業務ログとしては表示しない。

実際の確定時の強制は#104-B・#111、簡易一覧は#284で接続する。現在の製品開発版の共有・確定は試験操作であり、操作履歴一覧も未実装。担当Issueの登録だけを開始条件の充足とせず、技術設計承認と依存基盤の完了後に実装する。
