## DD-92-01 保存単位と不変条件

2026-10-20、開発者がPR #242の先頭`b1feded133426b21d7617e321ac14168a03b997f`をレビュー承認し、mainへ統合した（`1df62f334321f61c80b40548dabb7ada06a900d9`）。DD-92とADR-010の案Aが対象であり、14ケースの製品実行は未実施。

成功表示と共有送信は、端末内の保存トランザクションの完了後だけ許可する。個別書込みの成功通知を保存完了としない。再起動後は保存正本から復帰し、カメラや画面メモリーの状態を正本にしない。

IndexedDBの追加形式は`receptionSchemaVersion=1`。環境・公演と登録端末でキーを分け、以下を同じDBのトランザクション対象にする。業務本文は公演・端末専用の既存AES-GCM鍵で暗号化し、識別・同期用の最小メタデータと分ける。

| ストア・キー | 内容と不変条件 |
|---|---|
| `receptionHeads`／環境・公演・端末 | 形式版、登録時のstorageEpoch、revision、次の端末連番と未確認resultId。現在のownerEpoch・ownerTabIdも保持する |
| `receptionEvents`／eventId | UUID v4、環境・公演、端末と本人、連番・観測時刻と公演状態版を含む不変イベントの暗号文。業務内容を再送で変更しない |
| `receptionOutbox`／eventId | 未送信・送信中・再試行・確認済み・拒否、試行情報と受領結果。同じeventIdでイベントを参照し、別の内容へ差し替えない |
| `receptionResults`／resultId | 結果の暗号文、eventIdがある場合の参照と本人確認済みフラグ。表示に必要な最小情報を保持。QR生データ・購入者名を保存しない |

eventId・resultIdは送信前に固定する。無効QR等の業務イベントを作らない結果にもresultIdを付けるが、端末連番・送信キューを架空に作らない。業務イベントがある場合は、イベントとキュー、連番更新と未確認結果を全部保存するか、全部保存しないかのどちらかにする。

連番・revisionとownerEpochは安全に比較できる非負整数で管理し、上限超過・不正値では保存を止める。0への巻戻しを復旧手段にしない。ローカルのメタデータも無条件に信用せず、復号した本文のID・連番と参照を照合する。

現在席・来場状態の端末表示は既存イベント集合と受付イベントから導出する。保存前に仮成功を正本へ加算せず、再表示で別イベントを作らない。導出・復号に失敗した場合は記録を残して読取りを止める。

## DD-92-02 暗号化と確定の処理順

1. 所有タブが現在認可とオフライン許可、未確認結果なしを検査する。headの版・次連番を取得し、対象資格と表示結果を固定する。
2. eventId・resultIdと暗号化に必要な乱数を生成し、既存鍵でイベントと結果を暗号化する。追加認証情報は作らず、非抽出鍵を送信しない。環境・公演・端末と形式版、レコード種別・IDを認証付き追加データへ結び付ける。
3. 必要な全ストアのreadwriteトランザクションを開く。headの期待revision・次連番とownerEpochを再検査し、IDの未使用と参照の一致を検査する。異なれば全体を中止する。
4. 暗号文・キューと結果を保存し、headの連番・未確認参照とrevisionを更新する。暗号化・ネットワークやタイマーの待機をこのトランザクションへ持ち込まない。
5. トランザクションのcomplete後にだけ、同じ結果を画面へ渡してキュー送信を許可する。abort・容量不足なら成功表示・送信を行わず、保存状態を照合する。

受付保存では`durability: strict`を要求し、実際の応答・例外と対象実機の中断結果を記録する。これは耐久性の指定であり、記憶媒体故障や利用者による消去の復旧保証ではない。利用できない場合を同等合格に読み替えず、#233の対象環境判定へ戻す。端末の省容量対策として未受領記録を自動削除しない。

暗号化後に版・所有権が変わった案は破棄して復帰確認からやり直す。確定成否が不明な場合は、先に同じIDのイベント・結果とheadを照合する。別IDを発行して読み直したことにせず、曖昧な部分状態を補完書込みして成功へ変えない。

### 「次へ」と結果確認

resultIdと所有権を固定し、同じ結果の確認済みフラグ・headの未確認参照解除とrevisionを1トランザクションで保存する。参照先が別結果なら解除しない。イベント・未受領キューは削除せず、サーバー受領と本人の結果確認を別の状態にする。

completeの応答後に、#89の終了表示・500ms待機へ進む。応答不明では同じresultIdを照会し、未確認なら同じ結果を再表示する。確認済みでも新しい未確認結果があるならそちらを優先する。新規送信イベントは作らない。

## DD-92-03 複数タブの所有権

同じ保存領域を使う環境・公演・端末について、Web Locksの同じ名前のexclusiveロックを取得した1タブを所有タブとする。ロック名は識別子から一意に組み立て、氏名や資格を含めない。他のタブは閲覧に留め、「別のタブで受付中」と表示してカメラ読取り・書込みとキュー送信を始めない。

所有タブは取得後、既存headの形式と登録時storageEpochを照合してからownerEpochを進め、タブごとの不透明IDと共に保存する。head欠落を所有権取得時に初期化しない。全てのイベント保存・結果確認、同期状態変更で同じownerEpochを検査する。遅れて戻った旧タブの処理は新しいheadへ書けない。ロックの保持を表すPromiseは所有期間全体が終わるまで完了させない。

所有権は受付画面だけのものではなく、同じ公演・端末の共通保存処理に適用する。#104の他の業務保存と、#233のキュー送信もこの所有タブを通す。別Worker・Service Workerから独立に同じキューを書き換えない。所有権は協調制御であり、#110の本人・端末認可の代わりではない。

| 状況 | 停止・引継ぎ |
|---|---|
| 他タブで使用中 | 強制取得・時計による期限切れを行わない。所有側の「このタブの受付を止める」または終了後、利用者操作で取得をやり直す |
| 所有タブの通常引継ぎ | カメラ・新規要求とタイマーを止め、開始済みDB処理の完了・中止を確認してロックを解放。ネットワークの後着応答は旧epochで更新できない |
| タブ終了・クラッシュ後 | 実際にロックを取得できた新タブだけがepochを進めて復帰検査。未確認結果と同じキューを引き継ぎ、旧時計で連番を振り直さない |
| バックグラウンド・ロック喪失 | カメラと新規処理を停止。通常はDB処理を整理して解放する。停止中のタブがロックを保持し続けても他タブは奪わず、閉じるか紙受付へ |
| API非対応・取得失敗・版更新待ち | 排他を保証できたと表示せず、当該環境のQR受付を開始しない。DB更新を遮る旧接続は受付を止めて閉じ、再起動を案内する |

`steal`による取得は使用しない。BroadcastChannel等を案内に使っても、その応答やタイムアウトを所有権の証明にしない。別ブラウザープロファイルは別保存領域として#110で新しい端末IDを登録し、同じ端末連番を共有させない。

## DD-92-04 復帰と再送・異常時

1. 読取り停止のまま公演・本人と端末を照合する。オンライン復旧では現在状態を先に確認し、停止・失効を検知した場合は通常画面をロックする。
2. 所有権を取得し、head・未確認結果と必要なイベント・キューを同じ読取りトランザクションで取得する。復号・形式と参照を検査してから表示する。
3. 保存済み未確認結果があれば同じIDの結果を優先し、次への確認完了までカメラを再開しない。結果の共有状態が後から変わっても、自動で本人確認済みとしない。
4. 未確認結果がなく、保存の利用・版と現在の許可を確認できた場合だけ#89の待機へ進む。存在を確認できない状態を空の正常状態とみなさない。

| 対象 | 処理と保持 |
|---|---|
| 送信中で中断 | 再試行へ戻し、同じeventId・同じ業務本文を送る。サーバー受領済みなら本文一致を確認して確認済みへ。別IDで受付を作らない |
| サーバー保存後の応答喪失 | サーバー由来の同一ID・内容と受領結果を照会する。ローカルキャッシュだけで受領済みとしない。送信自体の再試行も同じIDで冪等に扱う |
| 同一IDの内容不一致・未対応版 | 上書きせず拒否・管理者確認。元イベントと未受領状態を保持する |
| 容量不足・鍵欠損・復号失敗 | 新規読取りと成功表示を停止し、管理者・紙照合へ。暗号文や他公演の鍵を消して空きを作らない |
| 登録済み端末のhead・storageEpoch欠落、参照不整合 | DB全消去・破損の可能性として照合待ち。既存の端末IDを連番0で自動初期化せず、#110の新規登録・旧端末の未確認追跡へ |
| 停止・失効後の未受領 | 既存BD-04の隔離送信と管理者照合へ。通常来場へ自動採用せず、鍵・本文と未受領記録を消さない |

既存headが正しく読み出せる場合に限り、その整合したスナップショットから未確認結果なしと判断する。利用開始時の初期headは#110の新規登録で明示作成し、通常起動での欠落を新規端末と推測しない。保存領域の消去・故障と端末回収不能は自動復旧の対象外であり、紙記録・他端末と管理者が照合する。

保存済みの受付本文と結果は、本人の確認・共有受領だけでは削除しない。#111の締め・#110の端末内削除条件に未確認結果と未受領キューを渡し、別公演を巻き込まない。無料600人必須・1,000人目標の保存・送信量と性能は#220へ含める。
