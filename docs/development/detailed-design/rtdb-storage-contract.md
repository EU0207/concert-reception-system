## 保存先と処理順

Hostingは画面・プログラムを配信する。Authenticationは本人と端末の別資格を管理する。開催中・過去公演とも、業務データ・画像と現在の認可正本をRTDBへ保存する。Firestoreへの状態別移動と認可の二重管理は初期方式に含めない。暗号化IndexedDBには端末の下書き・固定した送信案と未受領イベントを保持する。

1. 編集案と送信内容を端末へ一体保存する。保存失敗なら通信しない。
2. 現在の本人役割・端末許可と期限を確認し、対象の期待版を取得する。
3. 構成は不変候補を準備・検査する。業務の確定では正本・必要な投影と操作結果をRTDB内で一体更新する。
4. 同じ確定版の内容を取得してから成功を表示する。応答不明では同じ操作IDを照会し、入力内容との一致を確認する。

回線復帰だけでは下書きを自動確定しない。受付の変更不能イベントの再送と、編集案の明示確定を区別する。取得中の版変更・失効と欠落は受信候補を破棄し、途中状態を表示しない。

## 名前空間・形式版・索引

公演ルートは`/environments/{environmentId}/performances/{performanceId}`とする。環境は別Firebaseプロジェクトへ分離する。PoCの`checks/{run}`は配備しない。本文の環境・公演IDをパスと照合し、共通親からの広い読取りを許可しない。

| 領域 | 正式契約と取得範囲 |
|---|---|
| `roles`・`devices`・`sessions` | 本人役割と端末の結合、停止・期限を要求時に検査。本人UIDや端末IDの自己申告だけでは許可しない |
| `control` | 業務形式`businessSchemaVersion=3`、構成形式`layoutSchemaVersion=2`、公演管理版と初回受付開始を保持する。初回時刻を再開で振り直さない |
| `head`・`generations` | 構成形式2。1公演16区画、区画ごと256採番列、総4,096セル。16セル単位・1片64KiB以内を保存計画で検査する |
| `publicationChecks`・`numberProofs` | 世代と検査進捗を固定し、全体検査後だけ公開する。旧ID・消費番号と次番号を保護する |
| `event` | 業務形式3。人・席・表示名の正本と券・資格を分ける。正逆割当と変更した領域版、操作結果を同じ確定へ含める |
| `sectionViews`・`sectionPresentation` | 確定構成と表示版。一般受付には座席表示名・現在席と必要な来場状態だけを返す |
| `event/reception` | キー順・最大32件のページで取得する。購入者情報・任意項目と管理履歴を混ぜない |
| `sharedHead`・`sharedOperations`・`references` | 共有版は確定版と別にする。未解決操作・基準世代と端末参照は失効や時間経過だけで解除しない |
| `receipts`・`quarantine`・`receiptEventIds`等 | 端末別の不変受付イベントと連番。停止後到着を隔離し、管理判断前に来場へ自動加算しない |
| `deviceRoster`・`closingRuns`・`actuals`等 | 全登録端末を締め照合する。同じ締めIDで再開し、締め結果と現在の訂正後実績を分ける |
| `images/{slot}` | 5枠・各2バンク。原画像1,000,000 B以内。非公開側の準備後、公開先と操作結果を一体更新する |

細目の型・必須フィールドと不変条件は、[席管理の物理契約](seat-management-detail-design.md#v4の物理契約案)およびその根拠である[126のRules生成](../../../poc/GD91-126/contract-rules.mjs)へ対応付ける。これを製品名前空間へ移す際は#104・110で直接要求の拒否を確認する。試験用の管理投入・取込専用Rulesを通常業務Rulesの代用にしない。

キーによるID索引を使い、イベントと受付行はキー順に読む。子項目検索を追加する変更では`.indexOn`とクエリー許可を同時に定義する。現契約はその検索を追加しない。Firestoreの文書数・依存参照上限をRTDBの評価へ転用しない。64KiBは保存計画の検査値であり、RulesがJSON全体のUTF-8バイト数を直接検査するという意味ではない。

### 一体確定・操作IDとQR

`operationId`は操作案作成時に固定する。同じIDは同じ送信内容・期待版にだけ使い、結果を不変にする。競合後に内容を変える場合は再確認して新しい操作とする。`notFound`だけで無条件に再送しない。

不参加では人・席解放と券のcycle終了、旧資格無効化を同じ確定へ含める。復帰は未配置・未発行から始め、旧QRを再有効化しない。通常の移動・交換では資格を維持する。券発行・送付と入金のチェックは独立させ、発券済み保護をチェック解除で消さない。

QR資格は暗号学的乱数16バイトを正規のBase64url 22文字へ変換する。確認コードは`23456789ABCDEFGHJKMNPQRSTVWXYZ`から独立に8文字を生成する。コード予約の競合を検査し、旧予約を他人へ付け替えない。操作・席のUUIDとQR資格を同じ形式にしない。#112で生成・再発行と部分送信拒否を結合確認する。

### 画像と現在認可

管理端末でPNG／JPEGを復号し、原容量とSHA-256を確認してBase64化する。準備バンクを保存してから公開先を切り替える。取得側も復号とハッシュを検査する。RulesはBase64の形式・実長と末尾から原容量を検査し、画像の実体検査はアプリが行う。

業務と画像は同じ現在の役割・端末・セッションを参照する。準備バンク・旧バンクの取得を拒否し、現行バンクの上書き・削除を許可しない。旧バンクは参照解除後に通常権限で回収する。実画像の可読性と対象実機での完全オフライン表示は#105・110・220の未実施試験である。

## 初期化・保持・削除

初回の環境所有者による本人・端末承認と、公演の業務初期化を分ける。#110で現在の本人と端末を登録し、#111の通常権限で空名簿・構成未作成を含む初期状態を作る。管理資格によるPoCの投入をアプリ初期化として採用しない。全管理端末喪失時はBD-04の所有者復旧を経て再承認し、バックアップ内の資格で自己復帰させない。

確定履歴・過去公演と未解決参照は、利用者が明示削除するまで保持する。月数や容量不足による自動削除は行わない。構成の不要世代は現行・共有先と全参照を検査し、`deleting`→本文回収→`deleted`の順に進める。応答不明の操作結果を世代と一緒に消さない。

個人削除は対象の人・公演と理由を固定し、通常の変更を止めて対象目録を確定する。目録には正本・表示投影・券資格と関連履歴を含め、受付本文・画像等の関連有無も検査する。個人を含む外部出力とバックアップは、保管台帳から対象複製を特定する。詳細履歴だけの削除と、個人の削除を同じ操作にしない。

削除証跡は対象の不透明ID・削除種別と単調増加する境界を記録し、氏名・受付本文を残さない。本文削除と進捗を一体更新し、再開では同じ目録と操作IDを使う。DB内の完了と外部複製の確認待ちを分け、全確認前に全体の削除完了を表示しない。訂正は理由付きイベントとして追記し、元の締め結果を保持する。削除済み受付本文は訂正のために再生成しない。

## 正式バックアップ形式と復旧

対象は製品の正式形式だけである。旧PoC形式の変換器を付けず、不明な形式・領域と非対応版を保存前に拒否する。形式の版を変えるときは、実際の製品データを特定してBD-10の計画・検証・承認を行う。

### ファイル契約

BD-08-12の暗号方式と世代保管を維持する。生成と再取込は主担当だけがオンラインかつ15分以内の本人再認証後に行う。代理管理者は一覧と検証結果だけを確認できる。

| 部分 | 初期の正式形式 |
|---|---|
| 外側 | `format=concert-reception-product-backup`、`formatVersion=1`、`cipher=AES-256-GCM`、`kdf=none`。IV・暗号文と認証タグを持つ。旧PoC識別子を受け付けない |
| 暗号と鍵 | Web Cryptoで専用の256ビット鍵を生成する。IVは毎回新しい12バイト、認証タグは16バイト。追加認証データはUTF-8の`concert-reception-product-backup/1/AES-256-GCM/none`。復旧キーはファイルと別に保管し、端末CryptoKeyを流用しない |
| 内側の識別 | `schemaVersion=1`、`exportId`、元環境・公演ID、アプリ版と作成時刻。業務3・構成2を明記する |
| 同一版の証明 | 開始・終了の管理版と確定版、締めID・現在実績版、削除境界。領域ごとの件数・SHA-256と参照検査結果を持つ |
| 目録 | 含む領域・不在の領域を明記する。欠落と空を区別し、未知領域を黙って捨てない。出力対象と復旧後に再作成する対象を分ける |

含む業務領域は、構成・採番証跡、名簿・表示投影、券資格のサーバー側識別情報、変更不能イベントと操作結果、締め結果・現在実績と訂正、画像・削除証跡とする。管理用情報は管理者だけが復号できる。共有案は権限を持つ主担当が業務案として取り出してバックアップ専用鍵で包み直し、端末暗号文・端末鍵の複写では代替しない。未解決案は明示し、確定業務へ自動適用しない。

Authentication利用者・パスワードとトークン、端末CryptoKey・秘密鍵とQR生データを含めない。本人役割・端末登録とセッションは復元先で再承認する。旧端末の参照・稼働台帳を現行端末として登録せず、元の締め照合の証拠として必要な部分だけを保持する。

IV・暗号文と認証タグは正規の標準Base64で符号化し、復旧キーは32バイトの正規Base64urlとする。復号後の業務JSONと目録を照合する。ハッシュ計算では辞書キーを再帰的に昇順へ揃えてUTF-8のJSONへ変換し、配列の順序を保持する。非有限数とJSON外の型は受け付けない。暗号とハッシュの不一致は原本を変更せず拒否する。

生成中は対象環境を保守状態にする。開始・終了版が異なる場合は出力を未完了とし、正しい同一版から再生成する。公演前の設定確定後と、通常・例外締め後に取得する。CONF-049・050の復号・内容照合と復元練習を終えてから旧世代を手動で破棄する。実ファイルの無断削除はしない。

### 復旧の進行と最新削除証跡

| 段階 | 必須条件・失敗時の扱い |
|---|---|
| 検査 | 暗号・形式版、領域の件数・ハッシュと業務参照を全件検査する。現在認可を別に取得し、元環境・締め状態と現在の削除証跡を照合する |
| 隔離保存 | 通常業務から取得できない空の隔離先へ、`exportId`と内容ハッシュを固定して保存する。既存本番へ上書き・結合しない |
| 再開 | 同じID・同じ内容は保存済み進捗と照合して再開する。同じIDで異なる内容は拒否する。応答不明でも原本と現行正本を保持する |
| 有効化 | 再取得照合と現在認可、削除境界の再確認後だけ一度有効化する。新しい実績・訂正を古い値へ戻さず、未確認の取込を通常業務から見せない |
| 再開後 | 本人を再招待し端末を再承認する。元環境の変更禁止を維持し、二つの正本を同時稼働させない。未受領記録は照合し、自動加算しない |

最新削除証跡の取得元は、稼働正本の削除境界と、主担当が保管する独立した復旧目録とする。復旧目録には元環境・公演、確認済みの削除境界、復元禁止のexportId、現在採用中の世代と確認者・時刻を保持する。業務本文や認証秘密は置かない。個人削除時は旧世代を直ちに復元禁止とし、新世代の検証と旧複製の手動破棄へ接続する。

元DBが失われた場合も、バックアップが自分自身に記載した境界だけで「最新」と判定しない。主担当が独立目録の保管履歴と削除確認記録を照合できる場合だけ、その確認済み境界を復旧先へ設定する。初期設定を代行する管理操作は境界情報だけに限定し、業務本文の取込は現在認可を使うブラウザー経路に分離する。旧PoCの管理用台帳・専用資格をそのまま採用する指示ではない。

独立目録も古い可能性がある、保管記録が欠ける、または削除後の状態を確認できない場合は有効化を禁止する。ハッシュ一致やハッシュ連鎖だけでは、目録全体の古い正規版への巻戻しを検出できない。これは[160・162の制約](../technical-validation/seat-capacity-validation.md#gd91-162-独立保全台帳と復旧許可の消費)を残した運用境界であり、自動の最新性保証を主張しない。

## 保存容量・通信の設計予算

採用根拠は[134の画像込み計算](../technical-validation/seat-capacity-validation.md#gd91-134-qr形式修正後の画像込み設計予算)と[137の長期蓄積比較](../technical-validation/seat-capacity-validation.md#gd91-137-3案の共通条件と長期蓄積の予算比較)である。検証時の比較枠を使用した予約量であり、完成アプリの請求量・無料受入の実測ではない。

| 条件 | 600人 | 1,000人 |
|---|---:|---:|
| 月1公演・既定予約量の月間通信 | 4,584,321,318 B | 5,677,677,932 B |
| 同条件の保存予約 | 167,303,618 B | 180,590,270 B |
| 月4公演の月間通信 | 15,337,285,272 B・超過 | 19,710,711,728 B・超過 |
| 過去12公演・1人5イベント追加予約の保存量 | 1,011,811,034 B・超過 | 1,209,113,510 B・超過 |

安全係数2と、未測定業務・他用途の予約を含む。画像5枠・2バンク、6取得元とバックアップ2回も予約条件へ含める。長期保存は件数と履歴量に依存し、何年でも無料という保証は行わない。保持要件を縮小して予算へ合わせない。

登録・座席準備とQR発行は前日までに完了する案内を維持する。RTDBは前日分も同じ月間通信へ合算し、翌日の回復を案内しない。人数だけで無料を保証しない。残量不足では新規共有・確定を止めて入力と未送信イベントを保持し、既定の紙運用へ切り替える。課金登録を通常成立の代替にしない。

## 追加業務設計の適用境界
