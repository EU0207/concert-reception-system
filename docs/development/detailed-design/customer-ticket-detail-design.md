## DD-93-01 範囲と承認済み条件

対象はMCT-19・25～33、REQ-F-032・033・043・044、AC-002・023・026・032・035・036である。CONF-060・063・064・070を適用し、古い「購入確定」「交付済み」の名称を使わない。お客様情報は不参加者も含む名簿、お客様対応状況は来場予定者のチェック一覧とする。

本設計で作るものは購入者IDによる名前修正、固定3項目・確認用項目の管理、不参加と復帰の共同操作である。紙・電子チケットの実ファイル出力、Excel取込の全仕様と個別登録はそれぞれの担当設計で扱う。#97の個別登録も、本書のIDと版の契約を使う。

入金済み・券発行済み・券送付済みは独立した固定項目であり、改名・削除を許可しない。未入金での発行・送付を許可する。チェック操作は決済・発送と自動送信を行わない。券送付済みには郵送・データ送付・手渡しの完了を含む説明を表示する。

## DD-93-02 IDと保存の正本

公演ルートは正式RTDB契約と同じとし、新しい管理領域`customer`を置く。`customer/schemaVersion=1`は本領域の形式版であり、席・券の業務形式3と構成形式2を変更しない。現在認可は同じ公演の役割・端末・セッションを参照する。

| 保存先・ID | データと責務 |
|---|---|
| `customer/head` | 領域の確定revisionとoperationId。対象レコード・操作結果と一体更新し、取得前後の整合性確認に使う |
| `customer/buyers/{buyerId}` | 購入者名の現在値、revision・membershipRevisionと最後のoperationId。名前は前後空白を除き内部空白込み1～50文字。購入者IDは名前から生成しない |
| `customer/personBuyers/{personId}` | 1席分の来場者IDと購入者IDの対応。来場者が増減したときは購入者のmembershipRevisionも同じ確定で更新する |
| `customer/buyerMembers/{buyerId}/{personId}` | 購入者に紐づく対象行の逆参照。正参照と同じ確定で更新し、同名検索から勝手に追加しない |
| `customer/checkDefinitions/{itemId}` | 確認用項目の名称・表示順、scope（buyer／person）、revisionとactive。scopeは作成後に変更しない |
| `customer/checkValues/{itemId}/{subjectId}` | 定義に対応する購入者または来場者の値、最新チェック日時とrevision。別scopeのIDを受け付けない |
| `customer/operations/{operationId}` | 不変の操作種別・対象、変更前後と結果版。購入者名修正・項目定義変更の監査を保持する |
| `event/profiles`・`event/tickets` | 入金と席単位の券発行・券送付、座席表示名の既存正本。固定チェックと券cycleの契約は席管理の詳細設計を維持する |

同じ購入者が複数席を購入しても、来場者・券とQRを統合しない。購入者IDと連席用groupIdも別の意味である。同名の別購入者を自動統合しない。購入者IDの付与は登録時の明示した購入者との対応で行い、情報のない既存行を名前一致でまとめない。

購入者名の現在値は`customer/buyers`を正本とする。管理一覧と出力はpersonBuyersを経て現在名を取得し、席ごとの現在名の複写を正本にしない。従来の`event/profiles.name`は登録時点のスナップショットとして扱い、現在の購入者名表示や名前修正の判定には使わない。購入者名を直しても、本人用に変更済みの座席表示名を上書きしない。

この正本分離は#229の追加契約である。GD91-126等で検証した行単位のprofile.nameを、購入者ID単位の修正が合格した証拠へ読み替えない。初期製品の型と登録アダプターは新契約へ揃える。旧PoCデータの変換器は作らない。

新規の来場者登録では、event側の人と登録時点の情報、customer側の正逆参照とメンバー版を同じ確定へ含める。片側だけを登録して成功としない。購入者との対応が不明なら新しい独立IDとして確認し、既存購入者への結合を名前から推測しない。

### 一覧の取得と版の確認

お客様情報・対応状況は管理者だけがページ取得する。名前や確認項目を一般受付の`event/reception`へ追加しない。管理一覧は取得前後に業務確定版とcustomerのrevisionを照合し、混在した結果を表示しない。購入者・確認項目の参照もID単位で取得し、通常変更で名簿全体を再配布しない。

お客様対応状況から不参加者を除外する。席設定候補は入金済みを初期表示とし、未入金を含む来場予定・席未設定の全員へ切り替えられる。表示上の初期フィルターを登録・発券の禁止条件へ転用しない。

## DD-93-03 購入者名・案内の編集

1. 主担当・代理管理者が対象購入者と全対象行を確認する。購入者revision・membershipRevisionと現在認可を取得し、変更前後を表示する。
2. operationId、期待版と送信内容を暗号化IndexedDBへ保存する。未保存の破棄ではDBへ送らず、画面を閉じる際は未保存確認を出す。
3. RTDBで現在認可と期待版を再検査し、購入者名・revisionと操作結果を一体確定する。メンバー追加等で確認範囲が変われば拒否し、対象一覧と入力を保持して再確認する。
4. 同じ結果版を取得して全対象行の現在名へ反映する。他の購入者・座席表示名とQRは不変とする。

購入者名修正には変更前後・担当者と端末、サーバー確定時刻を残す。対象数分の名前書換えを順番に送信しない。応答不明では同じ操作IDの結果を照会し、異なる内容で再利用しない。

案内・例外は来場者単位の管理情報とし、既存の200文字以内・空欄解除を維持する。名前横と右端に案内ありを表示し、詳細で確認する。管理情報の取得権限を満たさない端末へ本文を送らない。案内の存在表示も許可された管理画面の範囲とする。

## DD-93-04 固定項目・確認用項目

| 操作 | 保存・表示と不変条件 |
|---|---|
| 固定チェックの変更・解除 | 対象席と影響を確認して、値・最新チェック日時と結果を同じ確定へ含める。入金と券の項目を勝手に連動させない |
| 複数席への一斉操作 | 全対象と期待版を固定して一度の確定とする。版競合・不参加への変更があれば全体を拒否し、未確認の対象だけを残して成功表示しない |
| 確認用項目の追加 | 作成時に購入者単位／席単位を選ぶ。itemIdは新規発行し、固定3項目のID・名称を上書きできない |
| 確認用項目の改名 | itemId・scopeと値を保持する。定義版を照合し、他端末の改名を無条件に上書きしない |
| 確認用項目の削除 | 対象確認後にactive=falseと削除記録を一体確定し、一覧・並べ替え候補から外す。復元UIを設けず、同じIDを再作成しない |
| 確認用チェックの変更 | 有効な定義・scopeとsubjectIdを照合する。購入者単位なら同じ購入者の行へ同じ値を表示し、席単位ならその来場者だけを変更する |

確認用項目の値は、入金・席設定と発券、受付可否の判定へ使わない。項目削除後も過去の値と履歴は既存の詳細履歴の保持規則に従い、利用者の明示削除まで保持する。削除済み定義への書込みと固定項目の改名・削除を直接要求でも拒否する。

固定チェックだけを変更・解除する操作は、CONF-037に従い操作担当者を記録しない。対象と変更前後、最新チェック日時は残す。名前修正・QR無効化と不参加の監査までこの例外で省略しない。認可のために検査するAuth UIDと、業務の履歴に保存する担当者を区別する。

チェック値はboolean、`checkedAt`は最後に済みにしたサーバー時刻、`changedAt`は最後に変更したサーバー時刻とする。解除で過去の到達日時を消さず、現値が未済であることと分けて表示する。確認用項目の定義管理の監査と、固定チェックだけの担当者非記録を同じ経路で混ぜない。

## DD-93-05 不参加・復帰と未更新端末

不参加は入金や記録の削除と別の状態変更である。氏名から開く詳細画面で対象・現在席と券状態を確認する。発券済みなら独立した2回の確認を行い、旧QRを取り消す影響を表示する。

| 対象状態 | 一体確定する内容 | 保持する内容 |
|---|---|---|
| 席・券なし | active=falseと業務版・結果 | 購入者名・入金と過去記録。存在しない資格を作らない |
| 席あり・未発券 | active=false、正逆の席割当解除と表示投影 | 席ID等の変更前と理由、担当者・端末と時刻 |
| 発券済み | 上記に券cycle終了・旧資格の不可逆無効化と現在券状態の解除を含める | 不参加前の席、券発行・券送付状態と履歴。入金は変更しない |
| 来場予定へ復帰 | active=true、未配置・未発行の状態と結果 | 過去の無効資格・cycleと不参加履歴。旧席・QRを復活させない |

保存時には確認した公演管理版と人・席・券の版を再検査する。部分送信を拒否し、全確定前に空席として他者へ再割当てしない。競合・応答不明では入力と同じ操作IDを保持する。復帰後の新規発券は#112の新cycleから行う。

旧QRの無効化・紛失再発行はBD-03-07の全稼働端末停止確認へ接続する。完全オフライン端末には無効化を即時通知できない。停止確認不能なら操作全体を保留して紙照合へ案内し、オンライン表示だけで端末停止を保証しない。成功後も対象端末の新しい版の受信確認前にQR受付を再開しない。

旧資格・旧版による受付記録が後から届いても削除しない。現在資格と公演状態を再照合し、通常来場へ自動採用せず管理者照合へ回す。#92の未確認結果を確認する前にカメラを再開しない。来場実績を不参加・復帰の画面操作だけで消さない。

## DD-93-06 権限・失敗とバックアップ

| 操作 | 主担当・代理管理者 | 臨時管理者・一般受付 |
|---|---|---|
| 購入者名修正・確認用項目の定義管理 | オンライン・現在の公演役割と承認端末を検査 | 拒否。#98の未承認カスタマイズを先取りしない |
| 固定・確認用チェックと案内編集 | 管理画面の対象・版確認を経て許可 | 初期契約では拒否。承認済みの当日座席表示名変更とは区別 |
| 不参加・復帰と券無効化 | 最新版と確認条件を満たす場合だけ許可 | 拒否 |
| 管理履歴・購入者名の取得 | 許可された公演の必要範囲 | 配布しない。一般受付の現在席・表示名の投影だけを使う |

端末停止・役割失効、期限切れと別公演の直接要求をサーバーで拒否する。通信失敗でも入力を保持し、回復時に管理編集を自動確定しない。一般受付の暗号化キューは既存の受付再送規則へ接続する。

`customer`領域を正式バックアップの目録へ追加する。購入者・対応関係、定義・値と不変操作結果の件数・ハッシュを検査する。項目削除済み状態を保持し、古いバックアップから復元UIや書込み許可を再作成しない。個人削除は購入者と来場者の参照範囲を確認し、他の来場者が参照する購入者正本を無断削除しない。#221の正式復旧試験へ渡す。
