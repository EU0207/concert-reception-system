## DD-93-02 IDと保存の正本

公演ルートは正式RTDB契約と同じとし、新しい管理領域`customer`を置く。`customer/schemaVersion=1`は本領域の形式版であり、席・券の業務形式3と構成形式2を変更しない。現在認可は同じ公演の役割・端末・セッションを参照する。

| 保存先・ID | データと責務 |
|---|---|
| `customer/head` | 領域の確定revisionとoperationId。対象レコード・操作結果と一体更新し、取得前後の整合性確認に使う |
| `customer/buyers/{buyerId}` | 購入者名の現在値、revision・membershipRevisionと最後のoperationId。名前は前後空白を除き内部空白込み1～50文字。購入者IDは名前から生成しない |
| `customer/personBuyers/{personId}` | 1席分の来場者IDと購入者IDの対応。来場者が増減したときは購入者のmembershipRevisionも同じ確定で更新する |
| `customer/buyerMembers/{buyerId}/{personId}` | 購入者に紐づく対象行の逆参照。正参照と同じ確定で更新し、同名検索から勝手に追加しない |
| `customer/checkDefinitions/{itemId}` | 確認用項目の名称・表示順、scope（buyer／person）、revisionとactive。scopeは作成後に変更しない |
| `customer/checkValues/{itemId}/{subjectId}` | 定義に対応する購入者または来場者の値、最新チェック日時とrevision。別scopeのIDを受け付けない |
| `customer/operations/{operationId}` | 不変の操作種別・対象、変更前後と結果版。購入者名修正・項目定義変更の監査を保持する |
| `event/profiles`・`event/tickets` | 入金と席単位の券発行・券送付、座席表示名の既存正本。固定チェックと券cycleの契約は席管理の詳細設計を維持する |

同じ購入者が複数席を購入しても、来場者・券とQRを統合しない。購入者IDと連席用groupIdも別の意味である。同名の別購入者を自動統合しない。購入者IDの付与は登録時の明示した購入者との対応で行い、情報のない既存行を名前一致でまとめない。

購入者名の現在値は`customer/buyers`を正本とする。管理一覧と出力はpersonBuyersを経て現在名を取得し、席ごとの現在名の複写を正本にしない。従来の`event/profiles.name`は登録時点のスナップショットとして扱い、現在の購入者名表示や名前修正の判定には使わない。購入者名を直しても、本人用に変更済みの座席表示名を上書きしない。

この正本分離は#229の追加契約である。GD91-126等で検証した行単位のprofile.nameを、購入者ID単位の修正が合格した証拠へ読み替えない。初期製品の型と登録アダプターは新契約へ揃える。旧PoCデータの変換器は作らない。

新規の来場者登録では、event側の人と登録時点の情報、customer側の正逆参照とメンバー版を同じ確定へ含める。片側だけを登録して成功としない。購入者との対応が不明なら新しい独立IDとして確認し、既存購入者への結合を名前から推測しない。

### 一覧の取得と版の確認

お客様情報・対応状況は管理者だけがページ取得する。名前や確認項目を一般受付の`event/reception`へ追加しない。管理一覧は取得前後に業務確定版とcustomerのrevisionを照合し、混在した結果を表示しない。購入者・確認項目の参照もID単位で取得し、通常変更で名簿全体を再配布しない。

お客様対応状況から不参加者を除外する。席設定候補は入金済みを初期表示とし、未入金を含む来場予定・席未設定の全員へ切り替えられる。表示上の初期フィルターを登録・発券の禁止条件へ転用しない。

## DD-93-03 購入者名・案内の編集

1. 主担当・代理管理者が対象購入者と全対象行を確認する。購入者revision・membershipRevisionと現在認可を取得し、変更前後を表示する。
2. operationId、期待版と送信内容を暗号化IndexedDBへ保存する。未保存の破棄ではDBへ送らず、画面を閉じる際は未保存確認を出す。
3. RTDBで現在認可と期待版を再検査し、購入者名・revisionと操作結果を一体確定する。メンバー追加等で確認範囲が変われば拒否し、対象一覧と入力を保持して再確認する。
4. 同じ結果版を取得して全対象行の現在名へ反映する。他の購入者・座席表示名とQRは不変とする。

購入者名修正には変更前後・担当者と端末、サーバー確定時刻を残す。対象数分の名前書換えを順番に送信しない。応答不明では同じ操作IDの結果を照会し、異なる内容で再利用しない。

案内・例外は来場者単位の管理情報とし、既存の200文字以内・空欄解除を維持する。名前横と右端に案内ありを表示し、詳細で確認する。管理情報の取得権限を満たさない端末へ本文を送らない。案内の存在表示も許可された管理画面の範囲とする。

## DD-93-04 固定項目・確認用項目

| 操作 | 保存・表示と不変条件 |
|---|---|
| 固定チェックの変更・解除 | 対象席と影響を確認して、値・最新チェック日時と結果を同じ確定へ含める。入金と券の項目を勝手に連動させない |
| 複数席への一斉操作 | 全対象と期待版を固定して一度の確定とする。版競合・不参加への変更があれば全体を拒否し、未確認の対象だけを残して成功表示しない |
| 確認用項目の追加 | 作成時に購入者単位／席単位を選ぶ。itemIdは新規発行し、固定3項目のID・名称を上書きできない |
| 確認用項目の改名 | itemId・scopeと値を保持する。定義版を照合し、他端末の改名を無条件に上書きしない |
| 確認用項目の削除 | 対象確認後にactive=falseと削除記録を一体確定し、一覧・並べ替え候補から外す。復元UIを設けず、同じIDを再作成しない |
| 確認用チェックの変更 | 有効な定義・scopeとsubjectIdを照合する。購入者単位なら同じ購入者の行へ同じ値を表示し、席単位ならその来場者だけを変更する |

確認用項目の値は、入金・席設定と発券、受付可否の判定へ使わない。項目削除後も過去の値と履歴は既存の詳細履歴の保持規則に従い、利用者の明示削除まで保持する。削除済み定義への書込みと固定項目の改名・削除を直接要求でも拒否する。

固定チェックだけを変更・解除する操作は、CONF-037に従い操作担当者を記録しない。対象と変更前後、最新チェック日時は残す。名前修正・QR無効化と不参加の監査までこの例外で省略しない。認可のために検査するAuth UIDと、業務の履歴に保存する担当者を区別する。

チェック値はboolean、`checkedAt`は最後に済みにしたサーバー時刻、`changedAt`は最後に変更したサーバー時刻とする。解除で過去の到達日時を消さず、現値が未済であることと分けて表示する。確認用項目の定義管理の監査と、固定チェックだけの担当者非記録を同じ経路で混ぜない。

## DD-93-05 不参加・復帰と未更新端末

不参加は入金や記録の削除と別の状態変更である。氏名から開く詳細画面で対象・現在席と券状態を確認する。発券済みなら独立した2回の確認を行い、旧QRを取り消す影響を表示する。

| 対象状態 | 一体確定する内容 | 保持する内容 |
|---|---|---|
| 席・券なし | active=falseと業務版・結果 | 購入者名・入金と過去記録。存在しない資格を作らない |
| 席あり・未発券 | active=false、正逆の席割当解除と表示投影 | 席ID等の変更前と理由、担当者・端末と時刻 |
| 発券済み | 上記に券cycle終了・旧資格の不可逆無効化と現在券状態の解除を含める | 不参加前の席、券発行・券送付状態と履歴。入金は変更しない |
| 来場予定へ復帰 | active=true、未配置・未発行の状態と結果 | 過去の無効資格・cycleと不参加履歴。旧席・QRを復活させない |

保存時には確認した公演管理版と人・席・券の版を再検査する。部分送信を拒否し、全確定前に空席として他者へ再割当てしない。競合・応答不明では入力と同じ操作IDを保持する。復帰後の新規発券は#112の新cycleから行う。

旧QRの無効化・紛失再発行はBD-03-07の全稼働端末停止確認へ接続する。完全オフライン端末には無効化を即時通知できない。停止確認不能なら操作全体を保留して紙照合へ案内し、オンライン表示だけで端末停止を保証しない。成功後も対象端末の新しい版の受信確認前にQR受付を再開しない。

旧資格・旧版による受付記録が後から届いても削除しない。現在資格と公演状態を再照合し、通常来場へ自動採用せず管理者照合へ回す。#92の未確認結果を確認する前にカメラを再開しない。来場実績を不参加・復帰の画面操作だけで消さない。

## DD-97-01 個別登録の範囲と入力

CONF-067、MCT-38、REQ-F-001・002とAC-001を対象とする。「お客様情報」から1席分の名簿行を追加し、Excel取込と同じpersonId（来場者ID）・購入者参照を使う。画面だけの仮行を別の名簿として残さない。方式の比較・理由は[ADR-008の登録への適用](../decisions/ADR-008-customer-identity-and-check-items.md#個別登録とexcel追加への適用97)へ分ける。

| 入力・初期値 | 契約 |
|---|---|
| 購入者名 | 前後空白除去後1～50文字。内部空白・全半角・英字大小を勝手に統一せず、超過時に切り詰めない。既存の名前検査を個別登録・Excel・名前修正で共用する |
| 座席表示名 | 任意入力。半角・全角の空白除去と6文字上限はBD-02・07の共通規則を使う。未入力なら上限内の購入者名を初期値とし、超過時は略称入力を求めて保存を止める。自動省略しない |
| personId・buyerId | 暗号学的乱数による既存のID形式。名前・名簿番号から生成せず、送信案を固定した後は再採番しない |
| 参加・席・券 | 来場予定、席未設定。入金・券発行・券送付は未済。券cycle・QR資格・受付イベントを登録操作で生成しない |
| 案内・グループ・確認用項目 | 案内とgroupIdは空。新しい行の席単位チェックは未済。既存購入者を明示して追加した場合の購入者単位チェックは購入者の現在値を参照し、既存値を解除しない |

個別登録では購入者名・座席表示名以外の追加編集を一緒に行わない。既存行への追加入力は、そのpersonIdを選んでDD-93の編集操作へ進む。新規登録を既存行の上書き・重複行の統合として使わない。

### 重複候補と購入者との対応

管理権限で取得済みの同一版の名簿を使い、前後空白除去後の購入者名が一致する行を候補表示する。不参加の既存行も候補へ含め、現在席・参加状態と座席表示名で対象を確認できるようにする。同名はエラーではなく、候補0件も別人であることの証明にはしない。名前検索用の公開索引や一般受付への氏名配布は追加しない。

- 別のお客様として追加：新しいbuyerIdとpersonIdを作る。同名の別購入者を許可する。
- 既存購入者へ1席分を追加：利用者がbuyerIdと対象行を明示して確認した場合だけ、新しいpersonIdを結び付ける。名前とmembershipRevisionを再検査し、既存の席・券・入金を複写しない。
- すでに登録済みの行だった：追加を取り消し、必要なら既存行の編集へ戻る。不参加からの復帰はDD-93-05を使い、新規登録で旧QRを復活させない。

候補がある場合に既存購入者を既定選択しない。候補一覧を取得できない・版が変わった場合も「候補なし」とせず、入力を保持して取得・確認をやり直す。追加確認中に他端末やExcelが名簿を更新した場合も同じ扱いとする。

## DD-97-02 名簿追加の処理と一体確定

1. 主担当・代理管理者が対象公演と入力を確認する。現在認可、名簿の業務版とcustomer/headの版を取得し、重複候補と購入者への対応を確認する。
2. 「追加する」は端末の編集案に1行を置く。名簿では未保存と表示し、共有名簿・席設定・発券へはまだ渡さない。「保存」でID・operationIdと期待版を固定し、送信案を暗号化IndexedDBへ一体保存する。端末保存に失敗したら通信しない。
3. RTDBで現在認可・公演状態と期待版を再検査し、下表を一体確定する。対象外の既存行や既存購入者の名前変更を登録要求へ混ぜた場合も拒否する。
4. 確定結果と同じ版の名簿行を取得してから登録済みを表示する。席設定候補には来場予定・席未設定の行として渡し、未入金を含む候補への切替を維持する。

保存前に複数行を追加した場合は、確認画面の対象セットを固定して1操作で全件確定する。1行ずつ送信して部分成功を表示しない。既定の保存予算を超える案は通信前に拒否する。通常の未保存入力は画面内の案であり、再読込み後の復元を保証しない。送信案を固定・端末保存した後の応答不明とは区別する。

| 一体確定の範囲 | 検査・保持する条件 |
|---|---|
| event側の新規来場者・登録時のprofile・表示名 | IDが未使用。profile.nameは登録時点のスナップショット。既存の人・割当・券・来場実績を変更しない |
| customer側の購入者と正逆参照 | 新規購入者は正本を生成。既存購入者は名前版とmembershipRevisionを照合し、personBuyers・buyerMembersとメンバー版を同時更新。片側だけを拒否 |
| 名簿順と配置用roster | DD-91の0始まり・未使用の次順序を使う。既存行・不参加行の順序は保持。個別登録のgroupIdはnull、Excelは下記の対応付け済みUUIDまたはnullを渡す。所属と名簿順の予約・確定を同じ業務版で保護する |
| 変更した業務版・customer/headと操作結果 | #104の同じ確定境界で更新。登録元（個別／Excel）、対象IDと結果版を結果に保持し、同じIDで内容を変えない |

`customer/operations/{operationId}`には登録種別と対象personId・buyerId、担当者・端末とサーバー時刻を残す。Excelでは取込ID・元行識別子と新規personIdの対応も不変の結果へ含め、ファイル名・原本を監査へ複写しない。個別登録は固定チェックだけの変更ではないため、担当者非記録の例外を適用しない。氏名は保護された業務正本と登録時profileに保持し、診断ログや一般受付の結果へ出さない。利用者の明示削除までは登録履歴を保持し、#221の目録へ含める。

### Excelとの共通境界

Excelの安全検査・全行検証とプレビューはBD-07を維持する。ファイル単位の500行制限を、公演全体や個別登録の500人制限へ読み替えない。無料600人必須・1,000人目標と#220の完成アプリ判定を維持する。公演全体の保存・通信の予算不足は正式RTDB契約に従い、課金登録や自動削除で回避しない。

Excelの各入力行も同じ新規来場者と購入者参照へ変換する。取込ID・元行識別子は入力行の識別に使い、名前一致を既存personId・buyerIdの証明としない。既存行・別の入力行へ追加する場合も明示したID対応を要求し、不明なら独立した購入者とする。groupIdから購入者IDを推測しない。

取込の新規行は既存の名簿順の後へ元行順で追加する。この追加経路では既存名簿の全置換や無指定の更新・削除を行わない。既存行への更新は対象IDと期待版を指定する既存の編集契約で扱い、BD-07の更新件数・除外件数の確認を削除しない。全行の検査完了・確定前には登録せず、正常行だけの部分成功を許可しない。席番号を指定したExcel行の既存の席整合性検査は維持し、個別登録へ自動席設定を持ち込まない。

個別登録とExcelの並行確定は同じ名簿版で競合を検出する。先に1件が確定したら、後の要求は全体を拒否し、最新候補・購入者対応と件数を再確認する。名簿順の衝突だけを直して無確認で再送しない。Excelの一括保存の物理計画・Rulesは#104・230で製品試験し、既存PoCの登録結果を追加customer領域の証拠へ流用しない。

### Excelのグループ所属から配置への契約（#251）

状態：Approved（PR #253）。REQ-F-036・AC-026とCONF-067の既存条件を維持する是正。個別登録の初期値をExcelへ一律適用しない。比較・採用理由は[ADR-008の所属是正](../decisions/ADR-008-customer-identity-and-check-items.md#excelのグループ所属の是正251)、照合結果は[設計照合記録](../technical-validation/excel-group-contract-review.md)へ分ける。

| 入力・識別 | 契約 |
|---|---|
| 個別登録 | groupId=null。グループ入力を個別登録へ追加せず、購入者への明示追加から所属を推測しない |
| Excel空欄 | 空セル・空文字は個人としてgroupId=null。同じ購入者の複数行でも自動でグループにしない |
| Excel指定あり | BD-07の0～50文字・セル安全検査を維持。検証済み文字列を「取込グループラベル」とし、保存用のUUIDと区別する。空白だけ・制御文字等の不正入力は空欄に置換せず行エラーとする |
| 比較範囲 | 同じ環境・公演の同じラベルは同じgroupId。別公演とは独立する。英字大小・全半角と前後空白を勝手に統一せず、先頭ゼロを落とさない。異なるラベルを名前・購入者から結合しない |
| 内部ID | groupIdは暗号学的乱数によるUUID v4。ラベルそのものやハッシュをID・RTDBキーに使わない。入力がUUIDに見えても既存IDの証明とはしない |

1. 同一版の全名簿と管理用のグループ情報を取得し、公演内のラベル→groupId対応を検査する。既存対応が一意なら再利用し、未使用ラベルには新規UUIDを1件だけ割り当てる。同一ラベルに複数ID、所属参照の欠落等があれば取込を止め、別グループを自動生成して回避しない。
2. プレビューへラベルごとの既存人数・追加人数と合計を示す。既存の不参加者も所属人数の確認に含め、同じラベルの追加が既存グループへ入ることを確定前に確認する。初回500行の制限を公演人数の上限にせず、別ファイルの追加でも同じ対応を使う。
3. 取込ID・元行識別子、personIdとgroupIdの対応をoperationId・期待版と一緒に端末へ固定保存する。同じ要求の結果照会・再送ではラベルにUUIDを振り直さない。確実な未確定後に期待版や対応を変える場合は再確認し、新しい操作IDで案全体を固定する。
4. 現在認可と同じ名簿版・グループ情報版を検査し、下表の範囲を全行一体確定する。対応が未登録であることも期待条件とし、並行取込で同じラベルが先に登録されたら後の要求を全体拒否する。入力と新旧対応を表示して再確認し、黙って別UUIDのまま登録しない。
5. 同じ確定版で全名簿のgroupId・rosterOrderを配置へ渡す。10人以下は既存の一般連続席の条件で配置し、11人以上はグループ全体を自動配置対象外とする。取込そのものの10人制限へ読み替えず、勝手な分割・人数切捨てをしない。不参加者を含む場合も残りだけで再編しない。

| 一体確定・参照範囲 | 維持する条件 |
|---|---|
| 人・購入者参照 | 上記DD-97-02の正逆参照と登録結果を維持。購入者IDとグループIDは独立し、同名別人を統合しない |
| 所属・名簿順 | 管理正本のpersonIdごとのgroupId・rosterOrderと配置用rosterを同時生成する。不参加を含む既存の所属・順序を変更せず、追加は未使用の次順序から元行順とする |
| ラベル対応 | 既存の管理用`event/groupInfo/{groupId}`へ`importGroupLabel`を属性として保持する。Excel由来の対応は公演内で一意・不変、ラベル未設定の既存グループへ名前から対応を付けない。管理権限で取得し、一般受付へ配布しない |
| グループ索引・固定 | groupInfoの全メンバー索引を所属正本から同じ確定で更新。新規グループのgroupStatesはfixed=false・manualReason=null。既存の固定・手動理由と既存割当・券を登録で解除しない。既存グループへ追加しても自動再配置を開始しない |
| 版・結果・監査 | 変更したグループ情報版と業務版、customer/headと操作結果を一体確定する。取込結果にラベル・groupIdと元行→personIdの対応を保持。診断ログへラベルを出さず、明示削除までの保持・バックアップの対象とする |

同一ラベルの一意性はクライアントのプレビューだけで保証したと扱わない。#104・230は現在正本と全要求を照合し、重複対応・所属と索引の不一致、既存固定状態の初期化を直接要求でも拒否する必要がある。具体的なRulesによる一意性検査と登録一体保存は未実装・未検証。#104は保存計画でこの条件を実現できることを確認してから当該経路を有効にし、通常権限で検査できない方式をクライアント検査だけで代替しない。

ラベルの取得と対応保存による容量・通信の追加分は#220、バックアップと明示削除時の参照は#221・239へ引き継ぐ。無料600人必須・1,000人目標と課金登録なしを維持する。#103の入力は内部UUIDと全名簿であり、Excel文字列を直接渡さない。途中実装PR #249は本是正の承認・統合後に契約を照合して再開する。

本節の未決定業務事項はなし。製品の取込・Rules、配置と画面の結合は未実施であり、本是正で実装を再開しない。

## DD-97-03 未保存・中断・拒否と権限
