## 結論

本番の本人認証には、ADR-001で採用した環境専用Firebase Authenticationのメールアドレス・パスワード方式を使用する。共有アカウント、匿名認証、端末共通暗証番号は使用しない。メール確認済みの個別利用者だけを業務利用者として扱い、AuthenticationのUIDと業務上の表示名・役割を分離する。

認証済みであることだけでは業務データへアクセスさせない。公演単位の役割割当と端末登録をFirestoreに保持し、Security Rulesがオンライン要求ごとに、利用者、メール確認、役割の有効状態、公演、端末、操作対象、期限を検証する。役割は主担当、代理管理者、一時管理者、一般受付担当者の4種類とし、明示的に許可していない読取り・書込みを既定で拒否する。

完全オフライン受付は、オンラインで本人、役割、端末、公演データ、期限を確認して発行した端末固有のオフライン許可が有効な場合だけ開始できる。許可は最長24時間かつ当日運用終了予定時刻までとし、役割期限を超えない。オフライン中の権限停止は即時反映できないため、復旧後のオンライン要求を拒否し、未送信イベントを失わず管理者確認へ回す。

## BD-04-01 認証方式と識別子

| 項目 | 方針 |
|---|---|
| 認証基盤 | 環境ごとに分離したFirebase Authenticationを使用し、他環境と利用者を共有しない |
| サインイン方式 | メールアドレス・パスワード。メールアドレス確認済みであることを業務アクセスの条件とする |
| 利用者識別子 | Firebase UIDを内部参照に用いる。メールアドレス、表示名、役割名を主キーにしない |
| 業務利用者 | UIDを参照する環境内利用者情報と、公演単位の役割割当を分離する |
| 端末識別子 | ブラウザー保存領域ごとに不透明な端末IDを発行し、利用者、公演、準備状態、有効状態へ結び付ける。端末の機種名や個人情報をIDにしない |
| 本人確認情報 | パスワード、IDトークン、更新トークンをFirestore、監査イベント、ログ、Gitへ保存しない |

メール・パスワード方式は、POC-004で検証済みであり、個別アカウント、再設定、費用0円、対象規模約10人を追加の外部認証サービスなしで満たせるため採用する。共有パスワードは個人を識別できないため採用しない。Google等の外部プロバイダーは、依頼者・スタッフのアカウント条件と同意画面を増やすため初期採用しない。

## BD-04-02 アカウント登録と初期設定

1. Firebaseプロジェクト所有者は、本番環境の初期設定手順で最初の主担当アカウントを作成し、メール確認と初期主担当割当を行う。初期主担当が存在しない状態で、最初にアクセスした利用者が自動的に主担当になる方式は採用しない。
2. 主担当または代理管理者は、スタッフのメールアドレス、公演、予定役割、有効期限を指定して1回限りの招待を作成する。招待は推測困難なID、有効期限、使用状態を持ち、一覧の閲覧を主担当・代理管理者へ限定する。
3. 招待されたスタッフは自分の個別アカウントを作成または既存アカウントでサインインし、メール確認後に招待を受諾する。招待メールとサインインメールが一致しない場合は役割を付与しない。
4. Firebase Authentication上にアカウントが存在しても、有効な役割割当と承認済み端末がなければ業務データを取得できない。招待なしで作成されたアカウントは未割当として拒否し、定期確認・削除の対象にする。
5. 同じ人が複数人の資格情報を共有せず、利用者の交代時は新しい個別アカウントを発行する。過去イベントの発生者UIDを新利用者へ再利用しない。

初期主担当の作成、招待の送付、未割当アカウントの確認、メールアドレス変更はBD-08の非技術者向け手順へ記載する。初期設定をFirebase Consoleだけの手作業へ依存させる範囲と、レビュー済みの設定補助手段を用意する範囲は詳細設計で決めるが、サービスアカウント鍵をクライアントへ配布しない。

## BD-04-03 役割、範囲、有効期間

| 役割 | 範囲 | 主な責務 | 制約 |
|---|---|---|---|
| 主担当 | 公演単位。各公演に有効な1人を必須とする | 公演全体、役割、締め、削除希望受付、運用判断の最終責任 | 後任の主担当が有効になる前に自分を停止できない |
| 代理管理者 | 公演単位。0人以上 | 主担当不在時の管理、一般・一時役割、準備、出力、削除の代行 | 主担当の変更、Firebase所有者・課金判断者の指定を行えない |
| 一時管理者 | 公演単位。開始・終了時刻を必須とする | 当日必要な手動受付、例外、訂正、座席・QR、連絡、競合確認 | 役割管理、任意項目、ZIP一括出力、完全削除、締め、課金判断を行えない。終了時刻で自動失効 |
| 一般受付担当者 | 公演単位 | QR受付、例外一覧・対応状態、未承認例外の仮登録、連絡確認 | 手動受付確定、正式編集・削除・訂正、管理出力、役割操作を行えない |

「管理者」は業務操作によって範囲が異なる。手動受付、例外承認、訂正、スタッフ連絡等の当日管理は主担当・代理管理者・有効な一時管理者を含む。任意項目、ZIP一括出力、完全削除、締め、役割管理等、要件で主担当・代理管理者を明示した操作は一時管理者へ広げない。

役割割当には、環境ID、公演ID、UID、役割、有効開始、有効終了、有効状態、付与者、付与時刻、停止者、停止時刻、理由、版を持たせる。現在状態を直接上書きする場合も、付与・変更・停止の監査イベントを別に追記する。

Firebaseプロジェクト所有者および公演中の課金判断者は、アプリ内役割と別の環境運用責務である。環境初期設定時に、実際にFirebaseプロジェクトを作成した主担当または代理管理者1人を課金判断者として指定し、開催前にFirebase Console上の実際の所有者と一致することを手動確認する。クライアントアプリはGoogle Cloud IAM所有者情報を権限判定に使用せず、課金を実行しない。

## BD-04-05 データ配布とサーバー側拒否

| データ区分 | 一般受付 | 一時管理者 | 代理・主担当 | サーバー側の境界 |
|---|---|---|---|---|
| 公演・座席・QR照合用データ | 当日必要分 | 必要分 | 全管理範囲 | 公演ID、役割割当、承認端末を検証 |
| 氏名・受付状態 | 例外対応等の必要最小限 | 当日管理に必要な範囲 | 管理範囲 | 一覧・単一取得の両方を同じ文書境界で制限 |
| 任意項目定義・値 | 配布しない | 配布しない | 許可済み端末へ暗号化値 | 通常データと別文書・別経路にし、文書単位で読取り拒否 |
| 役割・招待 | 自分の有効役割だけ | 自分と当日端末状態 | 公演内の管理範囲 | UID、役割、変更可能フィールドを検証 |
| 監査イベント | 自分に必要な結果 | 当日業務範囲 | 管理範囲 | 作成専用とし、既存イベント更新・削除を拒否 |
| 出力・削除記録 | 自分の操作結果 | 許可操作の結果 | 管理範囲 | 生成物本体、削除済み個人情報、秘密情報を含めない |

Cloud Firestore Security Rulesは文書の一部項目だけを隠せないため、任意項目、認証・役割管理監査等は、権限の弱い利用者が読める文書へ同居させない。クエリーはSecurity Rulesによる事後フィルターではないため、公演・データ区分・役割に一致する取得経路と条件を設計し、許可外文書を含み得るクエリーを発行しない。

環境IDと公演IDを画面入力だけから信頼せず、要求パス、既存文書、役割割当、書込み後文書の一致を検証する。クライアントは管理SDKやサービスアカウントを使用しない。将来サーバー処理を追加する場合は、Security Rulesを迂回する管理SDKのIAM、監査、費用、秘密情報を新しい設計・ADRで扱う。

## BD-04-06 セッションと再認証

Firebase IDトークンは約1時間で更新され、更新トークンは長期間利用できるため、IDトークンの有効期限だけを業務セッション終了とみなさない。アプリケーションは次の二層で管理する。

| 状況 | Authenticationの保持 | アプリ側の扱い |
|---|---|---|
| 通常の管理用PC | ブラウザーを閉じるまでのセッション保持を既定とする | 再開時にオンラインで本人・役割・端末を再確認 |
| 当日受付用の準備済み端末 | 利用者が明示的に端末準備を完了した時だけローカル保持を許可 | BD-04-07の期限付きオフライン許可と組み合わせる |
| 共有・信頼できない端末 | ローカル保持を許可しない | ブラウザー終了またはログアウトで認証状態を破棄 |
| ログアウト | Firebaseからサインアウト | オフライン許可、復号済み値、選択中公演、端末内認証関連状態を削除 |
| 締め済み | 対象公演のセッションを終了 | 送信完了確認後、認証状態と公演データを自動削除し次公演開始を拒否 |

アプリ起動、画面復帰、オンライン復旧、公演切替、高影響操作の前に、現在利用者、メール確認、役割、端末、公演状態を再取得する。オンライン中の最終許可は毎回Security Rulesが行うため、画面の再取得間隔だけで権限の安全性を決めない。

役割変更、完全削除、任意項目出力、ZIP出力、締め、主担当引継ぎ等の高影響操作はオンライン限定とし、最後の本人再認証から15分以内であることを要求する。期限を超えた場合はパスワード再入力等で再認証し、操作内容を保持したまま確認へ戻す。

## BD-04-07 端末準備とオフライン許可

完全オフライン開始には、次をオンラインで1回の準備結果として確認する。

1. メール確認済みの個別利用者で再認証できている。
2. 対象環境・公演が一致し、公演が受付準備可能である。
3. 利用者の役割が有効で、一般受付、一時管理者、代理、主担当のいずれかである。
4. 端末登録が同じUID・公演へ承認済みで、停止・削除対象でない。
5. 当日必要な許可済みデータ、PWA資産、版、端末時刻を取得・検証済みである。
6. オフライン許可の開始、終了、役割版、端末ID、公演IDを端末へ保存した。

オフライン許可の終了は、発行から24時間後、事前に設定した当日運用終了予定時刻、役割の有効終了のうち最も早い時刻とする。一時管理者は必ず当日運用終了予定時刻までに失効する。公演延長時は、期限前に主担当または代理管理者がオンラインで終了予定を変更し、各端末が再準備を完了した場合だけ延長する。期限切れ後に端末時刻を戻して継続させず、オンライン再確認または紙運用へ切り替える。

| オフラインで許可 | オフラインで拒否 |
|---|---|
| QR受付、再読取り理由、例外仮登録・対応状態、管理者の手動受付・訂正・競合確認、手動座席・QR対応、スタッフ連絡、必要最小限の閲覧 | アカウント・役割・端末の付与変更、主担当引継ぎ、任意項目取得、CSV・PDF・ZIP出力、完全削除、締め、Firebase上限時の課金判断、端末再準備 |

オフラインイベントは発生時のUID、役割、役割版、端末ID、許可期限をスナップショットとして持つ。復旧後は現在の役割と端末状態を再確認する。権限停止後または許可期限外のイベントを通常イベントとして自動受理せず、BD-03の`拒否`状態に残し、管理者が端末、紙記録、発生時刻、停止理由を確認する。

## BD-04-08 停止、紛失、期限切れ、ログアウト

| 契機 | オンライン時 | 完全オフライン時 | 復旧時 |
|---|---|---|---|
| 利用者停止 | 役割割当を無効化し、Rulesが以後の要求を拒否 | 端末へ即時通知できない | 同期前に停止を取得し画面をロック。未送信を管理者確認へ回す |
| 紛失端末停止 | 対象端末登録を無効化し、同じ利用者の他端末は維持可能 | 紛失端末のローカル利用を遠隔停止・物理削除できない | 対象端末IDの要求を拒否し、公演データ削除を要求する |
| 一時管理者期限切れ | 時刻条件によりRulesが拒否 | 事前保存した許可期限で管理操作を停止 | 一般受付等の別役割がなければロックし、データ削除へ進む |
| パスワード再設定・漏えい | Firebaseで再設定し、必要に応じてアカウント無効化・更新トークン失効を行う | 既存オフライン許可は期限まで残り得る | 役割・端末停止を優先してRulesで拒否し、再認証を要求する |
| ログアウト | サインアウトと端末内認証関連状態削除 | 未送信がある場合は先に警告し、イベント自体は失わない | 再ログイン・権限確認後に送信または管理者確認 |
| 締め | 新規業務操作を停止し、送信完了確認後に削除 | 締め受信までは継続可能という限界がある | 締めを取得し、送信確認、サインアウト、対象データ削除を行う |

権限停止は、Authenticationアカウント停止だけに依存せず、公演役割と端末の`active`状態をSecurity Rulesで確認する。これにより、最大約1時間残り得る既存IDトークンや長期更新トークンがあっても、オンライン業務データ要求を拒否できる。認証情報漏えい時はFirebase Console等の所有者手順でアカウント無効化・トークン失効も行う。

## BD-04-09 パスワード、失敗、再設定

- パスワードは12文字以上を必須とし、氏名、メールアドレス、公演名等の推測しやすい値を避けるよう案内する。パスワードを表示、ログ、監査、Firestoreへ保存しない。
- Firebase Authenticationのパスワードポリシーを必須モードで設定し、メールアドレス列挙保護を有効にする。ログイン、登録、再設定の失敗表示は、登録有無を推測できない共通表現にする。
- 同一ブラウザーで5回連続失敗した場合は15分間入力を停止し、Firebase側の不正試行制限と併用する。端末内の失敗回数はログイン成功または再設定後の正常ログインでリセットし、メールアドレス全文や入力内容を監査へ記録しない。
- パスワード再設定はFirebaseの期限付き再設定メールを使用し、主担当・代理管理者が仮パスワードを閲覧・発行しない。再設定要求は登録有無にかかわらず同じ完了案内を表示する。
- メールアドレス変更、パスワード変更、漏えい疑いでは再認証を必須とし、変更後に他端末のセッション、役割、端末一覧を確認する。

具体的なパスワード構成、メールテンプレート、送信上限、Firebase Console操作は、実装開始前に公式仕様と費用0円条件を再確認してBD-05・BD-08・BD-09へ反映する。

## BD-04-10 監査と高影響操作

次の操作は、成功・拒否・失敗について、対象公演、操作種別、UID、役割、端末ID、時刻、理由、結果、関連対象IDを、個人情報と秘密情報を最小化して監査イベントへ記録する。

- 招待、役割付与・変更・停止、主担当引継ぎ、端末承認・停止。
- ログイン成功、連続失敗による停止、再設定完了、ログアウト。パスワード、トークン、入力メール全文は記録しない。
- 手動受付、訂正、競合確認、QR再発行、出力、完全削除、締め。
- 権限拒否、別公演、期限切れ、停止済み端末、直接APIによる不正形式。
- Firebase上限時の課金判断者確認、紙・課金の選択、実施時刻、確認結果。支払情報は記録しない。

役割変更、削除、締め、主担当引継ぎには対象、影響、現在状態、実行後の状態を示す確認画面を設ける。主担当引継ぎは、後任のメール確認、受諾、有効端末を確認し、同一トランザクションで新主担当を有効化してから旧主担当を代理または停止へ変更する。主担当0人または2人の状態を許可しない。

## BD-04-11 Security Rulesへ渡す判定契約

Security Rulesはすべて拒否を初期値とし、各文書経路で少なくとも次を検証する。

1. `request.auth`が存在し、メール確認済みである。
2. 要求された環境・公演がパス、既存データ、書込み後データで一致する。
3. UIDに対応する役割割当が有効で、開始・終了時刻内、許可役割である。
4. 端末IDが同じUID・公演へ承認済みで、有効である。
5. 操作が作成・更新・削除のどれで、変更可能なフィールドと状態遷移が権限表に一致する。
6. 変更不能イベントは新規作成だけを許可し、イベントID、発生者UID、端末ID、役割版を要求と一致させる。
7. 高影響操作はオンライン、最近の再認証、必要な確認状態を要求する。
8. 別公演、役割外、期限切れ、停止済み、未対応版、余分なフィールドを拒否する。

Rulesが参照する文書数は公式上限内に収め、利用者、役割、端末、公演状態を無制限に連鎖参照しない。Rules参照も読取り使用量へ影響するため、費用・性能をBD-09で測定する。クエリー、単一取得、バッチ、トランザクション、直接SDK要求をそれぞれエミュレーターで許可・拒否試験する。

## BD-04-12 外部サービス交換境界と後続設計

業務層はFirebase固有の利用者オブジェクトやエラーコードではなく、次の共通境界を使用する。

| 境界 | 共通の入出力 | Firebase交換時の扱い |
|---|---|---|
| 本人認証 | 内部利用者ID、認証時刻、メール確認状態、再認証要否、失敗区分 | Authenticationのログイン、再設定、失効処理を交換する |
| セッション | 利用者ID、端末ID、開始・終了、オンライン状態 | トークン保存・更新方法を交換する |
| 権限判定 | 利用者、役割、端末、公演、操作、データ区分、時刻を受け許可・拒否理由を返す | Security Rulesと共有保存の実装を交換する |
| アカウント管理 | 招待、メール確認、停止、再設定、引継ぎの結果 | 管理API・Console手順を交換する |

変更不能イベント、役割種別、権限表、端末登録、監査項目はFirebaseから独立した版付き形式にする。移行時はパスワード、トークン、秘密情報を出力せず、UIDと内部利用者IDの対応、役割、端末、未送信、監査を移行する。新しい認証基盤では全利用者の本人確認と資格情報再設定を行い、旧・新基盤の併用期間、共通権限試験、切戻しを移行計画で承認する。代替認証を先行実装しない。

|---|---|

| BD-06 画面 | ログイン、招待、メール確認、再設定、役割・端末状態、期限切れ、オフライン許可、拒否、再認証、確認画面の操作見本 |
| BD-07 帳票 | 通常CSV、PDF、ZIP、任意項目選択出力の権限、出力記録、端末内一時生成 |
| BD-08 運用 | 初期主担当、招待、主担当引継ぎ、紛失・漏えい、端末回収、課金判断者確認、不要権限削除、Firebase交換時の再登録・切戻し手順 |

## 代替案、影響、残存リスク

### 採用しなかった主な代替案

| 代替案 | 採用しない理由 |
|---|---|
| 共有管理者・受付アカウント | 操作者を識別できず、停止、監査、端末紛失対応を個別に行えない |
| 役割をIDトークンのcustom claimsだけへ保持 | 公演単位・期限付きの変更を即時反映しにくく、トークン更新まで古い役割が残り得る |
| 画面でボタンを隠すだけ | 直接SDK・API要求、別公演識別子、改変要求を拒否できない |
| 全管理者へ同じ権限 | 一時管理者へ任意項目、完全削除、役割、締め、課金判断まで広がり、必要最小限にならない |
| 完全オフライン中も即時停止できるとみなす | 通信のない端末へ停止情報を届けられず、技術的に保証できない |

### 良い影響

- 操作者、役割、端末、公演を個別に追跡し、紛失端末だけを停止できる。
- 任意項目や役割管理データを一般受付・一時管理者へ配布せず、画面とサーバーの両方で最小権限を保てる。
- Firebase交換時も業務役割、権限表、監査形式を維持し、資格情報だけを安全に再設定できる。

### 注意が必要な影響と残存リスク

- 完全オフライン中は権限・端末停止、締め、パスワード変更を即時反映できない。最長24時間の許可期限、端末画面ロック、紛失連絡、紙切替が必要である。
- Firebase Authenticationの公開サインアップ自体を完全に招待制へできない構成では、未招待アカウントが作成され得る。ただし役割・端末がなければ業務データを拒否し、未割当アカウントを運用で確認・削除する。
- 最初の主担当作成とAuthentication利用者の無効化・トークン失効には環境所有者の管理操作が必要であり、非技術者向け手順と演習が必要である。
- ブラウザー保存領域を消去すると端末IDを復元できない。新端末として再承認し、旧端末を未確認・停止対象に残す。
- 15分の再認証、5回失敗・15分停止、24時間のオフライン許可は初期の安全側設定である。対象実機の操作性と当日運用をBD-06・BD-09で確認し、変更する場合は理由と影響を記録する。

## 公式情報

2026-09-16時点で、次のFirebase公式情報を設計根拠として確認した。

- [Firebase Authenticationのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions): IDトークンは約1時間、更新トークンは長期間有効であり、無効化・削除・主要なアカウント変更や管理操作による失効を扱える。
- [Cloud Firestore Security Rulesの条件](https://firebase.google.com/docs/firestore/security/rules-conditions): 認証、文書データ、他文書の参照による許可条件を記述できる一方、参照数上限と読取り使用量への影響がある。
- [Cloud Firestoreのフィールドアクセス制御](https://firebase.google.com/docs/firestore/security/rules-fields): 読取りは文書単位であり、同一文書の一部項目だけを隠せないため、機密度の異なるデータを別文書へ分離する必要がある。
- [Firebase Authenticationのパスワード認証](https://firebase.google.com/docs/auth/web/password-auth): パスワードポリシーとメールアドレス列挙保護を設定できる。

## 確認事項

**依頼者に確認してください**

- なし。承認済みの4役割と業務権限を維持し、一時管理者へ任意項目、役割管理、完全削除、締め、課金判断を広げていない。基本設計一式はBD-10で確認を依頼する。

**開発者が確認してください**

- 共有アカウントを使用せず、Authenticationの本人識別と公演単位の業務認可が分離されていることを確認してください。
- 4役割の許可・拒否・追加条件が要件と一致し、一般受付・一時管理者へ任意項目や高影響操作を広げていないことを確認してください。
- オフライン許可の期限と即時停止不能の限界、復旧後の拒否・管理者確認がBD-03と矛盾しないことを確認してください。
- Firebase交換時にパスワード・トークンを移行せず、内部利用者、役割、端末、監査を共通形式で移行して本人確認・資格情報再設定を行う境界を確認してください。
