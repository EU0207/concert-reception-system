## 結論

本番の本人認証には、ADR-001で採用した環境専用Firebase Authenticationのメールアドレス・パスワード方式を使用する。共有アカウント、匿名認証、端末共通暗証番号は使用しない。メール確認済みの個別利用者だけを業務利用者として扱い、AuthenticationのUIDと業務上の表示名・役割を分離する。

認証済みであることだけでは業務データへアクセスさせない。公演単位の役割割当と端末登録をFirestoreに保持し、Security Rulesがオンライン要求ごとに、利用者、メール確認、役割の有効状態、公演、端末、操作対象、期限を検証する。役割は主担当、代理管理者、一時管理者、一般受付担当者の4種類とし、明示的に許可していない読取り・書込みを既定で拒否する。

完全オフライン受付は、オンラインで本人、役割、端末、公演データ、期限を確認して発行した端末固有のオフライン許可が有効な場合だけ開始できる。固定24時間・48時間ではなく対象公演へ結び付け、会場に設定したタイムゾーンにおける公演翌日の23:59:59で自動失効させる。公演終了後は新規受付等を止めつつ、翌日中まで受付結果、未同期、競合、隔離記録の確認と同期を許可する。期限後も未同期記録を削除せず、通常画面をロックして同期・管理者確認・削除専用状態へ移す。オフライン中の端末停止は即時反映できないため、復旧後は通常の受付、同期、データ取得、オフライン再準備をサーバー側で拒否する。停止前または停止を知らない間に保存された未同期イベントは削除せず、停止端末専用の隔離領域へ全件送信し、管理者が採否を判断するまで正式な受付へ反映しない。

## BD-04-01 認証方式と識別子

| 項目 | 方針 |
|---|---|
| 認証基盤 | 環境ごとに分離したFirebase Authenticationを使用し、他環境と利用者を共有しない |
| サインイン方式 | メールアドレス・パスワード。メールアドレス確認済みであることを業務アクセスの条件とする |
| 利用者識別子 | Firebase UIDを内部参照に用いる。メールアドレス、表示名、役割名を主キーにしない |
| 業務利用者 | UIDを参照する環境内利用者情報と、公演単位の役割割当を分離する |
| 端末識別子 | ブラウザー保存領域ごとに不透明な端末IDを発行し、利用者、公演、準備状態、端末状態へ結び付ける。端末の機種名や個人情報をIDにしない。ブラウザーデータ消去等で端末IDを失った場合は新しい端末として扱い、自動承認せず管理者承認を必須とする |
| 本人確認情報 | パスワードの検証と保存はFirebase Authenticationへ任せ、アプリ独自に保存・暗号化しない。パスワードをFirestore、IndexedDB、ログ、監査、解析サービス、Git、GitHub、画面表示へ残さず、生のIDトークン・更新トークンもアプリ用データ、ログ、監査、解析サービス、Git、GitHub、画面へ複製しない。Firebase SDKがブラウザー内で管理する認証セッションをアプリから取得・復号・一覧表示できる管理機能にしない |

メール・パスワード方式は、POC-004で検証済みであり、個別アカウント、再設定、費用0円、対象規模約10人を追加の外部認証サービスなしで満たせるため採用する。共有パスワードは個人を識別できないため採用しない。Google等の外部プロバイダーは、依頼者・スタッフのアカウント条件と同意画面を増やすため初期採用しない。

## BD-04-02 アカウント登録と初期設定

1. Firebaseプロジェクト所有者は、本番環境の初期設定手順で最初の主担当アカウントを作成し、メール確認と初期主担当割当を行う。初期主担当が存在しない状態で、最初にアクセスした利用者が自動的に主担当になる方式は採用しない。
2. 主担当または代理管理者は、スタッフのメールアドレス、公演、予定役割、有効期限を指定して1回限りの招待を作成する。招待は推測困難なID、有効期限、使用状態を持ち、一覧の閲覧を主担当・代理管理者へ限定する。
3. 招待されたスタッフは自分の個別アカウントを作成または既存アカウントでサインインし、メール確認後に招待を受諾する。招待メールとサインインメールが一致しない場合は役割を付与しない。
4. Firebase Authentication上にアカウントが存在しても、有効な役割割当と承認済み端末がなければ業務データを取得できない。招待なしで作成されたアカウントは未割当として拒否し、定期確認・削除の対象にする。
5. 同じ人が複数人の資格情報を共有せず、利用者の交代時は新しい個別アカウントを発行する。過去イベントの発生者UIDを新利用者へ再利用しない。

初期主担当の作成、招待の送付、未割当アカウントの確認、メールアドレス変更はBD-08の非技術者向け手順へ記載する。初期設定をFirebase Consoleだけの手作業へ依存させる範囲と、レビュー済みの設定補助手段を用意する範囲は詳細設計で決めるが、サービスアカウント鍵をクライアントへ配布しない。

## BD-04-03 役割、範囲、有効期間

| 役割 | 範囲 | 主な責務 | 制約 |
|---|---|---|---|
| 主担当 | 公演単位。各公演に有効な1人を必須とする | 公演全体、役割、締め、削除希望受付、運用判断の最終責任 | 後任の主担当が有効になる前に自分を停止できない |
| 代理管理者 | 公演単位。0人以上 | 主担当不在時の管理、一般・一時役割、準備、出力、削除の代行 | 主担当の変更、Firebase所有者・課金判断者の指定を行えない |
| 一時管理者 | 公演単位。開始・終了時刻を必須とする | 当日必要な手動受付、例外、訂正、座席・QR、連絡、競合確認 | 役割管理、任意項目、ZIP一括出力、完全削除、締め、課金判断を行えない。終了時刻で自動失効 |
| 一般受付担当者 | 公演単位 | QR受付、例外一覧・対応状態、未承認例外の仮登録、連絡確認 | 手動受付確定、正式編集・削除・訂正、管理出力、役割操作を行えない |

「管理者」は業務操作によって範囲が異なる。手動受付、例外承認、訂正、スタッフ連絡等の当日管理は主担当・代理管理者・有効な一時管理者を含む。任意項目、ZIP一括出力、完全削除、締め、役割管理等、要件で主担当・代理管理者を明示した操作は一時管理者へ広げない。

役割割当には、環境ID、公演ID、UID、役割、有効開始、有効終了、有効状態、付与者、付与時刻、停止者、停止時刻、理由、版を持たせる。現在状態を直接上書きする場合も、付与・変更・停止の監査イベントを別に追記する。

Firebaseプロジェクト所有者および公演中の課金判断者は、アプリ内役割と別の環境運用責務である。環境初期設定時に、実際にFirebaseプロジェクトを作成した主担当または代理管理者1人を課金判断者として指定し、開催前にFirebase Console上の実際の所有者と一致することを手動確認する。クライアントアプリはGoogle Cloud IAM所有者情報を権限判定に使用せず、課金を実行しない。

## BD-04-05 データ配布とサーバー側拒否

| データ区分 | 一般受付 | 一時管理者 | 代理・主担当 | サーバー側の境界 |
|---|---|---|---|---|
| 公演・座席・QR照合用データ | 当日必要分 | 必要分 | 全管理範囲 | 公演ID、役割割当、承認端末を検証 |
| 氏名・受付状態 | 例外対応等の必要最小限 | 当日管理に必要な範囲 | 管理範囲 | 一覧・単一取得の両方を同じ文書境界で制限 |
| 任意項目定義・値 | 配布しない | 配布しない | 許可済み端末へ暗号化値 | 通常データと別文書・別経路にし、文書単位で読取り拒否 |
| 役割・招待 | 自分の有効役割だけ | 自分と当日端末状態 | 公演内の管理範囲 | UID、役割、変更可能フィールドを検証 |
| 端末管理情報 | 自端末の必要最小限 | 自端末の必要最小限 | 公演内の全端末 | 利用者、端末ID、公演、役割、最終接続・同期時刻、未送信件数、端末状態を分離して許可 |
| 停止端末の隔離記録 | 閲覧不可 | 閲覧不可 | 対象公演の管理範囲 | 通常受付と別経路に保存し、採否判断前の通常状態反映を拒否 |
| 監査イベント | 自分に必要な結果 | 当日業務範囲 | 管理範囲 | 作成専用とし、既存イベント更新・削除を拒否 |
| 出力・削除記録 | 自分の操作結果 | 許可操作の結果 | 管理範囲 | 生成物本体、削除済み個人情報、秘密情報を含めない |

Cloud Firestore Security Rulesは文書の一部項目だけを隠せないため、任意項目、認証・役割管理監査等は、権限の弱い利用者が読める文書へ同居させない。クエリーはSecurity Rulesによる事後フィルターではないため、公演・データ区分・役割に一致する取得経路と条件を設計し、許可外文書を含み得るクエリーを発行しない。

環境IDと公演IDを画面入力だけから信頼せず、要求パス、既存文書、役割割当、書込み後文書の一致を検証する。クライアントは管理SDKやサービスアカウントを使用しない。将来サーバー処理を追加する場合は、Security Rulesを迂回する管理SDKのIAM、監査、費用、秘密情報を新しい設計・ADRで扱う。

## BD-04-06 セッションと再認証

Firebase IDトークンは約1時間で更新され、更新トークンは長期間利用できるため、IDトークンの有効期限だけを業務セッション終了とみなさない。アプリケーションは次の二層で管理する。

| 状況 | Authenticationの保持 | アプリ側の扱い |
|---|---|---|
| 通常の管理用PC | ブラウザーを閉じるまでのセッション保持を既定とする | 再開時にオンラインで本人・役割・端末を再確認 |
| 当日受付用の準備済み端末 | 利用者が明示的に端末準備を完了した時だけローカル保持を許可 | BD-04-07の期限付きオフライン許可と組み合わせる |
| 共有・信頼できない端末 | ローカル保持を許可しない | ブラウザー終了またはログアウトで認証状態を破棄 |
| ログアウト | Firebaseからサインアウト | 未同期記録がないこと、または停止端末では隔離領域への全件送信とサーバー受領確認が完了したことを確認してから、オフライン許可、復号済み値、選択中公演、端末内認証関連状態を削除する |
| 締め済み | 対象公演のセッションを終了 | 送信完了確認後、認証状態と公演データを自動削除し次公演開始を拒否 |

アプリ起動、画面復帰、オンライン復旧、公演切替、高影響操作の前に、現在利用者、メール確認、役割、端末、公演状態を再取得する。オンライン中の最終許可は毎回Security Rulesが行うため、画面の再取得間隔だけで権限の安全性を決めない。

役割変更、完全削除、任意項目出力、ZIP出力、締め、主担当引継ぎ等の高影響操作はオンライン限定とし、最後の本人再認証から15分以内であることを要求する。期限を超えた場合はパスワード再入力等で再認証し、操作内容を保持したまま確認へ戻す。

## BD-04-07 端末準備とオフライン許可

完全オフライン開始には、次をオンラインで1回の準備結果として確認する。

1. メール確認済みの個別利用者で再認証できている。
2. 対象環境・公演が一致し、公演が受付準備可能である。
3. 利用者の役割が有効で、一般受付、一時管理者、代理、主担当のいずれかである。
4. 端末登録が同じUID・公演へ承認済みで、端末状態が`有効`である。ブラウザーデータ消去等で新しい端末IDになった端末は、同じUIDで本人認証できても再承認するまで準備できない。
5. 当日必要な許可済みデータ、PWA資産、版、端末時刻を取得・検証済みである。
6. オフライン許可の開始、終了、役割版、端末ID、公演ID、会場タイムゾーンIDを端末へ保存した。

オフライン許可の終了は、対象公演日の翌日23:59:59を会場に設定したIANAタイムゾーンで解釈し、UTCの期限時刻へ変換して保持する。準備完了からの固定24時間・48時間では失効させず、数日前に準備した端末も同じ公演期限を使用する。会場タイムゾーン未設定、形式不正、公演日との組合せ不正では端末準備を完了させない。端末のローカルタイムゾーンや時刻変更で期限を延長できないよう、準備時に受け取った期限とオンライン時のサーバー時刻を使用する。

公演終了後から許可期限までは、新規受付と新たな訂正等の通常業務操作を止め、受付結果、未同期、競合、隔離記録の確認と同期だけを許可する。許可期限後は通常業務操作と通常画面をロックする。未同期がある場合はデータを自動削除せず、同期・管理者確認・削除専用画面へ移し、全件のサーバー受領確認後にログアウトと端末内公演データ削除を行う。この専用送信は期限切れ後の新規業務操作を許可するものではない。

| 公演別端末利用状態 | 開始条件 | 許可する処理 | 次の状態 |
|---|---|---|---|
| 準備済み | オンライン端末準備が完了 | 公演開始前の確認。受付開始条件成立後に通常業務 | 公演開始で`受付中` |
| 受付中 | 公演が受付可能で許可期限内 | 役割範囲内の受付、訂正、確認、同期 | 公演終了で`終了後確認期間` |
| 終了後確認期間 | 公演終了後かつ翌日23:59:59の期限到達前 | 受付結果、未同期、競合、隔離記録の確認と同期。新規受付・新たな訂正は不可 | 全件受領後に削除、または期限到達で`期限切れ` |
| 期限切れ | 公演翌日23:59:59を経過 | 通常画面をロック。未同期があれば同期・管理者確認・削除専用処理だけ | 全件受領後に`削除可能` |
| 削除可能 | 未同期0件かつサーバー全件受領確認済み | ログアウト、端末内認証・公演データ削除 | `削除完了` |
| 強制削除確認中 | 管理者が未同期ありの端末で手動削除を選択 | 件数、対象、復元不能の警告、再認証、理由入力、再確認だけ | 実行で`削除完了`、取消しで直前状態 |
| 削除完了 | ログアウトと端末内公演データ削除を確認済み | 個人情報を含まない削除完了報告 | 終了 |

| オフラインで許可 | オフラインで拒否 |
|---|---|
| QR受付、再読取り理由、例外仮登録・対応状態、管理者の手動受付・訂正・競合確認、手動座席・QR対応、スタッフ連絡、必要最小限の閲覧 | アカウント・役割・端末の付与変更、主担当引継ぎ、任意項目取得、CSV・PDF・ZIP出力、完全削除、締め、Firebase上限時の課金判断、端末再準備 |

オフラインイベントは発生時のUID、役割、役割版、端末ID、許可期限をスナップショットとして持つ。復旧後は現在の役割と端末状態を再確認する。停止済み端末のイベントを通常イベントとして自動受理せず、通常同期ではBD-03の`拒否`として扱う。ただし停止前または停止を知らないオフライン期間中に保存された未同期イベントは削除せず、BD-04-08の隔離送信専用経路で全件を管理者確認用領域へ送る。

## BD-04-08 停止、紛失、期限切れ、ログアウト

| 契機 | オンライン時 | 完全オフライン時 | 復旧時 |
|---|---|---|---|
| 利用者停止 | 役割割当を無効化し、Rulesが以後の要求を拒否 | 端末へ即時通知できない | 同期前に停止を取得し画面をロック。未送信を管理者確認へ回す |
| 紛失端末停止 | 対象端末IDを停止し、同じ利用者の別の承認済み端末は維持する | `停止待ち（オフライン）`とし、紛失端末のローカル利用を遠隔停止・物理削除できない | 新規操作をロックし、通常要求を拒否する。既存未同期記録を隔離送信し、全件受領後にサインアウト・削除へ進む |
| 公演別許可期限切れ | 時刻条件によりRulesが通常業務を拒否 | 事前保存した公演期限で通常業務を停止 | 未同期があれば同期・管理者確認・削除専用画面、なければログアウト・削除へ進む |
| 認証情報漏えい疑い | Firebaseでパスワード再設定、更新トークン失効、利用者アカウント無効化を必要性に応じて行い、当該利用者の端末も停止する | 既存オフライン許可は期限まで残り得る | 役割・端末停止をRulesで確認し、本人確認後に必要な範囲だけ再開する |
| ログアウト | 未送信0件を確認後にサインアウトと端末内認証関連状態を削除 | 未送信がある場合は完了扱いにせず、イベントと送信に必要な状態を保持する | 停止端末は隔離領域への全件受領確認後に限り、サインアウトと端末内認証・公演データ削除を完了する |
| 締め | 新規業務操作を停止し、送信完了確認後に削除 | 締め受信までは継続可能という限界がある | 締めを取得し、送信確認、サインアウト、対象データ削除を行う |

権限停止は、Authenticationアカウント停止だけに依存せず、公演役割と端末の`active`状態をSecurity Rulesで確認する。これにより、最大約1時間残り得る既存IDトークンや長期更新トークンがあっても、オンライン業務データ要求を拒否できる。利用者アカウント全体の無効化と更新トークン失効は、パスワードやトークン等の認証情報そのものの漏えいが疑われる場合に限る。端末紛失だけを理由にFirebase AuthenticationアカウントやGoogleアカウント全体を停止しない。

紛失時の操作は利用者全体への単なる強制ログアウトではなく、端末ID単位の端末停止とする。ブラウザーに保存されたパスワードはアプリから削除できないが、停止された端末は、そのパスワードで本人認証へ成功しても、Security Rules等のサーバー側認可により通常の受付、同期、データ取得、オフライン再準備を拒否する。例外は、停止前または停止を知らない間に端末へ保存済みだった未同期イベントを隔離領域へ送るための作成専用経路だけとする。同じ利用者の別の承認済み端末は個別に停止されない限り継続利用できる。

### 端末状態と遷移

| 端末状態 | 意味 | 許可する処理 | 次の状態 |
|---|---|---|---|
| 有効 | 管理者承認済みで通常利用可能 | 役割範囲内の受付、通常同期、データ取得、オフライン準備 | 停止指示で`停止待ち（オフライン）` |
| 停止待ち（オフライン） | サーバーに停止指示があるが端末の検知を未確認 | サーバーは通常要求を拒否。端末が未検知の間は技術的にローカル操作が残り得る | 端末の復旧・停止取得で`停止検知済み` |
| 停止検知済み | 端末が停止を取得し、新規操作をロック済み | 既存未同期イベントの隔離送信と受領確認だけ | 全件受領後にサインアウト・端末内削除を実行し、隔離記録があれば`隔離記録確認待ち`。なければ`ログアウト・削除完了` |
| 隔離記録確認待ち | 隔離領域が全件を受領し、管理者の採否判断が未完了。サインアウト・端末内削除の完了有無は別項目で表示する | 管理者による紙記録等との照合、採用、重複、誤操作、不正使用疑いの判断 | 照合完了かつ端末内削除確認後`ログアウト・削除完了` |
| ログアウト・削除完了 | 隔離領域の全件受領、必要な照合、サインアウト、端末内認証・公演データ削除を確認済み | 監査閲覧と停止解除の検討だけ | 管理者が再利用条件を満たした場合`停止解除` |
| 停止解除 | 管理者が再利用を許可したが、オンライン端末準備は未完了 | 本人認証とオンライン端末準備だけ。通常受付は不可 | 準備と再承認完了で`有効` |

端末状態とは別に、未送信件数、隔離領域の受領済み件数、照合状態、サインアウト・端末内削除確認を保持する。隔離送信に失敗した端末はイベントを削除せず再送専用状態に留め、管理画面では`停止済み・未同期あり`と表示する。サーバーから当該端末ID・公演IDの最終連番まで全件受領した確認を得るまでは、サインアウト、認証情報削除、公演データ削除、`ログアウト・削除完了`への遷移を行わない。全件受領後はサインアウトと端末内認証・公演データ削除を実行するが、隔離記録の照合が残る間は主状態を`隔離記録確認待ち`とし、削除完了を併記する。

隔離領域は通常受付イベントと物理的または論理的に分離し、隔離イベントID、利用者、端末ID、公演ID、停止指示時刻、端末上の発生時刻、端末連番、サーバー到着時刻、停止前の最終同期時刻、受領結果、採否、判断者、判断時刻、判断理由を保持する。管理画面では`停止後に到着した記録`として目立たせる。管理者は紙記録等と照合して採用、重複、誤操作、不正使用の疑いを判断し、採用時も元の隔離記録を変更せず、正式受付へ反映する別の管理者イベントを作成する。

管理者の端末管理画面には、利用者、端末ID、対象公演、役割、最終接続時刻、最終同期時刻、未送信件数、端末状態、停止指示時刻、隔離受領・照合・削除状況を表示する。発見・回収した端末を再利用する場合は、本人、端末、未送信・隔離記録、端末内削除状況を管理者が確認してから停止を解除し、本人がオンラインで再認証して端末準備をやり直す。停止端末のブラウザーデータが消去され新しい端末IDになっても自動承認せず、旧端末を停止記録に残したまま新規端末として管理者承認を要求する。

公演終了後は主担当・代理管理者が端末内公演データを手動削除できる。未同期データがある場合は、件数、対象、公演、削除すると復元できないことを明示し、一般受付担当者と一時管理者には実行権限を与えない。未同期を残した強制削除は管理者限定の高影響操作とし、オンラインでの本人再認証、理由入力、影響の再確認を必須とする。実行時は担当者UID、役割、端末ID、公演ID、未同期件数、理由、サーバー時刻、結果を監査へ記録し、管理画面へ復元不能な未受領件数を残す。オフラインでは強制削除を許可しない。強制削除は全件受領確認や現行の締め条件を満たした扱いにせず、受領不能記録を残したまま締める必要が生じた場合はBD-08またはBD-10で依頼者判断へ戻す。

端末が起動・接続されない場合は遠隔物理削除を完了扱いにせず、公演別許可だけを失効させて管理画面へ未確認として残す。次回起動時は通常利用を禁止し、未同期があれば同期・管理者確認へ、全件受領済みならログアウト・削除へ誘導する。

## BD-04-09 パスワード、失敗、再設定

- パスワードはFirebase Authenticationの画面・SDKから安全な通信で認証処理へ渡し、アプリ独自の保存、暗号化、ハッシュ化、復号、一覧表示を行わない。Firebase SDKが返す認証結果だけを利用し、パスワード本体をFirestore、IndexedDB、ログ、監査記録、解析サービス、Git、GitHub、画面へ残さない。
- パスワードは12文字以上を必須とし、氏名、メールアドレス、公演名等の推測しやすい値を避けるよう案内する。パスワードや生のトークンを取得・復号・一覧表示できる管理機能を作らない。
- Firebase Authenticationのパスワードポリシーを必須モードで設定し、メールアドレス列挙保護を有効にする。ログイン、登録、再設定の失敗表示は、登録有無を推測できない共通表現にする。
- 同一ブラウザーで5回連続失敗した場合は15分間入力を停止し、Firebase側の不正試行制限と併用する。端末内の失敗回数はログイン成功または再設定後の正常ログインでリセットし、失敗時もパスワード、入力メールアドレス全文、その他の入力内容をログ、監査、解析サービスへ記録しない。
- パスワード再設定はFirebaseの期限付き再設定メールを使用し、主担当・代理管理者が仮パスワードを閲覧・発行しない。再設定要求は登録有無にかかわらず同じ完了案内を表示する。
- メールアドレス変更、パスワード変更、漏えい疑いでは再認証を必須とし、変更後に他端末のセッション、役割、端末一覧を確認する。認証情報漏えいが疑われる場合は、影響に応じてFirebaseの更新トークン失効、利用者アカウント無効化、当該利用者の端末停止を行う。端末紛失だけの場合は対象端末IDだけを停止する。

### Git・GitHubへ持ち込まない情報

実在する氏名、メールアドレス、電話番号、住所、受付情報は、機密度の認識にかかわらずGit・GitHubへコミットしない。サンプル、画面見本、試験、ログ例には明確な架空データだけを使用し、例示用メールアドレスのドメインは`example.com`とする。

`.env`、秘密鍵、サービスアカウント等の資格情報、認証済みブラウザー状態、依頼者用Firebase接続設定、実データファイルはGit管理対象外とする。プロジェクトルールと`.gitignore`は予防の一部であり、誤コミットを完全には防げない。BD-05で秘密情報スキャン、禁止ファイル検査、PRチェックリスト、ログ・エラー・解析情報のマスキング方針を設計し、自動化は基本設計承認後の適切な実装工程で導入する。

パスワード、トークン、秘密鍵等をGitHubへ送信した場合は、ファイル削除だけで対応完了としない。該当資格情報を直ちに失効・再発行し、リポジトリ履歴、派生ブランチ、Pull Request、成果物、ログ、端末キャッシュへの対応と影響確認を行い、事故対応記録を残す。具体的な連絡、履歴処理、再発防止の手順はBD-05・BD-08で定める。

具体的なパスワード構成、メールテンプレート、送信上限、Firebase Console操作は、実装開始前に公式仕様と費用0円条件を再確認してBD-05・BD-08・BD-09へ反映する。

## BD-04-10 監査と高影響操作

次の操作は、成功・拒否・失敗について、対象公演、操作種別、UID、役割、端末ID、時刻、理由、結果、関連対象IDを、個人情報と秘密情報を最小化して監査イベントへ記録する。

- 招待、役割付与・変更・停止、主担当引継ぎ、端末承認・停止・解除、端末状態遷移。
- ログイン成功、連続失敗による停止、再設定完了、ログアウト。パスワード、トークン、入力メール全文は記録しない。
- 手動受付、訂正、競合確認、QR再発行、出力、完全削除、締め。
- 公演終了後の端末内公演データ削除、未同期を残す強制削除の警告確認・実行・取消し。
- 権限拒否、別公演、期限切れ、停止済み端末、直接APIによる不正形式。
- 隔離送信の開始・再送・全件受領、サインアウト・端末内削除、隔離記録の採用・重複・誤操作・不正使用疑いの判断。
- Firebase上限時の課金判断者確認、紙・課金の選択、実施時刻、確認結果。支払情報は記録しない。

役割変更、削除、締め、主担当引継ぎには対象、影響、現在状態、実行後の状態を示す確認画面を設ける。主担当引継ぎは、後任のメール確認、受諾、有効端末を確認し、同一トランザクションで新主担当を有効化してから旧主担当を代理または停止へ変更する。主担当0人または2人の状態を許可しない。

## BD-04-11 Security Rulesへ渡す判定契約

Security Rulesはすべて拒否を初期値とし、各文書経路で少なくとも次を検証する。

1. `request.auth`が存在し、メール確認済みである。
2. 要求された環境・公演がパス、既存データ、書込み後データで一致する。
3. UIDに対応する役割割当が有効で、開始・終了時刻内、許可役割である。
4. 端末IDが同じUID・公演へ承認済みで、有効である。
5. 操作が作成・更新・削除のどれで、変更可能なフィールドと状態遷移が権限表に一致する。
6. 変更不能イベントは新規作成だけを許可し、イベントID、発生者UID、端末ID、役割版を要求と一致させる。
7. 高影響操作はオンライン、最近の再認証、必要な確認状態を要求する。
8. 会場タイムゾーンから算出した公演期限後の新規受付・訂正等、別公演、役割外、停止済み、未対応版、余分なフィールドを拒否する。

公演期限後は通常データの新規作成・訂正を拒否する一方、期限前に端末保存済みの未同期イベントを送る専用経路、受領確認、競合・隔離記録の管理者確認、削除完了報告だけを許可する。未同期を残す強制削除の監査書込みは、主担当・代理管理者、オンライン再認証、対象端末・公演、理由、未同期件数の整合を検証する。

停止済み端末には通常データ経路を一切許可しない。隔離送信専用経路だけは、認証済みUID、停止対象の端末ID・公演ID、停止指示、端末連番、イベントIDと保存済みイベント内容の整合を検証した作成専用要求として許可し、既存隔離記録の更新・削除、通常受付への書込み、通常データの読取りを拒否する。隔離送信の認可は端末停止を解除せず、同じ利用者の別端末の状態にも影響させない。

Rulesが参照する文書数は公式上限内に収め、利用者、役割、端末、公演状態を無制限に連鎖参照しない。Rules参照も読取り使用量へ影響するため、費用・性能をBD-09で測定する。クエリー、単一取得、バッチ、トランザクション、直接SDK要求をそれぞれエミュレーターで許可・拒否試験する。

## 代替案、影響、残存リスク

### 採用しなかった主な代替案

| 代替案 | 採用しない理由 |
|---|---|
| 共有管理者・受付アカウント | 操作者を識別できず、停止、監査、端末紛失対応を個別に行えない |
| 役割をIDトークンのcustom claimsだけへ保持 | 公演単位・期限付きの変更を即時反映しにくく、トークン更新まで古い役割が残り得る |
| 画面でボタンを隠すだけ | 直接SDK・API要求、別公演識別子、改変要求を拒否できない |
| 全管理者へ同じ権限 | 一時管理者へ任意項目、完全削除、役割、締め、課金判断まで広がり、必要最小限にならない |
| 完全オフライン中も即時停止できるとみなす | 通信のない端末へ停止情報を届けられず、技術的に保証できない |

### 良い影響

- 操作者、役割、端末、公演を個別に追跡し、紛失端末だけを停止できる。
- 任意項目や役割管理データを一般受付・一時管理者へ配布せず、画面とサーバーの両方で最小権限を保てる。
- Firebase交換時も業務役割、権限表、監査形式を維持し、資格情報だけを安全に再設定できる。

### 注意が必要な影響と残存リスク

- 完全オフライン中は権限・端末停止、締め、パスワード変更を即時反映できない。会場タイムゾーンの公演翌日23:59:59という許可期限、端末画面ロック、紛失連絡、紙切替が必要である。
- Firebase Authenticationの公開サインアップ自体を完全に招待制へできない構成では、未招待アカウントが作成され得る。ただし役割・端末がなければ業務データを拒否し、未割当アカウントを運用で確認・削除する。
- 最初の主担当作成とAuthentication利用者の無効化・トークン失効には環境所有者の管理操作が必要であり、非技術者向け手順と演習が必要である。
- ブラウザー保存領域を消去すると端末IDを復元できない。停止回避として自動承認せず、新端末として再承認し、旧端末を停止記録に残す。消去前の未同期記録は復元できないため、回収時は隔離受領完了前にブラウザーデータを消去しない。
- 15分の再認証と5回失敗・15分停止は初期の安全側設定である。オフライン許可は固定24時間・48時間を採用せず、公演翌日23:59:59までとする。対象実機の操作性と境界時刻をBD-06・BD-09で確認し、変更する場合は理由と影響を記録する。

## 公式情報

2026-09-16時点で、次のFirebase公式情報を設計根拠として確認した。

- [Firebase Authenticationのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions): IDトークンは約1時間、更新トークンは長期間有効であり、無効化・削除・主要なアカウント変更や管理操作による失効を扱える。
- [Cloud Firestore Security Rulesの条件](https://firebase.google.com/docs/firestore/security/rules-conditions): 認証、文書データ、他文書の参照による許可条件を記述できる一方、参照数上限と読取り使用量への影響がある。
- [Cloud Firestoreのフィールドアクセス制御](https://firebase.google.com/docs/firestore/security/rules-fields): 読取りは文書単位であり、同一文書の一部項目だけを隠せないため、機密度の異なるデータを別文書へ分離する必要がある。
- [Firebase Authenticationのパスワード認証](https://firebase.google.com/docs/auth/web/password-auth): パスワードポリシーとメールアドレス列挙保護を設定できる。
