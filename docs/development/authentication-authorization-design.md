## 結論

本番の本人認証にはADR-001で採用した環境専用Firebase Authenticationを使用する。[ADR-003](decisions/ADR-003-role-based-auth-providers.md)と`CONF-047`により、主担当・代理管理者は各自のGoogleアカウント、公演限定スタッフである一般受付担当者・臨時管理者は各自のメールアドレス・短期パスワードで認証する。共有アカウント、共有パスワード、匿名認証、端末共通暗証番号は使用しない。メール確認済みまたはGoogleで本人確認済みの個別利用者だけを業務利用者として扱い、AuthenticationのUIDと業務上の表示名・役割を分離する。

認証済みであることだけでは業務データへアクセスさせない。公演単位の役割割当と端末登録をFirestoreに保持し、Security Rulesがオンライン要求ごとに、利用者、メール確認、役割の有効状態、公演、端末、操作対象、期限を検証する。役割は主担当、代理管理者、臨時管理者、一般受付担当者の4種類とし、明示的に許可していない読取り・書込みを既定で拒否する。

同じ端末へ複数公演を準備できるが、役割割当、端末許可、オフライン許可は公演ごとに判定する。公演シリーズは認可条件に使用しない。1公演の停止、締め、削除は、同じ端末に準備済みの別公演へ自動的に適用しない。

完全オフライン受付は、端末固有のオフライン許可が有効で、最後にオンライン確認した公演状態が`当日運用中`の場合だけ開始できる。許可発行時には、本人、役割、端末、公演データ、期限を確認する。固定24時間・48時間ではなく対象公演へ結び付け、会場に設定したタイムゾーンにおける公演翌日の23:59:59で自動失効させる。公演終了後は新規受付等を止めつつ、翌日中まで受付結果、未同期、競合、隔離記録の確認と同期を許可する。期限後も未同期記録を削除せず、通常画面をロックして同期・管理者確認・削除専用状態へ移す。オフライン中の端末停止は即時反映できないため、オンライン接続・回線復旧時は通常操作より先にサーバーの端末状態を確認する。停止済みなら通常画面での復号・閲覧、新規受付、通常同期、データ取得、オフライン再準備を拒否する。端末停止は解除可能な一時ロックであり、PWA、会場画像、座席表、準備済み公演データ、非抽出CryptoKey、未同期記録を削除しない。停止前または停止を知らない間に保存された未同期イベントは画面表示を伴わない内部処理で隔離領域へ送り、管理者が採否を判断するまで正式な受付へ反映しない。端末廃止・データ削除は管理者が明示的に選ぶ別の高影響操作とする。

## BD-04-01 認証方式と識別子

| 項目 | 方針 |
|---|---|
| 認証基盤 | 環境ごとに分離したFirebase Authenticationを使用し、他環境と利用者を共有しない |
| 公演限定スタッフのサインイン | 一般受付担当者・臨時管理者は個別メールアドレス・パスワード。メール確認済みであることを業務アクセスの条件とする |
| 初期主担当のサインイン | Firebaseプロジェクト初期設定時に本人と2段階認証有効化を確認したGoogleアカウントを使用し、Googleプロバイダーで得たFirebase UIDを明示的に割り当てる |
| 代理管理者のサインイン | ADR-003により各自のGoogleログインを採用する。UID明示割当、同意画面、アカウント復旧、既存メール・パスワードアカウントとのリンクは実装時に架空アカウントで検証する |
| 利用者識別子 | Firebase UIDを内部参照に用いる。メールアドレス、表示名、役割名を主キーにしない |
| 業務利用者 | UIDを参照する環境内利用者情報と、公演単位の役割割当を分離する |
| 端末識別子 | ブラウザー保存領域ごとに不透明な端末IDを発行し、利用者、公演、準備状態、端末状態へ結び付ける。端末の機種名や個人情報をIDにしない。ブラウザーデータ消去等で端末IDを失った場合は新しい端末として扱い、自動承認せず管理者承認を必須とする |
| 本人確認情報 | パスワードの検証と保存はFirebase Authenticationへ任せ、アプリ独自に保存・暗号化しない。パスワードをFirestore、IndexedDB、ログ、監査、解析サービス、Git、GitHub、画面表示へ残さず、生のIDトークン・更新トークンもアプリ用データ、ログ、監査、解析サービス、Git、GitHub、画面へ複製しない。Firebase SDKがブラウザー内で管理する認証セッションをアプリから取得・復号・一覧表示できる管理機能にしない |

メール・パスワード方式はPOC-004で検証済みであり、公演限定スタッフの個別アカウント、短期利用、再設定を追加の外部認証サービスなしで満たせるため採用する。共有パスワードは個人を識別できず、漏えい・停止・監査の範囲も広がるため採用しない。主担当・代理管理者のGoogleログインはADR-003で採用した。実環境・対象実機の動作と無料枠内での運用は後続試験で確認する。

## BD-04-02 アカウント登録と初期設定

1. Firebaseプロジェクト所有者は、本番環境の初期設定手順で、主担当本人のGoogleアカウントとGoogleアカウント側の2段階認証有効化を確認し、Googleログイン後に発行されたFirebase UIDを記録する。対象公演の初期主担当役割を、そのUIDと公演IDの組合せへ明示的に割り当てる。メールアドレスだけの一致や、初期主担当が存在しない状態で最初にアクセスした利用者を自動昇格する方式は採用しない。
2. 主担当または代理管理者は、公演前日までを目安に、スタッフごとのメールアドレス、公演、予定役割、有効期限を指定して1回限りの招待を作成する。招待URLは推測困難な不透明トークンだけを含み、氏名、メールアドレス、公演名等をURLへ含めない。招待は有効期限、未使用・使用済み・失効の状態を持ち、一覧の閲覧を主担当・代理管理者へ限定する。
3. 管理者は招待URLをコピーまたは端末の共有機能へ渡し、メール、LINE、SMS等から選んで本人へ送る。基本設計では各サービスとの自動連携や連絡先アップロードを前提とせず、送信先の確認と誤送信防止を管理者操作に含める。
4. 招待された一般受付担当者・臨時管理者は自分の個別メール・パスワードアカウントを作成または再設定し、メール確認後に招待を受諾する。招待URLを知っているだけでは受諾・業務データ取得を許可せず、正規化した招待先メールアドレスとFirebaseで確認済みのメールアドレスが一致する場合だけ受諾できる。期限切れ、使用済み、失効済みの招待は拒否し、受諾と使用済み化を同じ処理で確定して二重受諾を防ぐ。
5. 主担当と代理管理者は、各自に割り当てるGoogleアカウントで本人確認する。既存のメール・パスワードアカウントと同じメールであっても、意図しない別UIDや重複アカウントを作らないリンク手順をBD-05・BD-08で定める。
6. 招待受諾で予定役割を有効な役割割当へ確定する。Firebase Authentication上にアカウントが存在しても、メール確認、招待受諾、有効な役割割当、当該ブラウザー保存領域の端末IDに対する管理者承認がすべて揃うまで、本番公演データとオフライン許可を取得できない。招待なしで作成されたアカウントは未割当として拒否し、定期確認・削除の対象にする。
7. 同じ人が複数人の資格情報を共有せず、利用者の交代時は新しい個別アカウントを発行する。過去イベントの発生者UIDを新利用者へ再利用しない。

初期主担当の作成、招待の送付、未割当アカウントの確認、メールアドレス変更はBD-08の非技術者向け手順へ記載する。初期設定をFirebase Consoleだけの手作業へ依存させる範囲と、レビュー済みの設定補助手段を用意する範囲は詳細設計で決めるが、サービスアカウント鍵をクライアントへ配布しない。

公演限定スタッフを翌年または別公演で再度招待する場合は、以前のパスワードを思い出すよう求めない。新しい招待からFirebaseの期限付き再設定手順へ案内し、新しいパスワードを設定してから新しい公演役割と端末許可を付与する。過去の役割・端末許可を再有効化して使い回さない。

招待受諾とメール確認が完了した利用者は、トップページから本人の登録状況、当日使用する受付画面の説明、操作説明、架空データ専用の練習画面を確認できる。練習画面は本番公演データ、受付イベント、集計、未同期キューと保存領域を分離し、架空QRで通常受付、受付済み再読取り、例外表示、理由・メモ入力を練習しても本番へ反映しない。PWAをホーム画面へ追加できる環境では、当日使用する端末ごとの追加手順を案内する。

## BD-04-03 役割、範囲、有効期間

| 役割 | 範囲 | 主な責務 | 制約 |
|---|---|---|---|
| 主担当 | 公演単位。各公演に有効な1人を必須とする | 公演全体、役割、締め、削除希望受付、運用判断の最終責任 | 後任の主担当が有効になる前に自分を停止できない |
| 代理管理者 | 公演単位。0人以上 | 主担当不在時の管理、一般・一時役割、準備、出力、削除の代行 | 主担当の変更、Firebase所有者・課金判断者の指定を行えない |
| 臨時管理者 | 公演単位。開始・終了時刻を必須とする | 当日必要な手動受付、例外、訂正、座席表示名・当日座席状態、連絡、競合確認 | 役割管理、端末管理、チケット・管理出力、任意項目、完全削除、締め、課金判断を行えない。公演終了後は確認・同期専用とし、会場タイムゾーンの公演翌日23:59:59に自動失効 |
| 一般受付担当者 | 公演単位。終了時刻を必須とする | QR受付、例外一覧・対応状態、未承認例外の仮登録、連絡確認 | 手動受付確定、正式編集・削除・訂正、管理出力、役割操作を行えない。公演終了後は確認・同期専用とし、会場タイムゾーンの公演翌日23:59:59に自動失効 |

「管理者」は業務操作によって範囲が異なる。手動受付、例外承認、訂正、スタッフ連絡等の当日管理は主担当・代理管理者・有効な臨時管理者を含む。任意項目、ZIP一括出力、完全削除、締め、役割管理等、要件で主担当・代理管理者を明示した操作は臨時管理者へ広げない。

受付開始と`受付を停止して準備に戻す`も、主担当・代理管理者だけに許可する。どちらもオンライン接続、最新公演状態の再取得、確認画面、サーバー側権限確認を必須とする。公演日時の到来、準備完了、端末内時計を権限付与や状態遷移の根拠にしない。

役割割当には、環境ID、公演ID、UID、役割、有効開始、有効終了、有効状態、付与者、付与時刻、停止者、停止時刻、理由、版を持たせる。現在状態を直接上書きする場合も、付与・変更・停止の監査イベントを別に追記する。

主担当を含むすべての役割はUIDと対象公演へ割り当て、端末IDへ役割を割り当てない。同じ主担当UIDがPCとスマートフォン等の複数端末から同時にログインすることを許可し、各端末が当該公演について承認済みであれば同じ主担当権限を使用できる。PCの準備完了をスマートフォンへ引き継がず、各ブラウザー保存領域へ別の端末IDを発行して、承認、準備、最終接続・同期、未同期件数、停止、監査を端末別に管理する。追加端末の登録や準備によって主担当役割を一般受付等へ変更しない。

一般受付担当者・臨時管理者の役割と当該公演の端末許可は、オフライン許可と同じく会場タイムゾーンの公演翌日23:59:59に自動失効する。期限後は過去のパスワードでFirebase本人認証に成功しても業務アクセスを許可しない。主担当と代理管理者の継続アカウントも公演役割と端末許可を公演ごとに判定し、Googleログインに成功しただけで別公演へアクセスさせない。

### 当日の臨時管理者任命

主担当・代理管理者だけが、対象公演の一般受付担当者を臨時管理者へ変更できる。臨時管理者と一般受付担当者には役割変更を許可しない。任命はオンライン限定の高影響操作とし、最近の再認証後に次を確認する。

- 対象者と対象公演。
- 現在の役割と変更後の役割。
- 臨時管理者の有効期限。

サーバーは対象者が当該公演の有効な一般受付担当者であることを再確認し、役割変更イベントと新しい役割版を確定する。対象者の承認済み端末は端末ごとに`臨時管理者の追加準備待ち`へ移る。役割はUIDと公演へ割り当てるが、臨時管理者用操作の利用開始は、各端末に保存した準備済み役割版が最新の役割版と一致する場合だけ許可する。

追加準備待ちの端末は、従来の一般受付担当者として許可されていた操作だけを継続できる。臨時管理者用操作は画面とSecurity Rulesの両方で拒否する。完全オフライン中は役割版を確認できないため、臨時管理者への追加準備を完了扱いにしない。

対象者がオンラインで追加準備を開始した時は、本人、対象公演、端末承認を再確認する。続いて、新しい役割と有効期限を確認する。臨時管理者の当日業務に必要な差分だけを取得し、既存の公演・端末専用CryptoKeyで暗号化して保存する。PWAの再インストール、CryptoKeyの再生成、全公演データの再取得は要求しない。件数、データ版、整合性、保存結果を確認し、準備済み役割版を更新した後に臨時管理者用操作を有効化する。

任期終了または役割解除後は、オンライン要求を直ちに拒否する。端末も検知時に管理者用操作をロックする。未送信の手動受付、訂正、例外記録は削除せず、サーバーの受領確認まで保持する。臨時管理者だけに配布した差分データは、未送信記録の受領確認後に削除する。データを直ちに物理削除できない場合は、準備済み役割版を無効化して復号・利用を拒否し、削除待ちとして管理する。一般受付担当者として継続する場合は、オンラインで役割、端末状態、一般受付用の準備状態を再確認する。

完全オフライン端末は、期限到達を保存済み期限から検知して臨時管理者用操作をロックする。管理者による期限前の役割解除は即時通知できないため、復旧時は通常操作より先に最新の役割版を確認する。この限界は端末停止・受付停止と同じ残存リスクとして扱い、解除後に発生した未同期記録を削除せず管理者確認対象にする。

Firebaseプロジェクト所有者および公演中の課金判断者は、アプリ内役割と別の環境運用責務である。環境初期設定時に、実際にFirebaseプロジェクトを作成した主担当または代理管理者1人を課金判断者として指定し、開催前にFirebase Console上の実際の所有者と一致することを手動確認する。クライアントアプリはGoogle Cloud IAM所有者情報を権限判定に使用せず、課金を実行しない。

## BD-04-05 データ配布とサーバー側拒否

| データ区分 | 一般受付 | 臨時管理者 | 代理・主担当 | サーバー側の境界 |
|---|---|---|---|---|
| 公演・座席・QR照合用データ | 当日必要分 | 必要分 | 全管理範囲 | 公演ID、役割割当、承認端末を検証 |
| 氏名・受付状態 | 例外対応等の必要最小限 | 当日管理に必要な範囲 | 管理範囲 | 一覧・単一取得の両方を同じ文書境界で制限 |
| 任意項目定義・値 | 配布しない | 配布しない | 許可済み端末へ暗号化値 | 通常データと別文書・別経路にし、文書単位で読取り拒否 |
| 役割・招待 | 自分の有効役割だけ | 自分と当日端末状態 | 公演内の管理範囲 | UID、役割、変更可能フィールドを検証 |
| 端末管理情報 | 自端末の必要最小限 | 自端末の必要最小限 | 公演内の全端末 | 利用者、端末ID、公演、役割、最終接続・同期時刻、未送信件数、端末状態を分離して許可 |
| 停止端末の隔離記録 | 閲覧不可 | 閲覧不可 | 対象公演の管理範囲 | 通常受付と別経路に保存し、採否判断前の通常状態反映を拒否 |
| 監査イベント | 自分に必要な結果 | 当日業務範囲 | 管理範囲 | 作成専用とし、既存イベント更新・削除を拒否 |
| 公演状態 | 現在状態と自端末の受付可否 | 現在状態と当日業務範囲 | 状態変更と履歴を含む管理範囲 | 状態変更は主担当・代理管理者のオンライン要求だけに許可 |
| 出力・削除記録 | 自分の操作結果 | 許可操作の結果 | 管理範囲 | 生成物本体、削除済み個人情報、秘密情報を含めない |

Cloud Firestore Security Rulesは文書の一部項目だけを隠せないため、任意項目、認証・役割管理監査等は、権限の弱い利用者が読める文書へ同居させない。クエリーはSecurity Rulesによる事後フィルターではないため、公演・データ区分・役割に一致する取得経路と条件を設計し、許可外文書を含み得るクエリーを発行しない。

臨時管理者用の要求では、有効な臨時管理者役割だけでなく、要求端末の準備済み役割版が最新の役割版と一致することも検証する。追加準備待ち、途中失敗、期限切れ、役割解除後は、臨時管理者用の読取りと書込みを拒否する。一般受付として継続可能な操作は、現在の役割状態と準備状態に応じて別に判定する。

環境IDと公演IDを画面入力だけから信頼せず、要求パス、既存文書、役割割当、書込み後文書の一致を検証する。クライアントは管理SDKやサービスアカウントを使用しない。将来サーバー処理を追加する場合は、Security Rulesを迂回する管理SDKのIAM、監査、費用、秘密情報を新しい設計・ADRで扱う。

## BD-04-06 セッションと再認証

Firebase IDトークンは約1時間で更新され、更新トークンは長期間利用できるため、IDトークンの有効期限だけを業務セッション終了とみなさない。アプリケーションは次の二層で管理する。

| 状況 | Authenticationの保持 | アプリ側の扱い |
|---|---|---|
| 通常の管理用PC | ブラウザーを閉じるまでのセッション保持を既定とする | 再開時にオンラインで本人・役割・端末を再確認 |
| 当日受付用の準備済み端末 | 利用者が明示的に端末準備を完了した時だけローカル保持を許可 | BD-04-07の期限付きオフライン許可と組み合わせる |
| 共有・信頼できない端末 | ローカル保持を許可しない | ブラウザー終了またはログアウトで認証状態を破棄 |
| ログアウト | Firebaseからサインアウト | 復号済み値、選択中公演、端末内認証関連状態を削除する。公演データとCryptoKeyは未同期・隔離対象の全件受領後の締めまたは端末廃止条件まで保持する。端末停止だけではログアウトや保存データ削除を実行しない |
| 締め済み | 対象公演のセッションを終了 | 未同期・隔離対象の全件受領確認後、対象公演の認証関連状態、業務データ、CryptoKeyを一緒に自動削除する。別公演のセッションとデータは維持する |

アプリ起動、画面復帰、オンライン復旧、公演切替、高影響操作の前に、現在利用者、メール確認、役割、端末、公演状態を再取得する。オンライン接続・回線復旧時は通常操作を保留し、端末状態と公演状態の取得に成功するまで新規受付を開始しない。最新の公演状態が準備中なら受付画面をロックする。オンライン中の最終許可は毎回Security Rulesが行うため、画面の再取得間隔だけで権限の安全性を決めない。

役割変更、完全削除、任意項目出力、ZIP出力、締め、主担当引継ぎ等の高影響操作はオンライン限定とし、最後の本人再認証から15分以内であることを要求する。期限を超えた場合は、パスワード利用者はパスワード、Googleログイン利用者はGoogleプロバイダーで再認証し、操作内容を保持したまま確認へ戻す。

高影響操作の条件はPC・スマートフォン等の端末種別で緩和しない。主担当のスマートフォンにも主担当権限を表示するが、削除、締め、役割変更、主担当引継ぎ、端末廃止等は、オンライン接続、最近の再認証、対象・影響の確認、UIDと端末IDを含む監査をすべて満たす場合だけ許可する。

`CONF-047`の当日再ログイン懸念に対し、一時的な通信断、App Check確認失敗、トークン更新失敗だけを理由に準備済み端末をサインアウトさせない。既存のオフライン許可と期限内で安全に継続し、オンライン復旧時に状態を先行確認する。明示的なログアウト、認証情報漏えい、アカウント無効化、保存領域消去、期限切れまで無効化するものではない。再ログインが必要でパスワードを忘れた場合、オフラインではメール再設定できないため、その端末の受付を止め、別の準備済み端末または紙へ切り替える。端末に残る未同期記録は削除せず、復旧後に照合する。

## BD-04-07 端末準備とオフライン許可

未準備または準備状態が無効な端末では、アプリ上部に`事前準備が完了していません`という大きな案内、Wi-Fi環境の推奨、`事前準備を開始`ボタンを表示する。ブラウザーからWi-Fi接続を確実に判定できない場合があるため、接続種別が不明またはWi-Fi以外であることだけを理由に準備を禁止せず、想定ダウンロード量と通信料の注意を示して利用者が開始を選べるようにする。

完全オフライン開始には、当日使用するブラウザー保存領域・端末IDごとに、次をオンラインで1回の準備結果として確認する。利用者単位の完了を端末単位の完了として流用しない。

1. メール確認済みの個別利用者で再認証できている。
2. 招待受諾済みで、対象環境・公演が一致し、公演が受付準備可能である。
3. 利用者の役割が有効で、一般受付、臨時管理者、代理、主担当のいずれかである。
4. 端末登録が同じUID・公演へ承認済みで、端末状態が`有効`である。ブラウザーデータ消去等で新しい端末IDになった端末は、同じUIDで本人認証できても再承認するまで準備できない。
5. PWA資産、役割に許可された受付用データ、座席表、会場画像等を取得し、予定件数と実取得件数、アプリ版、データ版、整合性、保存可否を検証済みである。
6. カメラ権限とカメラ起動を確認し、架空QRで受付結果を表示できる。受付済み再読取り、例外表示、例外メッセージ、理由・メモ入力の練習確認も完了している。
7. オフライン許可の開始、終了、役割版、端末ID、公演ID、会場タイムゾーンIDを端末へ保存し、画面へオフライン利用期限を表示できる。
8. 公演・端末専用のランダムなAES-GCM 256ビット鍵を非抽出CryptoKeyとして生成し、IndexedDBへ保存する。追加パスフレーズ・PIN、認証パスワード、共有パスフレーズ、PBKDF2、KEKを使用しない。

各項目は個別の進捗と検証結果を持つ。途中失敗では検証済みの安全な成果を再利用し、失敗項目から再試行する。ただし部分取得データを受付へ使用せず、全項目が成功するまで`準備完了`とオフライン利用を許可しない。再試行時も本人、役割、端末、期限、版を再確認する。

| 端末準備状態 | 表示・扱い | 遷移条件 |
|---|---|---|
| 未準備 | 大きな事前準備案内を表示。本番データ取得・オフライン受付は不可 | 管理者承認後に利用者が開始して`準備途中` |
| 準備途中 | 項目別進捗、完了・失敗・再試行を表示。部分取得データは本番利用不可 | 全項目成功で`準備完了`、中断・失敗は安全なチェックポイントから再開 |
| 準備完了 | 大きな案内を隠し、`準備完了`、対象公演、最終確認時刻、オフライン利用期限を小さく常時確認可能にする | 確定済み公演データの版更新で`差分更新待ち`、再準備条件で`再準備必要`、端末停止で`停止中` |
| 差分更新待ち | 端末登録、カメラ練習、CryptoKey生成等の完了結果を維持する。最新データ版と一致するまで本番の新規受付・オフライン利用は不可 | オンラインで変更分だけを取得し、件数、データ版、参照整合性、保存結果の成功後に`準備完了` |
| 再準備必要 | 理由と大きな事前準備案内を表示。本番の新規受付・オフライン利用は不可 | 原因を解消し、必要な準備項目の再検証にすべて成功して`準備完了` |
| 停止中 | BD-04-08に従い通常画面の復号・閲覧、新規受付、通常同期、データ取得、オフライン利用を禁止。画面表示を伴わない既存未同期記録の隔離送信だけを許可 | 管理者の停止解除とオンライン検証後、問題がなければ同じCryptoKeyと既存データを再利用して差分確認 |

名簿、座席、座席表示名等の確定済み公演データの版が更新された場合は、変更の影響を受ける準備済み端末だけを`差分更新待ち`にする。端末はオンラインで同期カーソル以後の変更分だけを取得し、予定件数と実取得件数、最新の確定済みデータ版、参照整合性、暗号化保存結果を再確認する。すべて成功した後に準備済みデータ版を更新し、`準備完了`へ戻す。端末登録、カメラ練習、CryptoKey生成、変更の影響を受けない取得済みデータはやり直さず、PWA再インストールや全件再取得も要求しない。更新できない端末は本番受付へ使用せず、更新済みの代替端末または紙運用へ切り替える。

`再準備必要`とするのは、ブラウザーデータ消去、端末ID変更、CryptoKey欠損、非互換アプリ版、役割・端末承認失効、参照整合性または保存整合性の異常に限る。端末停止は`停止中`として別に扱う。最新の確定済みデータ版と端末の準備済みデータ版が一致しない間は、画面と受付開始判定の両方で当該端末の本番受付を拒否する。

管理画面で主担当・代理管理者は、スタッフと端末IDの組合せごとに、招待、メール確認、アカウント登録、招待受諾、役割、端末承認、データ取得、カメラ確認、練習確認、準備完了、準備済みデータ版、最新データ版、最終確認時刻を確認できる。端末準備状態は少なくとも`未準備`、`準備途中`、`準備完了`、`差分更新待ち`、`再準備必要`、`停止中`を区別する。管理者はパスワードを設定・閲覧・記録・再通知せず、この進捗情報だけで誰のどの端末が準備済みかを判断する。

### 主担当本人の追加端末登録

主担当が自分の追加端末を登録する場合は、次をオンラインで順に満たす。

1. 新しいブラウザー保存領域へ既存端末と異なる端末IDを発行し、`承認待ち`として対象公演・主担当UIDへ仮関連付けする。
2. Googleプロバイダーで新しく再認証し、初期設定または主担当引継ぎで割り当てたFirebase UIDと一致し、再認証時刻が許容時間内であることをサーバー側で確認する。
3. Googleアカウントの2段階認証有効化は初期設定・引継ぎ手順で確認する。ただしGoogle側で実際に行われた第二段階はFirebase IDトークンだけでは毎回確認できないため、それだけを追加端末承認の根拠にしない。
4. 既存の承認済み・停止されていない主担当端末に、短時間で失効する推測困難な1回限りのQRまたは追加端末リンクを表示し、新端末で開く。関連付けは主担当UID、公演ID、発行元端末ID、登録対象端末ID、有効期限へ結び付け、別UID・別公演・別端末・再利用を拒否する。
5. Google再認証と既存承認端末の所持確認が両方成功した場合だけ、新端末を主担当本人の端末として承認し、UIDと公演に既存の主担当役割をそのまま参照させる。新端末は未準備から開始し、通常の端末準備を別途完了する。
6. 発行、読取り、承認、拒否、期限切れについて、主担当UID、発行元・登録対象の両端末ID、公演ID、時刻、結果を監査する。QR・リンクの平文トークンやGoogle認証情報は監査へ残さない。

既存承認端末を1台も使用できない場合は自己登録を許可せず、BD-08-03の全管理端末喪失時の復旧手順へ移す。Firebase MFAを採用する場合はサーバーで検証した第二要素情報を追加条件または代替条件にできるが、Authentication with Identity Platformの料金体系と費用0円条件をBD-05・BD-10で確認し、承認前に有効化しない。

オフライン許可の終了は、対象公演日の翌日23:59:59を会場に設定したIANAタイムゾーンで解釈し、UTCの期限時刻へ変換して保持する。準備完了からの固定24時間・48時間では失効させず、数日前に準備した端末も同じ公演期限を使用する。会場タイムゾーン未設定、形式不正、公演日との組合せ不正では端末準備を完了させない。端末のローカルタイムゾーンや時刻変更で期限を延長できないよう、準備時に受け取った期限とオンライン時のサーバー時刻を使用する。

公演限定スタッフの役割と端末許可も同じ期限を持ち、期限到達時にサーバー側で自動失効する。期限後の同期・管理者確認・削除専用経路は、期限前に保存済みの未同期記録を保全するための例外であり、公演限定スタッフの通常役割や新規受付権限を延長しない。

公演終了後は当日受付の新規操作を止め、一般受付担当者と臨時管理者には確認・同期だけを許可する。主担当・代理管理者はオンラインで本人、役割、端末、対象公演を再確認し、紙記録入力と理由付き訂正を行える。許可期限後は対象公演の当日画面をロックし、管理者は公演後管理画面からオンラインで継続する。未同期がある場合はデータを自動削除せず、同期・管理者確認・削除専用画面へ移す。全件のサーバー受領確認と、締めまたは端末廃止の条件成立後に、対象公演の端末内データを削除する。別公演の選択と利用は継続できる。

| 公演別端末利用状態 | 開始条件 | 許可する処理 | 次の状態 |
|---|---|---|---|
| 準備済み | オンライン端末準備が完了 | 公演開始前の確認。受付開始条件成立後に通常業務 | 公演開始で`受付中` |
| 受付中 | 公演が受付可能で許可期限内 | 役割範囲内の受付、訂正、確認、同期 | 公演終了で`終了後確認期間` |
| 終了後確認期間 | 公演終了後かつ翌日23:59:59の期限到達前 | 当日受付の新規操作を拒否。確認と同期を許可し、継続管理者だけオンラインで紙記録入力・理由付き訂正を許可 | 全件受領後に削除、または期限到達で`期限切れ` |
| 期限切れ | 公演翌日23:59:59を経過 | 当日画面をロック。未同期があれば同期・管理者確認・削除専用処理だけ。継続管理者は別のオンライン管理画面から公演後操作を行う | 全件受領後に`削除可能` |
| 削除可能 | 未同期0件、サーバー全件受領確認済み、締めまたは端末廃止条件成立 | 対象公演の端末内認証関連状態、公演データ、CryptoKeyを削除 | `削除完了`。別公演の状態は変更しない |
| 削除完了 | ログアウトと端末内公演データ削除を確認済み | 個人情報を含まない削除完了報告 | 終了 |

次の座席変更・QR再発行のオフライン拒否は、第三者品質レビューM-03への是正案であり、基本設計の再レビュー前には未承認として扱う。

| オフラインで許可 | オフラインで拒否 |
|---|---|
| QR受付、再読取り理由、例外仮登録・対応状態、管理者の手動受付・訂正・競合確認、スタッフ連絡、必要最小限の閲覧 | 座席の追加・変更、QR再発行、アカウント・役割・端末の付与変更、主担当引継ぎ、任意項目取得、CSV・PDF・ZIP出力、完全削除、締め、Firebase上限時の課金判断、端末再準備 |

オフラインイベントは発生時のUID、役割、役割版、端末ID、許可期限をスナップショットとして持つ。復旧後は現在の役割と端末状態を再確認する。停止済み端末のイベントを通常イベントとして自動受理せず、通常同期ではBD-03の`拒否`として扱う。ただし停止前または停止を知らないオフライン期間中に保存された未同期イベントは削除せず、BD-04-08の隔離送信専用経路で全件を管理者確認用領域へ送る。

同じUIDの複数端末は独立したセッション、端末状態、オフライン許可、未同期キューを持つ。1台の停止・準備無効化・廃止は対象端末IDだけへ適用し、認証情報漏えい等の別理由がない限り、主担当アカウント、UIDと公演の主担当役割、同じUIDの他の承認済み端末を停止しない。

同じ端末IDの複数公演は、公演・端末単位の独立した端末利用状態を持つ。端末停止指示は対象公演IDと端末IDの組合せへ記録する。紛失時は管理画面で同じ端末に準備済みの公演を確認し、停止対象を明示的に選ぶ。1公演だけを停止した場合、別公演を暗黙に停止しない。

## BD-04-08 停止、紛失、期限切れ、ログアウト

| 契機 | オンライン時 | 完全オフライン時 | 復旧時 |
|---|---|---|---|
| 利用者停止 | 役割割当を無効化し、Rulesが以後の要求を拒否 | 端末へ即時通知できない | 同期前に停止を取得し画面をロック。未送信を管理者確認へ回す |
| 紛失端末停止 | 対象端末IDを解除可能な状態で停止し、同じ利用者の別の承認済み端末は維持する | `停止待ち（オフライン）`とし、紛失端末のローカル利用を遠隔停止・物理削除できない | 復号・閲覧・新規受付・通常同期・オフライン利用をロックする。保存データは暗号化状態で保持し、未同期記録だけ隔離送信へ回す |
| 端末廃止・データ削除 | 管理者の明示操作後、対象公演・端末の再利用を不可にして削除要求を記録 | 接続までは物理削除できないため`廃止・削除待ち`として残す | 対象公演の未同期・隔離対象について条件を満たしてから、公演データ、準備済み資産、対象CryptoKeyを一緒に削除する。別公演は削除しない |
| 公演別許可期限切れ | 時刻条件によりRulesが通常業務を拒否 | 事前保存した公演期限で通常業務を停止。CryptoKeyと暗号化データは削除しない | 未同期があれば同期・管理者確認専用画面へ移し、全件受領後の締めまたは端末廃止条件で削除へ進む |
| 認証情報漏えい疑い | Firebaseでパスワード再設定、更新トークン失効、利用者アカウント無効化を必要性に応じて行い、当該利用者の端末も停止する | 既存オフライン許可は期限まで残り得る | 役割・端末停止をRulesで確認し、本人確認後に必要な範囲だけ再開する |
| ログアウト | サインアウトし端末内認証関連状態を削除 | 未送信がある場合は完了扱いにせず、イベント、CryptoKey、送信に必要な状態を保持する | 端末停止だけでは公演データ・鍵の削除へ進めず、停止状態のまま保持する。廃止・削除は別操作 |
| 締め | 新規業務操作を停止し、全件受領確認後に削除 | 締め受信までは継続可能という限界がある | 締めを取得し、未同期・隔離対象の全件受領確認、サインアウト、対象データとCryptoKeyの削除を行う |

権限停止は、Authenticationアカウント停止だけに依存せず、公演役割と端末の`active`状態をSecurity Rulesで確認する。これにより、最大約1時間残り得る既存IDトークンや長期更新トークンがあっても、オンライン業務データ要求を拒否できる。利用者アカウント全体の無効化と更新トークン失効は、パスワードやトークン等の認証情報そのものの漏えいが疑われる場合に限る。端末紛失だけを理由にFirebase AuthenticationアカウントやGoogleアカウント全体を停止しない。

紛失時の操作は利用者全体への単なる強制ログアウトではなく、端末ID単位の解除可能な端末停止とする。ブラウザーに保存されたパスワードはアプリから削除できないが、停止された端末は、そのパスワードで本人認証へ成功しても、Security Rules等のサーバー側認可により閲覧、新規受付、通常同期、データ取得、オフライン利用を拒否する。保存済みCryptoKeyによる通常画面の復号もアプリ状態で禁止する。例外は、停止前または停止を知らない間に端末へ保存済みだった未同期イベントを、画面表示せず内部復号して隔離領域へ送るための作成専用経路だけとする。同じ利用者の別の承認済み端末は個別に停止されない限り継続利用できる。

端末停止では、PWA資産、会場画像、座席表、準備済み公演データ、非抽出CryptoKey、未同期記録を削除しない。停止検知後は復号済み表示を閉じ、端末内データを暗号化状態のまま保持し、通常画面へ戻せないようにする。完全オフライン中に停止をまだ検知していない端末へ即時ロックを保証できず、保存済みCryptoKeyを不正利用され得る限界は`CONF-036`で受容する。次回オンライン・回線復旧時は通常操作より先に停止状態を確認する。

### 端末状態と遷移

| 端末状態 | 意味 | 許可する処理 | 次の状態 |
|---|---|---|---|
| 有効 | 管理者承認済みで通常利用可能 | 役割範囲内の受付、通常同期、データ取得、オフライン準備 | 停止指示で`停止待ち（オフライン）` |
| 停止待ち（オフライン） | サーバーに停止指示があるが端末の検知を未確認 | サーバーは通常要求を拒否。端末が未検知の間は技術的にローカル操作が残り得る | 端末の復旧・停止取得で`停止検知済み` |
| 停止検知済み | 端末が停止を取得し、復号済み表示と通常操作をロック済み | 暗号化データを保持し、既存未同期イベントの隔離送信と受領確認だけ | 未同期があれば`隔離記録確認待ち`、なければ`停止中` |
| 隔離記録確認待ち | 隔離領域が記録を受領し、管理者の採否判断が未完了 | 管理者による紙記録等との照合、採用、重複、誤操作、不正使用疑いの判断。端末データは削除しない | 照合完了後も`停止中`。廃止は別操作 |
| 停止中 | 対象端末IDがロックされ、暗号化データを保持 | 停止状態表示、隔離結果確認、管理者による停止解除または端末廃止の選択 | 解除で`停止解除確認中`、廃止で`廃止・削除待ち` |
| 停止解除確認中 | 同じ端末IDの停止を管理者が解除し、本人確認と整合性確認が未完了 | 本人の再ログイン、オンラインで公演・役割・端末・許可期限・アプリ版・データ版・整合性を確認 | 問題がなければ差分同期後`有効`。問題があれば`停止中`または再準備 |
| 廃止・削除待ち | 管理者が端末廃止・データ削除を選択し、端末側完了が未確認 | 未同期の隔離送信・受領確認。全件受領前はデータとCryptoKeyを保持する | 全件受領後、端末内削除確認で`廃止・削除完了` |
| 廃止・削除完了 | ログアウトと端末内認証・公演・準備済み資産の削除を確認済み | 監査閲覧のみ。停止解除不可 | 終了 |

端末状態とは別に、未送信件数、隔離領域の受領済み件数、照合状態、暗号化データ保持状態、廃止・削除確認を保持する。隔離送信に失敗した端末はイベントを削除せず再送専用状態に留め、管理画面では`停止済み・未同期あり`と表示する。隔離記録の全件受領と照合が完了しても停止中データを自動削除せず、管理者が停止解除または端末廃止を選ぶまで暗号化状態で保持する。

隔離領域は通常受付イベントと物理的または論理的に分離し、隔離イベントID、利用者、端末ID、公演ID、停止指示時刻、端末上の発生時刻、端末連番、サーバー到着時刻、停止前の最終同期時刻、受領結果、採否、判断者、判断時刻、判断理由を保持する。管理画面では`停止後に到着した記録`として目立たせる。管理者は紙記録等と照合して採用、重複、誤操作、不正使用の疑いを判断し、採用時も元の隔離記録を変更せず、正式受付へ反映する別の管理者イベントを作成する。

管理者の端末管理画面には、利用者、端末ID、対象公演、役割、最終接続時刻、最終同期時刻、未送信件数、端末状態、停止指示時刻、隔離受領・照合状況、廃止・削除状況を表示する。`停止`、`停止解除`、`端末廃止・データ削除`を別ボタンとし、停止確認には「データは暗号化状態で保持され、削除されない」、廃止確認には「端末を再利用不可にしてデータを削除する」と表示する。

発見・回収した端末を再利用する場合は、管理者が同じ端末IDの未同期・隔離記録と端末状態を確認して停止を解除し、本人が再ログインしてオンライン確認を行う。公演、役割、端末、許可期限、アプリ版、データ版、暗号化データの整合性に問題がなければ、既存のPWA、会場画像、座席表、準備済み公演データを再利用し、差分同期だけで受付へ復帰する。PWA再インストールや全データ再ダウンロードを通常条件にせず、版非対応、欠損、改変、不整合がある場合だけ再準備または全件取得を要求する。停止端末のブラウザーデータが消去され新しい端末IDになった場合は既存データ再利用の対象外とし、旧端末を停止記録に残したまま新規端末として管理者承認を要求する。

`端末廃止・データ削除`は、回収不能、再利用しない、または公演締め後に主担当・代理管理者が明示的に選ぶ。管理者は対象公演、端末、未送信・隔離対象件数を確認し、オンラインで再認証して廃止要求を記録する。未同期・隔離対象が残る間は通常利用を停止し、送信・管理者確認専用状態でデータとCryptoKeyを保持する。端末廃止要求だけでは全件受領済みまたは締め可能と扱わない。全件のサーバー受領後に限り端末内データとCryptoKeyを削除する。回収不能端末は物理削除を確認できないため、削除未確認として残し、未受領記録がある可能性を示す。一般受付担当者と臨時管理者には廃止権限を与えない。

紛失端末によって通常締めができない場合は、端末停止、稼働端末の全件受領、紙との照合、損失可能性の記録を経て例外締めを行う。例外締めでも紛失端末のCryptoKeyと暗号化データの削除条件は変えない。締め後に発見した端末の記録は自動受領・自動反映しない。

端末が起動・接続されない場合は遠隔物理削除を完了扱いにせず、公演別許可だけを失効させて管理画面へ未確認として残す。次回起動時は通常利用を禁止する。未締めなら未同期を隔離送信・管理者確認へ進める。例外締め済みなら自動送信せず、管理者の照合操作まで端末内データを保全する。全件受領済みならログアウト・削除へ誘導する。

## BD-04-09 パスワード、失敗、再設定

`CONF-047`により、依頼者は6～20文字・英字数字必須の現行条件を維持した。短いパスワードによる不正ログインの残存リスクを理解し、当日の再ログインのしやすさを優先した判断である。6文字なら失念しない、当日必ず再ログインできるとは扱わない。他サービスと同じパスワードの使い回しを推奨しない。開催前の再ログイン確認、本人による再設定、準備済み代替端末と紙切替で備える。この条件を依頼者への再確認待ちに戻さず、変更時だけ変更管理で扱う。

- パスワードはFirebase Authenticationの画面・SDKから安全な通信で認証処理へ渡し、アプリ独自の保存、暗号化、ハッシュ化、復号、一覧表示を行わない。Firebase SDKが返す認証結果だけを利用し、パスワード本体をFirestore、IndexedDB、ログ、監査記録、解析サービス、Git、GitHub、画面へ残さない。
- 公演限定スタッフのパスワードは6文字以上20文字以内とし、半角英字`A-Z`または`a-z`と半角数字`0-9`をそれぞれ1文字以上含める。記号は任意とする。共有パスワード、氏名、メールアドレスのローカル部、公演名、`123456`、連続・反復文字、既知の推測しやすい値を禁止する。パスワードや生のトークンを取得・復号・一覧表示できる管理機能を作らない。
- Firebase AuthenticationのパスワードポリシーはRequireモードで最小6文字、最大20文字、数字必須、記号任意に設定し、メールアドレス列挙保護を有効にする。Firebaseの標準ポリシーは「大文字または小文字のどちらかを1文字」というOR条件を直接表現しないため、半角英字1文字以上は登録・再設定画面で検証してからFirebaseへ渡す。登録・再設定画面には`半角英字と数字を含む6～20文字`と常時表示する。
- アカウント登録と再設定の両方で同じ正規化前文字列を検証し、全角英数字を半角へ黙って変換しない。条件違反時は不足条件を示すが、入力値をログ・解析・監査へ送らない。ログイン、登録、再設定の失敗表示は、登録有無を推測できない共通表現にする。
- 同一ブラウザーで5回連続失敗した場合は15分間入力を停止し、Firebase側の不正試行制限と併用する。端末内の失敗回数はログイン成功または再設定後の正常ログインでリセットし、失敗時もパスワード、入力メールアドレス全文、その他の入力内容をログ、監査、解析サービスへ記録しない。
- パスワード再設定はFirebaseの期限付き再設定メールを使用し、主担当・代理管理者が仮パスワードを閲覧・発行しない。再設定要求は登録有無にかかわらず同じ完了案内を表示する。
- メールアドレス変更、パスワード変更、漏えい疑いでは再認証を必須とし、変更後に他端末のセッション、役割、端末一覧を確認する。認証情報漏えいが疑われる場合は、影響に応じてFirebaseの更新トークン失効、利用者アカウント無効化、当該利用者の端末停止を行う。端末紛失だけの場合は対象端末IDだけを停止する。

### Git・GitHubへ持ち込まない情報

実在する氏名、メールアドレス、電話番号、住所、受付情報は、機密度の認識にかかわらずGit・GitHubへコミットしない。サンプル、画面見本、試験、ログ例には明確な架空データだけを使用し、例示用メールアドレスのドメインは`example.com`とする。

`.env`、秘密鍵、サービスアカウント等の資格情報、認証済みブラウザー状態、依頼者用Firebase接続設定、実データファイルはGit管理対象外とする。プロジェクトルールと`.gitignore`は予防の一部であり、誤コミットを完全には防げない。BD-05で秘密情報スキャン、禁止ファイル検査、PRチェックリスト、ログ・エラー・解析情報のマスキング方針を設計し、自動化は基本設計承認後の適切な実装工程で導入する。

パスワード、トークン、秘密鍵等をGitHubへ送信した場合は、ファイル削除だけで対応完了としない。該当資格情報を直ちに失効・再発行し、リポジトリ履歴、派生ブランチ、Pull Request、成果物、ログ、端末キャッシュへの対応と影響確認を行い、事故対応記録を残す。具体的な連絡、履歴処理、再発防止の手順はBD-05・BD-08で定める。

禁止する推測容易値の初期リスト、メールテンプレート、送信上限、Firebase Console操作、管理者GoogleログインとFirebase MFAの技術・費用条件は、実装開始前に公式仕様を再確認してBD-05・BD-08・BD-09へ反映する。

## BD-04-10 監査と高影響操作

次の操作は、成功・拒否・失敗について、対象公演、操作種別、UID、役割、端末ID、時刻、理由、結果、関連対象IDを、個人情報と秘密情報を最小化して監査イベントへ記録する。同じUIDの複数端末を識別できるよう、端末IDを省略せず、端末種別だけで代用しない。

- 招待、役割付与・変更・停止、主担当引継ぎ、端末承認・停止・解除、端末状態遷移。
- ログイン成功、連続失敗による停止、再設定完了、ログアウト。パスワード、トークン、入力メール全文は記録しない。
- 手動受付、訂正、競合確認、QR再発行、出力、完全削除、締め。
- 公演終了後の端末内公演データ削除、端末廃止要求、全件受領前の削除拒否。
- 紛失端末がある場合の例外締め確認と損失可能性の記録。
- 権限拒否、別公演、期限切れ、停止済み端末、直接APIによる不正形式。
- 隔離送信の開始・再送・全件受領、隔離記録の採用・重複・誤操作・不正使用疑いの判断。隔離完了だけでは端末データを削除しない。
- 端末廃止・データ削除の選択、警告確認、実行、失敗、端末側削除完了。
- Firebase上限時の課金判断者確認、紙・課金の選択、実施時刻、確認結果。支払情報は記録しない。

役割変更、削除、締め、主担当引継ぎには対象、影響、現在状態、実行後の状態を示す確認画面を設ける。主担当引継ぎは、後任のメール確認、受諾、有効端末を確認し、同一トランザクションで新主担当を有効化してから旧主担当を代理または停止へ変更する。主担当0人または2人の状態を許可しない。

## BD-04-11 Security Rulesへ渡す判定契約

第三者品質レビューC-01により、同じUIDの停止端末が有効端末IDを要求へ指定する場合を、現行のRules条件だけでは拒否できないことが判明した。以下の端末ID判定は目標条件であり、成立済みの実装方式ではない。[端末単位認可の成立性調査](device-authorization-feasibility.md)とIssue #71で読取り・書込み双方の方式を確定するまで、端末単位停止の実装へ進まない。

Security Rulesはすべて拒否を初期値とし、各文書経路で少なくとも次を検証する。

1. `request.auth`が存在し、メール確認済みである。
2. 要求された環境・公演が、パス、選択中公演、既存データ、書込み後データで一致する。公演シリーズの一致だけでは許可しない。
3. UIDに対応する役割割当が有効で、開始・終了時刻内、許可役割である。
4. 端末IDが同じUID・公演へ承認済みで、有効である。
5. 本番受付要求では公演状態が当日運用中であり、準備中への変更後は新規受付を拒否する。
6. 操作が作成・更新・削除のどれで、変更可能なフィールドと状態遷移が権限表に一致する。
7. 変更不能イベントは新規作成だけを許可し、イベントID、発生者UID、端末ID、役割版を要求と一致させる。
8. 高影響操作はオンライン、最近の再認証、必要な確認状態を要求する。
9. 会場タイムゾーンから算出した公演期限後の新規受付・訂正等、別公演、役割外、停止済み、未対応版、余分なフィールドを拒否する。

臨時管理者用経路では、最新役割版と端末の準備済み役割版の一致を追加で要求する。一般受付から臨時管理者への変更は、対象UIDが同じ公演の一般受付担当者である場合だけ許可する。変更要求には有効期限を必須とし、実行者が主担当または代理管理者であることを検証する。

公演期限後は当日受付経路の新規作成・訂正を拒否する一方、期限前に端末保存済みの未同期イベントを送る専用経路、受領確認、競合・隔離記録の管理者確認、削除完了報告を許可する。別の公演後管理経路では、主担当・代理管理者のオンライン再認証、有効な公演役割と承認端末、対象と理由を確認した後だけ紙記録入力・実績訂正・削除希望対応を許可する。端末廃止要求の監査書込みは、主担当・代理管理者、オンライン再認証、対象端末・公演、未同期件数の整合を検証する。削除完了報告は全件受領確認後だけ受け付ける。

例外締めは、主担当・代理管理者、オンライン再認証、紛失端末停止、稼働端末の全件受領、紙照合、損失可能性の記録を検証する。

停止済み端末には通常データ経路を一切許可しない。隔離送信専用経路だけは、認証済みUID、停止対象の端末ID・公演ID、停止指示、端末連番、イベントIDと保存済みイベント内容の整合を検証した作成専用要求として許可し、既存隔離記録の更新・削除、通常受付への書込み、通常データの読取りを拒否する。隔離送信の認可は端末停止を解除せず、同じ利用者の別端末の状態にも影響させない。

Rulesが参照する文書数は公式上限内に収め、利用者、役割、端末、公演状態を無制限に連鎖参照しない。Rules参照も読取り使用量へ影響するため、費用・性能をBD-09で測定する。クエリー、単一取得、バッチ、トランザクション、直接SDK要求をそれぞれエミュレーターで許可・拒否試験する。

## 代替案、影響、残存リスク

### 採用しなかった主な代替案

| 代替案 | 採用しない理由 |
|---|---|
| 共有管理者・受付アカウント | 操作者を識別できず、停止、監査、端末紛失対応を個別に行えない |
| 役割をIDトークンのcustom claimsだけへ保持 | 公演単位・期限付きの変更を即時反映しにくく、トークン更新まで古い役割が残り得る |
| 画面でボタンを隠すだけ | 直接SDK・API要求、別公演識別子、改変要求を拒否できない |
| 全管理者へ同じ権限 | 臨時管理者へ任意項目、完全削除、役割、締め、課金判断まで広がり、必要最小限にならない |
| 完全オフライン中も即時停止できるとみなす | 通信のない端末へ停止情報を届けられず、技術的に保証できない |

### 良い影響

- 操作者、役割、端末、公演を個別に追跡し、紛失端末だけを停止できる。
- 任意項目や役割管理データを一般受付・臨時管理者へ配布せず、画面とサーバーの両方で最小権限を保てる。
- Firebase交換時も業務役割、権限表、監査形式を維持し、資格情報だけを安全に再設定できる。

### 注意が必要な影響と残存リスク

- 完全オフライン中は権限・端末停止、締め、パスワード変更を即時反映できない。会場タイムゾーンの公演翌日23:59:59という許可期限、端末画面ロック、紛失連絡、紙切替が必要である。
- 臨時管理者の期限前解除も完全オフライン端末へ即時通知できない。追加準備をオンライン限定とし、復旧時の役割版確認と解除後記録の管理者確認で影響を限定する。
- Firebase Authenticationの公開サインアップ自体を完全に招待制へできない構成では、未招待アカウントが作成され得る。ただし役割・端末がなければ業務データを拒否し、未割当アカウントを運用で確認・削除する。
- 最初の主担当作成とAuthentication利用者の無効化・トークン失効には環境所有者の管理操作が必要であり、非技術者向け手順と演習が必要である。
- ブラウザー保存領域を消去すると端末IDを復元できない。停止回避として自動承認せず、新端末として再承認し、旧端末を停止記録に残す。消去前の未同期記録は復元できないため、回収時は隔離受領完了前にブラウザーデータを消去しない。
- 15分の再認証と5回失敗・15分停止は初期の安全側設定である。オフライン許可は固定24時間・48時間を採用せず、公演翌日23:59:59までとする。対象実機の操作性と境界時刻をBD-06・BD-09で確認し、変更する場合は理由と影響を記録する。

## 公式情報

2026-09-16時点で、次のFirebase公式情報を設計根拠として確認した。

- [Firebase Authenticationのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions): IDトークンは約1時間、更新トークンは長期間有効であり、無効化・削除・主要なアカウント変更や管理操作による失効を扱える。
- [Cloud Firestore Security Rulesの条件](https://firebase.google.com/docs/firestore/security/rules-conditions): 認証、文書データ、他文書の参照による許可条件を記述できる一方、参照数上限と読取り使用量への影響がある。
- [Cloud Firestoreのフィールドアクセス制御](https://firebase.google.com/docs/firestore/security/rules-fields): 読取りは文書単位であり、同一文書の一部項目だけを隠せないため、機密度の異なるデータを別文書へ分離する必要がある。
- [Firebase Authenticationのパスワード認証](https://firebase.google.com/docs/auth/web/password-auth): パスワードポリシーとメールアドレス列挙保護を設定できる。
- [Firebase AuthenticationのPasswordPolicy](https://firebase.google.com/docs/reference/js/auth.passwordpolicy): 最小・最大文字数と小文字、大文字、数字、記号の各必須条件を確認できる。
- [Firebase AuthenticationのGoogleログイン](https://firebase.google.com/docs/auth/web/google-signin): FirebaseプロジェクトでGoogleプロバイダーを有効化し、Web SDKで個別のGoogleアカウントを認証できる。
- [Firebase Authentication JavaScript API](https://firebase.google.com/docs/reference/js/auth): Google等の認証プロバイダーによる再認証処理を提供する。
- [Firebase IDトークン](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.decodedidtoken): UID、認証時刻、Firebase MFAの第二要素等を検証できるが、Googleアカウント側の2段階認証実施を同じ第二要素情報として保証するものではない。
- [Firebase TOTP MFA](https://firebase.google.com/docs/auth/web/totp-mfa): Firebase MFAはAuthentication with Identity Platformへのアップグレードを前提とするため、料金体系と費用0円条件の確認が必要である。
