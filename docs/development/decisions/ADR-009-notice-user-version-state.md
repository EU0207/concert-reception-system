## 問題と比較

連絡の既読を端末だけで持つと同じ本人の別端末に反映できず、全員共通にすると他人の読了で本人の未読が消える。内容版を持たない確認は、旧版をオフラインで確認した記録で訂正後の重要連絡を確認済みにしてしまう。

| 案 | 利点 | 欠点・影響 |
|---|---|---|
| A・提案：内容版×本人の状態をRTDBへ分離 | 他人と旧版を混ぜず、同じ本人の複数端末を収束できる | 新しいnotice領域・自己専用取得のRulesと未受領状態が必要 |
| B：端末内だけで保持 | 通信が少ない | 端末間で状態を維持できず、消去・再準備で本人の確認を失う |
| C：連絡に全員共通の既読・確認を保存 | 状態が少ない | 利用者別の要件を満たさない。管理者の既読管理へも広がりやすい |

## 提案と適用範囲

2026-10-20、開発者がPR #240の先頭`ba382f492a39649c1b3d3906c91302cdfae93252`をレビュー承認し、mainへ統合した（`ae07d7b53cdb6d065c5d9b66b6830605a0f04fdf`）。案AをAcceptedとし、以下の提案時の説明は判断根拠として保持する。製品試験・配備の承認は含まない。

Aを提案する。連絡の原文・訂正と取消しは不変イベントとし、現在表示はその投影とする。本人状態は内容版ごとの読了と明示確認を分離し、通常の管理画面に他人の読了一覧を公開しない。#221の保守中バックアップの限定取得は別に認可・監査し、通常の取得許可へ転用しない。重要確認を管理者による代理確認や新しい認可条件へ使わない。

訂正後は新しい内容を未読とし、重要なら本人が改めて確認する。同じ版の既読・確認は一方向に合流させ、旧版の事実を現在版へ移さない。並行する訂正・取消しはBD-03の競合確認へ接続し、到着順の上書きを採らない。

重大操作の確認はBD-06の共通UIへまとめる。対象と期待版を固定した独立2画面とし、業務側の現在認可・全件受領等の検査を省略しない。回復可能な通常訂正へ一律に2回確認を増やさない。

## 影響と未確認

保存・差分取得と本人状態の同期は#234、現在認可は#110、各重大操作の確定は業務担当へ渡す。連絡領域も#221のバックアップ・削除照合、#220の追加通信・保存測定へ含める。保持要件を縮小したり課金登録で無料条件を代替したりしない。

新しいRules・端末復帰と競合解決の実行は未確認。既存PoCへ合格件数を加算しない。技術レビューで採用を判断し、本番実装・配備と追加外部試行は別の開始条件に従う。
