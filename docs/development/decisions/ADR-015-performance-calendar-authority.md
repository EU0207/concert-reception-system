## 問題と確認済みの範囲

当日の初回席確定にも理由が必要である。初回本番受付開始前でもこの条件を適用し、端末時計や要求本文の`isPerformanceDay`をサーバーの判定根拠にしない。

現行製品の公演初期化は、公演管理版と形式版を作成する。環境所有者による初期主担当UIDの割当とスタッフ期限は前提設定である。一方、公演日と会場タイムゾーンの正本、その変更権限と日付境界の登録経路は未接続である。端末用の`venueDateAtServerTime`と`offlineDeadline`があることだけでは、直接API要求の検査を代替しない。

本ADRでは業務上の理由条件を変えず、判定に使う公演暦の登録責任を決める。採用前にはこの登録経路の製品コードを追加しない。

## 候補

| 候補 | 利点 | 欠点・影響 |
|---|---|---|
| A：環境所有者の初期設定へ公演暦を含める（推奨） | 初期主担当UIDの明示割当と同じ信頼境界を使える。通常の確定要求は保存済みのUTC境界とRTDBのサーバー時刻を比較する | 公演ごとの初期設定に暦の登録が増える。暦の変更を通常の席編集APIへ含めない。公演日時変更の画面接続は別途設計が必要 |
| B：アプリからの公演日時登録・変更まで先に設計する | 公演の設定を通常画面から管理できる | 会場暦からUTC境界への変換の検証方法、変更権限と監査を確定する必要がある。#111・#264の範囲が増え、席の確定保存の接続順も変わる |

## 案Aの具体案

2026-11-15、開発者が「案A：初期設定に含める（推奨）」を選択した。環境所有者の初期設定へ公演暦を含める。案Bは採用しない。以下は採用した登録責任であり、製品試験の合格や実環境への登録完了とは区別する。

環境所有者が、初期主担当UIDの割当時に次の暦を同じ公演へ登録する。端末へ秘密情報を配布せず、初期設定用の管理資格を製品アプリへ組み込まない。

| 項目 | 内容 |
|---|---|
| `performanceDate` | 会場の年月日。実在する日付として検査する |
| `venueTimeZone` | IANAタイムゾーン。端末の設定は使わない |
| `dayStartsAt`・`dayEndsAt` | その会場日が始まるUTC時刻と翌日が始まるUTC時刻。開始を含み終了を含まない |
| `calendarRevision` | 公演暦の版。対象公演への所属と一緒に検査する |

登録前に、日付・タイムゾーンと両UTC境界の対応を、信頼する初期設定手順で検証する。固定24時間を足して翌日を作らず、夏時間がある会場も扱う。登録先は公演の`control`配下とし、通常の本人・端末認証からの作成・変更を拒否する。

確定保存側は登録済みの境界とサーバー時刻で当日を判定する。暦が未登録・不正なら確定を拒否し、端末の下書きを保持する。下書き編集・保存の理由不要は維持する。確定済み構成の有無と初回受付開始は、それぞれ保存側の現在値を使う。

暦の訂正は、未確定の公演で環境所有者が行う。既存の準備確認と送信案を古いまま使わせず、期待版に暦の版を含める。確定済み構成または初回本番受付開始がある公演の日時変更は、本案の通常経路に含めない。保存・バックアップと復旧に同じ暦と版を含める。

## 採用後の実装と確認

- #111：初期設定の検査と公演初期化への結合、暦がない公演の拒否を確認する。初期設定の事前値を製品の通常初期化の成功と混同しない。
- #104・#283：古い暦の版、端末時計の変更と本文の当日フラグ偽装を直接要求で拒否する。当日開始・終了の直前直後、初回確定と再確定で理由条件を確認する。
- #105・#264：未登録時の案内と入力保持を接続する。#221はバックアップと復旧の版照合へ含める。

このADRの承認だけで上記の製品試験を合格にしない。RTDBの現在認可、明示停止と受付優先の同期契約は維持する。
