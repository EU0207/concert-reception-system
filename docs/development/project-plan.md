## 開発工程

| 工程 | 主な目的 | 主な成果物 | 次工程へ進む条件 |
|---|---|---|---|
| 要件定義 | 必要な機能と条件を合意する | プロジェクト概要書、要件定義書、受入条件書 | 依頼者による承認 |
| 設計 | 要件を満たす構成と方法を決める | ADR、基本設計、テスト方針 | 依頼者および開発担当者による確認 |
| 実装 | 承認済み設計に基づいて構築する | アプリケーションコード、単体テスト | 実装内容と自動テストの確認 |
| テスト | 要件と受入条件を満たすか確認する | テスト仕様書、テスト結果 | 不具合対応と受入条件の確認 |
| リリース | 利用可能な状態で提供する | リリース記録、運用手順 | 依頼者による最終確認 |

## GitHubでの管理

- 正式な仕様と設計は `docs/` で管理します。
- 作業と議論はGitHub Issueで管理します。
- 進捗はGitHub Projectsで管理します。
- 変更はIssue単位のブランチとPull Requestで確認します。
- 重要な判断はADRで記録します。

## GitHub Projectsの状態

| 状態 | 移動条件 |
|---|---|
| Todo | 目的と完了条件が記載され、着手可能である |
| 進行中 | 担当者が作業を開始している |
| レビュー | 文書確認、Pull Requestレビュー、または依頼者確認を待っている |
| 完了 | 完了条件を満たし、必要な文書更新と統合が完了している |

## 工程承認

要件定義、設計、リリース前に承認用Issueを作成します。承認対象、確認結果、承認日をIssueと対象文書の両方に記録します。

## 変更管理

承認済み要件を変更する場合は、影響する設計、テスト、運用、日程を確認し、IssueとPull Requestに記録します。

## CI/CD

初期段階では導入しません。実装技術、自動テスト、公開先、権限管理が決まった時点で必要性を評価します。GitHub中心の運用に適合する場合は、GitHub Actionsを第一候補として比較します。
