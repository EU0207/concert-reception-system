## 用語

| 用語 | 説明 |
|---|---|
| 要件 | システムが満たす必要のある機能、品質、制約などの条件 |
| 機能要件 | システムが「何をできる必要があるか」を示す要件 |
| 非機能要件 | 性能、セキュリティ、操作性、可用性など、機能以外の品質に関する要件 |
| 受入条件 | 依頼者がシステムを完成と判断するための具体的な確認条件 |
| Issue | 作業、課題、確認事項をGitHub上で管理する単位 |
| ブランチ | 他の作業に影響を与えず変更を行うために、履歴を分岐させたもの |
| Pull Request | ブランチで行った変更を確認し、統合を依頼するGitHubの機能 |
| GitHub Flow | Issueごとにブランチを作り、Pull Requestで確認して `main` に統合する開発方法 |
| GitHub Projects | Issueなどを一覧化し、状態や担当者を管理するGitHubの機能 |
| ADR | Architecture Decision Recordの略。重要な技術上・設計上の判断と理由を残す文書 |
| ワイヤーフレーム | 画面に必要な情報、操作順、状態、権限制御を確認するための簡略図。本基本設計では最終的な見た目の詳細を固定しない |
| UIモック | 本番実装前に画面遷移や操作感を確認する、操作可能な画面見本。本システムでは架空データを使用し、Firebase接続や実データ保存を行わない |
| API | 画面や別のプログラムからサーバーの機能・データを利用するための接続方法。画面でボタンを隠すだけでなくAPI側でも権限確認が必要となる |
| セッション | ログイン後の利用者を一定期間識別し、許可された操作を継続するための状態 |
| 本人認証 | メールアドレスとパスワード等により、操作しようとしている人が登録利用者本人であることを確認すること |
| 認可 | 認証済みの利用者について、役割、公演、端末、操作、データに応じて実行を許可または拒否すること |
| 役割割当 | 利用者へ特定公演の主担当、代理管理者、臨時管理者、一般受付担当者のいずれかと有効期間を結び付ける情報 |
| 公演 | 受付、認可、同期、締め、削除の管理境界となる1回分の開催。複数日開催では1日目と2日目を別々の公演として登録する |
| 公演シリーズ | 複数の公演を整理し、設定をコピーするための任意のまとまり。受付や権限の境界には用いず、コピー後のデータは公演ごとに独立して変更する |
| 配置対象 | 初回名簿から取り込んだ席未割当の来場者。別の正本を作らず、配置確定までは座席、チケット、QR、受付資格を持たない |
| 席設定 | お客様に席を割り当てる操作。CONF-062で画面上の「配置」「割当」をこの表現へ統一した。席がない状態は「席未設定」、席が決まった状態は「席設定済み」とする。過去文書の「配置対象」は席未設定の対象者を指す |
| 公演状態 | 公演が準備中、当日運用中、終了確認中、締め済みのどこにあるかを示す状態。開催日時だけでは変更しない |
| 公演後管理 | 主担当・代理管理者がオンライン再認証後に過去公演の実績、訂正、削除希望、バックアップを扱う操作。当日受付の許可期限とは分けて判定する |
| 受付開始 | 主担当または代理管理者がオンラインで確認して、公演状態を準備中から当日運用中へ変更する操作 |
| 受付停止・準備戻し | 主担当または代理管理者が新しい本番受付を止め、公演状態を当日運用中から準備中へ戻す操作。既存の受付記録、未送信記録、履歴は削除しない |
| 受付停止後到着記録 | 受付停止を知らない完全オフライン端末で保存され、回線復旧後にサーバーへ到着した記録。通常受付へ自動反映せず、管理者が内容を確認する |
| 公演限定スタッフ | 一般受付担当者と臨時管理者。公演単位の個別メール・短期パスワード、役割、端末許可を使用し、会場タイムゾーンの公演翌日23:59:59に業務権限が失効する |
| 臨時管理者 | 主担当または代理管理者が当日だけ一般受付担当者から任命し、端末ごとの追加準備後に許可された当日管理操作を行う役割。主担当引継ぎ、環境設定、課金は行えない。2026-09-22の`CONF-046`より、過去文書の「一時管理者」「一時許可」と同じ役割を指す |
| 臨時管理者の追加準備 | 当日に一般受付担当者から任命された利用者が、承認済み端末ごとにオンラインで最新の役割と期限を確認し、当日管理に必要な差分データだけを取得する処理。完了するまで臨時管理者用操作は利用できない |
| 招待 | 管理者がメールアドレス、公演、予定役割、有効期限を指定し、本人の登録・受諾へ結び付ける1回限りの手続き。URLには個人情報を直接含めず、招待先メールとの一致とメール確認を必要とする |
| 端末の事前準備 | 当日使用するブラウザー保存領域・端末IDと公演の組合せごとに行う処理。本人、役割、端末承認を確認し、版、データ、整合性、保存、カメラ、架空データ練習、オフライン期限をオンラインで検証する。全項目成功時だけ準備完了とする |
| 差分更新待ち | 端末準備後に名簿、座席、座席表示名等の確定済み公演データ版が更新され、影響端末が変更分の取得を待つ状態。端末登録、カメラ練習、CryptoKey生成は維持するが、最新データ版との一致を確認するまで本番受付できない |
| 再準備必要 | ブラウザーデータ消去、端末ID変更、CryptoKey欠損、非互換アプリ版、役割・端末承認失効、整合性異常により、端末準備の必要項目を再実行する状態。通常の確定データ版更新だけではこの状態にしない |
| 端末関連付け | 同じ主担当UIDの追加端末を、Google再認証と既存承認端末に表示する短時間・1回限りのQRまたはリンクによって対象公演へ結び付ける処理。役割付与と端末準備とは分離する |
| オフライン許可 | オンラインで本人、役割、端末、公演、期限を確認した準備済み端末に、公演中の通常操作と公演翌日中までの確認・同期を許可する公演・端末固有状態。固定24時間・48時間ではなく、会場タイムゾーンの公演翌日23:59:59に失効する |
| 会場タイムゾーン | 公演日と期限時刻を解釈するため、会場スナップショットへIANAタイムゾーンIDとして保存する地域時刻の基準。端末の現在設定は期限計算に使用しない |
| 会場スナップショット | 公演ごとに保持する公演時点の会場名、会場住所、会場タイムゾーン等の情報。後日、別公演やコピー元の会場情報を変更しても過去公演の値を上書きしない。会場住所は購入者住所とは別の情報である |
| 端末停止 | 紛失等の対象となった公演・端末の組合せを一時的にロックする解除可能な処理。対象公演のデータを暗号化状態で保持し、停止検知後の復号、閲覧、新規受付、通常同期、オフライン利用を拒否する。同じ端末の別公演と同じ利用者の別端末は、個別に停止されない限り継続利用できる |
| 端末廃止・データ削除 | 回収不能、再利用しない、または公演締め後に管理者が明示的に選ぶ高影響操作。対象となる公演・端末の認証関連状態、準備済み公演データ、暗号鍵を削除し、その組合せを再利用不可にする。同じ端末の別公演には波及させず、端末停止とは別に扱う |
| 隔離領域 | 停止端末に残る未同期記録を正式な受付へ自動反映せず、管理者が紙記録等と照合して採否を判断するまで分離して保持する管理者専用領域 |
| 再認証 | ログイン中であっても、高影響操作の直前にパスワード等を再確認し、現在の利用者本人による操作であることを確かめること |
| メールアドレス列挙 | ログインや再設定画面の応答差から、特定のメールアドレスが登録済みか第三者に推測されること |
| スクリプト注入 | 入力値等へ不正なプログラムを混ぜ、他の利用者の画面で実行させようとする攻撃。一般にXSSとも呼ばれる |
| CSP | Content Security Policyの略。ブラウザーが実行・読込みできるスクリプト、通信先、画像等を制限し、スクリプト注入の影響を抑えるHTTP応答方針 |
| App Check | 正規のアプリからの要求である可能性を検査し、不正クライアントを減らすFirebaseの追加防御。本人認証やSecurity Rulesの代替ではない。本システムではWeb向けreCAPTCHA Enterpriseプロバイダーを第一候補とする |
| App Checkトークン | App Checkの判定後に発行され、保護対象サービスへの要求へ付与される値。本システムではFirestore要求ごとの使い捨てにせず、有効期間内で再利用する |
| reCAPTCHA評価 | Webアプリの操作リスクをスコア方式で判定する処理。App Check向けの方式では、通常利用者へ画像選択等の課題を要求しない |
| URLフラグメント | URLの`#`以降の部分。通常のHTTP要求やリファラーへ送られない性質を利用し、本設計では1回限りトークンの受渡しに用いる |
| ダイジェスト | 元の値から一方向ハッシュで得る照合値。本設計では招待等のトークン平文をサーバーへ保存しないために用いる |
| CryptoKey | Web Crypto APIが暗号処理に使用する鍵オブジェクト。本システムでは公演・端末単位のAES-GCM 256ビット鍵を非抽出として生成し、IndexedDBへ保存する |
| 非抽出鍵 | 鍵素材をアプリからエクスポートできない設定のCryptoKey。同一オリジンのスクリプトによる暗号処理まで禁止するものではない |
| データ暗号鍵 | 業務データ本体を暗号化・復号する公演・端末単位のCryptoKey。DEKとも呼ぶ |
| 鍵暗号化鍵 | データ暗号鍵を包んで保存するための鍵。KEKとも呼ぶ。本番設計では`CONF-036`により共有パスフレーズ、PBKDF2、KEK、鍵包みを採用しない |
| 追加認証データ | 暗号文には含めず、改変されていないことをAES-GCM等で同時に検証する識別情報。AADとも呼ぶ |
| 脆弱性 | 不正操作、情報漏えい、停止等につながる設計・実装・依存パッケージの弱点 |
| トレーサビリティ | 要件、設計、テストなどの対応関係を追跡できること |
| 本番相当構成 | 完成品と同じ主要な接続・認証・保存・配布の境界を備え、架空データで最終的な受入条件を試す構成。PoCの仮構成とは区別する |
| 試験証跡 | 入力条件、環境、操作、実測、結果を後から確認できる記録。秘密情報と実在する来場者情報は含めない |
| CI | 変更のたびにテストや静的解析を自動実行し、問題を早期に発見する仕組み |
| CD | 確認済みの成果物を検証環境や本番環境へ継続的に提供する仕組み |
| QRコード | 情報を二次元の図柄として表し、カメラなどで読み取れるようにしたコード |
| QR余白 | QRコードの周囲に確保する何も印刷しない白い領域。読取り機器がコード範囲を識別するために必要で、クワイエットゾーンともいう |
| CSV式注入 | CSVの値が`=`等で始まることにより、表計算ソフトで文字列ではなく数式として実行される問題 |
| 補助出力 | 日常運用の主要な出力とは分け、追加加工や個別集計が必要な場合に選ぶ出力。本システムでは通常CSVと任意項目選択CSVを指す |
| 未保存変更 | 編集画面で変更し、最後の明示保存から更新されている内容。端末下書き保存済みと業務確定済みは別の状態 |
| 下書き | 業務へ未反映の編集案。座席編集の「下書き保存」は端末内、「下書きを共有」は管理端末間の引継ぎを指す。どちらも受付・発券・確定帳票の入力にはしない |
| 端末下書き | IndexedDBへ暗号化して保存した未確定案。同じ端末・ブラウザーと許可された本人で再開できる。端末故障や保存領域消去への保証とは別 |
| 応答不明の操作記録 | 共有・確定前に端末へ保存する操作IDと送信内容。応答喪失後も同じ操作の結果を照会し、二重確定を防ぐために用いる |
| 基準版 | 編集開始時に取得した共有データの版。共有保存・確定時に現在版と比較し、他端末の変更を自動上書きしないために用いる |
| 環境所有者 | 本番Firebaseプロジェクトと料金契約を所有し、2段階認証、課金判断、所有権引継ぎを管理する者。主担当と同一人物が兼務できるが、業務責務とは分け、高影響操作の再認証、確認、記録を省略しない |
| 復旧キー | バックアップ専用鍵を安全に受け渡すための推測困難な秘密情報。暗号化バックアップファイルと別の場所・経路で保管する |
| 紙原本識別子 | 障害時に使用した当日運営表の紙を区別し、復旧時の転記元と重複を追跡するための個人情報を含まない識別子 |
| マジックバイト | ファイル先頭等にある形式固有の識別情報。拡張子だけに頼らず、実際のファイル形式を確認するために使用する |
| 確認コード | QRコードを読み取れない場合に、認証済みの受付画面で同じチケットを照合するための短い文字列。パスワードではない |
| 受付用データ | 既存の購入者名簿から、氏名、座席、必要な状態・例外など当日の受付に必要な項目だけを取り込んだデータ |
| 購入者名簿 | 主催者がシステム外で管理する元データ。住所、電話番号、メールアドレス等を含む場合がある |
| 購入者名 | チケット購入者として各席へ保持する氏名。前後の空白を除去後、内部の空白を含めて1～50文字とし、超過時は省略せず修正を求める。同じ購入者が複数席を購入した場合は各席に同じ値を登録し、座席表示名を変更しても上書きしない |
| 座席表示名 | 座席表や会場席管理画面で席ごとに表示する編集可能な名前。半角・全角の空白を除いて最大6文字とする。購入者名が上限内なら初期値とし、利用者名が判明した場合や代理来場時に変更できる |
| 管理用表示ラベル | 確保済み席の用途を座席表上で示す`スタッフ`等の表示。来場者の座席表示名とは区別し、来場者未割当ての間はチケットやQRコードを発行しない |
| 座席キャンバス | 会場席の編集、席配置、会場席管理で広い座席表を操作する領域。ドラッグまたはスワイプへ追随して全方向へ移動でき、ズームと選択席への復帰を行える |
| 交付方法 | 席ごとのチケットを電子チケットまたは紙チケットのどちらで渡すかを示す区分。未選択も許容する |
| チケット準備状態 | 席ごとの購入確定、入金確認、発行済み、交付済みを独立したチェックで示す記録。各項目の最新チェック日時を持つ。未入金でも発行・交付できる |
| 初回受付 | 対象公演で有効なQRコードを最初に受け付け、来場として記録すること |
| 再読取り | 初回受付済みのQRコードを再び読み取ること。正当な再入場か二重提示かを確認する契機となる |
| 例外対応 | 当日手渡し、現金受領、紛失、座席変更、特別案内など、通常受付と分けて確認・記録する対応 |
| 手動受付 | QRコードを提示または読取りできない場合に、管理者権限を持つ利用者が確認して受付を確定する操作 |
| 競合 | 複数端末で同じQRコードが初回受付として記録されるなど、復旧・統合後に管理者の判断が必要な状態 |
| 無効化 | データを通常利用の対象外にしつつ、履歴を残して必要に応じて復活できる状態にすること |
| 完全削除 | データを復活できない形で削除する高影響操作 |
| 管理者権限を持つ利用者 | 主担当、代理管理者、臨時管理者など、現在の役割により管理画面と高権限操作を許可された利用者 |
| 当日運営表 | システムを利用できない場合に紙受付へ切り替えるための、氏名・座席等を含む印刷用一覧 |
| 欠番 | 座席番号の並びの途中に、その番号の実在する座席が存在しないこと。画面上へ空間を置くスペースセルとは区別する |
| スペースセル | 通路や座席間の空間を座席表上で表す、座席ではない配置用の枠。来場者割当、QR発行、空席数・座席数の対象にしない |
| オフライン受付 | 通信を利用できない状態で端末に受付記録を保持し、復旧後の統合を前提として受付を継続すること |
| 独立した受付環境 | 他の環境とは別の端末内保存領域と識別子を持ち、受付記録を独立して保持・同期できる検証単位 |
| 事前取得 | 公演前の通信可能な時に、当日必要なデータや画像を端末へ保存して利用可能か確認すること |
| 差分同期 | 前回同期後に追加・変更された情報だけを送受信し、全データの反復取得を避ける同期方法 |
| 論理データモデル | データベース製品やコード上の型を決める前に、業務で扱う情報の意味、関係、制約を整理したもの |
| エンティティ | 公演、来場者、座席、チケット等、業務上ひとまとまりとして識別・管理する情報の単位 |
| 正本 | 同じ意味のデータが複数箇所にある時に、最終的な判断根拠とする記録。本システムではデータ区分と通信状態に応じて明示する |
| 変更不能イベント | 受付や訂正等の発生した事実を、後から上書きせず新しい記録として追記するデータ。本システムでは現在状態と履歴の根拠にする |
| 現在状態 | 変更不能イベントを順序と業務規則に従って読み取り、現在の来場、座席、QR、例外等を表示できる形へ導出した情報 |
| 冪等性 | 同じ送信や操作を再実行しても、1回実行した時と同じ結果になり、同じ受付記録等を重複作成しない性質 |
| 送信キュー | 端末へ保存済みで、オンライン共有の確認が完了していないイベントと再試行状態を公演・端末ごとに管理する並び。業務イベント本体とは分離する |
| 同期カーソル | 端末が共有先のどこまで差分を取得済みかを示す位置情報。差分を端末へ保存した後にだけ進める |
| 状態導出 | 変更不能イベントの集合と業務規則から、来場状態、未送信、競合等の現在表示を再計算すること |
| 未解決競合 | 矛盾する複数イベントについて、管理者の判断イベントがまだ記録されていない状態。到着順だけでは解消しない |
| 競合確認イベント | 競合する候補イベントを参照し、管理者が判断区分と理由を追記する変更不能イベント。元イベントを削除・上書きしない |
| 同期アダプター | 業務層の共通イベント形式とFirebase等の共有サービス固有API・エラーの違いを変換する境界 |
| 共有確認位置 | 端末のどの連番まで共有先で受領確認できたかを示す位置。締め前の未送信0件確認に用いる |
| 削除記録 | 削除の対象区分、理由、実行者、時刻、結果等を残す監査情報。削除した個人情報を復元できる内容は含めない |
| 締め処理 | 公演終了、全送信確認、管理者確認の後に、公演を通常終了状態とし端末データ削除へ進む操作 |
| 例外終了 | 回収不能端末を停止し、紙記録等と照合した後、未確認記録の範囲と理由を残して公演を終了する管理者操作。全件受領や回収不能端末の削除完了を意味しない |
| PoC | Proof of Conceptの略。技術方式を採用または本番実装する前に、限定した範囲で実現可能性や制約を確認する検証 |
| Firebase | Googleが提供するアプリ開発向けサービス群。本件のPOC-001では認証とCloud Firestoreだけを検証した |
| Firebase Hostingプレビューチャネル | live公開を変更せず、期限付きの公開URLへ静的Webアプリを配信して確認するFirebase Hostingの機能 |
| Firebase Console | Firebaseのプロジェクト、利用サービス、権限などをブラウザで管理する画面 |
| Cloud Firestore | Firebaseで利用できる文書形式のデータベース |
| Sparkプラン | Firebaseの請求先登録を必要としない無料プラン。無料枠超過時の利用継続を保証するものではない |
| 端末別認証主体 | 本人の認証とは別に、端末のブラウザープロファイルへ与えるFirebase Auth UID。端末停止のRules判定に使用する。端末の物理的な非複製性は保証しない |
| セッション証跡 | 本人Authから対象端末UIDに対して作成する、有効期限付きのログイン確認情報。端末Authだけでは作成できない |
| 画像バンク | 会場画像の確定版または作業版を格納する固定2枠の一方。版番号を増やして保存量が無制限に増えることを防ぐ |
| 原子的な確定 | 一つの操作に必要な変更がすべて成功するか、一つも適用されないこと。席交換の片方だけを保存しないために使用する |
| トランザクション | 関連するデータの読取りと書込みを一つの確定単位で実行する仕組み。読み取った版が変わった場合は再試行または競合として扱う |
| 期待版 | 編集や確認の根拠にしたデータの版。保存先の現在版と比較し、古い確認による上書きを防ぐ |
| 座席表投影 | 確定構成と席設定から、画面・帳票の表示に必要な共通形式へ変換したデータ。表示のために席番号を再採番しない |
| 成立性確認 | 提案した方式が、容量や認可などの制約内で実現できるかを確認すること。資料の確認と実証結果を区別する |
| 割当表集約 | 一つの文書へ席IDと来場者IDの対応を保持する保存候補。来場者から席への逆引きは取得済みの対応から導出し、二重保存しない |
| フィールドマスク | 保存要求で変更対象のフィールドを指定する仕組み。変更しない席を再送せず、保存後の全体整合性はRulesで別に検証する |
| 番号索引 | 列と表示番号から重複を検査する補助データ。席の識別子はseatIdのままとし、席データと索引を同じ保存で更新・検証する |
| ID索引 | IDから対象データを直接探せるようにした対応表。席ごとに全セルを検索し直す処理を避けるために使う |
| 比較用fact | 新旧の同じ席を比較するための論理データ。Seat全項目と対応するCell、重複検査用の表示番号を含む。保存文書の形式や完成証明そのものを意味しない |
| chunk | 大きなデータを分割した保存片。GD91-04では同じ列のセル群を一文書に保持する。画面上の列や座席IDとは別の保存単位 |
| manifest | 保存片IDと版の一覧。GD91-05では端末の手元の版と比較し、見逃した更新も含めて取得対象を判定する |
| 世代切替 | 新しい状態一式を準備・検証した後、現在有効な世代への参照を切り替える保存方式。準備中のデータを確定状態として配布しない |
| ordinal | 検証用の連続した通し位置。席番号や座席IDとは分け、変更片を飛ばさず確認したことの証明に用いる |
| Owner | Google Cloud／Firebaseプロジェクトの所有者権限。権限や請求を含む広い管理ができるため、依頼者側で保持する |
| Google Analytics | Webサイトやアプリの利用状況を計測するサービス。POC-001では目的がないため無効にした |
| PITR | Point-in-time recoveryの略。データベースを過去時点へ戻す機能。POC-001では課金対象機能のため使用しない |
| 追加要望 | 利用者から追加で示された要望。採否・詳細の決定前は受入対象と分離し、決定後は由来を示す要望IDと新しい要件ID・受入条件IDを対応付ける |

| 来場cycle | 一人の来場予定に対応する券の内部管理単位。不参加で閉じ、復帰後の新しい券操作では次の単位を使う。過去の発券履歴を保持しつつ、復帰だけで旧QRを有効にしないために使用する候補 |
| 配布目録 | 対象データの版・識別子と照合値、予定件数を示す一覧。目録との一致だけでは端末への保存成功を証明しない |
| 単体テスト | 一つの関数や小さな処理を取り出し、入力に対する結果や失敗時の動作を確認する試験。自動か手動かとは別の分類 |
| 結合テスト | 複数の処理やサービスを接続し、認証から保存までの流れや境界を確認する試験。Emulatorによる自動試験と実機の結果を区別する |
| SDK | サービスをアプリケーションから利用するためのライブラリー群。Firebase SDKは認証やデータ取得・保存のAPIを提供する |
| バッチ書込み | 複数の書込みを一括確定する操作。通常のFirestore SDKではオフライン中の要求が待機し、接続回復後に送信される場合がある |
| コールバック | 別の処理から呼び出される関数。トランザクションでは競合により同じ関数が再実行されるため、操作IDなどを毎回作り直さない |
| gRPC | サービス間の要求と応答をやり取りする通信方式。GD91-61のNode SDKではHTTP/2経由で使用し、UNAVAILABLEは要求先を利用できないことを表す |
| プロキシ | 通信を中継する処理。GD91-61ではローカル試験用にエラーを注入し、送信失敗と回復後の動作を確認する |
