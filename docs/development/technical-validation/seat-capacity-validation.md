## GD91-74 要求量と容量

計測結果は[measurement.json](../../../poc/GD91-74/artifacts/measurement.json)、容量と参照の算定は[analysis.json](../../../poc/GD91-74/artifacts/analysis.json)を正本とする。計画組立て・試験再確認のGETと前提投入を含むため、課金額の実測とは扱わない。

10人・500人の全工程2件と回収境界の7件が合格。同じV2の最終Rulesを使用し、18件のソースハッシュを現在ファイルと照合した。V2の225件を今回の実行へ加算しない。

| 通常要求として計測した範囲 | 10人・2区画 | 500人・2区画 |
|---|---:|---:|
| 構成準備と2区画公開 | 134書込み | 3,284書込み |
| 通常登録 | 60書込み | 3,000書込み |
| 配置の段階検査と最終確定 | 12＋4書込み | 502＋4書込み |
| 全工程の成功書込み | 219 | 6,799 |
| 受付投影の明示取得1回 | 56 GET | 2,006 GET |

全工程には両端末のセッション発行、初期化と共有2書込みも含む。ownerの前提投入・提案組立て代用は別集計。500人の最大REST JSONは288,201 B、送信された最大文書の公式式による容量モデルは174,087 B。REST JSONは実際の10MiB要求上限のプロトコル容量と同一ではなく、文書モデルには索引・サーバー時刻変換を含めない。

現在の投影取得は、不変構成と割当済み表示名を1件ずつ結合する。500席・2区画では明示取得1回が2,006 GETとなる。再描画ごとの取得ではない。Rulesの依存読取りは別途必要であり、全取得を繰り返す端末数・回数を制限せずに無料成立とは判断できない。[依存文書の課金規則](https://firebase.google.com/docs/firestore/pricing#cloud_firestore_security_rules)も上限評価へ含める。

### 最大構成の制約

1区画・偶数列の下限。列台帳・候補発行と公開の書込みは含まない。文書容量は差替え時の`baseSeats/current`の主要4フィールドだけで、他の必須項目と索引は別。

| セル／席 | 文書容量の下限 | 構成準備の書込み下限 | 判定 |
|---|---:|---:|---|
| 500／500 | 112,286 B | 3,250 | この下限だけでは成立確定できない |
| 1,000／500 | 149,786 B | 6,000 | 上限候補としての追加評価が必要 |
| 5,000／5,000 | 1,120,286 B | 32,500 | 文書上限と日次無料書込み枠を超える |
| 10,000／500 | 824,786 B | 55,500 | 日次無料書込み枠を超える |

[公式の上限](https://firebase.google.com/docs/firestore/quotas)は1文書1MiB、無料書込み20,000件／日。10,000セルは検証器の入力条件で、承認済み製品上限ではない。日次枠は他の公演・操作とも共有する。複数日に分ける場合も、原子的な確定境界を分割しない。

### 参照上限

GD91-63の分岐別予算へGD91-73の索引検査を加えた算定では、通常登録23、保護なし2席操作21、保護付き2席操作23。構成公開25、再発行・券あり不参加23、復帰22となる。これはキャッシュ減算なしの机上値で、実際に毎回拒否されるという意味ではない。

[公式資料](https://firebase.google.com/docs/firestore/security/rules-conditions#access_call_limits)のキャッシュ除外を、この候補の一定回数の減算保証へ置き換えない。最新の文書単位予算の全分岐再計算、式評価回数と参照上限の保証は未完了。Emulator合格を採用保証へ流用しない。

## 保持と回収

[retention.json](../../../poc/GD91-74/artifacts/retention.json)は正本・現行構成と退役構成、操作結果の削除拒否を確認する。拒否によって結果を保てることと、不要な構成を回収できることは別である。

| 保持対象 | 回収前に満たす条件 |
|---|---|
| 現行の構成・受付参照 | 現行目録が指す世代は対象外。回収開始時も最新版と照合する |
| 準備中の構成・基準世代 | 完成候補と送信中の参照を確認し、排他的な削除中状態へ遷移させる |
| 端末・共有下書き | 未送信参照を把握する仕組みが必要。ローカル下書きが無いと推測して回収しない |
| 操作IDの結果・業務履歴 | 構成片と一緒に消さない。承認済み保持条件と遅延再送の照合を先に成立させる |

現候補には端末参照の登録・期限、削除中の再公開拒否と上限付き回収の実装がない。`usedIds`は過去IDを増加保持するため、構成片の削除だけで索引容量の増加も解消しない。自己申告だけの「参照なし」やowner権限での削除を合格証拠にしない。

CONF-049・050の手動削除とバックアップ保管を維持する。[保持・復旧の基本設計](../basic-design/retention-backup-remediation.md)へ追跡する。承認済み期限を再確認せず、無人TTL削除へ置き換えない。

## 次の対応

現候補は本番採用へ進めない。無料条件を維持したまま、容量ガードと不変構成の再取得削減を優先する。参照の保証と安全な回収も同じ#167で閉じる。製品上限は技術案として500人・全区画合計1,000セルを評価し、現時点では採用・強制しない。区画数と文字長も文書・要求容量の予算に含める。

この縮小対応で成立しない場合は候補を増やし続けず、制約と代替案を#168へ提示する。外部Firebaseでの確認、課金有効化と有料実行基盤の追加は今回の作業に含めない。

- **決めてください**：無料条件を維持する縮小対応を優先するか。推奨は500人・合計1,000セルを上限候補として評価し、容量ガードと取得再利用を組み込む案。上限の製品採用は今回確定しない。広い配置の自由度は再評価が必要になる。
- 現候補の上限なし採用は推奨しない。有料の信頼済みサーバー案は基盤・運用と承認済み条件が変わるため、今回は導入しない。
