## 結論

`POC-002`は、承認済みの範囲と合格基準に対して**合格**と判定する。

- デコード済み架空QR 500件を6つの独立環境で処理し、通常判定の最大は実Firebaseで3.0ミリ秒、95パーセンタイルは1.6ミリ秒、失敗は0件だった。
- 500件の自動処理合計は実Firebaseで108.25ミリ秒だった。
- オンライン変更30件を他5環境で観測した150標本の最大共有時間は273.63ミリ秒、95パーセンタイルは250.55ミリ秒で、目標5秒・上限10秒を満たした。
- 各環境は初期同期後の変更を30件ずつ受信し、500件の全件反復取得がないことを確認した。
- 実Firebaseの環境別外部通信量は最大23,866 bytes（約0.023 MiB）で、1端末20 MiB上限を満たした。
- ローカルエミュレーターと実Firebaseの両方で同じ合格条件を満たした。

この合格は、Chromium上でデコード済み文字列を処理する候補方式の性能と通信量についての限定的な結果である。カメラ、QR画像解析、実端末、実回線、本番負荷、個別認証、権限制御、暗号化またはFirebase採用の承認を意味しない。

## 測定方法と解釈上の制約

- 通常判定は、QR画像を読み取った後に相当する架空文字列の業務判定からIndexedDB保存完了までを測った。カメラ起動、焦点、画像解析、人の提示時間は含まない。
- 500件合計は自動投入によるシステム処理時間であり、500人の実受付に要する現実の経過時間ではない。
- 共有時間は送信側のFirestore書込み開始から、受信側5環境の画面状態反映までを測った。
- 通信量はChromium NetLogのソケット送受信量である。接続先不明は外部扱いにして過小評価を避け、ループバックと確認できた通信だけを除外した。携帯回線のIP層、TLS以外の端末通信、OSの通信は含まない。
- 実測最大約0.023 MiBは20 MiB上限より大幅に小さいが、実機・実回線の最終確認はPOC-003等の別承認範囲で行う。

## 検証中に判明し対処した事項

| 事項 | 対処 | 本番候補への引継ぎ |
|---|---|---|
| オンライン受付のたびに全件一覧を再取得すると測定と通信量が増える | 未送信分だけを送る`pushPending()`を追加し、一覧取得と分離した | 受付時は差分送信、必要時だけ明示的に全体同期する |
| 6環境が同じ実行親文書を同時作成するとRulesの更新拒否が起きた | 初期準備を順次実行し、既存親文書との一致確認を追加した | 作成の冪等性と競合を設計・試験する |
| NetLogの依存関係だけではlocalhostソケットを外部と誤分類できた | ソケット自身の接続先アドレスを優先し、ループバック試験を追加した | 通信量集計規則と除外根拠を証跡に残す |
| オフライン再読込みはPOC-001と重複し、性能測定中に旧オンライン画面を残した | 事前準備済み画面をオフライン化して測定した | 再起動成立性と処理性能を別試験として維持する |

## 保存データ、費用、終了処理

- 実在する来場者情報、実在QR、メールアドレスは使用していない。
- 実Firebaseには専用実行ID配下の架空イベント530件と匿名利用者6件だけを作成した。
- Sparkプラン、請求未設定の既存検証資源だけを使用し、追加サービスや有料機能を有効化していない。
- 環境別通信量、文書件数、認証利用者数は開始承認書の停止上限を大幅に下回った。
