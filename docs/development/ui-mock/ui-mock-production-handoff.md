## 結論と適用方法

2026-09-28の静的UIモック充実計画に基づく更新状況は、[静的モック確認記録](ui-mock-static-review.md)に記載する。次の対応表のモック状態は同記録を踏まえて更新した。本番の実装済みを意味しない。

本番の対象は、モックにある機能だけに限定しない。下表の承認内容を要件・基本設計・受入条件の追補として適用する。古い比較案と相違する場合は、下表の最新内容を採用する。過去の回答と変更経緯は削除しない。

モックの「反映」は表示と架空データによる操作の再現を意味する。本番の保存、認証、同期が実装済みという意味ではない。全項目の本番実装と本番試験は未実施である。

CONF-068の締め権限制限はモックに反映する。臨時管理者の権限カスタマイズはモック対象外とし、設定可能な操作と安全条件を[変更Issue #98](https://github.com/EU0207/concert-reception-system/issues/98)で設計する。本番の画面表示とサーバー側判定の双方で、主担当・代理管理者以外の締めを拒否する。

2026-10-02に依頼者から、お客様情報で個別にお客様を追加できない点への指摘があった。モックで追加操作を試せるようにした後、CONF-067で本番採用と権限・必須入力・初期状態の承認を受領した。重複候補、履歴、同時更新の設計は#97で追跡する。

2026-10-02の開発者指摘により、モックの主担当端末の廃止は別の準備済み主担当端末を必要とする比較案へ変更した。カードの常時警告を外し、廃止を押した時に理由を示す。後続のCONF-069で、主担当端末の廃止条件は本番でも採用された。代理管理者端末は主担当引継ぎの完了前には代替としない。差分は#94で追跡する。

表の`MCT-xx`は本番試験への引継ぎIDとする。既存のACを置き換えず、関連ACに追加して確認する。モック専用のFB-13は本番機能から除外する。

## データと安全性の追加条件

以下は既存要件に対する変更・補足であり、表示だけの対応で完了にしない。

1. **購入者名**：誤字修正は主担当・代理管理者の管理操作とする。1～50文字の検証を維持し、購入者IDに結び付く対象席を一覧確認して一括修正する。同名だけで別購入者を統合しない。代理来場による表示名変更とは分離し、変更前後を履歴へ残す。未保存の破棄と版競合時の入力保持を維持する。
2. **不参加**：来場者記録と入金状態は削除しない。席解放、現在の券状態の解除、旧QRの無効化と履歴登録を一つの業務操作として扱う。一部だけ成功した状態で席を他者へ再割当てしない。発行済みQRの無効化は回復不能な操作として2回確認する。一般的な座席変更でQRを維持する既存規則と区別する。
3. **復帰**：来場予定へ戻しても未配置・未発行から再開する。旧QRを再有効化しない。履歴は不参加前の席、券発行・券送付状態を確認できるようにする。紙・電子チケットが手元に残る場合も旧QRを有効と扱わない。
4. **固定項目**：入金済み・券発行済み・券送付済みを固定し、最新チェック日時と確認付き一斉操作を維持する。未入金発行を許可する。券送付済みは郵送・データ送付・手渡しの完了を含む旨を説明する。チェックだけで決済・発送・自動送信は行わない。
5. **確認用項目**：購入者単位・席単位の記録範囲を項目作成時に指定する。削除は復元UIを設けず、過去のチェック記録の保持期間は既存の詳細履歴規則へ合わせる。権限と保存形式を詳細設計へ落とす。
6. **セル採番**：開始番号1で`席／欠番／空間／席／通路／席`なら、`1／欠番2／番号なし／3／番号なし／4`とする。配置前の種別変更はこの規則で再採番し、確定前に番号の変化をプレビューする。割当済み・発行済みの席は自動で番号をずらさず、個別変更の確認へ進める。画面と帳票は同じ確定構成を使う。

2026-09-29に各列内の席番順序を反転する操作をモックへ実装し、[CONF-061](ui-mock-client-response.md#conf-061-席番の逆順設定の本番採用)で本番採用の承認を受領した。横方向は左から／右から、縦方向は上から／下からを選択し、列名の並びは変えない。固定セルIDと番号消費規則を維持し、配置への影響は既存の確認・券発行済み保護を通す。#91、MHD-03で本番の保存形式と試験へ引き継ぐ。
