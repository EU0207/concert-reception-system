| 関連作業 | #110・263の本人認証・端末登録、#111の公演初期化、#264の運用手順、#220・266の完成アプリ受入 |

**本書は完成版の操作手順書ではない。** 「実装待ち」の節では作業を止める。公開中のソース、UIモック、過去の検証成功を、本番利用可能の意味に読み替えない。#220の完成アプリ無料受入と、対象版の受入条件を満たすまで本番利用しない。

## 最初に読むこと

- 通常の利用にNode.jsの起動は不要。完成したアプリは利用者自身のHostingのHTTPS URLで開く。
- 依頼者用・開発用・各主催者用のFirebaseプロジェクトは別にする。公開リポジトリにアクセスしても、依頼者のアプリを利用する権限は付かない。
- URLを知ること、ログインできること、業務を許可されることは別である。本人の役割・端末承認と事前準備が必要。
- Googleのパスワード・確認コードと復旧コードは本人が管理する。開発者やIssueへ送らない。
- 通常は支払方法を登録せずSparkを使う。無料トライアルや課金への切替を、手順を進めるために選ばない。
- 設定の失敗時に、Rulesを全許可にしたり、端末内データを消したりして回避しない。

## 役割と第三者利用の範囲

| 役割 | 担当すること |
|---|---|
| 環境所有者 | Googleアカウント・Firebase環境の所有、利用量確認、復旧手段と権限管理 |
| 主担当 | 公演準備、スタッフ招待、端末の承認、受付開始・停止と終了処理 |
| 受付スタッフ | 自分のログイン、端末準備、練習と当日の受付 |
| 開発・保守担当者 | 別途合意した範囲だけの技術作業。通常運用のための恒久的な所有者にはならない |

同じ人が環境所有者と主担当を兼ねてもよい。役割によって確認する項目は省略しない。

第三者の自主運用では、利用者自身が専用の環境を所有する。第三者向けの設定代行・個別サポートと復旧支援の範囲は、公開前に別途確定する。手順書の提供だけで支援を約束したものと扱わず、依頼者との個別の引渡し・保守の合意と分ける。

ソフトウェアの利用許諾条件、保証範囲と問い合わせの扱いは、第三者への公開前に別途確定する。本書だけで利用許諾や法的責任の免除を定めない。

## 用意するもの

| 項目 | 確認する内容 |
|---|---|
| 管理用Googleアカウント | 利用主体が管理し、本人がログインと2段階認証を行える |
| 復旧方法 | 管理担当者の交代や端末喪失時にも回復できる |
| 設定用PC | 完成版の対応OS・ブラウザーと、配布手順で指定したツールを使える |
| 受付端末 | 完成版が対応するブラウザー・カメラと端末内保存を利用できる |
| 回線 | 初期設定・ログインと事前準備をオンラインで行える |
| 配布物 | 本番利用可能と明示された版と、その版に一致する手順書 |

実際の環境名やアカウントは、利用者自身の非公開の記録へ保存する。公開Issueやリポジトリへ実値・実在する来場者情報を記入しない。

## 1. 自分専用の環境を用意する

### 1-1. アカウントを確認する

1. 管理用Googleアカウントでログインする。
2. Googleアカウントのセキュリティ設定を開き、2段階認証を確認する。
3. 復旧手段を安全な場所へ保管する。第三者へパスワードを預けない。

完了の目印：環境所有者本人がログインでき、復旧方法の保管場所を把握している。

### 1-2. Firebaseプロジェクトを作成する

この節は、完成版の配布開始と設定手順の検証後に実施する。現在は実行しない。

1. 所有者本人のアカウントで[Firebase Console](https://console.firebase.google.com/)を開く。
2. 規約が表示された場合は、利用主体と内容を本人が確認する。
3. プロジェクトの新規作成を選び、自分の環境と分かる名前を指定する。
4. プロジェクトIDを確認してから作成し、自分の非公開の管理記録へ控える。
5. Google Analyticsは有効化せず、通常運用はSpark・請求先未接続とする。

完了の目印：自分が所有する独立したプロジェクトで、予定したIDと料金プランになっている。開発者や他の主催者のプロジェクトを選んでいない。

### 1-3. アプリ用のサービスと配布物を設定する【実装待ち】

完成時には次の各項目について、実際の画面名・操作と確認結果を記載する。

| 設定対象 | 完成版で記載・検証すること |
|---|---|
| Webアプリ登録 | Web設定値の取得方法と、環境別設定へ反映する方法 |
| Authentication | Googleとメール・パスワードの設定、認証メールと許可ドメイン |
| RTDB | 対象版で確認済みの地域、拒否を基準とする製品Rulesの適用方法 |
| App Check | 対応する設定・本番用登録と、正規端末の確認方法 |
| Hosting | 環境設定と製品版を組み合わせる方法、対象プロジェクトを誤らない配布手順 |
| 配布後確認 | 未認証・役割外アクセスの拒否、利用量と対象版の確認 |

現時点では製品用の配布設定・認可処理が未完成である。Firebaseの一般的な初期化コマンドやPoCのRulesを代用しない。「とりあえずテストモード」で実データを置かない。

完了の目印：完成版の実行可能な手順と確認結果がすべてそろい、自分の環境で対象版の確認に合格していること。未記入なら先へ進まない。

## 2. 最初の主担当と管理端末を登録する【実装待ち】

最初の登録端末が0台でも、環境所有者が本人を確認して初期設定する経路を設ける。既存管理端末を使う「追加端末登録」とは分ける。

1. 環境所有者が、対象環境と初期主担当本人を確認する。
2. 主担当本人がGoogleログインを行う。パスワードや確認コードを所有者へ送らない。
3. 本人のFirebase UIDと対象公演を照合し、初期主担当の役割を明示的に割り当てる。
4. 初回端末の識別情報を確認し、所有者による初期承認を完了する。
5. 端末の事前準備を行い、本人の環境・公演と管理機能を確認する。

本人UIDを明示割当する方針は、BD-04-02で承認済みである。具体的な初期化手段と操作画面は、#111・263・264の設計・実装に合わせて追記する。Consoleで行う範囲と補助手段の範囲を、本書だけで確定しない。

上記は手順案であり、現在実行できるボタンやコマンドの名称ではない。未検証のDB操作を代用手順にしない。

### 公演暦を初期設定へ含める（ADR-015・案A）

2026-11-15の開発者判断により、初期主担当の明示割当と一緒に公演日・会場タイムゾーンを環境所有者が登録する。[ADR-015](../development/decisions/ADR-015-performance-calendar-authority.md)を登録責任の正本とする。通常の受付端末から公演暦は変更しない。

開発用Node.js環境を準備済みの場合、次の補助コマンドで架空公演の登録用本文を検証できる。**このコマンドはDBへ接続・登録しない。** 実環境での登録完了や、本書全体の受入完了の代わりにはならない。

```powershell
node scripts/prepare-performance-calendar.mjs --environment-id 00000000-0000-4000-8000-000000000001 --performance-id 00000000-0000-4000-8000-000000000002 --date 2026-11-22 --time-zone Asia/Tokyo --revision 1
```

出力の`path`は対象公演の`control/calendar`、`calendar`は登録用本文である。日付・会場とUTC境界を確認してから、環境所有者の初期設定手順へ渡す。`control`全体を置き換えたり、本人の役割・端末を出力から作り直したりしない。IANAタイムゾーンが不正、日付が存在しない場合は出力しない。

初回は暦の版を1とする。訂正は準備中で確定構成がなく、初回本番受付を開始していない公演に限る。既存版に1を加え、公演管理版が初期化済みならその版も更新する。古い準備確認と送信案を再利用せず、関連する期限も照合する。実環境へ登録する具体的な操作手順の完成は#111・#264で確認する。

### 初期登録全体の完了確認

完了の目印：管理端末0台から、指定した本人と端末だけが主担当として利用できる。別のGoogleアカウントや、URLへ先にアクセスした人は管理者にならない。

初期設定に一時的な技術支援を利用した場合は、完了後に不要な権限を削除する。環境所有者本人の権限は残す。初期設定を外部の特定個人へ依存させない。

## 3. URLを開き、初回の動作を確認する【製品経路は未実装】

1. 自分のHostingに割り当てられたHTTPS URLをブラウザーのアドレス欄で開く。
2. 表示された利用環境と配布版が、自分の管理記録と一致するか確認する。
3. 登録済みの主担当本人としてログインする。
4. 管理機能・端末状態を確認し、架空データで画面操作と事前準備を確認する。
5. 対応ブラウザーのブックマーク、または検証済みのホーム画面追加手順で入口を保存する。

Hostingの標準ドメインを使えるため、独自ドメインの購入は必須ではない。実際のURLは配布結果で確認する。URLをログイン画面のメールアドレス欄へ入力しない。

入口の案内には、通常URLのリンクを使う。紙の案内に通常URLのQRを載せる場合も、権限を付与する招待QRとは区別する。QRの作成方法は、採用する案内方式と確認済み手順を完成時に記載する。

| 種類 | 目的 | 扱い |
|---|---|---|
| 通常のアプリURL | 自分の環境のログイン入口を開く | URLだけで業務権限は得られない |
| スタッフ招待リンク | 招待された本人が対象公演へ参加する | 期限付き・1回限り。本人宛てだけに送る |
| 主担当の追加端末QR・リンク | 本人の追加端末を既存の承認端末と関連付ける | 初期端末0台の登録には使わない |

完了の目印：入口を保存でき、正しい本人・環境で再度開ける。ブックマークやホーム画面追加だけを端末の事前準備完了とみなさない。

## 4. 公演を準備し、スタッフを招待する【製品経路は未実装】

1. 主担当が公演・会場を作成する。
2. 名簿を登録し、会場席と来場者の席を設定する。
3. 公演データを確認し、確定した版を記録する。
4. スタッフ本人のメールアドレス・予定役割と有効期限を指定し、招待リンクを作る。
5. リンクを本人宛てのメール・LINE・SMS等で送る。パスワードは送らない。

完了の目印：公演データが確定し、対象者だけへ招待が届いている。誤送信した招待は失効させて作り直す。

実際の画面の名称と、名簿の入力例は#111・264および関連する業務画面の実装後に追記する。

## 5. 各スタッフの端末を承認・準備する【製品経路は未実装】

1. スタッフ本人が、当日使うブラウザーで招待リンクを開く。
2. 指定された個別認証の手順で登録・ログインする。一般受付担当者はメール確認と招待受諾を済ませる。
3. 管理者が、本人・対象公演と登録対象の端末を確認して承認する。
4. 本人が事前準備を開始し、必要なデータ取得と端末内保存を完了する。
5. カメラと架空データでの練習を確認し、対象公演・データ版と利用期限を確認する。

完了の目印：管理者側と本人側の両方で、当日使う各端末が準備完了になっている。1人の準備完了を別端末へ流用しない。

主担当本人の追加端末は、Googleの再認証と、既存の承認済み端末を用いた1回限りのQR・リンクによる関連付けを使う。スタッフ招待と取り違えない。

準備後に名簿・席などの確定版が変わった場合は、必要な差分を更新して最新版との一致を確認する。端末登録や練習を理由なくすべてやり直さない。

当日は主担当または代理管理者がオンラインで受付開始を行う。受付開始状態と端末の準備が確認できるまでは、本番の受付を始めない。

## 困ったときに止まる場所

| 状況 | 行うこと | 行わないこと |
|---|---|---|
| 開発版・モックしか見つからない | 対象版の完成と受入結果を確認する | 実データで本番運用しない |
| 利用環境が違う・設定が不正 | URLと環境設定の対応を確認する | 端末保存を消して無理に起動しない |
| 課金の有効化を要求された | 選んだ製品・プランが手順どおりか確認し、作業を止める | カード登録で先へ進まない |
| 初期主担当・端末を登録できない | 初期設定経路と本人・対象環境を確認する | 先着順管理者や全許可Rulesへ変更しない |
| 招待が期限切れ・誤送信 | 管理者が失効・再発行を行う | 招待リンクを公開Issueへ貼らない |
| 準備が途中で止まる | 失敗項目と画面の案内を確認する | 準備未完了のまま受付しない |
| 承認済み管理端末が0台になった | 所有者による復旧手順へ進む | 招待やバックアップだけで端末承認を省略しない |

第三者が自主運用する際は、自分の環境内で記録と復旧方法を管理する。公開資料へ利用者の氏名・ログイン情報や秘密を貼らない。問い合わせ窓口や回答期限は、別途の合意なしに保証されたものとして扱わない。

## 完成前に埋める項目と確認方法

次の未完了項目を#264の運用手順と、対応する実装・受入へ引き渡す。ここに記載しただけで担当Issueや受入条件を完了扱いにしない。手順案の確認項目であり、既存の受入条件の追加・変更を確定するものではない。

- [ ] 完成版の取得先、版の選び方と対応PC・端末を記載する。
- [ ] 1-3に、対象版のFirebase設定・Rulesと明示的な配布コマンドを記載する。
- [ ] 管理端末0台からの初期登録を、実際の画面・補助手段で説明する。
- [ ] 3～5の画面名・操作と完了表示を、製品コードの実物に一致させる。
- [ ] 対応ブラウザー別の入口保存・ホーム画面追加を確認する。
- [ ] 設定に不慣れな読者が、作者の口頭説明・遠隔操作なしで1～5を完了できる。
- [ ] 各節に、開く場所・入力例・成功表示と失敗時の戻り先を記載する。
- [ ] 画像は架空データを使い、秘密情報や実際のアカウントを載せない。
- [ ] 初期端末登録・追加端末・紛失復旧を区別して演習する。
- [ ] 許諾条件・保証範囲と第三者向けサポート方針を公開前に確認する。
- [ ] #220と全受入の結果を対象版に照合し、本番利用可能の表示を判断する。

確認結果には対象版・実施日と実施範囲を残す。完了できなかった項目を、開発者が横から操作して成功扱いにしない。追加の外部試行は、範囲と予算の承認を先に行う。

## 非公開の管理記録へ残す項目

| 分類 | 記録内容 |
|---|---|
| 環境 | 所有主体、プロジェクトIDと利用URL |
| 配布 | 対象版、確認済みの構成と配布日 |
| 本人・端末 | 初期主担当の識別情報、承認済み管理端末と復旧担当 |
| 契約・費用 | 利用プラン、請求先の状態と確認日 |
| 運用 | バックアップの保管先、終了・削除と担当交代の手順 |
| 支援 | 個別契約がある場合だけ、その対象と終了時の扱い |

パスワード・確認コード、秘密鍵と生の招待トークンは管理記録にも書かない。利用者情報を公開リポジトリへ保存しない。
