## 先に知っておくこと

- 開発中の検証環境と、本番環境は別にする。
- 検証専用プロジェクトは複数PoCで再利用できるが、PoCごとに架空データと不要な利用者を削除し、後続PoCは個別承認後だけ開始する。本番へ転用しない。
- 本番環境は、依頼者が指定する組織用Googleアカウントが常に所有する。開発者個人のアカウントを本番の唯一のOwnerにしない。
- Googleアカウントのパスワード、確認コード、復旧コードを開発者へ渡さない。
- アカウント所有者本人にしかできない作業は、初回規約の確認・承諾、二段階認証、復旧手段の管理である。
- Firebaseの技術設定は、依頼者が一人で行う前提にしない。依頼者が一時的に招待した技術担当者が設定し、完了後に権限を削除または縮小する。
- 通常の公演運用は将来のアプリ管理画面で行い、Firebase Consoleを日常的に操作しない構成を目標とする。

## 担当の分け方

| 作業 | 依頼者・後任管理者 | 技術担当者 |
|---|---|---|
| 管理用Googleアカウントの保有 | 必須 | 不要 |
| 規約確認、二段階認証、復旧手段 | 本人が実施 | 画面案内だけ |
| プロジェクトのOwner維持 | 必須 | 原則Ownerにしない |
| Firebaseの技術設定 | 完了確認 | 一時権限で実施 |
| パスワード・確認コードの共有 | しない | 求めない |
| 納品時の権限整理 | 実施または立会い | 不要な権限を返却 |

## 用意するもの

1. 組織で管理するGoogleアカウント。個人が退職・離任しても回収できるものを推奨する。
2. 二段階認証に使う機器と、別の安全な場所に保管する復旧方法。
3. 本書と、納品時に確定する「本番プロジェクト名・プロジェクトID・リージョン」の控え。
4. 初期設定を支援する技術担当者のGoogleアカウント。

## 初期設定手順

### 1. 管理用Googleアカウントを保護する

1. 管理用アカウントでGoogleへログインする。
2. Googleアカウントの「セキュリティ」を開き、二段階認証を有効にする。
3. 復旧用電話番号・メールアドレスまたは復旧コードを、組織のルールに従って登録・保管する。
4. パスワードと確認コードは他人へ送らない。

完了の目印：管理用アカウントでログインでき、二段階認証と復旧手段を管理者が説明できる。

### 2. 規約を確認する

1. 管理用アカウントで[Firebase Console](https://console.firebase.google.com/)を開く。
2. Google CloudまたはFirebaseの規約画面が表示された場合は、内容と利用主体を確認する。
3. 承諾する場合は、アカウント所有者本人がチェックと承諾を行う。
4. 無料トライアル、カード登録、請求先アカウント作成を勧められても、このプロジェクト用には選ばない。

完了の目印：Firebase Consoleのプロジェクト一覧が表示される。規約の判断を技術担当者へ代行させない。

### 3. 本番プロジェクトを作成する

Firebase採用が正式承認された後だけ実施する。

1. Firebase Consoleで「プロジェクトを作成」を選ぶ。
2. 納品手順に記載された本番用の表示名を入力する。
3. プロジェクトIDを確認し、納品資料へ記録する。作成後の変更はできないため、入力間違いがあれば作成前に戻る。
4. Google Analyticsは**無効**にする。利用目的と承認が別途生じた場合だけ再検討する。
5. Spark（無料）プランであること、請求先が未設定であることを確認して作成する。

完了の目印：プロジェクト概要に本番用の名前が表示され、プランがSpark、Analyticsが無効、請求先が未設定になっている。

### 4. 技術担当者を一時的に招待する

1. Firebase Console左上の歯車から「ユーザーと権限」を開く。
2. メンバー追加を選び、支援する技術担当者のGoogleアカウントを入力する。
3. 初期設定期間だけ必要な権限を付ける。最初の案はEditorとし、本番構成確定時に、より狭い権限へ変更できるか確認する。
4. Ownerは依頼者側の管理用アカウントに残す。
5. 招待したアカウント、付与日、目的、削除予定日を納品チェック表へ記録する。

完了の目印：依頼者側Ownerが残り、技術担当者は依頼者のパスワードを知らずに自分のアカウントで操作できる。

### 5. 技術担当者がFirebaseを設定する

この節は技術担当者が実施し、依頼者は完了結果だけを確認する。

1. Web Appを1件登録し、環境設定値を秘密情報と分けて安全に配置する。
2. Cloud Firestoreを、承認済みリージョンとStandard構成で作成する。
3. Authenticationで、承認済みのログイン方式だけを有効にする。
4. Firestore Security Rulesを配備し、未認証・権限外アクセスが拒否されることをテストする。
5. 必要なドメインだけを認証の許可対象にする。
6. PITR、バックアップ、課金製品、Analyticsなど、承認されていない機能を有効にしない。
7. 設定結果と確認日を納品資料へ記録する。APIキー、パスワード、秘密鍵、認証トークンは資料やGitHubへ書かない。

サービスの有効化直後は設定反映に数分かかる場合がある。エラー時は連打せず、画面を更新して少し待ってから再試行し、それでも失敗する場合は表示文を秘密情報を除いて技術担当者へ伝える。

### 6. 依頼者が最終確認する

Firebase Consoleで次を順番に確認する。

- 「ユーザーと権限」：依頼者側の管理用アカウントがOwnerである。
- 「使用量と請求」またはプラン表示：Sparkで、請求先アカウントが接続されていない。
- 「プロジェクトの設定」：本番用プロジェクトIDが納品資料と一致する。
- 「統合」またはAnalytics表示：Analyticsが無効である。
- Authentication：承認したログイン方式以外が無効である。
- Firestore：リージョンが納品資料と一致し、テスト用の実在個人情報が残っていない。

不一致があれば本番利用を始めず、技術担当者へ修正を依頼する。

### 7. 開発者・技術担当者の権限を整理する

1. 初期設定と納品確認が終わったら「ユーザーと権限」を開く。
2. 継続保守契約がなければ、技術担当者のメンバーを削除する。
3. 継続保守がある場合も、Ownerを付けたままにせず、契約上必要な最小権限へ縮小する。
4. 削除・縮小後、依頼者側OwnerでConsoleを開けることを確認する。

メンバー削除は相手のGoogleアカウント自体を削除せず、このFirebaseプロジェクトへのアクセスだけを失効させる。

## 納品時に書面へ残す項目

| 項目 | 記録内容 |
|---|---|
| 管理者 | 個人メールを公開資料へ書かず、管理部署・担当役割を記録する |
| Firebase | プロジェクト表示名、プロジェクトID、リージョン、作成日 |
| 契約 | Spark、請求先未設定、Analytics無効の確認日 |
| 有効サービス | Web App、Firestore、Authenticationなど承認済みのものだけ |
| 権限 | Ownerの管理主体、外部技術担当者の有無、見直し日 |
| データ | 保存項目、保存期間、締め処理、削除確認方法 |
| 復旧 | アカウント復旧責任者と社内の安全な保管先。秘密そのものは記載しない |
| 問合せ | 保守窓口、契約終了時の引継ぎ先 |

## 普段の管理を少なくする方針

- 公演作成、スタッフ登録、事前準備、終了処理はアプリ内の分かりやすい管理画面へまとめる。
- Firebase Consoleを開くのは、初期設定、権限変更、障害確認、年次点検などに限定する。
- 開催前チェックでは、アプリ側に「同期済み」「未送信0件」「事前取得済み」「利用期限」などを表示する候補とする。
- 無料枠の上限に近づく設計を避け、料金・利用量を採用時と各開催前に確認する。
- カード登録や有料プラン変更は、依頼者の別途明示承認なしに行わない。

これらは設計方針であり、具体的な管理画面は要件・設計承認後に作成する。

## 後任者向け引継ぎチェック

1. 管理用Googleアカウントへログインできる。
2. 二段階認証と復旧手段の管理責任者が分かる。
3. FirebaseプロジェクトIDを納品資料と照合できる。
4. Spark、請求先未設定、Analytics無効を確認できる。
5. Ownerと外部メンバーを確認し、不要なメンバーを特定できる。
6. 通常運用はアプリで行い、Firebase Consoleでデータを直接編集しないことを理解している。
7. 障害時の連絡先と、開催時に紙運用へ切り替える条件が分かる。

## 禁止事項

- Googleアカウントのパスワード、確認コード、復旧コードをメール、チャット、Issueへ貼らない。
- サービスアカウント鍵やCLI認証トークンをGitHubへ保存しない。
- 内容が分からないままBlaze、無料トライアル、請求先接続を選ばない。
- 本番FirestoreのデータやSecurity RulesをConsoleで直接変更しない。
- Ownerをすべて削除しない。
- 開発用・POC用プロジェクトを本番へ転用しない。

## この手順を確定する時期

Firebase採用と本番構成が承認された後、納品前に次を追加して`Approved`へ変更する。

- 実際の画面名に合わせたスクリーンショット。アカウント名、メール、プロジェクト固有値、個人情報はマスキングする。
- 本番用の確定したプロジェクト名、リージョン、有効サービス、権限。
- アプリ管理画面で行う通常運用手順。
- 障害時、契約終了時、管理者交代時の連絡・復旧手順。
- 依頼者または後任者による手順の読み合わせ結果。
