## 結論と前提

- 既存の購入者名簿を元に受付用データとQRコードを準備し、当日の来場受付、例外対応、来場状況確認を行う。
- 通信停止中も複数端末で受付を継続し、復旧後に統合する。利用不能時は紙の当日運営表へ切り替える。
- 紙チケットとシステムが出力した電子チケットPDFを通常提示とし、販売、オンライン決済、実印刷、発送、来場者への送信は扱わない。
- `RQ-001`～`RQ-006` は詳細確認を終えて正式要件化した。技術方式は未決定であり、PoCの承認または技術採用とは区別する。
- 技術方式の影響が大きい要件は、Issue #5で検証条件を確認し、Issue #6で承認済みの調査・PoCを完了した。結果、制約、未達目標は本書と受入条件書へ反映済みであり、技術方式の採用は要件承認後にADRで別途決定する。

## 承認条件

- 依頼者が決定済み要件、対象外、追加要望、未決定事項の区分を確認する。
- `TBD-005`、`TBD-006`、`TBD-008`、`TBD-010`、`TBD-013` の確認済み方針と後続設計の境界を確認する。
- Issue #5で[技術検証計画書](../development/technical-validation-plan.md)を確認し、技術検証が必要な要件、評価方法、合格基準、PoC実施可否を合意する。
- 承認されたIssue #6の調査・PoCを完了し、結果と要件への影響を反映する。
- [受入条件書](acceptance-criteria.md)を検証結果に合わせて更新し、要件との対応を確認する。
- 技術検証後に別途作成する最終承認Issueへ、承認結果を記録する。
- 本書と受入条件書が承認されるまで、アプリケーションコードの実装を開始しない（INT-Q-035）。
