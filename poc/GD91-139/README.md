# GD91-139 Firestore中心候補の通常登録と6SDK取得

状態：In Review。#168の隔離検証。本番実装ではない。

空の名簿から管理端末が来場者を登録し、6つのFirebase Web SDK接続が一般受付向けの表示名を取得する。購入者名と入金情報は管理用正本へ分ける。認可正本はFirestore内に置き、RTDBの接続表示へ依存しない。

```text
node poc/GD91-139/run-local.mjs
node poc/GD91-139/audit.mjs
```

既存POC-004のFirebase CLI・SDKとJavaを使う。追加インストールなし。専用demoプロジェクトのFirestore 8383・Auth 9493だけへ接続する。4／600／1,000人を別のEmulatorプロセスで実行し、Javaヒープ上限は各8GiBとする。同じプロセスを4GiBで使い続けた先行実行ではメモリ不足と後処理409が発生したため、[失敗記録](artifacts/heap-failure.json)を保持した。実サービスのメモリ要件を示す値ではない。

登録はhead・来場者正本・公開表示名・新操作結果の4書込みを一体送信する。新操作結果で現在の認可を検査し、他の文書を同じ新規操作と版へ結ぶ。通常のセッション発行後に実行し、来場者・表示名のowner投入は0件。headの4096セル・16区画、役割と端末登録は前提投入で、公演開始もowner前提である。共有購入者・券と受付イベントの全契約を実装した登録ではない。

各規模で8登録端末・6SDK接続を用意する。受付担当6人と匿名UID6件を別々に発行し、各本人からセッションを作る。SDKは永続キャッシュを使わず`getDocFromServer`で取得する。公開表示名は12件ずつの並列単件取得であり、32件のクエリーページやリアルタイム通知の検証ではない。

30群を実行するうち、3群は期限境界の反例観測である。「期限切れをSDK単独で必ず拒否できた」という合格数に含めない。端末停止・役割失効の拒否と別公演の継続は確認対象とする。SDKの実通信量・請求数、全業務と無料成立は未測定。

先行実行で、期限切れをRESTは拒否しても既存SDK接続が値を返す例があった。新しいSDK接続では拒否した。新規セッションの発行後も接続を作り直す条件を入れている。原因は未特定で、実サービスでも起きる、または製品が利用不能とは判断しない。

比較用の取得関数は、取得前後に短いREST要求で現在の権限・公演状態を検査し、どちらかが拒否ならデータを呼出し元へ返さない。これは表示へ渡す境界の候補であり、直接SDK要求のサーバー側認可を置き換える採用仕様ではない。取得中の失効と混在版への処理を含む全受信経路は未確認。画面表示・IndexedDBも未実装。

各人数の終了時にSDKを閉じ、全拒否Rules・空試行データ・Auth 0件を確認する。最終結果は[集約記録](artifacts/local-summary.json)、[ソース監査](artifacts/audit-summary.json)、[正式な検証記録](../../docs/development/technical-validation/seat-capacity-validation.md#gd91-139-firestore中心候補の通常登録と6sdk取得)を参照する。過去の失敗・smoke結果を最終30群へ加算しない。
