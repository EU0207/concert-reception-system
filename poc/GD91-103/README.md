# GD91-103 グループ所属・固定と席操作理由の保存接続

## データと処理の流れ

| コード・保存先 | 方式・理由 |
|---|---|
| `model.mjs`・`event/people` | 通常登録でgroupId・rosterOrderを設定する。入金・不参加と復帰では保持する。所属変更と並替えの操作は追加しない |
| `event/roster`・`event/groupInfo` | 名簿順と所属を導出する索引。登録1人分を名簿と同時保存し、人数カウンターと索引の欠落・直接削除を拒否する。登録人数自体を10人へ制限しない |
| `event/groupStates` | グループ単位にfixed・manualReasonを保存。全員分の名簿へ固定フラグを複製しない。通常の席変更から固定状態を書き換えない |
| `group-rules.mjs` | 登録済み所属を使い、最大10人全員の前後席を検査。自己申告の人数と履歴だけで公開・再配置を許可しない |
| `event/operations` | 手動分割・固定解除と再配置、直前取消しを共通版へ結合。直前の確定履歴から元席・固定と理由を復元し、版は巻き戻さない |
| `common-groups.mjs` | 同じ8群をRESTと実SDKへ接続する比較手順。管理履歴を一般受付へ配布せず、通常の移動・交換でQRを保持する |

構成・業務と公演管理版、本人・端末の権限を確定時に照合する。候補参照の予約を維持し、古い版や同一IDの再確定を拒否する。空席は構成上の席の存在・利用可否を保存側で確認する。

空白理由は[公式の文字列replace](https://firebase.google.com/docs/reference/security/database#replacesubstring_replacement)で空白文字を除いて判定する。200文字は隔離評価値で、製品上限の採用ではない。理由判定は次の承認済み業務条件に限る。

| 操作 | 理由と保護 |
|---|---|
| 手動分割 | 空白だけを拒否し、全所属を固定。発券履歴・有効QRまたは不参加者が一人でもいれば再編を拒否 |
| 空席への移動 | 発券履歴・有効QRがある場合は理由必須。QR・グループ状態を保持 |
| 二人の交換 | 初回受付開始前は理由不要。開始後は停止中も必須。公演管理版の競合を拒否 |
