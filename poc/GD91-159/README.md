# GD91-159 同じDB内の削除台帳と正本移管

状態：In Review。#168・TECH-DD91-118-Aの隔離検証。初期化した台帳が最新であることは試験前提であり、正式な初期化の成立は未確認である。

## 作るものと理由

`restoreAuthorities/{performanceId}`を公演の正本台帳とする候補を作る。空の移行先に置いたバックアップ自身を、最新の削除状態の根拠にしないためである。各環境の`restoreBinding`は書換え禁止とし、通常クライアントによる台帳の新規作成と削除を拒否する。

台帳の現在環境と、移行中の対象環境だけを扱う。正本を凍結してから業務本文を照合し、一つの移行先へ許可を発行する。旧環境は公開時に参照・更新を停止する。元の本文を自動削除することはなく、全複製回収の合格ではない。

## 処理とデータの流れ

1. 現在認可と15分以内の再認証を満たす主担当が、正本を凍結する。凍結と業務更新を混ぜた要求は全体を拒否する。凍結後の読取りと本人によるセッション更新は維持する。
2. 取込開始と台帳の移行ロックを一体更新する。移行先の主担当に加え、正本側の主担当が現在も有効か検査する。台帳版と元データの削除版を目録へ固定する。
3. 既存155の片単位の通常取込と再取得を使う。公開、台帳の正本移管と元環境の許可停止を同じルート更新へ含める。片側の更新は拒否する。
4. 公開後は通常訂正と受付詳細削除へ接続する。削除境界と台帳の削除版を一体更新する。古い削除版や、現在版だけを偽装した削除済み本文は拒否する。

台帳の変更に連動する`restorePermit`を、Rulesが保護する許可として使用する。業務書込みは更新後の許可も確認する。Authの既存3領域は元の式を維持する。元の認可式を除去せず、業務118読取り・769書込みに保護条件を追加した。

25反例では、次の経路を拒否した。

- 台帳の自己初期化・削除と、結び付けの改変。台帳不明時の業務読取り。

## 未確認と境界

- 同一DBの同じ主担当を対象とする。別DB・別プロジェクトの認証と、所有者変更の引継ぎは未確認。
