# GD91-162 独立保全台帳と復旧許可の消費

状態：In Review。TECH-DD91-120-Aの隔離候補。独立した保全台帳が最新のまま残る前提を置いた局所結果である。通常バックアップの復旧全体を合格としない。

## 作るものと理由

元DBを閉じた時点の復旧許可を、業務DBと別の保全端末へ残す候補を作る。復旧先を有効にする要求の前に許可を消費することで、同じ古い許可から二つ目の復旧先を開かない。

許可に含めるのは、公演識別子と本文ハッシュ、削除版と削除操作IDなどの最小メタデータである。氏名や受付本文、認証情報を台帳へ保存しない。本文は別の業務バックアップに保持する。台帳ファイルを復旧用バックアップから再作成せず、管轄を確認した保全先の現在値だけを読む。

## 処理とデータの流れ

| 段階 | 処理 | 失敗時の扱い |
|---|---|---|
| 保全 | 元DBの現在認可で凍結し、管理用の固定状態と取得停止を確認する。移行先に有効な台帳がないことも照合し、独立台帳へ許可を追記する | 元DBを閉じられなければ発行しない |
| 再取得 | 業務DBを失っても、独立台帳の現在の許可とバックアップのハッシュを照合する | 台帳不明・管轄不明や古い許可なら有効化しない |
| 復旧準備 | 本文と現在認可を準備し、移行先の許可を閉じる。台帳は管理専用の`recovering`に保ち、通常クライアントによる早期有効化を拒否する | 閉じたまま停止する |
| 許可消費 | 対象と現在認可を再確認し、独立台帳へ`activation-intent`を追記して同期保存・再取得する | 記録前の失敗は同じ許可から再試行できる。記録後は古い許可を再利用しない |
| 有効化 | 消費済みを確認してから移行先の管理用状態を解除し、取得・更新許可を開く | 応答不明でも独立台帳の消費を巻き戻さない。未完了を成功として表示しない |

書込み列はハッシュで前の記録へ結び付け、各追記後に`fsync`と再取得を行う。排他ファイルで同時発行を止める。欠落・末尾途中の書込みは復旧禁止とし、過去の読み取れる位置へ自動的に切り戻さない。残留ロックを自動解除する処理も実装しない。

[モデル24条件](artifacts/model-summary.json)では、許可の発行と消費、5か所の停止を確認した。対象違い・本文違いと現在の認可失効を拒否した。台帳の欠落、記録破損と管轄未確認も止めた。保管証明書自身を「現行台帳」として採用しない。

[Emulatorの5経路](artifacts/local-summary.json)では、通常認可で架空1人の実績を2回訂正してから元DBを凍結した。両方の業務DBを削除する故障を注入し、独立台帳とAuth Emulatorだけを残した。GD91-163の検査を使って訂正後の本文と削除版を照合した。準備中に通常クライアントが移行先を開く要求は拒否した。

正常時と許可消費前の停止からは有効化できた。消費後・管理用状態解除後の停止では、古い許可の再利用を拒否した。許可を開いた後に応答を失った場合も再利用を拒否し、公開要求前に台帳の消費が永続化されていた。読取り可能になった3経路では、保持実績を使う通常訂正をさらに1回行い、元の締め結果と削除境界を維持した。端末停止後の取得も拒否した。

業務本文と初期認可は試験用管理権限で前提投入した。正式ブラウザー取込・暗号化バックアップとの接続や、別プロジェクトのAuth復旧を確認したものではない。159のRules生成は変更していない。終了時は両DBを全拒否・空データにし、Auth 0件を確認した。要求量とソース照合は結果JSONを正本とし、実サービスの無料利用量へ換算しない。

モデルの先行準備はディレクトリURLをファイルパスへ変換する前に停止した。[初回の失敗](artifacts/initial-setup-failure.json)を保持し、`fileURLToPath`による変換後に全条件を実行した。未実施の先行結果を合格へ含めない。

## 実際に確認できた制約

モデルでは、消費前の完全な台帳ファイルへ全体を戻すと、古い許可が再び有効と判定された。**ハッシュ鎖だけでは台帳全体の巻戻しを検出できない。** これは保全成立の合格ではなく、信頼する保全先の境界を示す制約である。`independentCurrentStore`は呼出側の管轄確認であり、最新性を自動証明する機能ではない。

保全端末と台帳が現在のものであることを確認できなければ、復旧を保留する。保全先そのものも失った場合に、保管中の古い証明書から新しい台帳を作らない。端末の保護と保管担当の引継ぎ、台帳全体の巻戻しを検出・回避する実運用は未検証である。Windowsのアクセス権を設定して保護した試験でもない。

この候補が復旧できるのは、元DBの通常変更を止めて許可を発行した時点に限る。移行先の有効化を始めると古い許可は無効になる。その後の通常削除を逐次記録する経路はない。主担当の通常バックアップと、全削除経路の外部証跡保全を代替したとは扱わない。既存の保持期間や通常業務手順は変更しない。

試験は例外を処理して台帳を閉じ、開き直したものである。プロセス強制終了や電源断は未検証。独立台帳が失われた状態での復旧、全サービス・全認証の喪失からの回復も未確認である。全DB喪失時の保全ゲートは条件付きの部分証拠として維持する。
