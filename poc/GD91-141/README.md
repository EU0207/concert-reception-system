POC-004の既存依存関係とEdgeを使う。600／1,000人を別のEmulatorで実行する。Firestore 8385・Auth 9495、ブラウザ配信4892はlocalhost限定。6つの独立したブラウザAuthとfetchによるREST取得であり、Firestore SDKのデータ取得や通知を検証したものではない。4人のsmokeは`--smoke`で実行でき、最終26群へ加算しない。

GD91-139の生成Rulesを変更せず使用する。8登録端末のうち6取得元を用意し、本人から通常のセッションを発行する。役割・端末登録と開催中状態は試験前提。業務本文はowner投入であり、139の通常登録を今回再実行した合格には数えない。

受信は、必要な3項目だけのheadで版と現在の認可を検査する。同じ版なら既存キャッシュを再利用する。変更があればhead全体と表示名の版を取得し、変更した表示名だけ本文を再取得する。最後にheadの版と認可を再確認してからキャッシュを入れ替える。途中失効・混在版・欠落応答では前のキャッシュを保つ。管理情報を一般受付へ返さない。

13群ずつ、計26群を記録する。初回全件取得・変更なしと1名変更を確認する。割当だけの変更、受信中の別版と実際の欠落文書も確認する。通常の端末停止・役割失効と、受信中に自然に到達するセッション期限を検査する。本文の改変・削除と復元は隔離試験のowner前提で、通常業務機能の合格ではない。

32件batchGetは診断用である。現Rulesは1文書7参照、32件ではキャッシュ減算なし224となり、20以内の静的保証がない。Emulatorの受理を採用根拠にしない。2件なら14、単件なら7の算定となるが、2件形式での全規模試験は未実施。batchGetはクエリーによるページ取得ではなく、既知IDをまとめた直接取得である。

表示名1件の変更でも全N人の版を読むため、本文だけの差分化では無料の読取り件数を抑えられない。予算は6取得元が同日50回の異なる変更版を観測する感度条件を計算し、業務文書だけの下限でも日次50,000を超える。これは正式な利用回数上限ではなく、全工程の50業務を表示名変更へ置換した比較でもない。運用制限で無料成立とせず、変更IDを追跡できる索引を次に検証する。

計測はREST要求・応答のJSON本文量。SDK認証通信とHTTPヘッダー・TLSは含めない。課金数・索引容量と全工程費用は未測定。GD91-140の直接SDK期限反例も未解決のまま保持する。

REQ-NF-013の共有5秒目標・10秒上限と1端末20MB以下を維持する。50変更版の応答本文だけでも20MBを超える。初回取得を省いた下限比較であり、初回名簿を正式な通信量対象から除外する判断ではない。通知・ポーリング周期と遅延の受入は未実施。
