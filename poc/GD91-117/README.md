# GD91-117 最大構成の結合と追加境界

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167条件1・DD91-T72・102を対象とする。本番実装と外部接続は行わない。

## 最大構成の結論

承認済みの上限を同時に使う構成で、600／1,000席の通常権限による初回保存・公開・取得が合格。1公演16区画、各区画256採番列、総4,096セルである。横・縦採番と正逆順を混在させ、未・通路・空間と欠番のセルも含めた。区画名100、列名64と席番64文字を保存し、用途100と理由200文字も全席へ付けた。

| 測定 | 600席 | 1,000席 |
|---|---:|---:|
| 非席セル数 | 3,496 | 3,096 |
| 保存片数 | 256 | 256 |
| 最大書込みJSON | 145,124 B | 145,124 B |
| 世代全体のJSON | 5,181,123 B | 5,858,134 B |
| 初回取得のREST要求数 | 309 | 309 |
| 保存・公開と取得などの通常要求数 | 643 | 643 |
| キャッシュ再利用時の世代再取得 | 0 | 0 |

全セルの全項目を保存前と照合し、席IDと表示席番の一意性も確認した。来場者レコードは0件であり、通常登録から発券までの600／1,000人合格はGD91-115の別証拠を使う。3,000人の構造・負荷試験ではない。

[models.mjs](models.mjs)が入力を作り、GD91-116の共通上限で検査する。[local.mjs](local.mjs)は通常管理要求で保存・公開し、同じ取得契約で全セルを復元する。[audit.mjs](audit.mjs)は最大構成と追加境界のソースを照合し、実行Rulesの一致を確認する。[測定結果](artifacts/audit-summary.json)。

Emulatorは8GiBを維持する。SDK接続のない工程境界だけで評価系を再初期化し、業務データのハッシュ不変と元Rulesの復元を確認した。この補助通信を通常要求へ算入せず、本番の高速化手段にも扱わない。最初の制限下の起動は待受け失敗で業務試験に未到達。ローカル待受けを許可した実行結果だけを合格へ数える。

## 追加境界

[addition-local.mjs](addition-local.mjs)で600／1,000席を維持した追加保存の2群が合格した。607→609セルと1,007→1,009セルで、それぞれ38→39片、63→64片へ増える。追加は2セルのうち1席と未1セルとする。部分公開を拒否し、既存の席IDと情報を保持する。[追加結果](artifacts/addition-summary.json)。

初回は復元後に付く`displayOrder`を入力モデルと比較して不一致となった。追加前後を同じ復元モデルで照合する方式へ訂正し、Rulesを変更せず再確認した。[失敗時の原データ](artifacts/addition-first-failure.json)。
