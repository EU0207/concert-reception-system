# GD91-95 共有予約の暗号化再開

状態：Draft。読者：開発者・設計担当者・テスト担当者。#167の共有送信中保持を、既存の非抽出鍵方式と実IndexedDBへ接続する隔離検証。来場者は架空データのみ。

[recovery.mjs](recovery.mjs)はGD91-94の保存接続口へ、GD91-76のAES-GCM・非抽出CryptoKey保存を接続した。[7群の結果](artifacts/recovery-summary.json)は全件合格。1,000席の候補・固定案を保存し、Edgeのブラウザープロセス終了後も同じ操作ID・予約IDを復元した。追加パスフレーズは使わない。

保存中断では直前の下書きを保持し、サーバー予約0件。公演・利用者と端末を区別し、古い端末保存版を拒否する。共有確定後に実REST応答ソケットを切断し、別端末が共有先を置換した後も元の結果を照会できた。照会の書込みは0件で、後続の共有先を巻き戻さない。

復号前の最新権限はNode側で確認した。失効時は復元を拒否し、暗号文・鍵と予約を残す。ブラウザーからDBへの要求は0件。ブラウザー内の認証持続とアプリ全体の通信、実機・物理容量不足は未検証。PoCの環境ID・鍵版を本番設定として扱わない。

GD91-94のdemo Auth・Database Emulatorと、GD91-86のVite設定をポート4181で起動し、本フォルダーの`recovery.mjs`を実行する。試行後に全拒否Rules・空ルートを再取得する。外部接続・本番実装と方式の採用は含めない。受付キューと全業務予算を同じ#167で継続する。
