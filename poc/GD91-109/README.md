# GD91-109 最大入力と保存・再開の境界

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の条件1・3・4を対象とする。PR #210は2026-10-16に承認・main統合済み。本番実装と外部接続は行わない。

## 結論

正式形式の600／1,000席で4,096セルを保存・取得できた。共有と確定の実REST応答を切断し、暗号化IndexedDBとEdgeの再起動から同じ操作を照会できた。参照が残る世代は回収しない。

一方、4,097セルは保存・公開できるのに既定の取得側が拒否した。TECH-DD91-101で総4,096セルへの共通化Aを選択済み。#167の条件3は保存契約のPoC確認を完了したが、共通上限の適用と締め・全登録端末の回収、全業務無料成立は未完了。本番採用は#168で別判定とする。

| 4,097セルの取得境界 | 通常保存・公開は成功、既定取得は拒否。明示的な257片予算では取得成功。[上限不一致](artifacts/read-boundary-summary.json) |

文字列境界は今回のRulesが使う長さで評価する。区画名100、列名64と表示席番64を使い、用途100と理由200を載せた。接頭部と番号の連結結果も64以内とし、16桁番号には48の接頭部を使用する。Unicodeコードポイントによる業務文字数の最終実装を、この比較だけで承認しない。

登録・発券の全工程はGD91-108の結果を維持する。今回の席操作試験は人数別データを管理用経路で投入し、通常要求で交換を試す。管理用の診断読取りを含む通信量を課金通信として加算しない。

demo Emulatorは8GiB。計測補助は業務データ不変と元Rulesへの復元を照合し、通常要求と分ける。実機手動試験とSDK内部の切断は別確認。保存領域の実容量不足・故障は未確認。

## 上限を揃える案（TECH-DD91-101）

2026-10-16、開発者がAを選択。総4,096セルへ保存と取得の予算を揃える方針を採用した。適用は未実装であり、PR #211全体のレビュー承認とは区別する。

| 案 | 内容 | 利点・影響 |
|---|---|---|
| A・採用 | 初期の構成予算を総4,096セルに揃える。16区画・1区画256列設定を評価範囲の候補とし、保存前とRules、取得側へ共通設定を適用 | 今回の根拠を使える。未・通路も総数へ含み、超過時は確定せず端末下書きを保持する |
| B・今回未採用 | 取得側を8,192セルへ広げ、保存・再開と総予算を追加検証する | 大きな余白を扱えるが、現在の合格を流用できず検証範囲が増える |

Aも未実装であり、現候補が超過をサーバー拒否できるという意味ではない。採用後は共通の容量設定から、画面入力・保存計画・Rules生成と取得予算を作る。区画単位で4,096を許可せず、公演の座席構成全体へ適用する。人数からセル上限を逆算しない。

将来は保存片の形式や席IDを変えず、設定と予算の再評価で増やす。4,097セルの明示予算による取得はその確認であり、8,192セルや3,000人の保証ではない。今回は3,000人の試験を行わない。
