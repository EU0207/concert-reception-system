# GD91-101 最新候補の人数別取得・受付と容量再接続

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の人数別・最大構成と総費用の残条件を同じ検証単位で継続する隔離PoC。本番採用・外部試行は行わない。

GD91-96の人数別シナリオを、GD91-100の凍結Rulesと共通連番の通信アダプターへ接続する。Rulesの複製・変更は行わず、既存の結果を新しい候補の合格へ流用しない。600人・1,000人は別のローカルEmulatorプロセスで確認する。

通常登録から発券・6SDK環境の取得と受付、再接続までの範囲を先に確認する。緊急編集・グループと最大構成は、同じ保存契約に接続済みかを照合し、未接続部分を単なる費用計算で合格にしない。公演管理・端末登録は前提投入。実機・ブラウザー内認証持続と全業務無料成立は別判定とする。

## 人数別の結果

2026-10-15、4人の接続確認後に600人・1,000人を別プロセスで実行した。通常登録→一括割当→QR生成・発行チェック→6SDKへの合同取得・受付→再接続まで合格。予約・確定・予約解除を通常管理要求へ含め、ownerで人・券を投入していない。

| 人数／非席セル／区画 | 通常管理要求 | 最大確定要求／ローカル時間 | 試行根JSON |
|---|---:|---:|---:|
| [600／600／2](artifacts/capacity-600-summary.json) | 5,403 | 336,910 B／約33秒 | 6,684,137 B |
| [1,000／1,000／16](artifacts/capacity-1000-summary.json) | 9,003 | 566,114 B／約50秒 | 11,150,228 B |

各SDKは3回取得し、配置本体の取得は初回だけ。各人数分の受付通知を受信し、再接続での過去イベントは0件。キューはこの人数試験ではRAMで、実IndexedDBの既存結果とは区別する。認証・構成準備と診断は通常管理要求の表へ加算せず、原データの別欄へ保持する。時間は実環境の性能保証ではない。

[参考計算](artifacts/budget-estimate.json)は本文観測約14.0／23.4MBにTLSと通知の仮定を加え、安全係数2で約82／138MB／公演。同じ限定操作を月間通信枠の半分以内で繰り返す机上値は60／36公演となる。未接続の業務を0件と仮定した保証ではなく、全業務の費用判定は保留する。

[公式課金説明](https://firebase.google.com/docs/database/usage/billing)と[同時接続制限](https://firebase.google.com/docs/database/usage/limits)を2026-10-15に確認。Sparkの保存1GB・月間ダウンロード10GBと同時接続100は別の制限であり、来場者数へ直接換算しない。1公演1,000人超の無料保証対象外を維持する。

`contract-diagnostic.mjs`の[6群](artifacts/contract-diagnostic-summary.json)は不足の再現であり、要件への合格ではない。GD91-100の凍結Rulesをそのまま使い、認証済み通常要求で確認した。

| ID | 再現した事実 | 次候補に必要な対策 |
|---|---|---|
| D01 | 座標・採番方式、席属性と緊急理由を追加した保存が拒否される | DD-91-02のセル・席を区別する完全な保存契約と版を設ける |
| D02 | 区画の行列・方向・舞台位置、列設定の保存が拒否される | 区画・列設定と採番カーソルを接続する |

| D04 | 初回受付開始後の理由なし交換が確定できる | 操作時点・種類に応じた理由検査を保存側へ接続する |

現在の配置項目は`id/kind/sectionId/lineId/label`を中心とする比較用モデルで、正式な`cellId`と`seatId`の分離も未接続。旧Firestore候補GD91-73の225件をRTDBの合格へ流用しない。64片・16区画を製品上限として確定せず、承認済み入力を削って合格にしない。

D04の初回受付開始時刻は前提投入で、通常の開始操作による時刻生成も未接続。D05の来場者・割当と受付用行は通常操作で作成し、欠落配置を取得側へ渡して確認した。

## 次候補の補完案

TECH-DD91-093は検証継続方針の開発判断で、本番採用・外部実行の承認ではない。Aを推奨する。#167の4完了条件を維持し、順序ごとの中間結果をコミットして同じ検証単位で継続する。

| 順序 | 具体化するもの | 確認方法・到達条件 |
|---|---|---|
| 1：形式と取得 | 既存の論理IDを維持する形式版。区画・列設定、セルと席を保存片へ対応付ける。32スロット・64KiBは初期評価値 | 最大入力と多バイト文字の往復一致。片追加時も同じ取得契約。クライアントの容量申告だけで許可しない |
| 2：業務と公開保護 | グループ・固定、緊急変更理由。旧版・新版の対応と発券済み・割当済み席を公開前に検査 | 部分要求・直接RESTと競合を拒否。通常席替えのQR維持、余白スライドの理由不要を確認 |
| 3：保持と再開 | 新形式の送信中・共有・受付参照を既存の保持機構へ接続。締めと実績生成の前提投入を通常経路へ置換 | 応答喪失後も同じ操作IDで復旧。全登録端末の未回収を検出し、実績正本と集計を一体生成 |
| 4：総費用 | 上記の同一候補で600／1,000人・6受付環境。緊急変更と再送、複数公演の保持も算入 | Rules容量と各資源制限を測定。無料600人必須・1,000人目標を判定し、未達は根拠付きで#168へ渡す |

確認済みの認可・券・受付と監査は回帰対象として残す。論理IDを保存片の番号へ置き換えず、通常スライドは移動量更新を維持する。一般受付へグループ管理情報を配布しない。候補を補完しても無料成立は未確定であり、有料実行基盤を追加して成立させない。
