## 目的と流れ

TECH-DD91-118-Aのブラウザー取込を、削除後の訂正まで同じ架空公演へ接続する。現在の本人・端末認可を使い、個別PoCの成功だけで一連の成立と判断しないための試験である。

通常操作による元データ作成 → 元環境の停止 → 新環境での取込・再開 → 公開と後処理 → 受付履歴の確認・削除 → 残した実績の理由付き訂正を予定する。原本の実行時認可は移さない。

## 修正と確認結果

削除確認headがなければ通常処理を許可し、headがある場合は取り消し済みだけを許可する。確認中・確認済みと不正状態では業務更新を止める。存在しないheadを引数へ使う旧条件を避けた限定修正である。取込開始と通常業務を同じ更新へ混ぜる要求は一体で拒否する。

```text
node poc/GD91-155/run-local.mjs
node poc/GD91-155/run-local.mjs --guard-only
node poc/GD91-155/meter-check.mjs
node poc/GD91-155/restore-check.mjs
node poc/GD91-155/preflight-check.mjs
node poc/GD91-155/audit.mjs
```

合同7群は現在認可、89片の取込・応答不明時の再照会と端末切替を確認した。全領域を取得して照合し、一度だけ公開して複製を回収した。未照合で削除を止め、訂正後に再走査して受付詳細を削除した。保持した実績へ2訂正を確定し、元の締め結果と削除時点のハッシュが一致した。

本文の元データはownerで固定fixtureを投入する。現在の本人が通常トークンでセッションを発行し、取込以降の対象業務を行う。暗号化IndexedDBや実ブラウザーの再起動は未確認。元データを作る通常操作の証拠と、合同試験へのowner前提投入を区別する。

最初の7群成功時は外部予約を含め624呼出し・69,773,967 Bで予算未達だった。無用なowner応答を`print=silent`で省き、役割と端末準備を一体化した。最終はローカル467呼出し、外部予約込み596呼出し・63,028,720 B。TLS・SDK内部通信の実測ではない。

本文上限と呼出し予約は計測器9条件で確認した。送信前に拒否した要求は未発行として扱い、応答受信の進捗も回復台帳へ保存する。上限を超える応答は停止して不合格とする。復元10条件では途中失敗後も他の回収を続け、再開時に残った試行Authだけを回収した。未知のAuthは削除しない。
