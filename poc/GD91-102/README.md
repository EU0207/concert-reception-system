# GD91-102 正式な座席契約と公開保護の接続

状態：In Review。読者：開発者・設計担当者・テスト担当者。TECH-DD91-093-Aに従う#167の隔離候補。GD91-100を保持し、保存形式の版を付けて正式なセル・席のデータ項目を接続する。本番採用ではない。

`layout-model.mjs`は論理上のセルIDと席IDを別々に保持し、保存時だけ一つのスロットへ対応付ける。座標・採番設定と席属性、緊急変更理由を保持する。16スロットは64KiBの保存片を評価する値で、製品の人数上限ではない。

## 保存と公開の流れ

| コード | 処理・データ |
|---|---|
| `layout-model.mjs`・`layout-rules.mjs` | 区画・列設定を保存し、セル・席を16件ずつ準備。座標・番号の逆引きと一体保存し、全セルの受領数が行列の総数に一致してからreadyへ進む |
| `snapshot.mjs` | 現行の構成小片を取得し、セルID・席IDへ復元。配置本体は同じ版だけ再利用し、最後に公開版を再確認する |
| `publication.mjs`・`publication-rules.mjs` | 候補参照・操作IDを登録し、旧配置を小片順に検査。各スロットのRulesが割当済み席の新旧を照合する。自己申告の検査旗だけでは進めない |
| `collection.mjs`・`collection-rules.mjs` | 公開済み結果の確認または明示取消し後に候補参照を解除。非公開・参照なしの世代だけをdeletingへ移し、索引→小片→区画の順で回収する |

公開時は構成・業務と公演管理の基準版を再照合する。同じ要求へ別の業務更新を混ぜても、更新後の版照合で拒否する。公開後に同じ操作を取消し扱いにせず、確定結果から完了記録を作る。古くなった候補の明示取消しは、新しい割当を壊さずに参照だけを解除する。

1片の[保守的なJSON上界](artifacts/part-bound.json)は58,767 B。相互排他の項目も同時に算入し、制御文字のJSONエスケープも含む。区画名100、番号・列文字64と理由200は隔離評価値で、製品の文字数上限として採用しない。構成の取得ガード256片・256区画も検証予算であり、呼出し側から設定する。今回66片・1,050セルの追加境界を確認した。

## 確認結果と限界

- [ローカル20群](artifacts/validate-summary.json)：形式・座標と索引の拒否、割当済み席の欠落・属性変更の拒否を確認。版競合・検査旗の偽装、QR保全と候補保持・回収を含む。
- [共通8群](artifacts/common-local-summary.json)：同じ保存・公開経路を実SDKの取得へ接続。通常登録は架空3人、構成10セル。Google本人はローカル模擬認証。
- 既存116群：GD91-100の20群・共通12群と既存84群を新しいRulesで再実行。旧形式の確認であり、新形式の業務全体の合格へ加算しない。

すべてローカルEmulatorの自動確認。公演制御・端末登録は前提投入。新しい公開検査の端末状態はRAMで、IndexedDBと全画面の権限持続へは未接続。旧形式での実IndexedDB・Edge再起動の証拠と区別する。

初期化と一括配置を受付中に行った試験の拒否は、準備期間の手順へ修正した。確認用の非公開参照読取りは、通常権限で読める検査結果とownerの診断へ分離した。修正前の結果・ソースは`a985d03`・`ba207ce`・`524cb23`に保持し、Rulesの認可を緩めて通していない。

| #167で継続する残条件 | 次の接続 |
|---|---|
| 座席業務全体 | グループ所属・固定と履歴、初回受付後の理由検査。個別変更と構造拡張・余白スライドを操作ごとに検査する |
| ID・保持と再開 | 回収後の過去ID再利用防止。新形式の固定案・検査IDを既存IndexedDBと応答喪失の照会へ接続する |
| 締め・費用 | 締めと実績生成の通常経路、完全な座席業務を含む600／1,000人・6受付環境と月内保持の費用 |

旧形式を扱う回帰経路を候補へ残している。`control.layoutSchemaVersion=2`では旧形式の新規作成・公開への迂回を拒否するが、本番データの形式移行は未検証。新形式での全業務無料成立は未判定。GD91-101の人数別結果を、新形式の600／1,000人の合格へ流用しない。

## 再現と証拠の監査

既存POC-004の依存関係を使う。PowerShell 7でリポジトリ直下から実行する。

```powershell
node poc/GD91-102/generate.mjs
node poc/GD91-102/run-local.mjs validate.mjs
node poc/GD91-102/run-local.mjs common-local.mjs
node poc/GD91-102/run-local.mjs regression.mjs
node poc/GD91-102/bounds.mjs
node poc/GD91-102/audit.mjs
```

各runnerは生成コードとRulesの一致を実行前に確認し、demo Auth・Database Emulatorだけを起動する。全拒否Rules・空試行根を再取得後に、自身の待受を終了する。既存の失敗・旧結果は履歴コミットへ照合し、現在のソースハッシュと混ぜない。

## 外部の最小確認案（TECH-DD91-094）

TECH-DD91-093-Aは検証継続方針の承認であり、外部実行を含まない。終了済みTECH-DD91-092-Aも再利用しない。新しい構成形式・公開検査と候補参照は、実サービスのRules・SDKでも照合が必要なため、次の少量確認を提示する。`remote-layout.mjs --plan`は外部要求0件で範囲だけを出力する。

| 範囲 | 上限・扱い |
|---|---|
| 対象 | 既存Spark検証環境の1試行。ローカルと同じ共通8群。架空10セル・3人で、600／1,000人の外部負荷試験ではない |
| Auth | Google本人1・架空メール本人1と匿名端末2の最大4Auth。検証用Googleアカウントを推奨。メール等はFirebase Authへ一時登録する |
| データ・要求 | 2,000ノード・試行根1MiB、後処理込み300アプリケーション呼出し。うち60呼出しを後処理へ確保。観測JSON本文20MiB以内 |
| 実行前 | 全拒否Rules・空DBとAuth残数0、請求先未登録を確認。生成Rulesがソースと一致しなければ停止する |
| 後処理 | SDK接続・ログイン待受を終了し、全拒否Rulesへ戻す。試行根と検証Authを削除し、認証設定と許可ドメインを再取得確認する |

Googleアカウント自体は削除せず、課金・公開とIdentity Platformへの切替を行わない。認証情報と個人プロフィールをGitへ保存せず、結果は件数・判定とソースハッシュだけにする。新経路の再開はRAMで、実回線切断・実機と新形式のIndexedDBの合格にはしない。
