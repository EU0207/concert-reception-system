## 現在の結果

[local-summary.json](artifacts/local-summary.json)は同じRulesの32試験群。本人Authが端末Authへセッションを発行し、通常の管理端末要求で構成・名簿を作成した。役割・端末登録と公演状態はownerの前提投入であり、招待・初回承認と端末準備の全業務を試したものではない。

| 対象 | 限定結果／残条件 |
|---|---|
| 本人・端末認可 | 4役割と17認可試験群。本人トークンのprovider・確認済み属性とauth_timeを照合。昇格時の準備待ち、降格後の旧権限拒否を確認。Google本人認証・メール確認はEmulatorの前提で、実際の確認メール・招待は未検証 |
| 分割準備・公開 | 7試験群。片とID・番号索引を同時検査し、部分送信・IDと同列番号の重複を拒否。未検査の構成を公開せず、一般受付へ名簿と未選択世代を配布しない |
| 共有・結果照会 | 4試験群。同じ共有版の競合は一方だけ成功。結果内容を同じIDで照合し、確定の公開根を変えない。実パケット喪失・暗号化送信案の復元は未接続 |
| 容量・取得 | 600・1,000人×2・16区画の4試験群。最大入力名簿、同数の非席セルを通常権限で準備。6環境の初回＋2回再取得をRESTで計測。SDKの再接続・全業務費用ではない |

公開根は世代・版と操作IDだけで、計測は128 B以内。片は配置32件、最大入力名簿4件で64 KiB以内にした。最大入力を切り捨てず、先にバイト数へ達する名簿では片の幅を狭める。購入者名50文字、任意10項目・各200文字を使い、現試験の文字は主に漢字である。全Unicodeの文字数契約や製品最大値の採用は未完了。

自由番号の索引は`%`を先にエスケープし、RTDBキーの禁止文字を置き換える。[生成式](generation-rules.mjs)で元の表示番号から同じキーを導く。クライアント申告のハッシュを信頼せず、`A.1`と`A%2E1`を混同しない。部分準備でmeta更新を省けた初期診断を修正し、各片・索引にも同一要求のカーソル更新を要求した。

回収は現行・共有の参照を保護する。準備済み端末の基準参照も、対応する参照記録と一体解除する。別端末による参照の横取りを拒否し、回収中の再公開・再参照を拒否した。片と逆引きの同時削除、中断後の保存済み状態からの再開を確認。参照解除は試験の明示操作で、実際の端末下書き確認や喪失端末の復旧の合格ではない。

## 期限切れの未達と対策候補

最初に[stream-probe.mjs](stream-probe.mjs)で未達を再現し、[共通手順](revocation-cases.mjs)を使う[stream-check.mjs](stream-check.mjs)で4架空Authを再利用して再確認した。結果の正本は[基準候補](artifacts/stream-check-summary.json)と[配信版を検査する候補](artifacts/stream-check-fence-summary.json)。初期診断は別ファイルへ保持し、合格件数へ加算しない。

| 条件 | 基準候補／配信版検査候補 |
|---|---|
| 役割・端末・セッションの明示停止、公演停止 | 新規RESTと既存SDK・REST受信を拒否。他の有効利用者は継続。公演停止だけ同じ公演の両者を止める |
| セッション期限の経過だけ | 基準は新規REST401でも既存SDK・RESTへ新データが到着。配信版検査候補は新データを書いた時点で、受信前に両方を拒否 |
| 役割期限とセッション期限の同時経過 | 同じ結果。発行時にセッション期限を役割期限以内へ制限するため、役割だけの孤立した期限試験とは呼ばない |

対策は`.read`へ`data.child('revision').val() > 0`等を加え、**配信データの変更も認可の依存にする**候補である。時刻だけで接続が切れた結果ではない。アプリの時計ロックとサーバーの新データ拒否は別に検証する。クライアントの解除や、期限後の猶予を認可成立の代替にしない。

本候補は診断用の配信ノードだけへ適用した。可変な全配布経路への接続は未実施。版を更新しない便乗書込みをRulesで拒否し、部分項目の直接取得・購読でも拒否できることが必要である。外部環境がローカルと同じ挙動かも未確認。SDKを使わない実装にしても、利用者が直接REST受信できる問題は残る。

承認が必要な理由は、GD91-82の承認済み少量比較には「時刻だけの期限切れ」と正常な本人セッション発行が含まれず、Auth上限も2件だったためである。今回の計画は外部の人数試験・本番移行ではなく、認可の環境差の切り分けに限定する。

1. 空データ・全拒否RulesとAuth残数0を確認する。既存CLIの環境所有者と請求先未登録も再確認する。新しいプロジェクト・DBや鍵を作らない。
2. 2架空メールAuthと2匿名端末Authを使う。架空メールの確認済み属性はownerが試験前提として設定し、確認メールを送信しない。正常な本人要求でセッションを発行する。匿名認証だけ一時有効化し、終了時に元へ戻す。
3. ローカルと同じRules・共通手順で6条件を比較する。外部の期限は通信時間を見込み10秒とし、製品のセッション期限を変更しない。他の有効利用者の継続も確認する。
4. 試行ごとに全拒否Rules、空データとAuth残数0を再取得する。認証設定の復元・請求先未登録を再確認してから次の候補へ進む。失敗時も同じ後処理を試み、未解決の試行を残したまま再実行しない。
