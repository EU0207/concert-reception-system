# GD91-121 通常業務のTLS通信と総無料予算

状態：Approved（PR #218の限定検証・予算評価）。読者：開発者・設計担当者・テスト担当者。#167条件4、DD91-T70・71へ追跡する。本番実装は行わない。

## 現在地

4／600／1,000人の登録から通常締めまでがローカルTLS経由で合格した。追加操作などの予約量を含む1公演・月間比較は、600／1,000人とも無料枠の比較値内となった。ただし、予約量の妥当性と完成アプリの無料成立は未確認。[TECH-DD91-110-A](../../docs/development/decisions/ADR-007-seat-edit-commit-boundary.md#無料予算の評価方法tech-dd91-110)とPR #218に続き、PR #219も2026-10-17に開発者レビュー承認・main統合済み。承認されたTECH-DD91-111-Aにより#167の設計検証4／4を完了し、完成アプリの無料受入は#220で未実施のまま維持する。

| 通常業務の計測 | 600人 | 1,000人 |
|---|---:|---:|
| 通常REST要求 | 14,722 | 23,927 |
| TLS下り／上り | 44,615,291／28,333,326 B | 66,094,231／44,349,038 B |
| 締め後のJSON | 10,046,283 B | 15,397,187 B |
| 登録端末／SDK環境 | 8／6 | 8／6 |

489件の現行ソースを照合し、全員の名前・来場状態と終了後の全拒否・空試行根を確認した。[人数別の監査](artifacts/audit-summary.json)。1,000人の一括割当では通信異常3件を記録したが、同じ操作IDの照会で完了し、書込みの再送は0回。切断までのTLS通信も計測に含め、過去の応答本文モデルを重ねて加算しない。

| 運用日別の通常REST要求 | 600人 | 1,000人 |
|---|---:|---:|
| 前日まで：構成準備・登録、割当・QR発行確認 | 5,708 | 9,312 |
| 当日：端末準備・受付、通常締め | 9,014 | 14,615 |

前日までの準備完了を案内し、当日は受付と例外対応へ絞る。要求本文と応答本文は監査の`stageTotals`へ分ける。メソッド別の読取り・書込み件数や日別TLS量は未計測であり、要求数から換算しない。総通信は前日分も含めて月間予算へ合算する。

## 計測方法

[generate.mjs](generate.mjs)はGD91-115の通常業務試験へ最新GD91-116 Rulesを接続する。業務内容を変更せず、[bootstrap.mjs](bootstrap.mjs)が通常RESTだけをTLS中継へ送る。6 SDK環境も同じ中継を使う。通常RESTの全要求が中継されたことを件数で照合する。

登録・一括割当と券操作を行い、受付を6環境へ通知する。全8登録端末を照合して通常締めと初回実績を生成し、名前・来場状態を維持する。構成の初期公開も通常権限で実行する。初期台帳と終了状態の投入は試験用前提であり、通常業務の合格へ加算しない。

ownerの前提投入とEmulator保守は計測中継を迂回する。これらが代用する初期化・公演終了の本番通信を0と評価せず、予算へ別の予約量を置く。Authの通信も計測器の対象外である。

同じ端末環境でのスナップショット3回と、受信カーソルを維持した再購読を含む。SDKの`goOffline`→`goOnline`による同じ接続環境の復帰とは区別する。後者の未確認はGD91-120に残す。

## 予算モデルの仮定

[budget-model.mjs](budget-model.mjs)で実測と予約量を分ける。通常SDKを含む実測にGD91-115の本文を重ねて加えない。[scenarios.mjs](scenarios.mjs)の入力は比較用であり、承認済みの製品上限ではない。

| 区分 | 比較に置く量 |
|---|---|
| 通常業務 | 今回のTLS実測。保守的に上りも加える |
| 追加の構成保存 | 最大構成の保存10回。通常権限のGD91-117要求数を使用し、保存本文・スナップショットと6環境取得を加える |
| 全件再取得 | GD91-120の6環境・最大プロフィールを含む取得を追加2組。一般受付の実際の権限範囲より広い負荷データである |
| その他の追加業務 | 50回×4MiBの予約。1回4MiBが十分という実測証明ではない |
| バックアップ | 締め後JSON相当を2回。各回に通常業務一式と同数の要求を予約し、付加量も加える。実装時の取得要求数は未確認 |
| 初期化・終了と認証 | 締め後JSONの4倍を予約。前提投入を通常経路で実測した意味ではない |
| 通信付加量 | 通常RESTと追加構成保存の各要求に8,192 Bを予約。既存通信量へ意図的に重ねる余裕であり、公式上限ではない |
| 他の利用 | 月間通信1GB、保存100MBを別に予約 |

公演ごとの計算に既存の安全係数2を適用する。1／4公演の比較、構成保存20回、通信付加量8倍の感度比較も出す。保存は締め後JSONへ保護中の構成2世代を加え、20世代を保持する比較も残す。未解決参照が増えたときに強制削除して予算へ合わせない。

無料枠は[公式料金](https://firebase.google.com/pricing)と[通信算定](https://firebase.google.com/docs/database/usage/billing)を2026-10-17に再確認した。RTDBの比較値は保存1GB・下り10GB／月。拒否応答や暗号化の付加量も見込む。日付変更による通信枠の回復を案内しない。他サービスの枠へ合算・振替しない。

上の予約量は未検証の仮定であり、比較結果が枠内でも全業務の無料保証には使わない。完成時に通常経路を実装して再計測し、無料条件の表示を更新する。1,000人を超える利用の無料維持は保証対象外とする。

## 比較結果と制約

GBは10億B、MBは100万B。月間通信には他利用1GB、保存には他利用100MBを含む。保存容量はJSONの比較値であり、サービスの保存メーターと同一とは扱わない。[全12比較の入力・計算結果](artifacts/scenario-summary.json)を保持する。

| 比較条件 | 600人の月間通信／保存 | 1,000人の月間通信／保存 |
|---|---:|---:|
| 基準・月1公演 | 4.10GB／140.82MB | 5.19GB／154.23MB |
| 同じ条件・月4公演 | 13.40GB／263.27MB | 17.77GB／316.91MB |
| 月1公演・構成保存20回 | 5.58GB／140.82MB | 7.09GB／154.23MB |
| 月1公演・要求付加量8倍 | 9.90GB／140.82MB | 14.16GB／154.23MB |
| 月1公演・保護中20世代 | 4.10GB／327.34MB | 5.19GB／365.12MB |
| 月4公演・各20世代保護 | 13.40GB／1,009.35MB | 17.77GB／1,160.48MB |

基準比較では600人必須・1,000人目標に収まる設計案となる。一方、月4公演は通信、各20世代も保持する場合は保存も超過する。付加量8倍では1,000人が超過する。これらの条件まで無料維持を保証する根拠はない。回収できない参照を削除せず、共有・確定前の残量確認と新規操作の停止条件へ引き継ぐ。

開発者が承認したAに従い、基準の操作量と予約量で設計評価を進める。完成アプリの600人受入は必須のまま、未計測業務を実装した時点で再測定する。周辺業務もPoCへ先行実装するBは採用しない。PR #218の承認を完成アプリの受入合格へ読み替えず、#168の方式採用とも分ける。

## 再現と証拠

```text
node poc/GD91-121/generate.mjs
node poc/GD91-121/run-local.mjs 4 600 1000
node poc/GD91-121/audit.mjs
node poc/GD91-121/budget-test.mjs
node poc/GD91-121/scenarios.mjs
```

8GiBのEmulatorで人数別に隔離実行する。TLS証明書はGit管理外へ一時作成し終了時に削除する。Googleログイン・認証設定変更は不要。初回の試験接続で見つかった参照先不一致は[停止記録](artifacts/setup-failures.json)に保持し、合格へ数えない。

自動PoCの結果であり、実機受入は後続タスクへ追跡する。容量と方式の最終採用は#168のゲートを維持する。
