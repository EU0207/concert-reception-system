# GD91-163 削除後訂正を含む実績の復旧

状態：In Review。120-Aの追加設計・隔離検証。現在のRTDB形式の最小モデルを対象とし、全形式の再移行を合格にしない。

## 作るものと理由

161の候補は、現在実績のハッシュが削除時点と同じ場合だけを扱った。削除後に正当な訂正をした実績は、削除時点のハッシュと一致しない。本候補はGD91-154の再計算を使って訂正を削除時点まで逆にたどり、現在実績と削除時点の正本を分けて照合する。

1. 訂正結果と確定した候補窓を全件照合し、元の削除境界まで戻した実績・集計のハッシュを確認する。
2. 現在の実績と全訂正履歴を移行先の未公開本文と照合する。削除時点の値へ戻して保存しない。
3. 161と同じ台帳・結び付け・許可だけの管理手順で有効にする。復旧後の通常訂正も、現在実績の版から続ける。

未完了・孤立した訂正窓があれば停止する。古い訂正へのhead差替えも拒否する。受付詳細削除の対象16領域は残存を拒否し、削除済み本文を訂正から再生成しない。検査用の削除時点への射影はメモリー内の照合だけに使い、DBへは書き込まない。

[モデル33条件](artifacts/model-summary.json)では、訂正済み実績の保持と現在ハッシュを確認した。実績・集計の改変と訂正履歴の欠落を拒否し、削除済み16領域の残存も拒否した。再開計画の改変と古い移行先実績も拒否した。

[Emulatorの7経路](artifacts/local-summary.json)では、架空1人の来場を通常権限でtrue→false→trueと2回訂正した。161と同じ6書込みの各応答喪失から再開し、移行先の実績版3を確認した。その後は通常訂正でfalse・版4へ更新し、3回分の訂正から元の削除境界まで照合できた。元の締め結果と削除境界を保持し、旧受付本文は存在しなかった。

各段階で通常読取り可能なDBは最大1つだった。移行元の通常再開と古いETagの更新を拒否し、移行先の端末停止後の取得も拒否した。159のRules生成は変更していない。終了時は両DBを全拒否・空データにし、Auth 0件を確認した。

業務本文と最初の削除境界は試験用管理権限の前提投入である。訂正本文と履歴は通常トークンで作成した。正式ブラウザー取込、暗号化バックアップと全業務イベントの変換を検証したものではない。161の結果へ件数を加えて一つの合格数にせず、それぞれの入力条件を保持する。162との接続は、独立した台帳が残る凍結点の復旧に限定する。

## 残条件

個人単位削除、新しい訂正履歴の再削除と2回目の削除境界は未対応である。未完了の訂正窓を含む取込も有効化せず、対応方針は未確定とする。旧Firestore全形式、例外締めと全複製回収も残る。通常の片単位ブラウザー取込から訂正済み公演を再移行した証拠ではない。

600／1,000人と画像を含む予算は未確認。要求量・ソース照合は結果JSONを正本とし、今回の最小モデルを無料受入へ換算しない。実資格の取得・失効と外部でのRules受理も確認していない。

追加外部試行0件、119-Aは消費済み。本番実装・配備と方式採用は行っていない。
