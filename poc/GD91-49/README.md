# GD91-49 保存形式の比較候補

## 目的と範囲

GD91-48の論理factを別文書へ重複保存する案と、構成の小分けデータから復元する案を比較する。既存の自動席専用codecは変更せず、手入力席に対応する形式を隔離して評価する。本番コード・Firestore Rulesは変更しない。

状態はIn Review。読者は開発者、設計担当者、テスト担当者。

## 実行

リポジトリのルートでNode.jsを使用する。外部通信と追加依存はない。

```text
node poc/GD91-49/tests/codec.mjs
node poc/GD91-49/analyze.mjs
```

先に保存・復元20ケースを実行し、次に3形状のJSON容量と文書数を計算する。各結果は実行前後のソースハッシュを保持する。

## 形式と処理

[pack](codec.mjs)はGD91-48の検査後に、座標で索引化して行ごとに最大3セルの小片を作る。大きさ1～5は計算試験用。区画・列の共通情報は親へ置く。各セルに採番方式と番号を保持し、manualNumberを文字列のまま保存する。元が欠番ならconsumedNumberも残す。席属性は対応する属性片へ置く。

[unpack](codec.mjs)は片の完全性と位置、属性の対応を検査する。親の区画・列情報からSeatを復元し、GD91-48の検査へ戻す。対応するSeat・Cellの内容が一致することを[試験](tests/codec.mjs)で照合する。元の配列順は保存契約にしない。

## 評価の限界

- 物理形式のformatVersion=2はこの候補内だけの番号で、本番のpreparedDataSchemaVersionを更新しない。
- codecの成功は、サーバーの完成証明・認可ではない。公演IDの自己申告を信用する試験ではなく、サーバー照合が別に必要なことも確認する。
- JSONのUTF-8容量はFirestoreの保存容量・索引・通信量ではない。入力長上限は未採用。今回の小片に採番証明文書やID索引の保存方式は実装していない。
- 340文書は10行×50列を3セルずつにした構成片と属性片だけの数。準備全体の書込みではない。過去方式の総数1,209は残し、新候補の総費用は未測定とする。
- Emulator・SDKと実機は未実行。過去44件と63件は再実行へ数えない。方式未採用・本番未着手。

結果は[技術検証記録](../../docs/development/technical-validation/seat-save-validation.md#gd91-49-手入力席の保存復元と物理形式比較)、判断は[ADR-007](../../docs/development/decisions/ADR-007-seat-edit-commit-boundary.md#手入力席を保持する物理形式候補gd91-49)へ追跡する。
