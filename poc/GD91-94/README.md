[pending.mjs](pending.mjs)は操作ID・予約IDを固定案へ含め、端末保存の接続口を完了してからサーバー予約を行う。作成直後の候補を予約し、小片のアップロードと完成処理へ進む。[pending-rules.mjs](pending-rules.mjs)は候補・基準への2参照を予約と一体登録する。共有操作には同じ予約IDを必須とし、別端末・別内容と版の書換えを拒否する。

予約は、共有結果の一致か旧要求の拒否確定後だけ解除する。拒否確定は共有版・基準版または公演管理版の進行で判断する。候補が別の共有先へ置換されても、応答不明の予約が残る間は回収しない。解除応答を失った場合も同じ記録を照会し、二重解除しない。時計の経過・端末失効だけでは解除しない。

- [共有予約14群](artifacts/validate-summary.json)：保存失敗時の通信0件、部分予約と他端末の解除を拒否。候補・基準の保護と共有応答無視後の照会を確認した。予約と回収の競合は一方だけ成功する。
- [既存参照12群](artifacts/regression-summary.json)：同じ最終RulesでGD91-92の管理端末参照を再検証。未解決案の保持、明示解除後の上限付き回収と操作結果を維持する。

今回の保存は試験用コールバックであり、暗号化IndexedDB・ブラウザー再起動と実機の合格ではない。応答はアプリ側で無視して照会し直す試験で、物理的な通信切断ではない。端末喪失時の管理手順と受付キューの参照、全業務予算は残条件。候補・固定案の実保存との接続も後続で確認する。

旧世代を全て永久保持する方式と比較し、必要な候補・基準だけを予約する。予約と解除の要求、2参照と予約記録の保存量が増えるため、無料条件の総予算へ含める。本番コード・外部Firebaseの変更と方式の正式採用は含めない。

## 再現

既存POC-004の依存関係を使用する。`generate.mjs`でRulesを生成し、本フォルダーの`firebase.json`でdemoプロジェクト`demo-concert-seat-gd91-84`のAuth・Database Emulatorを起動する。

`validate.mjs`、`regression.mjs`を順に実行する。各試行で全拒否Rules・空ルートを再取得し、`audit.mjs`でソースと原データを照合する。実行後にEmulatorを終了する。
