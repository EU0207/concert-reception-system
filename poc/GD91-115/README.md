# GD91-115 工程別の通信計測と製品上限

状態：Approved（PR #216、2026-10-17）。読者：開発者・設計担当者・テスト担当者。#167の条件1・4を対象とする。PR #215は2026-10-17に承認・main統合し、条件2・3の2／4が完了。本番実装と外部接続は行わない。

## 処理と測定範囲

[meter.mjs](meter.mjs)はローカルREST要求を工程と権限で分類する。要求開始時点の工程へ応答本文を計上し、拒否応答と通信失敗も記録する。試験用owner通信は別集計とし、URL・トークンや本文を記録しない。SDKの取得と受信本文は既存のコールバック計測を使う。ヘッダー・WebSocketとTLSの実通信量は未測定。

集計キーの`diagnostic`はownerによる前提投入・確認とEmulator補助を含む。業務通信との差引きができるという意味であり、前提投入が代用している初期化・公演終了の本番通信をゼロと評価しない。未接続の業務操作とバックアップの通信は総予算の残条件として扱う。

[generate.mjs](generate.mjs)はGD91-111の人数別試験へ計測を接続する。業務処理を変更せず、適用RulesだけGD91-113へ更新する。原コードと生成コードのハッシュを両方保持する。Emulatorは全拒否Rulesで起動し、試験内で最新Rulesへ切り替える。終了時は全拒否・空試行根へ戻す。

4人・6SDK環境で登録から締めまで接続した。通常の締め116 REST要求・応答本文85,797 Bを診断から分離し、締め後JSONは77,925 B。取得準備では既存コードによる存在未確認の参照照会6件が拒否されるが、続く正常な予約で全工程が完了する。この拒否通信も集計へ含む。[4人の原データ](artifacts/capacity-4-summary.json)。

600／1,000人も同じ計測器で登録から締めまで完了した。過去の大規模結果は保持し、今回の結果で上書きしない。1,000人超の無料保証はしない。3,000人試験は行わない。

| 通常経路の測定 | 600人 | 1,000人 |
|---|---:|---:|
| REST要求数 | 14,725 | 23,930 |
| RESTの完了応答本文 | 21,105,572 B | 32,746,245 B |
| SDKの取得・受信本文（論理量） | 17,536,320 B | 24,282,462 B |
| 本文の小計 | 38,641,892 B | 57,028,707 B |
| うち締めのREST要求数／本文 | 7,779／9,580,047 B | 12,579／14,974,654 B |
| 締め後の試行根JSON | 10,046,283 B | 15,397,187 B |
| 本文を完了取得できなかった通信 | 2件 | 6件 |

本文が未完了の通信は一括割当だけで発生し、同じ操作の結果照会で再開した。書込みを再送せず、全員の氏名と来場状態を維持した。未完了本文をゼロと評価せず、件数×最大送信案による別モデル884,700 B／4,449,324 Bを加えた比較も残す。これは失われた本文の実測ではなく、ヘッダーやTLSを含む上限でもない。[原データと329件のソース照合](artifacts/audit-summary.json)。

## 入力上限の判断（TECH-DD91-108）

[input-review.mjs](input-review.mjs)は現行の共通設定と検証範囲を照合する。総4,096セルは共通化済みだが、区画宣言・取得予算は最大4,096区画まで許す。計画側では17区画や採番列257本となる形もセル数以内で通過する。これは計画とRules宣言の静的確認であり、その構成のサーバー保存・無料成立の実証ではない。[確認結果](artifacts/input-review-summary.json)。

実測済みの候補はGD91-109の16区画と、1区画256採番列である。区画数と列数は別上限として扱い、セル上限から無制限に外挿しない。

[serialization.mjs](serialization.mjs)は1,000席・4,096セル・256採番列の実際の保存計画をメモリー内で組み立てる。3バイト文字とJSONで6バイトへ展開される制御文字を比較し、最大本文148,201 B／234,517 Bを確認した。1MiBは保守的な比較値でありRTDBの公式上限とは扱わない。制御文字の表示形式を承認した結果でもない。サーバー保存は既存の最大入力試験と分ける。[原データ](artifacts/serialization-summary.json)。

[collection-budget.mjs](collection-budget.mjs)で実際の回収関数へRAMの読書きカウンターを接続した。最大256片で、16区画は582要求、現行予算の4,096区画は16,902要求となる。式は`6 + 2 × 片数 + 4 × 区画数`。これは要求モデルで、サーバー保存や請求量の実測ではない。操作結果を回収対象へ含めないことも検査した。[原データ](artifacts/collection-budget-summary.json)。

[root-model.mjs](root-model.mjs)は16区画×256採番列・総4,096セルを同時に組み立てる。最大長文字列を含む1世代のJSONは約11.3MB／18.1MB、分割要求の最大は148,201 B／234,517 Bとなる。来場者は0人の容量モデルであり、4,096人の試験ではない。この組合せ全体のサーバー保存合格や、制御文字の業務上の使用可否を示さない。[原データ](artifacts/root-model-summary.json)。

| 案 | 内容 | 影響 |
|---|---|---|
| A・推奨 | 初期版を1公演16区画、1区画256採番列へ揃える。総4,096セルは維持 | 現在の最大入力証拠を使える。超過入力は端末下書きに残し、共有・確定を止める |
| B | 必要な区画数・採番列数を指定し、追加検証して拡大 | より多い区画を扱えるが、取得・容量と通信の評価範囲が増える |

採番列は縦採番なら縦列、横採番なら横列を指す。区画名の自由入力と舞台位置の仕様は維持する。将来の拡大は同じ保存片・席IDを使い、設定と検証範囲を更新する。2026-10-17、開発者がTECH-DD91-108-Aを承認。適用はGD91-116へ追跡し、本GD91-115の測定Rulesを変更しない。静的確認の原データは判断前の状態を保持する。

## 予算の比較方法

[estimate.mjs](estimate.mjs)は月間の公演数と再取得回数を入力し、他公演の通信も合算する。本文に対する1通信8,192 Bの上乗せは比較用仮定であり、公式の上限や外部測定値ではない。既存の当日安全係数2を適用しても、この仮定が正しいことの証明にはならない。人数だけの無料保証に使わない。

SparkのRealtime Databaseは月間通信枠で評価し、前日準備後の翌朝回復を前提にしない。[公式料金](https://firebase.google.com/pricing)と[通信算定](https://firebase.google.com/docs/database/usage/billing)を2026-10-17に確認した。準備・当日と締めの通信を別表示し、保存データと保持中の未解決世代も合算する。600人必須・1,000人目標の全業務無料成立は未判定。

[scenarios.mjs](scenarios.mjs)は未完了本文の比較モデルも含め、上記の付加通信仮定と安全係数2を適用する。SDK再取得は初回取得と観測済み受信の1組を追加し、登録や締めを繰り返す計算にはしない。

| 比較シナリオ（運用上限ではない） | 600人 | 1,000人 |
|---|---:|---:|
| 1公演・再取得追加なし | 約423MB | 約661MB |
| 1公演・SDK再取得1組追加 | 約561MB | 約856MB |
| 月4公演・各公演でSDK再取得1組追加 | 約2.24GB | 約3.42GB |

保存容量は締め後のJSONに最大構成の追加2世代を加え、月4公演を保持するモデルも記録した。未解決参照が増えた場合はこのモデルを超え得る。容量に合わせて保護中の世代を強制削除しない。[比較入力・結果と除外範囲](artifacts/scenario-summary.json)。追加席操作・バックアップと未接続の業務操作は未算入であり、残りの無料枠を保証する結果ではない。

この単位の工程別計測と予算モデル作成は完了。初期上限の適用・境界は[GD91-116](../GD91-116/README.md)へ接続する。#167条件1の最大構成の結合確認、条件4の実通信と追加業務を含む総予算は引き続き未完了とする。
