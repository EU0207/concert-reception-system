既存POC-004のFirebase CLIとJavaを使う。専用demoプロジェクトのFirestore 8382・Auth 9492にだけ接続する。RTDB・Hostingと外部サービスへ接続・配備しない。

版と公開割当を一つのheadへまとめ、同じ要求で作成する操作結果に現在の認可を結び付ける。追随文書は、操作結果が以前から存在しないことと、要求UID・要求時刻の一致を検査する。操作結果の作成が拒否されれば全体が拒否される。既存の操作結果を読めるだけでは後続更新を許可しない。

600／1,000人の登録済み状態をownerで前提投入する。本人からの正常セッション発行と、二者交換・追加公開の2経路を通常権限で確認する。4032セルから4096セル・16区画へ追加する。準備済み構成証明と開始・停止状態も前提投入であり、構成の通常発行・登録から締めまでの合格ではない。

最終26群。先行24群を保持して同時交換を追加した。部分送信14通りと公開の片側2通りを拒否し、同じ元版の競合は一方だけ確定した。券・資格の改変、理由なしと旧版、停止・失効を拒否する。Rulesの直接参照と呼出し先から、キャッシュ減算なしで交換18・追加公開9を算定する。交換の操作結果作成は単一書込み上限の10に達し、他の条件を追加する余裕を保証しない。

headは全席IDと全割当IDを含む。1MiB未満の文書量モデルでも、更新・取得の通信が小さい証拠ではない。管理者だけのREST経路であり、6受付SDK・IndexedDBと画面は未接続。氏名等を含む受付向け投影と全業務回帰、画像と無料受入は未確認。旧225件を今回の合格へ数えない。

終了時に全拒否、空試行データとAuth 0件を確認する。詳細と未確認は[検証記録](../../docs/development/technical-validation/seat-capacity-validation.md#gd91-138-firestore中心候補の統合headと同一要求の認可)を参照する。
