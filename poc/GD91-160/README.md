# GD91-160 別DBと誤った台帳初期化の境界

状態：In Review。#168の採用前ゲートに残る具体的な制約を再現した。正常な復旧の合格ではない。

## 作るものと理由

同じRulesでも、別DBの最新台帳を自動参照できるとは限らない。2つのローカルDB名前空間を用意し、最新の削除版がある元DBと、古い本文だけを持つ移行先を分ける。管理初期化の対象と最新性を別に保証する必要があるか確認する。

## 処理と確認結果

```text
node poc/GD91-160/run-local.mjs
node poc/GD91-160/audit.mjs
```

[最小モデル](artifacts/local-summary.json)は、管理権限で前提登録した架空1人と受付1件を使った。同じAuth Emulatorプロジェクトの現在認可を両DBに用意し、認証不成立だけによる拒否と区別した。業務削除の代表経路は159で確認し、今回はその再計測ではない。

| 手順 | 観測したこと |
|---|---|
| 元DBに削除版1、移行先に台帳なし | 移行先の業務取得を拒否した。台帳不明を削除版0に置き換えない |
| 通常クライアントが移行先へ台帳0を作成 | 拒否した。利用者自身の申告だけでは正本を初期化できない |
| 管理権限で古い台帳0を誤って初期化 | 移行先は台帳0を正本として扱い、古い受付本文を返した。元DBは削除版1のままであった |
| 現在端末の認可を停止 | 移行先の取得を拒否した。上記の誤初期化と端末失効を区別する |

**管理権限による誤初期化は未解決の制約であり、合格として加算しない。** Rulesで保護された正本でも、その初期値を古いバックアップから作ると最新性を保証できない。159の通常クライアントの防御が、管理操作の正しさまで証明したとは扱わない。

[公式のRuleDataSnapshot API](https://firebase.google.com/docs/reference/security/database)は、現在DB内の`root`・`child()`と`parent()`を使う。この再現と合わせ、本候補の参照式だけでは別DBの削除版1を移行先の判断へ自動で結び付けられないと判断する。別DBや全環境喪失時には、最新の台帳を確認して初期化する信頼済みの境界が必要である。

37要求・本文20,933,196 Bを最終Rulesでローカル観測した。前提投入とRules 2件分を含み、実サービスの無料枠とは比較しない。[54ソース照合](artifacts/audit-summary.json)が一致した。両DBは全拒否Rulesと空データ、Auth 0件を確認した。

先行試験は名前空間の準備中に停止し、データ投入前の診断が不足していた。[先行結果](artifacts/first-namespace-probe-failure.json)を残し、名前空間を63文字以内に固定した。診断に状態コード・発生行を加え、最終試験は別名の両DBで後処理まで再取得した。先行の後処理未確認を最終の回収成功へ加算しない。

2つの名前空間は同じEmulatorにあり、別プロジェクトのAuth設定や実サービスの移行を確認したものではない。最新の削除台帳そのものを失った復旧も未確認。古いバックアップを最新と見なさず、採用前ゲートを維持する。追加外部試行0件、本番実装・配備なし。
