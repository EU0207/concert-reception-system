# GD91-158 現行削除台帳と旧バックアップの照合モデル

状態：Draft。#168の全形式移行に必要な検査条件を整理する。Rulesと取込経路への接続は未実施である。

## 作るものと理由

バックアップを開いただけでは、その作成後の削除を判断できない。BD-08-12に従い、復旧時に現行台帳を取得して照合する検査モデルを作る。台帳の取得失敗を「削除なし」に置き換えない。

## 処理とデータの流れ

現行台帳を取得 → 対象公演・削除版・復元禁止の世代を確認 → 削除境界と本文を比較 → 公開直前に同じ台帳を再取得する。取得できない場合や検査後の変更は有効化を拒否する。

今回のモデルは受付詳細全体の削除だけを対象とする。削除前の世代と、削除済みの領域を含む入力を拒否する。元締めの結果と削除時点の実績ハッシュを比較する。その他の業務整合性は既存の全件検証と履歴再計算で別に確認する。

## 確認方法と限界

```text
node poc/GD91-158/model-check.mjs
```

[20反例](artifacts/model-summary.json)では、台帳不明・旧世代・削除済み本文の混入を拒否した。公開直前の削除版変更、同じ版の台帳本文変更と検査後のバックアップ変更も拒否した。先行の検査実行はNodeのassert引数の曖昧さで停止し、検査ラベルの渡し方を修正した。

**これはサーバーによる旧バックアップ拒否の合格ではない。** 台帳は呼出側が渡すモデル値であり、取得元の真正性を確認していない。改造したクライアントからの要求をRulesが拒否した証拠ではなく、通常の取込へも未接続である。

## 次の設計・検証条件

| 対象 | 必要な条件・未決定事項 |
|---|---|
| 台帳の正本 | 移行先が空でも参照できる正本と、対象公演への結び付けを定める。クライアントが別の空台帳を選んで迂回できないこと |
| 更新の一体性 | 削除の確定と削除版更新を一体化する。取込の許可・コピーと公開の各段階で、古い版を拒否する |
| 認可 | 現在の本人・端末を検査する。旧UID、失効済み端末と古い許可で取得・更新できないこと |
| 対応する削除 | 個人単位の削除、削除後訂正の再削除と全複製回収は未対応。未対応のscopeを拒否し、完了へ読み替えない |
| 台帳も失った復旧 | 全環境喪失時の台帳・削除証跡の保全と回復手順が未確定。古いバックアップ自身を最新の証明に使わない |
| 容量・無料条件 | Rulesの余裕210,064 B内で認可を維持できるか確認する。台帳と再照合通信を600人必須・1,000人目標の同条件予算へ追加する |
