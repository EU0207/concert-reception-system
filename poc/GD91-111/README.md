# GD91-111 全登録端末の締めと初回実績生成

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の条件2を中心に、締めの前提投入を通常権限の保存へ置き換える隔離PoC。PR #212は2026-10-16に承認・main統合済み。本番実装は対象外。外部接続は別途承認した小規模試行だけを行う。

## 処理とデータ

| 段階 | 処理 |
|---|---|
| 登録 | 端末本体と順番付き台帳を一体保存。台帳は追記専用で、停止端末も残す。来場者は既存の`event/roster`を再利用 |
| 締め準備 | 終了・停止済みの公演で主担当・代理が再認証。台帳版・名簿版と構成版を固定し、元データを凍結。セッションの再認証は継続できる |
| 受付照合 | 登録順に全端末を走査。本人の未送信0申告と最終連番を照合し、通常・隔離の受領索引を1件ずつ検査。未判断の隔離記録を採用済み扱いしない |
| 構成・実績 | 固定した構成片から席数を集計。名簿順に氏名と来場有無を保存し、64人ごとの集計と進捗を一体更新。未完成を締め済みへ公開しない |
| 確定 | 全件検査後だけ締め状態と不変の操作結果を一括保存。公演時点の会場名・住所は締め結果へ保存し、各実績から同じ締めIDで参照 |

端末数を手入力した一覧で代用しない。全件数と順序を登録時に保護することで、確認されていない端末を一覧から落として締める要求を拒否する。座席構成と実績を1つの巨大な要求へ集約せず、進捗を持つ分割処理にする。途中中断後も同じ操作IDから再開する。

保持項目の「開催回」は、[帳票基本設計](../../docs/development/basic-design/file-output-report-design.md)に従い公演名を使う。券の内部連番currentCycleとは区別し、締め結果のperformanceNameを実績と同じ締めIDで参照する。

例外締めは承認済みADR-004を維持する。停止済みの回収不能端末は、紙照合と未受領の不明記録を持つ場合だけ例外へ進める。端末内データ・CryptoKeyの削除完了とは扱わない。

## 確認範囲と残条件

台帳8群を中間コミット`86b6a4f`へ保存した。初回の統合失敗はソースとともに`8b4f09a`へ保持した。最新Rulesで台帳8群と締め17群が合格した。通常・例外締め、実績正本の初回生成に加え、応答切断後の実行処理の再開を確認した。

認証・初期台帳と終了・停止状態は試験前提として投入する。これを#110の端末準備や#111の公演終了操作の本番合格とは扱わない。締め済み状態と初回実績は通常権限で作成することを検査する。

本人の未送信0申告はサーバー受領との整合を検査するが、端末内部に隠された未送信データがないことまで証明しない。実機の保存と削除確認は後続タスクへ追跡する。600人必須・1,000人目標の全業務無料成立は未確認。#167はOpen。
