# GD91-81 過去時点取得の対策候補比較

| 項目 | 内容 |
|---|---|
| 状態 | In Review |
| 読者 | 開発者、設計担当者、テスト担当者 |
| 目的 | #167でGD91-80の制約に対する小修正を比較し、本番採用の可否を分ける |
| 前提 | 承認済みのSpark隔離環境。架空Auth 2利用者で比較し、環境設定はGD91-80のGit管理外設定を使う |
| 結論 | getAfterと要求条件の検査は未達。期限後の拒否は確認したが、停止直後の過去時点取得が残る。本番方式へ採用しない |

## 結果

[4案の比較](artifacts/remote-summary.json)は同じ読取り専用Rulesで実施した。通常取得4経路は全案でHTTP 403。別の有効な利用者は全案で追加後の2文書を取得した。個人の資格失効で他の有効利用者まで停止する方式にはしていない。

| 案 | 失効後の過去時点取得4経路／読取り専用トランザクション | 判定 |
|---|---|---|
| 基準のget参照 | HTTP 200、各1文書 | 未達を再現 |
| getAfterへ変更 | HTTP 200、各1文書 | 読取りを最新認可へ固定できた証拠にならず、不採用 |
| request.queryで時点・トランザクション指定を検査 | HTTP 200、各1文書 | APIの指定がRulesの検査対象へ届くとは限らず、不採用。get経路も保護しない |
| expiresAtとrequest.timeを比較 | 期限後はHTTP 403、0文書 | 期限到来後の拒否だけを確認。停止直後の拒否とは区別 |

[期限内外の追加確認](artifacts/lease-window.json)は、20秒の資格を発行後すぐに無効化し、get・runQueryを比較した。期限内の現在取得は403、過去時点取得は200で各1文書。期限後は両方403になった。別の有効な利用者は継続できた。20秒は診断用の値で、製品の停止猶予ではない。

現在拒否と期限後拒否から、オンライン停止直後の過去時点取得まで拒否できるとは推測しない。短期資格の採用は猶予の許容判断と更新負荷の再評価を伴うため、承認済み要件へ自動追加しない。今回のRulesは本人認証・業務書込みと資格更新を実装していない。

## 実施範囲と回収

4案は133アプリケーション呼出し、再確認11回の計144回。追加確認は28回、再確認11回の計39回。各試行200回以内で、各試行前の環境再準備11管理要求は別記録とする。SDK内部通信・再試行と課金読取りは未計測。人数別の無料成立へ流用しない。

試行ごとに全拒否Rulesへ戻し、16文書／3文書と各2利用者を回収した。[4案後](artifacts/cleanup-summary.json)と[追加確認後](artifacts/window-cleanup-summary.json)のAPI再取得で、5種類のコレクション群とAuthが空であることを確認した。認証設定の復元と請求先未登録も確認した。プロジェクトとデータベースは残す。

```powershell
node poc/GD91-81/probe.mjs --dry-run
node poc/GD91-81/audit.mjs
```

外部再実行は、GD91-80の接続前確認と認証方式の再準備を済ませてから行う。`probe.mjs --run-approved`で4案、`lease-window.mjs --run-approved`で期限内外を比較する。対応するverifyスクリプトで回収後の状態を再確認する。トークンはメモリーだけに置き、結果へ環境識別子を出力しない。

正式判断と次の検証案は[ADR-007](../../docs/development/decisions/ADR-007-seat-edit-commit-boundary.md#過去時点取得の対策比較と次の調査gd91-81)を参照する。認可要件・無料600人必須・1,000人目標は維持し、本番実装と3,000人検証は行わない。
