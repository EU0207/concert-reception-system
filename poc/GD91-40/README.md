# GD91-40 業務正本との配布接続設計

状態：In Review。読者：開発者、設計担当者、テスト担当者。

Issue #101の接続候補を静的に照合する。[契約](../../docs/development/detailed-design/seat-management-detail-design.md#gd91-40-業務正本との配布接続契約)と[結論・残作業](../../docs/development/technical-validation/seat-save-validation.md#gd91-40-業務正本との配布接続設計)を参照する。新しいRulesと本番コードは実装しない。

## 入出力と確認範囲

[analyze.mjs](analyze.mjs)はGD91-36の参照数算定コードを実行し、当時の57シナリオの証拠と比較する。GD91-39の5文書・18参照も当時の証拠から確認する。既存20参照へ単純追加すると38、中央の10参照へ1追加すると11になることを機械計算する。

表示名正本を分割する候補の参照先を文書別に定義し、7＋3＋3＋2＋4＝19という設計目標を別欄へ出力する。この値は未実装の分担案であり、新Rulesの参照数や式評価量を測った結果ではない。

PowerShell 7でリポジトリ直下から実行する。外部接続と依存追加は不要。

```powershell
node poc/GD91-40/analyze.mjs
```

[出力](artifacts/contract-analysis.json)へ静的照合結果と実行前後の6ソースハッシュを記録する。同じパスの再参照も数え、キャッシュ削減を見込まない。過去のEmulator合格は再実行した結果へ数えない。

## 後続の確認

最初は通常の登録から表示名正本を作り、当日表示名変更の5文書を通常認可で検証する。理由・変更前後の確認と本人履歴を接続し、部分送信・競合と不正な配布版を拒否する。一般受付への管理情報配布拒否と、未割当者の表示名の取得拒否も確認する。

続いて既存48保存シナリオの意味を維持して新形式へ移し、同じRulesで回帰する。旧形式の証拠は保持し、試験データを新形式へ変換しただけで合格にはしない。全編集・複数区画と500人、SDK・端末保存と実機、方式採用のゲートは継続する。
