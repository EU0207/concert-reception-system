## 処理とデータ

[business-rules.mjs](business-rules.mjs)は席→人・人→席、一般受付用の表示を操作履歴へ結ぶ。更新後の共通版と全対応が一致した場合だけ確定する。購入者情報と券参照は一般受付へ配布しない。操作履歴の本人UIDは端末登録の本人と照合する。

対象は交換・移動と未発券者の割当・取消し。発券済みのお客様の席だけを未設定へ戻す要求は拒否する。券を変更せず移動・交換できる。当日の理由と公演状態別の専用業務許可は未接続であり、この診断用の汎用経路を本番の許可として採用しない。発券・不参加と再発行のライフサイクルも未接続で、この4操作を全業務の代用にしない。

[sdk-adapter.mjs](sdk-adapter.mjs)は提案を固定し、同じIDの結果を通常RESTで先に照会する。未確定の場合だけWeb SDKで送信し、保存済み提案を送信時に組み替えない。明示的なオフラインでは送信しない。照会不能なら未確定と断定せず、端末の提案を残す。

端末保存は既存の[暗号化IndexedDB](../GD91-73/local-draft.mjs)を再利用する。公演・本人で分離し、トランザクション完了後に成功を返す。試験は実Edgeの隔離プロファイルとNodeのSDKを接続する。画面・認証供給と実機運用の本番合格ではない。

## 外部の管理者認証を確認する範囲（TECH-DD91-085、未承認）

GD91-84で承認・完了した外部2試行は、4架空Authによるメール本人認証と匿名端末だった。正式な管理者はGoogle本人認証を要求するため、その結果を管理者経路の合格へ流用しない。Google本人認証の属性をEmulatorで作る試験とも区別する。

**決めてください**

**開発者が確認してください**

- A（推奨）：検証用のGoogleアカウント1件を実際にログインして、既存Sparkで最小の管理者確認を行う。匿名端末2件と合わせ最大3Auth・500 JSONノード、後処理込み400アプリケーション呼出し以内の1試行。本人のメール等がFirebase Authenticationへ一時登録されるため追加の承認が必要。
- B：実アカウントを使う外部確認を保留し、ローカルの全業務接続を続ける。Google本人認証を含む外部成立は採用ゲートに残し、本番方式の確定はしない。

### Aの手順と後処理

1. 既存CLIの所有者と請求先未登録、全拒否Rules・空DBとAuth残数0を再確認する。新しいプロジェクト・鍵や課金基盤を作らない。
2. Googleログインとlocalhostの許可設定を確認する。未設定なら公式コンソールの必要箇所を開発者へ案内する。設定前の有効・無効と許可ドメインを保持し、実行中だけ必要な設定を使う。
3. 開発者が通常ブラウザーでGoogleログインを行う。パスワード・確認コードをチャットへ送らない。SDKはメモリー保持を使い、本人トークンをログ・Gitへ保存しない。Firebase Authの本人UIDと試験用匿名UIDだけをGit管理外の後処理台帳へ追跡する。
4. 正常なGoogle本人要求で2端末へセッションを発行する。公開根・共有根と世代meta、基準参照と受付表示、未作成の操作結果を親・子の12経路で確認する。セッション期限だけの経過と、本人役割・両セッションの同時期限を分ける。期限は10秒とし製品期限は変更しない。
5. セッションだけの期限では別の有効端末を継続する。本人役割が切れた場合は同じ本人の両端末を停止する。正常な管理要求でデータを変え、SDKと独立RESTが新データを受信前に拒否するか照合する。
6. 認可の変更による試験を終え、全購読を閉じる。全拒否Rules・空DB、追跡した3Authの削除と残数0を再取得する。Googleログイン・匿名認証と追加ドメインの有効設定を戻し、請求先未登録も確認する。既存のGoogleアカウント自体は削除しない。

初期化によりOAuthの構成情報が作られた場合は、残存を記録する。有効設定の復元とGoogleアカウント側の同意解除は別の操作であり、無断で鍵やOAuth構成を削除しない。未解決の後処理台帳を残したまま再実行しない。上限のうち50呼出しを後処理へ確保し、権限不足や課金要求で停止する。

実アカウントのメール・表示名と写真URLはAuthサービス内の一時登録に限る。成果物は件数・判定とソースハッシュだけにする。実来場者・連絡先と本番移行は対象外。SDK内部通信はアプリケーション呼出し数と別で、課金実測ではない。
