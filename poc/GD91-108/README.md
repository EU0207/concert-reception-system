# GD91-108 正式保存形式の人数別統合容量

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の条件1・4の部分検証。PR #209は承認・main統合済み。本番実装と外部接続を含まない。

## 処理と確認範囲

[setup.mjs](setup.mjs)は、区画・列設定を作り、セルIDと席IDを分離して初期採番する。GD91-107の最終Rulesへ通常管理要求で構成を保存し、公開前検査後に確定する。非席セルは人数と同数とし、600人は2区画、1,000人は16区画で評価する。評価候補であり、製品上限の承認ではない。

[capacity.mjs](capacity.mjs)は、既存GD91-101の人数別シナリオを最新形式へ接続する。通常登録はGD91-103の名簿契約を使う。登録・一括割当とQR生成・発行確認の後、6SDK環境で3回ずつ取得する。全人数の受付通知と、再接続時の既読通知0件を確認する。

構成作成も通常管理要求へ含めて集計する。認証と端末登録は前提投入であり、来場者・券を管理用経路から直接投入しない。ブラウザー内の認証持続とIndexedDB再開、緊急編集と障害再送はこの人数試験へ含めない。SDKの本文観測を実課金通信へ換算しない。

## 結果と完了判定

600人・600非席セル・2区画と、1,000人・1,000非席セル・16区画で、通常登録→一括割当→QR生成・発行確認→6SDK取得・受付→再接続が合格した。1,000人は2026-10-16に8GiB内で完了。6環境で各1,000件を受信し、再接続の既読通知は0件。

| 人数 | 通常管理要求 | 最大確定要求 | 試行根JSON |
|---|---:|---:|---:|
| [600](artifacts/capacity-600-summary.json) | 5,403 | 442,350 B | 7,333,816 B |
| [1,000](artifacts/capacity-1000-summary.json) | 9,006 | 741,554 B | 12,235,662 B |

1,000人では書込み応答の90秒待ち後に同じ操作IDを照会した。照会1回・GET追加再試行1回と、通常再認証によるセッション更新1回を上表へ含める。Auth要求1回は別記。同じIDの書込み再送は0回で、発券済みQRとの対応を6SDKの取得でも確認した。

1,000人はローカルEmulator用の試験補助を5つのSDK接続前境界で実行し、毎回業務データ不変・元Rulesへの復元を照合した。補助の管理用30要求は通常要求と分ける。受付中のRules再初期化は0回。JVMから取得した最大ヒープは8GiB。600人は以前の合格版を保持し、未変更の業務契約を不要に再実行しない。

[初回の応答時間切れ](artifacts/first-capacity-1000-summary.json)と[ヒープ不足](artifacts/heap-failed-capacity-1000-summary.json)を保持する。初回は後処理の再取得も未確認で、Emulator・待受を終了した。ヒープ不足の試行と改善後は全拒否Rules・空試行根を再取得し、SDK・待受も終了した。失敗を合格へ書き換えない。

[容量監査](artifacts/integrated-capacity-summary.json)は3合格・2履歴結果のソース333件を照合した。うち3件は実行コミットの凍結ソースと照合する。旧4人試験の再認証13回は[履歴](artifacts/reauth-capacity-4-summary.json)へ保存し、今回の実行群へ加算しない。実Googleログインの自動操作は今回の確認対象外。

最大入力・追加変更と障害再送、最新形式の保持・再開を含む総予算と実機確認は残る。#167の4大項目を完了扱いにせず、全業務無料成立・本番採用を宣言しない。

初回の4人接続では旧登録処理が名簿契約を満たさず拒否された。[失敗証拠](artifacts/first-capacity-4-summary.json)を残し、登録処理を正式な名簿契約へ接続した。試験後の全拒否Rules・空試行根を確認した。旧ソースのハッシュは履歴として扱い、現在の合格へ加算しない。

## メモリー診断

TECH-DD91-100のAとして、8GiBを維持して同じ架空1,000人・2,000セルで比較した。診断は状態を管理用経路で投入し、発行確認100件を通常要求で行う。通常登録から受付までの合格とは分ける。各測定はメモリーGC後の保持量で、性能保証用の時間計測ではない。

| 診断用対照 | 業務操作履歴 | 100件後の保持メモリー |
|---|---:|---:|
| 現行Rules・全履歴 | 2,001件 | 約1.68GiB |
| 現行Rules・投入時に履歴量を削減 | 1件 | 約1.67GiB |
| Rules検査を外した対照 | 2,001件 | 約45MiB |
| 全拒否から元のRulesへ復元 | 2,001件を保持 | 約1.68GiB→約138MiB |

[9条件の比較](artifacts/memory-comparison-summary.json)から、業務履歴の量よりEmulatorのRules評価側の蓄積が主因と判断する。データ内容のハッシュは復元前後で一致し、元のRulesも一致した。二重送信・別操作者の更新を拒否し、その後の通常操作が成功した。4人での同内容再投入だけではメモリー解放を観測しなかった。

EmulatorにはRules式の評価回数と評価値を確認する[診断機能](https://firebase.google.com/docs/rules/emulator-reports)がある。今回の内部実装レベルでの原因特定は未完了で、本番のメモリー消費へ換算しない。クラスヒストグラムには種類・個数とサイズだけを残し、内容ダンプは作成しない。

[試験補助](emulator-maintenance.mjs)を明示的に有効にした場合だけ、SDK接続前の工程境界で全拒否から元のRulesへ復元する。未解決の操作があれば停止し、毎回業務データの不変を照合する。JVMの実際の最大ヒープが8GiBであることも照合する。補助の管理用要求は通常要求と分け、実運用の費用へ加算しない。本番アプリへ組み込む処理ではない。

改善後の1,000人全工程が8GiBで合格。診断9条件のソース261件を照合し、うち14件は実行コミットの凍結ソースと照合する。以前の失敗と600人の合格は保持する。

### 診断方針の承認（TECH-DD91-100）

2026-10-15に開発者がAを選択。8GiB内で原因を切り分ける。PR #210全体のレビュー承認と区別する。

- A（採用）：ヒープ8GiBを維持し、Rules検査・履歴量とEmulatorのメモリー消費を分けてローカルで切り分ける。原因に応じて方式を改善する。診断と改善後1,000人のローカル結果を記録する。
- B（今回未採用）：このPCの物理メモリー約32GBに対し、試験JVMだけを一時12GiBにして比較する。OS・Firebase設定は変更せず、他アプリへのメモリー圧迫に注意する。成功しても本番成立・無料成立の根拠へ直結させない。

承認範囲は8GiBのローカル診断。外部接続・課金・公開を含まず、無料600人必須・1,000人目標を下げない。
