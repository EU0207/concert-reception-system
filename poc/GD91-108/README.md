# GD91-108 正式保存形式の人数別統合容量

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の条件1・4の部分検証。PR #209は承認・main統合済み。本番実装と外部接続を含まない。

## 処理と確認範囲

[setup.mjs](setup.mjs)は、区画・列設定を作り、セルIDと席IDを分離して初期採番する。GD91-107の最終Rulesへ通常管理要求で構成を保存し、公開前検査後に確定する。非席セルは人数と同数とし、600人は2区画、1,000人は16区画で評価する。評価候補であり、製品上限の承認ではない。

[capacity.mjs](capacity.mjs)は、既存GD91-101の人数別シナリオを最新形式へ接続する。通常登録はGD91-103の名簿契約を使う。登録・一括割当とQR生成・発行確認の後、6SDK環境で3回ずつ取得する。全人数の受付通知と、再接続時の既読通知0件を確認する。

構成作成も通常管理要求へ含めて集計する。認証と端末登録は前提投入であり、来場者・券を管理用経路から直接投入しない。ブラウザー内の認証持続とIndexedDB再開、緊急編集と障害再送はこの人数試験へ含めない。SDKの本文観測を実課金通信へ換算しない。

## 結果と完了判定

600人・600非席セル・2区画で、通常登録→一括割当→QR生成・発行確認→6SDK取得・受付→再接続が合格。通常操作5,403要求、最大確定要求442,350 B、試行根7,333,816 B。各6環境で600件を受信し、再接続時の既読通知は0件。

| 人数 | 判定 | 根拠 |
|---|---|---|
| 4 | 接続・通常再認証が合格 | [結果](artifacts/capacity-4-summary.json)。毎操作で再認証する条件で13回成功。通常要求52、Auth要求13を別記 |
| 600 | 正式形式の通常受付まで合格 | [結果](artifacts/capacity-600-summary.json)。通常要求5,403。認証・端末登録は前提投入 |
| 1,000 | ローカルEmulatorのメモリー制約で未完了 | [再試行結果](artifacts/capacity-1000-summary.json)。登録3,000・一括割当6・QR生成3,001要求までをランナー出力で確認。発行確認の部分件数・総計は未取得 |

1,000人は初回に一括割当と結果照会がタイムアウトした。再試行では書込みを再送せず同じ操作IDを照会して一括割当が確定し、QR生成まで通過した。発行確認の途中でローカルDatabase EmulatorがHTTP 500・Java heap spaceとなり、試験用ヒープ8GiBで停止した。6SDK受付へは未到達で、総要求量・最終保存量は未取得。実Firebaseでの1,000人試験と全業務無料成立は未判定。

[初回1,000人](artifacts/first-capacity-1000-summary.json)は、タイムアウト後の全拒否Rules・空試行根の再取得も未確認だった。Emulatorと待受を終了し、外部環境への影響はない。再試行では全拒否Rules・空試行根を再取得し、起動したSDK・待受も終了した。失敗を合格や後処理成功へ書き換えない。

書込み応答は90秒で不明扱いにし、GETだけを最大8回照会する。同じ書込みは再送しない。長時間試験の通常再認証はdemo Authの同一本人で行い、時刻・権限を管理用書込みで差し替えない。実Googleログインの自動操作を確認した結果ではない。

[監査](artifacts/integrated-capacity-summary.json)は合格2結果・制約1結果のソース197件を照合した。うち2件は実行コミットの凍結ソースと照合し、取得側の一部はmainとの事後照合として区別する。旧合格を現行ハーネスの再実行として数えない。

最大入力・追加変更と再送、最新形式の保持・再開と全業務無料成立は未判定。#167の大項目は未完了。具体的なメモリー制約のため、ここまでをPRで提示する。

初回の4人接続では旧登録処理が名簿契約を満たさず拒否された。[失敗証拠](artifacts/first-capacity-4-summary.json)を残し、登録処理を正式な名簿契約へ接続した。試験後の全拒否Rules・空試行根を確認した。旧ソースのハッシュは履歴として扱い、現在の合格へ加算しない。
