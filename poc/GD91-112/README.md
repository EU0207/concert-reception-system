# GD91-112 受付保存の時刻差と送信待ち時間

状態：In Review。読者：開発者・設計担当者・テスト担当者。#167の外部停止の継続分析。PR #213は2026-10-16に承認・main統合済み。本番実装・外部試行・課金・公開は行わない。

## 結果

端末時計の先行と送信待ち時間を変える8条件が合格した。通常登録から作った前提と、owner投入の最小前提の両方で同じ結果となった。RulesはGD91-111のまま変更していない。

| 端末時刻のずれ | 送信待ち | HTTP状態 | 両前提の結果 |
|---|---|---|---|
| 1秒遅れ | なし | 200 | 保存 |
| 1秒遅れ | 1.5秒 | 200 | 保存 |
| 1秒進み | なし | 401 | 拒否・業務データ不変 |
| 1秒進み | 1.5秒 | 200 | 保存 |

同じ観測時刻の要求でも、到着までの待ち時間で許否が変わる。GD91-111の単独診断は観測後にSDK通知を待っており、即時送信の成立を示さない。前提データの差だけが原因とは扱わない。外部103-A・104-Aの実HTTP状態と受領時刻は未記録で、外部停止の原因は依然未確定である。

## 処理と確認

[timing-probe.mjs](timing-probe.mjs)は最初の受付送信直前の架空DBを保存する。各条件の前に同じDBへ戻し、観測時刻と待ち時間だけを変える。拒否時はDB全体が不変、成功時は観測時刻が維持され、サーバー受領時刻が保存されたことを検査する。

全条件の後に元の前提へ戻し、通常の共通10経路を最後まで実行する。締め4群と既存6群は合格し、最小診断の200／401／200も確認した。端末保存はRAMで、本番や実機の合格にはしない。[原データ](artifacts/local-summary.json)へ追跡する。全拒否Rules・空試行根とEmulator停止を確認する。

## 技術判断案（TECH-DD91-106）

状態：未決定。外部実行の承認を求める判断ではない。

| 案 | 方針 | 利点・影響 |
|---|---|---|
| A（推奨） | 端末観測時刻を非信頼の記録として保持し、未来という理由だけで受付受領を拒否しない | 時計のずれによる受付停止を避ける。型・範囲検査は維持し、認可・公演状態の判定をサーバー側で保証する |
| B | 現在の未来時刻拒否を維持し、時計の修正・送信待ちを運用条件にする | Rulesの変更を抑えられる。一方、時計が大きく進んだ端末では長時間受領できず、固定した未送信要求を勝手に書き換えることもできない |

Aでは認証期限と役割失効の判定を変更しない。受付の連番と操作IDも維持する。停止後・締め後の回収で観測時刻を使う条件を洗い出し、観測時刻だけで許可が得られないことを検査する。回収許可と公演状態版の境界を保つ。基本設計の[端末観測時刻と共有確認時刻](../../docs/development/basic-design/logical-data-model.md#共通イベント情報)に合わせ、元の観測時刻をサーバー時刻へ書き換えない。

採用後に隔離PoCへ適用して、通常受領・隔離受領と締め後回収をまとめて検証する。権限失効と終了後の無許可送信は拒否を維持する。未来時刻・過去時刻と不正な型を含め、同じ操作の再送で二重保存しないことも確認する。外部確認が必要なら、関連変更のローカル合格後に範囲を一括提示する。終了済み105-Aを再利用しない。
